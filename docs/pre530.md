## 0. 一句话总纲

**宇树解决了机器人身体：轻、快、便宜、可二开；我解决机器人上岗后的工作系统：听懂任务、记住场景、调用企业工具、安全执行动作、批量协同调度，并把稳定工作流导出成可复用、可认证、可交易的机器人场景资产。**

最推荐的项目定位：

> **Robot Task OS for Unitree：面向宇树机器人的具身智能任务操作系统。**

更商业化的完整定位：

> **Robot Task OS + Workflow Marketplace：让宇树机器人从“单台可演示硬件”升级为“可复制、可调度、可审计、可生态化交付的机器人劳动力网络”。**

## 1. 你现在最应该改变的商业叙事

### 1.1 旧叙事的问题

旧叙事容易被评委理解成：

> “我把 Harness / Realtime / Codex / MCP 接到了宇树机器人上，所以机器人更智能。”

这个叙事的问题是：

1. **商业价值不够清晰**：评委会问“谁付钱？为什么现在付钱？规模化怎么发生？”
2. **容易被看成一次性Demo**：机器人能听懂、能走、能创建工单，但似乎只是一个项目。
3. **技术复杂但商业聚焦弱**：快慢脑、MCP、多Agent、安全、记忆都很强，但没有形成一个“平台型产品”。
4. **生态价值没有被放大**：你真正有潜力的不是某个机房巡检Demo，而是“稳定场景工作流可以导出、复用、分发、交易、认证”。

### 1.2 新叙事：三层商业主线

新的商业主线应该分成三层：

```text
第一层：Robot Task Runtime
让单台宇树机器人从“会演示”变成“能完成真实SOP”。

第二层：RobotOps / Swarm Coordinator
让多台机器人能够被远程管理、任务分配、协作调度、统一审计。

第三层：Certified Workflow Marketplace
让稳定可复用的场景工作流、Agent、MCP连接器、安全策略成为可导出、可复用、可交易的生态资产。
```

这比“卖一个机器人项目”强很多，因为它让你的商业模型从项目制升级为平台制：

| 层级 | 产品形态 | 谁付钱 | 为什么付钱 |
|---|---|---|---|
| Runtime | 单台机器人任务操作系统 | 企业客户 / 集成商 | 让机器人跑通真实任务闭环 |
| RobotOps / Swarm | 多机器人调度与远程运维 | 企业客户 / 园区 / 机房 / 工业客户 | 管多台机器人，降低人力和运维成本 |
| Marketplace | 工作流、Agent、连接器、认证生态 | 集成商 / 开发者 / OEM / 企业 | 复用已有场景方案，避免每个项目从0开始 |

### 1.3 最核心的商业金句

建议你在路演中至少说出其中2-3句：

1. **机器人硬件厂商卖“身体”，我卖让身体进入真实工作的任务操作系统。**
2. **最有价值的不是某个Demo，而是把Demo沉淀成可复用、可认证、可交易的机器人工作流资产。**
3. **从单台机器人到一队机器人，真正稀缺的不是动作能力，而是任务分工、工具连接、安全审计和场景记忆。**
4. **我不是让机器人多聊几句，而是让机器人能安全上岗、接入业务、完成SOP、留下trace。**
5. **宇树把机器人硬件开源化、低成本化；我的系统把机器人应用交付标准化、生态化。**
6. **机器人未来不会只靠一个通用大模型落地，而是靠一套可复用的任务工作流、连接器、安全策略和运维系统落地。**
7. **把机器人从“遥控器”变成“员工”，中间缺的就是Robot Task OS。**
8. **Swarm层不是让机器人群聊，而是让机器人团队能分工、排队、协作、接管和审计。**

## 2. 新商业化主线：从Paid Pilot到生态社区

### 2.1 你原来的三阶段是对的，但要重新定义重点

原路线：

1. Paid Pilot
2. Robot Task OS订阅
3. 平台化和生态化

现在建议改成：

```text
P0：可信Demo
证明单台机器人可以跑通“语音任务 → 工具调用 → 安全动作 → 记忆 → trace”的闭环。

P1：垂直场景Paid Pilot
用机房/园区/工业巡检作为第一个高ROI场景，拿到真实SOP、真实工具、真实异常数据。

P2：RobotOps平台
把单台机器人升级成多机器人任务队列、远程Bridge、Coordinator AI、Fleet Dashboard。

P3：Certified Workflow Ecosystem
把稳定工作流、Agent、MCP连接器、安全策略打包成可导出、可复用、可认证、可交易的生态资产。
```

一句话：

> **Paid Pilot不是终点，而是采集真实SOP、验证安全边界、沉淀工作流模板的入口。真正的终点是机器人工作流生态。**

## 3. 为什么“机房 / 园区 / 工业巡检”仍然是第一落点

你提出的生态社区是长期更大的商业价值，但5分钟路演里不能只讲“生态愿景”，否则评委会觉得落地太远。因此最好的结构是：

> **先用机房/园区/工业巡检作为第一个标准化场景，再把这个场景里沉淀出来的工作流、Agent、连接器、安全规则打包成生态资产。**

### 3.1 第一落点为什么选巡检

| 判断维度 | 巡检场景优势 |
|---|---|
| ROI是否清楚 | 替代重复巡查、异常记录、告警、复查、工单流转 |
| 是否需要记忆 | 需要记住地点、设备、历史异常、SOP、上次处理结果 |
| 是否需要MCP | 可接工单系统、CMDB、设备台账、地图、知识库、摄像头、IoT |
| 是否需要安全 | 人机共处、障碍物、禁区、速度限制、急停、审计刚需 |
| 是否容易Demo | 能展示语音、动作、异常确认、工单、记忆、trace |
| 是否能沉淀模板 | 非常适合沉淀“巡检工作流包” |

### 3.2 巡检只是入口，不是天花板

上台可以这样说：

> “我第一步会从机房、园区、工业巡检切入，因为这里ROI清晰、SOP稳定、工具接入明确、安全审计刚需。但我真正要做的不是一个巡检项目，而是把巡检这种稳定任务沉淀成可导出、可复用、可认证的机器人工作流包。未来接待、实验室助手、仓储盘点、应急巡查都可以用同一套Runtime和生态机制复制。”

## 4. 你的产品应该被拆成六个模块

你的图1里已经抓住了非常关键的产品优势。建议把它升级成“六层产品结构”：

```text
1. Harness / Task Orchestration：任务编排外壳
2. Memory / Scene Memory：长期记忆与场景资产
3. Multi-Agent / Coordinator：多Agent协作与任务仲裁
4. Realtime Interaction：低延迟语音与现场打断
5. MCP / Enterprise Connector：企业系统连接器
6. Safety + Trace + Swarm：安全审计与多机器人运营层
```

### 4.1 模块—痛点—价值主张总表

| 你的模块 | 解决的核心痛点 | 为什么这是宇树客户会在意的痛点 | 一句话价值主张 |
|---|---|---|---|
| Harness / 任务编排外壳 | 把模型输出转成可执行、可追踪、可回滚的机器人任务 | 客户不想买一个“会回答”的机器人，而是要一个能稳定执行巡检、接待、搬运、记录、告警的机器人 | 让机器人从“能展示”变成“能交付任务”。 |
| 记忆模块 | 解决无上下文、无个性化、无场景持续学习的问题 | 真实部署依赖场地、人员、设备、历史异常、偏好和标准操作流程；不能每次从零开始 | 让机器人记住人、地点、物体、异常和SOP。 |
| 多Agent并发合作 | 解决单模型串行决策慢、脆弱、难监督的问题 | 复杂任务需要感知、计划、动作、安全、工具、对话、审计并行工作 | 让机器人像一个小团队，而不是一个单线程聊天大模型。 |
| Realtime API | 解决语音交互延迟、打断困难、离线指令式交互的问题 | 现场人员需要边走边说、随时纠正、实时确认，而不是等模型完整转录/完整回答 | 让机器人具备自然、低延迟、可打断、可调用工具的语音交互。 |
| MCP | 解决企业系统、工具、数据源接入碎片化的问题 | 机器人要接工单、地图、数据库、库存、摄像头、IoT/PLC、日历和知识库 | 让机器人从孤立设备变成企业工具网络中的行动节点。 |

| Swarm / Remote Bridge | 解决从单机Demo到多机器人规模化运营的问题 | 企业最终要管一队机器人：分配任务、避免冲突、远程接管、统一看板 | 让机器人从“单个员工”升级为“可调度的机器人团队”。 |
| Workflow Export / Marketplace | 解决每个客户项目都从0二开的问题 | 集成商和开发者需要复用稳定SOP，企业希望买成熟方案而不是定制研发 | 让场景经验变成可复用、可认证、可交易的机器人工作流资产。 |

## 6. 最重要的新概念：Robot Workflow Package

如果你要把“生态社区”讲清楚，必须定义“社区里交易的东西到底是什么”。不要模糊地说“生态”。建议定义成：

> **Robot Workflow Package：一个可导出、可复用、可测试、可认证的机器人场景工作流包。**

它不是普通脚本，而是包含：

```text
workflow.yaml              # 任务定义：目标、输入、输出、前置条件、后置条件
agents/                    # 需要的Agent角色：Planner, Safety Reviewer, Memory Agent, Tool Agent
connectors/                # MCP工具：工单、地图、数据库、IoT、摄像头、知识库
safety_policy.yaml         # 速度、区域、权限、确认、急停、禁止动作
memory_schema.md           # 需要记住什么：地点、设备、异常、人员、SOP
skills/                    # 可调用技能：walk, turn, gesture, inspect, report, ask_human
trace_spec.md              # 日志与审计格式
evals/                     # 测试集：成功率、接管次数、安全拦截、延迟
README.md                  # 部署说明和适配要求
```

### 6.1 为什么这个概念很值钱

因为它把“项目经验”变成“平台资产”：

| 传统机器人交付 | 你的Workflow Package模式 |
|---|---|
| 每个客户从0定制 | 相似场景复用模板 |
| 代码散在项目里 | 工作流包可导出和版本化 |
| 安全靠现场经验 | 安全策略随包交付 |
| 出问题难复盘 | trace和eval随包绑定 |
| 集成商难复制 | 集成商可上架、复用、分成 |
| 企业不敢买不透明Demo | 企业可选择已认证场景包 |

### 6.2 可以上架的工作流例子

| 工作流包 | 目标客户 | 价值 |
|---|---|---|
| 机房巡检包 | 数据中心、园区运维 | 设备异常识别、通道检查、工单创建、复查提醒 |
| 展馆接待包 | 展厅、博物馆、门店 | 讲解、问答、引导、客户信息记录 |
| 实验室助手包 | 高校、科研机构 | 设备状态检查、材料记录、安全提醒 |
| 仓储盘点包 | 小仓库、零售后仓 | 货架巡查、库存差异记录、异常上报 |
| 应急巡查包 | 园区安防、物业 | 夜间巡查、异常声音/障碍/人员聚集告警 |
| 机器人训练数据采集包 | 机器人公司/研究团队 | 远程采集任务、标注、回放、失败样本沉淀 |

### 6.3 生态社区不是“随便上传代码”

物理机器人和软件插件不同，不能像普通App Store一样随便上架。因此你要强调：

> **这是Certified Workflow Marketplace，不是无约束插件市场。每个工作流必须经过仿真、参数检查、安全策略、日志规范、人工确认和场景试点，才能进入企业部署。**

认证流程可以这样讲：

```text
提交Workflow Package
→ 静态检查：schema / 权限 / 工具白名单 / 禁止动作
→ 仿真测试：路径、障碍、人距、失败恢复
→ 安全评测：速度、区域、急停、人工确认、权限
→ 小规模试点：真实场景连续运行
→ 生成评分：任务完成率、人工接管、安全拦截、平均时长
→ 上架Marketplace / 私有企业商店
```

## 7. Swarm / Remote Bridge 层应该怎么讲

你提到的swarm层、remote bridge层、总Coordinator AI，是商业化主线里非常关键的“平台升级点”。建议这样定义：

> **Swarm Coordinator：在Robot Task OS之上增加的多机器人任务调度与远程运维层。它负责知道每台机器人在哪里、能做什么、正在做什么、是否安全、是否需要人接管，然后把任务分配给最合适的机器人。**

### 7.1 Swarm不是炫技，而是商业刚需

单台机器人Demo很酷，但企业买机器人后会立刻遇到：

| 企业问题 | Swarm层解决方式 |
|---|---|
| 多台机器人谁去做哪个任务？ | Task Queue + Capability Matching |
| 两台机器人会不会去同一区域冲突？ | Global State + Geofence + Lease |
| 某台机器人低电量/故障怎么办？ | Health Monitor + Reassign |
| 人类主管怎么接管？ | Remote Bridge + Human-in-the-loop |
| 多机器人记忆如何共享？ | Shared Site Memory + Local Robot Memory |
| 怎么复盘整队表现？ | Fleet Trace + Metrics Dashboard |

### 7.2 Swarm层组件

```text
Robot Registry
记录每台机器人：型号、能力、位置、电量、当前任务、可用工具、场地权限。

Task Queue
把企业任务变成可排队、可优先级排序、可中断、可转交的任务对象。

Coordinator AI
根据任务类型、机器人状态、位置、风险、权限，分配机器人和工作流。

Remote Bridge
实现远程观察、语音接管、人工确认、紧急停止、任务回滚。

Shared Memory
场地级记忆：地图、设备、异常、工单、历史路线；机器人级记忆：自身经验和故障。

Safety Lease
同一空间/同一工具/同一设备操作权必须加锁，避免机器人之间冲突。

Fleet Trace
所有机器人任务统一记录：谁接了任务、为什么、调用什么工具、安全层是否拦截、结果如何。
```

### 7.3 上台时怎么讲Swarm

建议不要说：

## 11. 5分钟完整演讲稿

### 0:00-0:20 标题与定位

大家好，我的项目叫 **Robot Task OS for Unitree**，面向宇树机器人的具身智能任务操作系统。

宇树已经把机器人身体做得轻、快、便宜、可二开；我做的是补上真实落地最缺的一层：让机器人听懂现场任务、记住场景历史、调用企业工具、安全执行动作，并把每一步记录成可审计trace。

一句话：**机器人硬件厂商卖身体，我卖让身体进入真实工作的任务操作系统。**

### 0:20-0:55 痛点

今天很多机器人Demo看起来很聪明，但客户真正部署时，会遇到一个断层：机器人不是不能动，而是很难长期、稳定、低人力地完成真实任务。

它可能能看见画面，但不能稳定变成任务流程；能听懂一句话，但没有长期记忆；能走两步，但接不进工单、地图、数据库和知识库；更重要的是，机器人动作会映射到现实世界，不能只靠prompt保证安全。

所以客户真正需要的不是一个“会回答”的机器人，而是一个能执行巡检、接待、记录、告警、复查的机器人场景员工。

### 0:55-1:30 产品优势

我的系统核心是Harness任务编排层。它把大模型输出转成可执行、可追踪、可回滚的机器人任务。

在这个基础上，我做了五个关键模块：第一是记忆模块，让机器人记住人、地点、物体、异常和SOP；第二是多Agent协作，让感知、计划、安全、工具、对话、审计可以分工；第三是Realtime语音，让现场人员可以自然对话、随时打断；第四是MCP连接器，让机器人接入工单、地图、数据库、IoT和知识库；第五是安全和trace，让每次动作都有规则、有记录、有复盘。

这就是我想强调的：**机器人不是缺一个更聪明的嘴，而是缺一套能安全上岗的任务操作层。**

### 1:30-2:05 技术架构

技术上，我把系统分成快脑、慢脑、Harness、安全网关和Unitree runtime。

快脑用Realtime，负责低延迟语音、现场对话、打断和工具调用；慢脑用Codex，负责跨session记忆检索、复杂推理和离线总结；Harness负责把任务拆成工具调用、动作调用、记忆写入和trace；安全网关负责把所有动作经过SafetySupervisor、FSM、Watchdog和E-stop，最后才进入宇树底层控制。

这里最关键的一点是：慢脑不能直接控制机器人，所有动作执行权都回到快脑，并且必须经过安全网关。这让系统既有AI灵活性，又保留了物理世界需要的确定性边界。

### 2:05-2:35 商业主线

商业上，我不会把它只做成一个单次项目。我的路线是：先从机房、园区、工业巡检切入，因为这个场景ROI清楚、SOP稳定、工具接入明确、安全审计刚需。

但Paid Pilot只是入口。真正的商业价值是把每个稳定场景沉淀成 **Robot Workflow Package**：里面包含任务SOP、Agent角色、MCP连接器、安全策略、记忆schema和评测数据。这样集成商和开发者可以导出、复用、认证和上架，企业客户可以直接购买成熟工作流。

所以我的长期模式不是卖一个巡检项目，而是做机器人工作流生态。

### 2:35-3:00 Swarm与规模化

同时，我的架构里预留了swarm和remote bridge层。单台机器人完成任务闭环后，下一步就是让多台机器人注册到Coordinator AI里：它知道每台机器人在哪里、能做什么、是否安全、是否需要充电，然后统一分配任务、共享场地记忆、远程接管和审计。

这让系统从“单个机器人员工”升级成“可调度的机器人团队”。这也是从项目制走向平台制的关键。

### 3:00-4:30 Demo旁白

下面我演示一个巡检任务闭环。

我先对机器人说：开始巡检A区，如果发现异常，先问我确认，再创建工单。

大家可以看到，语音进入快脑，快脑生成工具调用；动作调用不会直接发到底层，而是先进入安全检查。

现在我中途打断它：停，前面有人，改从左边绕过去。

这里展示的是现场人机协作：用户可以打断，机器人可以重新规划，危险动作会被安全层拦截。

接下来机器人发现A7区域异常，它不会擅自处理，而是询问我是否创建工单。确认后，它通过MCP工具创建工单，把位置、描述、时间和证据写进去。

最后，它会把这次异常写入记忆。下次我问它A7区域发生过什么，它可以召回历史，并提醒我复查。

右侧屏幕展示的是完整trace：语音、工具调用、安全校验、动作、用户确认、工单和记忆写入。这个trace以后可以用于审计、回放和评测。

### 4:30-5:00 收尾

总结一下：短期我从巡检Paid Pilot切入，证明机器人能跑真实SOP；中期做Robot Task OS订阅，按机器人、场地、连接器和安全审计收费；长期做Workflow Marketplace和Swarm平台，让稳定工作流、Agent和连接器成为可复用、可认证、可交易的生态资产。

**宇树解决机器人身体，我解决机器人进入真实场景后的任务智能层。**

我的目标是让机器人从“能演示的设备”变成“能交付任务的场景员工”，再进一步变成“可调度、可复用、可生态化扩展的机器人劳动力网络”。

## 12. 评委可能追问与最佳回答

### Q1：你这个商业模式和普通项目制机器人集成有什么区别？

普通集成是每个客户从0做项目，我的目标是把项目沉淀成Workflow Package。每个包都包含SOP、Agent、连接器、安全策略、记忆schema、trace和eval。这样第二个客户不是重写代码，而是复用并少量适配。长期看，我卖的是可复用场景资产和运行时，而不是一次性交付。

### Q2：为什么你认为生态社区是最大的价值？

因为机器人硬件会越来越便宜，开发者和集成商会越来越多，但真实场景工作流仍然碎片化。谁能把稳定工作流、安全策略、企业连接器、评测标准和部署工具统一起来，谁就能成为机器人应用生态入口。我的系统正好卡在硬件和真实业务之间。

### Q3：为什么先做巡检？

巡检有清晰ROI，任务结构稳定，安全和审计刚需强，而且天然需要记忆和MCP：要记住地点、设备、历史异常，要接工单、地图、知识库、IoT。它是最适合把Robot Task OS从Demo推到Paid Pilot的场景。

### Q4：Swarm会不会太早？

我不会一开始就声称大规模fleet已经验证。当前重点是单机任务闭环。Swarm是第二阶段平台化能力：当一个场地有多台机器人时，任务分配、远程接管、共享记忆、冲突避免和统一审计会成为刚需。我的runtime、trace、记忆和工具接口已经为这一层做了结构准备。

### Q5：你的技术创新到底是什么？

我不会说快慢脑概念是首创。我的创新是把它工程化到具身语音机器人里：Realtime做低延迟快脑，Codex做按需慢脑和离线记忆固化，Harness把任务、工具、记忆、动作、安全和trace连起来；慢脑只建议，所有动作必须回到快脑并经过安全网关。这是一个可运行、可审计、可复用的机器人任务runtime。

### Q6：安全怎么保证？

我不依赖prompt保证安全。系统有动作白名单、参数限制、FSM、Watchdog、E-stop和trace。慢脑不能直接发动作，所有动作都由唯一执行入口进入SafetySupervisor。即使LLM或Codex失败，安全栈仍然可以独立工作。

### Q7：为什么宇树客户会需要你？

宇树把本体和运动能力做得很好，但企业客户要的是“机器人能不能接入我的业务、记住我的场地、按我的SOP执行、出错能复盘”。我的系统补的是本体之上的任务智能层，可以提高宇树硬件进入真实场景的交付率。

### Q8：MCP只是连接工具，为什么是壁垒？

单个MCP连接器不是壁垒。壁垒在于：连接器与任务工作流、安全策略、权限、记忆、trace、评测绑定在一起。机器人调用工单系统和普通软件调用API不同，因为它还要考虑物理动作、位置、人员、风险和人类确认。这个组合才是壁垒。

### Q9：如果大厂也做Robot OS怎么办？

大厂可能会做通用机器人基础模型或云平台，但具体到宇树和中小场景交付，仍需要大量SOP、连接器、安全策略、场地适配和集成商生态。我的切入点是轻量、开放、面向Unitree开发者和集成商的任务层，不与底层硬件或基础模型正面竞争。

### Q10：你怎么证明不是PPT生态？

用Demo证明单机闭环：语音任务、动作、安全、工单、记忆、trace。用Paid Pilot证明真实场景：连续运行、任务完成率、人工接管次数、异常处理时长。用第二场地迁移证明平台化：同一工作流包迁移到另一个场地或另一台机器人。
