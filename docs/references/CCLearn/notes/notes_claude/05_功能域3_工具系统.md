**角色**: 定义工具的**完整接口契约**和核心类型。

#### Tool 接口（30+ 方法/属性）

#### buildTool() 工厂函数

```typescript
const TOOL_DEFAULTS = {
  isEnabled: () => true,                    // 默认启用
  isConcurrencySafe: () => false,           // 默认不并发安全（保守）
  isReadOnly: () => false,                  // 默认非只读（保守）
  isDestructive: () => false,               // 默认非破坏性
  checkPermissions: () => ({ behavior: 'allow' }),  // 默认允许
  toAutoClassifierInput: () => '',          // 默认跳过分类器
  userFacingName: () => name,              // 默认用工具名

buildTool(def) → { ...TOOL_DEFAULTS, userFacingName: () => def.name, ...def }
```

### 文件 3: `services/tools/toolOrchestration.ts` (约 100 行) — 工具编排

**角色**: 决定工具的**并行/串行执行策略**。

#### 核心函数

```typescript
async function* runTools(
  toolUseMessages: ToolUseBlock[],
  assistantMessages: AssistantMessage[],
  canUseTool: CanUseToolFn,
  toolUseContext: ToolUseContext,
): AsyncGenerator<MessageUpdate>
```

#### 编排算法

```
partitionToolCalls(toolUseBlocks, context):
│
├── 遍历所有 tool_use blocks
├── 对每个 block:
│   ├── findToolByName(tools, block.name)
│   ├── tool.isConcurrencySafe(input) → 是否并发安全
│   └── 分区:
│       ├── 连续的并发安全工具 → 一批 { isConcurrencySafe: true, blocks: [...] }
│       └── 非并发安全工具 → 一批 { isConcurrencySafe: false, blocks: [single] }
│
├── 并发安全批次:
│   runToolsConcurrently(blocks, ...) ← Promise.all 风格
│   ├── 所有工具同时启动
│   ├── 结果按完成顺序 yield
│   ├── contextModifier 队列化 → 批次完成后按顺序应用
│   └── 最后 yield 更新后的 context
│
└── 非并发安全批次:
    runToolsSerially(blocks, ...) ← 逐个执行
    ├── 一个完成后才启动下一个
    └── context 实时更新

示例: 模型一次返回 [Grep, Glob, Read, Edit, Bash]
├── 批次 1: [Grep, Glob, Read] → 并行执行（全是只读）
├── 批次 2: [Edit] → 串行执行（写入操作）
└── 批次 3: [Bash] → 串行执行（写入操作）
```

### 文件 4: `services/tools/toolExecution.ts` (1745行) — 单工具执行

**角色**: 单个工具调用的**完整生命周期管理**。

#### runToolUse() 完整流程

```
runToolUse(toolUse, assistantMessage, canUseTool, toolUseContext):
│
├── [1] 工具查找
│   ├── findToolByName(options.tools, name) ← 从可用工具中查找
│   ├── 失败 → findToolByName(getAllBaseTools(), name) ← 降级到别名查找
│   └── 仍然失败 → yield error "No such tool available" + return
│
├── [2] 中止检查
│   └── abortController.signal.aborted → yield cancel message + return
│
└── [3] streamedCheckPermissionsAndCallTool() ← 进入主执行流
```

#### checkPermissionsAndCallTool() 完整流程

```

├── [步骤 1] Zod Schema 校验
│   ├── tool.inputSchema.safeParse(input)
│   ├── 失败 → formatZodValidationError + buildSchemaNotSentHint

│   └── 返回 InputValidationError
│
├── [步骤 2] 工具特定验证
│   ├── tool.validateInput?(parsedInput, toolUseContext)
│   └── 失败 → 返回验证错误消息
│
├── [步骤 3] 推测性分类器启动（仅 BashTool）
│   ├── startSpeculativeClassifierCheck(command, permCtx, signal)
│   └── 与后续步骤并行运行
│
├── [步骤 4] 安全净化
│   ├── 移除 _simulatedSedEdit（防止模型注入内部字段）
│   └── backfillObservableInput（补充可观测字段，浅拷贝）
│
├── [步骤 5] PreToolUse Hooks
│   ├── runPreToolUseHooks(context, tool, input, ...)
│   ├── 结果类型:
│   │   ├── message → yield 进度/附件消息

│   │   ├── preventContinuation → 阻止继续

├── [步骤 7] 权限决策
```

### 文件 5: `services/tools/StreamingToolExecutor.ts` — 流式工具执行器

**角色**: 在模型流式输出期间**边流边执行工具**，减少总等待时间。

#### 核心设计

```typescript
class StreamingToolExecutor {
  tools: TrackedTool[]          // 工具队列
  siblingAbortController        // 子 abort（一个 bash 出错 → 取消兄弟）
  discarded: boolean            // fallback 时丢弃

  addTool(block, assistantMsg)  // 模型流出 tool_use 时立即调用
  getCompletedResults()         // 在流式循环中获取已完成的结果
  getRemainingResults()         // 流式结束后获取剩余结果
  discard()                     // 模型 fallback 时丢弃所有
}
```

#### 并发控制策略

```
TrackedTool 状态机: queued → executing → completed → yielded

执行规则:
├── 并发安全工具 → 立即开始执行（不等待前一个完成）
├── 非并发安全工具 → 等待所有前面的工具完成
├── 结果按接收顺序 yield（保序）
│
├── 一个 Bash 工具出错 → siblingAbortController.abort()
│   └── 取消兄弟工具（但不取消 parent → query 不会终止）
│
└── progress 消息 → 立即 yield（不保序）

示例时序:
  模型流出: [Grep]  [Glob]  [Read]  [Edit]
  执行:      Grep→→→→→→→→
              Glob→→→→→
               Read→→→→→→→→→→
                         等待...  Edit→→→→
  yield:     Grep结果, Glob结果, Read结果, Edit结果（按接收顺序）
```

## 六、关键设计决策

### 决策 1: buildTool() 工厂 + 失败关闭默认值
**做法**: 30+ 方法的 Tool 接口 + buildTool() 填充默认值
**原因**: 默认 `isConcurrencySafe=false` 和 `isReadOnly=false` 确保新工具在没有显式声明前被保守对待。60+ 个工具都通过 buildTool() 构建，默认值集中维护。

### 决策 2: 并行/串行自动分区
**做法**: `partitionToolCalls()` 根据 `isConcurrencySafe` 自动分组
**原因**: 模型可能一次返回 5+ 个工具调用。Grep/Glob/Read 等只读工具可以安全并行，Edit/Bash 必须串行（文件竞争）。

### 决策 3: 流式工具执行 (StreamingToolExecutor)
**做法**: 在模型还在输出时就开始执行已完成的 tool_use blocks
**原因**: 模型输出一个 tool_use 后通常还有更多输出。并发安全工具可以立即开始，节省等待时间。一个 Bash 出错时通过 siblingAbortController 取消兄弟。

### 决策 4: 10 步执行管线
**做法**: Zod→validate→分类器→净化→hooks→span→权限→execute→hooks→错误
**原因**: 每步都是独立关注点。Zod 保证类型安全，validate 保证业务规则，权限保证安全，hooks 保证可扩展。

### 决策 5: Agent 工具限制列表
**做法**: `ALL_AGENT_DISALLOWED_TOOLS` 等白/黑名单
**原因**: 子代理不应该能问用户问题（AskUserQuestion）、进入计划模式（EnterPlanMode）、或停止任务（TaskStop）。这些是主线程的权限。

### 决策 6: ToolSearch 延迟加载
**做法**: `shouldDefer` 标记的工具不发送完整 schema 给模型
**原因**: 40+ 工具的完整 schema 占用大量 token。不常用的工具延迟到模型通过 ToolSearch 发现后再加载。
