### 文件 3: `services/api/withRetry.ts` (~400行) — 重试与回退

**角色**: API 调用的**重试逻辑和模型回退**。

```
withRetry<T>(getClient, fn, options): AsyncGenerator<SystemAPIErrorMessage, T>
│
├── 重试策略:
│   ├── MAX_RETRIES = 10 (默认)
│   ├── BASE_DELAY_MS = 500 (指数退避基数)
│   ├── MAX_529_RETRIES = 3 (过载重试上限)
│   ├── FLOOR_OUTPUT_TOKENS = 3000 (最低 output tokens)
│   │
│   └── 退避公式: delay = BASE_DELAY * 2^attempt + jitter
│
├── 错误分类与处理:
│   ├── 429 rate_limit:
│   │   ├── 读取 retry-after header
│   │   ├── yield 限流消息给用户
│   │   └── sleep(delay) → 重试
│   │
│   ├── 529 overloaded:
│   │   ├── 只有 FOREGROUND_529_RETRY_SOURCES 才重试
│   │   │   └── repl_main_thread, sdk, agent:*, compact, 安全分类器
│   │   ├── consecutive529Count > MAX_529_RETRIES → FallbackTriggeredError
│   │   └── 非前台查询 → CannotRetryError（不重试）
│   │
│   ├── 401 unauthorized:
│   │   ├── OAuth → handleOAuth401Error() → 刷新 token
│   │   ├── API key → 清除缓存 → 重新获取
│   │   └── AWS/GCP → 清除凭据缓存
│   │
│   ├── 413 prompt_too_long:
│   │   ├── 计算 token gap
│   │   ├── 降低 maxTokens (retryContext.maxTokensOverride)
│   │   └── 如果降到 FLOOR_OUTPUT_TOKENS 以下 → 不再重试
│   │
│   ├── APIConnectionError:
│   │   ├── 首次 → disableKeepAlive() + 重试
│   │   └── 后续 → yield 错误消息
│   │
│   └── FallbackTriggeredError:
│       ├── 包含 originalModel 和 fallbackModel
│       └── query.ts 捕获 → 切换模型 + 重试
│
├── Fast Mode 处理:
│   ├── 529 → triggerFastModeCooldown('overloaded')
│   ├── API 拒绝 → handleFastModeRejectedByAPI()
│   └── 超额拒绝 → handleFastModeOverageRejection()
│
└── 返回: T (成功) 或 throw (耗尽重试)
```

### 文件 6-16: `services/compact/` (11文件) — 消息压缩系统

**角色**: 管理对话历史的**多级压缩**，防止超出上下文窗口。

#### 压缩系统总览

```
5 级压缩体系（从轻到重）:

[级别 1] toolResultBudget (query.ts 内联)
├── 对过大的 tool_result 裁剪
├── 超过 maxResultSizeChars → 持久化到磁盘 + 预览替换
└── 不影响消息结构

[级别 2] snipCompact (snipCompact.ts, feature: HISTORY_SNIP)
├── 裁剪最旧的消息轮次
├── 保留最近 N 轮和压缩边界
├── 最轻量，无 API 调用
└── 返回 tokensFreed 供 autocompact 参考

[级别 3] microCompact (microCompact.ts)
├── 删除冗余内容（空 tool_result、重复附件等）
├── 缓存编辑模式: 通过 cache_edits API 参数删除
├── 不调用 Claude，纯客户端操作
└── 与 toolResultBudget 正交组合

├── 当 token 数接近上下文窗口时自动触发
```

## 四、Prompt Cache 优化全景

```
Prompt Cache 三级缓存策略:

┌── 全局缓存 (scope: 'global', TTL: 服务端管理) ──────┐
│ 静态系统提示词 (身份、规则、工具说明)                   │
│ 所有 Claude Code 用户共享                              │
│ SYSTEM_PROMPT_DYNAMIC_BOUNDARY 之前的内容              │
├── 用户缓存 (scope: 'ephemeral', TTL: 5min/1h) ───────┤
│ 动态系统提示词 (CLAUDE.md、环境、技能)                  │
│ 工具 Schema (按名称排序以保持稳定)                      │
│ 最近几轮的消息内容                                      │
├── 无缓存 (新消息) ────────────────────────────────────┤
│ 当前轮的用户输入和工具结果                               │
└──────────────────────────────────────────────────────┘

Cache 保护机制:

1. Beta Header Latching（锁存）
   ├── 一旦启用 auto_mode/fast_mode/cache_editing
   ├── 永远保持发送该 header
   └── 防止 toggle 改变 cache key → bust 50-70K tokens

2. Tool Schema 排序
   ├── 内置工具: 按 name 排序（字母序）
   ├── MCP 工具: 排在内置之后
   └── uniqBy(name) 去重

3. Prompt Cache Break 检测
   ├── 每次 API 调用记录 prompt hash
   ├── 比较连续调用的 cache_read_input_tokens
   └── 突降时发送 tengu_cache_break 遥测

4. Cache Editing (微粒度缓存管理)
   ├── 通过 API 的 cache_edits 参数
   ├── 删除特定 tool_use_id 的缓存条目
   └── 比全量重建省 token
```

## 五、关键设计决策

### 决策 1: 流式 AsyncGenerator 贯穿全路径
**做法**: queryModelWithStreaming → queryModel → withRetry 都是 AsyncGenerator
**原因**: 重试时可以通过 yield 向调用方发送系统消息（如"rate limited, retrying in 30s"），而不是静默等待。

### 决策 2: withRetry 与 SDK maxRetries 分离
**做法**: SDK `maxRetries: 0`，自建 withRetry
**原因**: 需要在重试间隙 yield 消息给用户、处理模型 fallback、实现 529 专属策略。SDK 的内置重试无法满足。

### 决策 3: Beta Header 锁存
**做法**: 一旦 auto_mode/fast_mode 首次启用，该 beta header 保持到会话结束
**原因**: Prompt cache key 包含 beta headers。每次 toggle 都会 bust ~50K tokens 的缓存。锁存让 toggle 只影响 body 参数，不影响 cache key。

### 决策 4: 五级压缩体系
**做法**: toolResultBudget → snip → micro → auto → reactive
**原因**: 每级成本递增。裁剪 tool_result 几乎免费；snip/micro 无 API 调用；auto/reactive 需要调 Claude 生成摘要。先尝试廉价手段，只在必要时升级。

### 决策 5: 静态/动态提示词分界标记
**做法**: `SYSTEM_PROMPT_DYNAMIC_BOUNDARY` 分隔缓存区
**原因**: 静态区（身份、规则）全用户共享 → 全局缓存。动态区（CLAUDE.md、环境）用户特定 → 用户级缓存。clear separation 让服务端缓存策略高效工作。

### 决策 6: ToolSearch 延迟加载与动态发现
**做法**: 不常用工具标记 `defer_loading`，模型通过 ToolSearch 发现后才发送完整 schema
**原因**: 40+ 工具的完整 schema 占大量 token。延迟加载减少初始 prompt 大小，同时不限制工具数量。
