# 功能域 8: 远程/桥接通信 — 逐文件深度分析

---

## 一、域概览

| 指标 | 值 |
|------|-----|
| 涉及文件 | ~42 个 |
| 总代码行数 | ~14,000 行 |
| 核心职责 | 让本地机器成为云端 Claude 的执行环境 + 远程会话管理 |
| 关键设计模式 | 长轮询+WebSocket 混合、子进程隔离、JWT 令牌刷新、指数退避 |

**这是 Claude Code 的"远程触手"** — 让 claude.ai/code 网页端能远程控制用户的本地环境。

### `cli/transports/HybridTransport.ts` (282行)

**角色**: **混合传输** — WebSocket 读 + HTTP POST 写。

```
HybridTransport extends WebSocketTransport:
│
├── [读取] ← 继承自 WebSocketTransport (WebSocket)
│
├── [写入] → HTTP POST (SerialBatchEventUploader)
│   │
│   ├── stream_event 消息:
│   │   ├── 累积到 streamEventBuffer
│   │   ├── 每 100ms 批量 enqueue
│   │   └── 减少 POST 次数
│   │
│   └── 非 stream_event 消息:
│       ├── 先刷新 streamEventBuffer
│       └── 立即 enqueue
│
├── [SerialBatchEventUploader]
│   ├── 串行: 同时最多 1 个 POST
│   ├── 批量: POST 期间到达的消息合并到下一批
│   ├── 重试: 失败后指数退避 + 无限重试
│   ├── 背压: 队列超 maxQueueSize → enqueue() 阻塞
│   └── POST_TIMEOUT_MS = 15s
│
└── [关闭]
    ├── CLOSE_GRACE_MS = 3s
    └── 等待队列排空后关闭
```

**设计原因**: 为什么读写分离？
- **读**: WebSocket 是最佳选择（低延迟、服务器推送）
- **写**: HTTP POST 更可靠（Bridge 用 `void transport.write()` 火忘；并发 WS 写 → Firestore 碰撞 → 重试风暴 → 报警）

## 六、Bridge 完整数据流

```
用户在 claude.ai/code 输入消息
    │
    ▼
Anthropic 服务器
    ├── 创建 WorkResponse
    │   ├── type: 'session'
    │   ├── id: 'session_xxx'
    │   └── secret: base64url(WorkSecret)
    │
    ▼
用户本地: bridgeMain.ts :: runBridgeLoop()
    ├── api.getWork(environmentId) ← 轮询获取
    ├── decodeWorkSecret(work.secret)
    │   ├── session_ingress_token (JWT)
    │   ├── api_base_url
    │   └── auth tokens
    │
    ├── spawner.spawn(opts, dir)
    │   ├── 子进程: claude --sdk-url <url>
    │   │   │
    │   │   ├── sdk-url 包含 session_ingress_token
    │   │   ├── 子进程通过 WebSocket/HybridTransport 连接服务器
    │   │   │
    │   │   ├── [接收] WebSocket ← 服务器消息 (用户输入、控制请求)
    │   │   ├── [处理] query() 循环 → 工具执行
    │   │   └── [发送] HTTP POST → 服务器 (assistant 响应、工具结果)
    │   │
    │   └── 主进程通过 stdout readline 监控子进程
    │       ├── stream_event → 更新状态显示
    │       ├── control_request → 转发权限请求到服务器
    │       └── result → 会话完成
    │
    └── api.heartbeatWork() ← 定期心跳
```

## 七、关键设计决策

### 决策 1: 子进程隔离
**做法**: 每个远程会话是独立的 claude 子进程
**原因**: 会话之间完全隔离（不同 CWD、不同环境变量、不同权限）。崩溃不会影响其他会话。多会话模式（最多 32 个）安全并行。

### 决策 2: WebSocket 读 + HTTP POST 写 (HybridTransport)
**做法**: 分离读写通道
**原因**: 火忘式写入 (`void transport.write()`) 在并发 WebSocket 写中导致 Firestore 碰撞和重试风暴。HTTP POST 通过 SerialBatchEventUploader 串行化，消除并发冲突。

### 决策 3: WorkSecret 密钥机制
**做法**: 服务器将 JWT + 认证 + 配置打包到 base64url 编码的 secret 中
**原因**: 单次传输包含子进程需要的所有信息。不需要额外的配置获取步骤。JWT 有过期时间，tokenRefresh 调度器提前 5 分钟刷新。

### 决策 4: 三种 SpawnMode
**做法**: single-session / worktree / same-dir
**原因**:
- `single-session`: 最简单，一次一个会话
- `worktree`: 每个会话独立 git worktree（完全隔离，不会文件冲突）
- `same-dir`: 多会话共享 CWD（可能冲突，但无需 git）

### 决策 5: 自适应轮询 + 睡眠检测
**做法**: 轮询间隔动态调整 + 检测系统睡眠唤醒
**原因**: 活跃会话期间需要频繁轮询；空闲时减少请求。笔记本合盖→开盖后，轮询间隔异常长 → 检测到睡眠 → 重置错误计数（而不是误认为连接失败）。

### 决策 6: 容量释放信号 (capacityWake)
**做法**: 会话完成时通过 capacityWake.wake() 唤醒等待的轮询
**原因**: 多会话模式下，达到容量上限后轮询进入等待。会话一结束立即唤醒，不需要等到下一个轮询周期。
