框架 II · 动态运行流程
事件驱动的完整时序
从工具执行事件发生到下一轮 query 注入，再到 resume 时的链图恢复，全链路九个阶段
01 事件触发
工具执行 / assistant 输出 / 系统事件
工具执行完成、assistant 输出新消息、系统事件发生，触发 transcript 写入路径。
02 transcript 持久化
recordTranscript / appendEntry
调用 recordTranscript、appendEntry、insertMessageChain 把事件写入当前 session 的 JSONL。
sessionStorage.ts
03 多流分发
sidechain / 元数据 / 远程
sidechain 与 subagent transcript 分流，metadata re-append，远程 / session ingress 持久化。
04 记忆搜索
SessionMemory / memdir 检索
下一轮 query 开始前，从 SessionMemory 与 memdir 搜索 relevant memories 作为注入候选。
05 · 核心 · attachment 组装
attachments.ts 结构化
把 file changes、plan、memory / context deltas 组装为 attachment messages。
attachments.ts
06 · 核心 · query 注入
attachments + memories 进入下一轮
query.ts 把 attachments 与 memories 注入下一轮 messages，形成回流闭环。
query.ts
07 恢复触发
用户 / 系统 resume / continue
resume 或 continue 命令触发，进入 transcript 读取与状态重建路径。
08 transcript 读取
loadTranscriptFile + JSONL parse
读取 JSONL，修复 compact boundary / snip / preserved segment / parallel tool results，恢复 metadata 与 snapshots。
loadTranscriptFile
09 状态回接
messages / session state 回运行时
恢复出的 messages 与 session state 重新交回运行时，恢复断点之前的一致性。

框架 V · 五条设计结论
最重要的架构判断
原文档第 9 节：这个子系统的五条设计结论，逐条列出不作省略
结论 1
resume 是恢复一个消息图
sessionStorage.ts 最关键的不是写文件，而是 compact boundary relink、snip removal relink、orphaned parallel tool results recovery、metadata / snapshot 恢复。transcript 已经不是简单日志，而是一个带拓扑的事件流。
结论 2
attachments 是上下文回流机制
很多人容易把 attachment 当成 UI 附属物，但它是工具结果外的额外上下文补充机制，post-tool / post-compact / post-memory 的结构化回流层。attachment 是运行时的一等公民。
结论 3
transcript 与 SessionMemory 与 memdir 不同
transcript 是原始事件流，SessionMemory 是当前 session 记忆协作层，memdir 是 durable memory 存储层。三者职责不同，但共同支撑长期会话能力。
结论 4
auto-memory 路径安全是硬边界
memdir/paths.ts 最重要的不是路径拼接，而是哪些 source 可以设置 memory path、哪些危险路径必须拒绝、worktree 是否共享 memory root。memory 系统直接影响文件系统安全边界。
结论 5
长期连续性的真正底座
没有它，就没有长期 session continuity、compact 后继续工作、resume / continue 的可靠恢复、memory 驱动的下一轮上下文增强。
