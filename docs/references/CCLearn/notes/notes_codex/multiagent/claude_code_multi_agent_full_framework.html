Claude Code 多 Agent 通信框架全景

从 AgentTool 调度入口到 Task 协作总线、Mailbox 消息通道与 Swarm 执行后端的完整四相位深拆

cc/claude_code · 37_multi_agent_communication_full_framework · 深拆 01–04 合集
Phase 01 · Agent 调度入口

AgentTool / fork / run / resume 链

研究 leader agent 如何创建子 agent、fork / run / resume 三条主链如何组织,以及 AgentTool 在多 agent 协作里的职责边界。AgentTool 本体只做 orchestration,真正的任务协作总线、消息通道与执行后端都在它下游。

leader agent / query runtime │ ▼ AgentTool.tsx - 决定调用哪类 agent │ ├── forkSubagent.ts ── 创建新 agent 分支 │ ├── runAgent.ts ── 真正运行 agent │ └── resumeAgent.ts ── 恢复已有 agent │ ▼ spawnMultiAgent.ts / builtInAgents / loadAgentsDir │ ▼ 返回 agent handle / task / status / output 回流
AgentTool 是多 agent 调度入口,不是 agent 本体 —— fork、run、resume 是 3 条不同运行路径,spawnMultiAgent 是多 agent 并发的共享编排层,built-in 与 loadAgentsDir 让 agent 能力既可内建也可外部加载。

关键结论
  1. AgentTool 是多 agent 调度入口,不是 agent 本体
  2. fork / run / resume 是 3 条不同的运行路径,分别对应「新建分支」「真正运行」「恢复会话」
  3. spawnMultiAgent 是多 agent 并发生成的重要共享层,是 fork / run / resume 的共同底座
  4. built-in agents 与 loadAgentsDir 说明 agent 能力既可内建,也可外部加载
  5. AgentTool 本身更偏 orchestration,而不是任务协作总线;task、message、mailbox 还在下游
Phase 02 · Task 协作总线 · 核心

Task 体系作为多 Agent 协作总线

在 Claude Code 的多 agent 协作里,真正稳定的协作对象往往不是直接 message,而是 task 这个中间对象。因为 task 可以被创建、查询、更新、列举、停止,还有独立 output,天然适合做多 agent 协作总线。

leader / coordinator / agent │ ▼ TaskCreateTool -> 创建 task │ ▼ worker / teammate / subagent 处理 task │ ├── TaskUpdateTool ── 更新进度 ├── TaskGetTool ── 查询状态 ├── TaskListTool ── 列出全部 ├── TaskOutputTool ── 取得输出 └── TaskStopTool ── 终止分支 │ ▼ TaskAssignmentMessage / hooks/useTasksV2 / useTaskListWatcher │ ▼ leader 看到状态、输出、完成度,再继续调度其他 agent
task 不是附属物,而是多 agent 协作的核心共享对象 —— Create / Get / List / Update / Stop / Output 这组工具共同构成了 task 总线协议面,而 message 更像局部通知。要理解 Claude Code 的 agent 协作,必须先理解 task 体系,再看 mailbox。

关键结论
  1. task 不是附属物,而是多 agent 协作的核心共享对象
  2. TaskCreate / Get / List / Update / Stop / Output 这组工具共同构成了 task 总线协议面
  3. message 更像局部通知,task 更像结构化协作实体
  4. UI hooks 和 assignment message 说明 task 同时服务于 runtime 与界面层
  5. 如果要理解 Claude Code 的 agent 协作,task 体系必须优先于 mailbox 单独理解
Phase 03 · Mailbox 消息通道

Mailbox / SendMessage / Queued / Bridge Messaging

研究 agent 之间如何显式发消息、mailbox 与 queued messages 在运行时里是什么角色,以及 bridge messaging 如何把消息扩展到跨进程、跨环境通信。这条链更像 actor / message 系统,而不是同步函数调用。

agent A -> SendMessageTool │ ▼ mailbox / queued messages ├── context/mailbox.tsx ├── context/QueuedMessageContext.tsx ├── utils/mailbox.ts └── utils/teammateMailbox.ts │ ▼ hooks/useMailboxBridge.ts │ ▼ bridge/bridgeMessaging.ts │ ▼ agent B / teammate / remote session 收到消息
SendMessageTool 是显式 agent message passing 的顶层入口 —— mailbox 说明消息不是立即调用而是事件队列模型,queued messages 让通信天然支持异步,bridgeMessaging 把 mailbox 从本地运行时扩展到跨进程远端场景。

关键结论
  1. SendMessageTool 是显式 agent message passing 的顶层入口
  2. mailbox 说明消息很多时候不是立即调用,而是事件队列 / 收件箱模型
  3. queued messages 让通信天然支持异步
  4. bridgeMessaging 把 mailbox 从本地运行时扩展到远端 / 跨进程场景
  5. 这条链更像 actor / message 系统,而不是同步函数调用
Phase 04 · Swarm 执行后端

Swarm Backend / Leader-Worker / Permission / Reconnection

研究多 agent / swarm 的执行后端是怎么组织的、leader 与 worker 如何做权限同步、以及多 agent 环境下如何做 reconnect、layout、mode snapshot。这层通信不仅传消息,还传执行环境、权限、布局和状态。

leader agent │ ▼ utils/swarm/backends/registry.ts - 根据 detection 选择 backend │ ├── InProcessBackend ── 进程内运行 ├── TmuxBackend ── tmux pane ├── ITermBackend ── iTerm pane └── PaneBackendExecutor ── 通用 pane 执行器 │ ▼ spawnInProcess / inProcessRunner / spawnUtils │ ▼ leaderPermissionBridge / permissionSync │ ▼ worker agents 执行 │ ▼ reconnection / teammateLayoutManager / teammateModeSnapshot
swarm 是有真实后端执行层的,不只是逻辑上的多个 agent —— backend 可切换(in-process / tmux / iTerm / pane),leader-worker 权限同步是独立于 task 与 message 的第三条通信链,reconnection 与 mode snapshot 说明 swarm 是长生命周期协作环境。
