**Cache优化研究目标**：彻底弄清 Claude Code 在每一次 API 调用时，**哪些 prompt 字节是绝对不变的**（静态模板，一字不改 / 顺序不动），以及**哪些字节是动态拼接的**（每会话 / 每轮 / 每次请求才变）。只有静态前缀完全逐字节一致，Anthropic API 的 `cache_control: ephemeral` 才会命中；任何偏离（空格、换行、顺序）都会让整段 prefix miss，退化到 input token 全额计费。

# 1. 一次请求的全景

## 1.1 一次 Messages API 请求的完整形状

Claude Code（走 Anthropic Direct API 时）每一次 `POST /v1/messages` 的 body 是下面这个形状 —— **顺序、字段、数组切分方式都固定**。违反任何一项都会让 prompt cache miss：

```jsonc
{
  "model": "claude-opus-4-7",                 // 来自 --model 或默认
  "max_tokens": ...,                          // 会话级参数
  "system": [                                 // ← 注意是数组，不是字符串
    {
      "type": "text",
      "text": "You are Claude Code, Anthropic's official CLI for Claude.",
      "cache_control": { "type": "ephemeral", "ttl": "1h" }   // ◀ 断点 #1
    },
    {
      "type": "text",
      "text": "<主 system prompt —— 就是第 2.2 节的全文 + 第 3.1 节的动态填充>",
      "cache_control": { "type": "ephemeral", "ttl": "1h" }   // ◀ 断点 #2
    }
  ],
  "tools": [ /* 静态 schema，顺序必须稳定；本身不能带 cache_control */ ],
  "messages": [
    // ——— 历史 turn 1 ———
    { "role": "user",      "content": "..." },
    { "role": "assistant", "content": [...] },
    // ——— 历史 turn 2 ———
    { "role": "user",      "content": [...tool_result...] },
    { "role": "assistant", "content": [...] },
    // ——— 当前 turn ———
    {
      "role": "user",
      "content": [
        { "type": "text",
          "text": "<当前用户输入>",
          "cache_control": { "type": "ephemeral", "ttl": "1h" }  // ◀ 断点 #3（最后一条 user 的最末 block）
        }
      ]
    }
  ]
}
```

**来源**：结构与字段名来自 `providers/anthropic.js`（下见 §1.2）。断点 #1/#2 打在 `system[*]` 的每一个 block 上；断点 #3 打在 `messages[messages.length - 1].content[content.length - 1]` —— 而且仅当末消息是 `role: user` 且最末 block 是 `text | image | tool_result` 时。`assistant` 消息、`thinking` block 永远不打 `cache_control`。

## 1.2 Cache breakpoint 布局图（最多 4 个 ephemeral 断点）

Anthropic 官方给到 Messages API 最多 **4 个** 独立 `cache_control` breakpoint；但 Claude Code 实际只用到其中 **2–3 个**，规则如下（**pi-ai 实测**，`providers/anthropic.js`）：

```
┌─────────────────────────────────────────────────────────────────────┐
│                      POST /v1/messages body                          │
├─────────────────────────────────────────────────────────────────────┤
│                                                                     │
│  system[0]  "You are Claude Code, ..."                              │
│             cache_control: ephemeral, ttl=1h     ◀── 断点 #1        │
│             （OAuth 时才有；API Key 走 system[0] 即主 prompt）     │
│                                                                     │
│  system[1]  主 system prompt 正文                                  │
│             cache_control: ephemeral, ttl=1h     ◀── 断点 #2        │
│                                                                     │
│  ────────────────────────────────────────────────                   │
│                                                                     │
│  tools      [{ name, description, input_schema }, ...]              │
│             （不打 cache_control —— API 不允许在 tools 数组内打）  │
│                                                                     │
│  ────────────────────────────────────────────────                   │
│                                                                     │
│  messages                                                           │
│    [0..N-2]    历史消息，不打 cache_control                         │
│    [N-1]       最后一条 user，content 数组最末一个 block 上         │
│                cache_control: ephemeral, ttl=1h  ◀── 断点 #3        │
│                                                                     │
└─────────────────────────────────────────────────────────────────────┘

      ┌───── 命中缓存的理想路径 ─────┐
      │  断点 #1 + #2：每一轮都命中  │   ← 只要 system 没被修改
      │  断点 #3：上一轮的 #3 成为   │   ← 新一轮的 #3 前移到新末尾
      │  下一轮的 cache prefix       │
      └──────────────────────────────┘
```

**关键代码片段（pi-ai 实测）**：

```javascript
// providers/anthropic.js  —— 系统 block
params.system = [
  {
    type: "text",
    text: "You are Claude Code, Anthropic's official CLI for Claude.",
    ...(cacheControl ? { cache_control: cacheControl } : {}),   // 断点 #1
  },
];
if (context.systemPrompt) {
  params.system.push({
    type: "text",
    text: sanitizeSurrogates(context.systemPrompt),
    ...(cacheControl ? { cache_control: cacheControl } : {}),   // 断点 #2
  });
}

// providers/anthropic.js  —— 末 user 消息
if (cacheControl && params.length > 0) {
  const lastMessage = params[params.length - 1];
  if (lastMessage.role === "user") {
    if (Array.isArray(lastMessage.content)) {
      const lastBlock = lastMessage.content[lastMessage.content.length - 1];
      if (lastBlock &&
          (lastBlock.type === "text" || lastBlock.type === "image" || lastBlock.type === "tool_result")) {
        lastBlock.cache_control = cacheControl;                 // 断点 #3
      }
    } else if (typeof lastMessage.content === "string") {
      // 字符串 content 要先转数组才能挂 cache_control
      lastMessage.content = [
        { type: "text", text: lastMessage.content, cache_control: cacheControl },
      ];
    }
  }
}
```

## 1.3 TTL 策略：5m vs 1h 的触发条件

`resolveCacheRetention()`（**openclaw 实测**，`pi-embedded-*.js` 行 18437–18448）：

| `cacheRetention` 参数 | 结果                                               | 备注                                                         |
| --------------------- | -------------------------------------------------- | ------------------------------------------------------------ |
| `"none"`              | 不打任何 `cache_control`                           | 显式关缓存                                                   |
| `"short"`             | `{ type: "ephemeral" }`（隐含 5 分钟）             | Anthropic Direct 默认                                        |
| `"long"`              | `{ type: "ephemeral", ttl: "1h" }`                 | 仅当 `baseUrl` 含 `api.anthropic.com` 时才真的带 `ttl: 1h`；OpenRouter / Bedrock 会退化成 5m |
| 兼容别名              | `cacheControlTtl: "5m"` → `short`；`"1h"` → `long` | 老参数，仍被解析                                             |

**Provider 差异**：

- **Anthropic Direct**：默认 `short`，可升 `long`（1h）。
- **OpenRouter**：永远强制 5m，且需要一个 payload patch（`provider-stream-*.js` 的 `createOpenRouterSystemCacheWrapper`）在 system 最末 block 强行补 `cache_control`。
- **Amazon Bedrock**：只有显式传 `cacheRetention` 才启用，否则不缓存。
- **其它 provider**（Gemini、Vertex 等）：完全不打 `cache_control`。

## 1.4 "滑动"行为：为什么 breakpoint 不需要显式 rotation

API 文档上"最多 4 个 breakpoint"听起来像要显式管理槽位，但 Claude Code 并没有 rotation 逻辑 —— 它只打 #1/#2/#3 三个固定位置，而"滑动"是隐含的：

- **第 N 轮**：断点 #3 打在 `messages[N-1]`（当轮 user）。系统把 `system[0..1] + messages[0..N-1]` 当作写入 cache 的 prefix。
- **第 N+1 轮**：断点 #3 重新打在 `messages[N]`（新 user）。旧 prefix 仍然在服务器侧存活 5m/1h，新 prefix 只是旧 prefix + 上一轮 assistant + 新 user；命中仍然只差 **几百 token 的增量**。

这样实现的代价：每轮只有 1 次 cache write（增量写入），其余都是 cache hit。这也是为什么 **system prompt 必须一字节都不能改** —— 它是所有轮共享的 prefix，改一个字节就让所有历史轮的 cache 全部作废。

```

### 2.2.8 `# Committing changes with git` —— Git commit 协议

```

Only create commits when requested by the user. If unclear, ask first. When the user asks you to create a new git commit, follow these steps carefully:

Git Safety Protocol:
- NEVER update the git config
- NEVER run destructive git commands (push --force, reset --hard, checkout ., restore ., clean -f, branch -D) unless the user explicitly requests these actions. ## 2.9 错峰场景：SDK 子进程身份首行

当 Claude Code 作为 Agent SDK 的子进程运行（即用户在自己的代码里 `import { query } from "@anthropic-ai/claude-agent-sdk"` 启动时），`system[0]` 变成：

**这意味着**：在 SDK 子进程内 cache 与 CLI 本体不共享，因为 `system[0]` 字节不同。这是 SDK vs CLI 最大的 cache 分界。

# 3. 动态拼接点（每个都会让 cache 失效到那一行为止）

## 3.1 `system[1]` 内部的动态填充点

`system[1]` 正文本身是静态的，但 Claude Code 在正文**之前**和**之后**各拼了少量动态段。**会话内保持不变** 的动态段（开会话一次性计算，之后缓存命中）：

| #    | 占位符 / 来源                                                | 来源代码（openclaw 近似）                           | 生命周期                             | 典型值                                          |
| ---- | ------------------------------------------------------------ | --------------------------------------------------- | ------------------------------------ | ----------------------------------------------- |
| 1    | 模型显示名（`Claude Opus 4.7 (1M context)`）                 | `buildAgentSystemPrompt()`                          | 会话级（切模型变）                   | 跟 `--model` 走                                 |
| 2    | `# Environment` 段（见 §3.5）                                | `buildEmbeddedSystemPrompt()` → `buildEnvSection()` | 会话级                               | cwd、os、platform、date                         |
| 3    | `# auto memory` 里的 MEMORY 目录路径                         | 同上                                                | 会话级                               | `/home/ubuntu/.claude/projects/-<hash>/memory/` |
| 4    | `# Session-specific guidance` 末尾追加的 skill/subagent 列表 | 同上                                                | 会话级                               | `- skillName: description` 列表                 |
| 5    | Output Style 首行 `# Output Style: <name>`                   | 同上                                                | 会话级（/output-style 切换才变）     | `# Output Style: default`                       |
| 6    | CLAUDE.md 汇总：`# claudeMd` + 正文                          | `loadProjectClaudeFiles()`                          | 会话级                               | 项目 + 父目录逐层合并                           |
| 7    | 用户自定义 system prompt (`--system-prompt` 或配置)          | `appendUserSystemPrompt()`                          | 会话级                               | 用户输入                                        |
| 8    | MEMORY.md 内容（`# MEMORY.md` 注入）                         | `loadAutoMemory()`                                  | 会话级                               | 前 200 行                                       |
| 9    | `# userEmail` / `# currentDate`                              | `buildSessionHeader()`                              | 会话级                               | 邮箱 + `YYYY-MM-DD`                             |
| 10   | `gitStatus` 段（分支、status、最近 5 个 commit）             | `collectGitStatus()`                                | **会话启动时一次**（不随 turn 刷新） | 见本会话 system prompt                          |

> 关键：上面全部是**会话级静态**。只要一次会话内不切模型、不切 style、不切 cwd，`system[1]` 字节不变，断点 #1/#2 永远命中。

**会让 cache miss 的真正动态变化**：

- 切 `--model`（#1 变，整个 `system[1]` 重新拼）。
- 用 `/memory` 命令修改 MEMORY.md（#8 变）。
- 切 output-style（#5 变，甚至可能改整段风格指令）。
- 打开 Plan Mode 时 `EnterPlanMode` 会插入一段额外 block（整个 `system[1]` 字节变）。

## 3.2 Tools 数组的动态填充

**工具 schema 本身是静态的**（每个工具的 `description` + `input_schema` 是字面量），但**哪些工具被 include** 是动态决策（会话级）：

| 决策点                                                    | 影响                                                         | 位置                             |
| --------------------------------------------------------- | ------------------------------------------------------------ | -------------------------------- |
| 权限模式（`bypass` / `acceptEdits` / `default` / `plan`） | 某些工具被剔除或 schema 变化                                 | `buildEffectiveTools()`          |
| `--allowedTools` / `--disallowedTools`                    | 过滤 tools                                                   | 同上                             |
| MCP 服务器发现                                            | 每个 MCP server 动态注入一组 `mcp__*` 工具                   | `materializeMcpTools()`          |
| Deferred tools（延迟加载）                                | `AskUserQuestion`、`TaskCreate` 等先只暴露 **名字**，schema 通过 `ToolSearch` 延迟获取 | 见本会话顶部 `<system-reminder>` |
| Plugin 工具（openclaw 术语）                              | 每个 plugin 可注入工具                                       | `loadPluginTools()`              |

**顺序稳定性**：

- 内置工具顺序 **固定**（`Bash, Edit, Glob, Grep, Read, ...`）—— 按字母或按优先级，取决于 runner。
- MCP 工具按 MCP server 名字母序。
- 用户不要在自己的代码里"乱序重排"工具数组 —— 一旦顺序变了，整个 tools 区段 cache miss。

**tools 数组的 description 里本身有"动态片段"吗**？CC 实测：**几乎没有**。唯一可能动态的是 Agent tool description 里列出的 `Available agent types` —— 这个列表会根据用户配置和 plugin 扩展。所以如果你加装了一个 subagent 插件，Agent tool 的 description 就变了，断点 #2 之后整个 tools 区段的 cache miss。

## 3.3 Messages 数组的组装流程

**openclaw 实测**（`pi-embedded-*.js:37537..38469`）：

```
用户输入
   ↓
runEmbeddedAttempt()
   ├─ [1] sanitizeSessionHistory(activeSession.messages)       // 清洗坏工具调用
   ├─ [2] validateReplayTurns(prior)                           // 验证轮次
   ├─ [3] limitHistoryTurns(truncated, dmHistoryLimit)          // 截断长历史
   ├─ [4] sanitizeToolUseResultPairing(limited)                // 修复 tool_use/tool_result 配对
   ├─ [5] assembleAttemptContextEngine({ messages, tokenBudget, prompt })
   │        └─ 当历史接近 context window 上限时，触发压缩
   └─ [6] activeSession.prompt(effectivePrompt, { images })    // 追加当前 user
```

**关键**：`[5] assembleAttemptContextEngine` 就是"上下文压缩"逻辑（对应你熟悉的"自动 compact"）。它会**重写历史 messages 数组** —— 一旦触发，之前所有轮的 cache prefix 全部 miss，必须重建。这是最昂贵的 cache 失效事件。

**规避策略**：

- 把 `tokenBudget` 设得尽量大（1M context 模式下就不容易触发 compact）。
- Claude Code 2.1.x 的 1M context 就是为了减少 compact 频率设计的。
- 手动清掉大 tool_result 的策略（在你本地文档 `docs/cache_optimized-plan.md` 里提到的"大结果外置"）是让单轮 token 不爆从而避免 compact 的关键。

## 3.4 `<system-reminder>` 注入点（运行时注入，不在 system 里）

这是 Claude Code 最被误解的点之一。`<system-reminder>` **不在 `system` 数组里**，而是附加在 **最新的 user 消息** 末尾（有时也在 tool_result 里）。典型注入内容：

| 触发                                   | 内容                                                         | 位置                      |
| -------------------------------------- | ------------------------------------------------------------ | ------------------------- |
| 每轮首条 user 消息                     | `Codebase and user instructions are shown below...` 跟 CLAUDE.md 摘要 | user 消息尾               |
| `TaskCreate` / `TaskUpdate` 最近被调用 | `The task tools haven't been used recently...`               | tool_result 尾            |
| 用户打 `/clear`                        | `<command-name>/clear</command-name>` + `<local-command-stdout>` | user 消息开头             |
| 延迟工具可用                           | `The following deferred tools are now available via ToolSearch...` | user 消息开头             |
| 可用 skills 列表                       | `The following skills are available for use with the Skill tool:` | user 消息开头             |
| `currentDate` / `userEmail`            | `# currentDate` 段                                           | user 消息开头（每轮刷新） |

**cache 影响**：因为 `<system-reminder>` 在 **messages 最末**，它们只影响断点 #3 之后（= 只影响**本轮**的 cache write，不污染历史 cache）。这是精心设计的："信息注入到用户消息 tail" 而不是 "注入到 system prompt"，就是为了保护 system cache。

# 4. 复刻清单：做一个"最省 cache"的拼接层

## 4.1 system 数组的正确拆法

**规则**：`system` 必须是 **数组**，每个 block 一个 `{type:"text", text, cache_control?}`。不要把所有内容揉进 `system[0]` 一个大字符串。

推荐三 block 布局：

```jsonc
{
  "system": [
    // block 0 —— 身份锚，整个产品生命周期不变（除非换 CLI 品牌）
    { "type": "text",
      "text": "You are <YourApp>, <description>.",
      "cache_control": { "type": "ephemeral", "ttl": "1h" } },

    // block 1 —— 主 system prompt（静态模板 + 会话级动态段，按 session 第一次请求时拼好并 memoize）
    { "type": "text",
      "text": "<主 prompt：包含 # Doing tasks / # Using your tools / # Environment ...>",
      "cache_control": { "type": "ephemeral", "ttl": "1h" } }

    // 不要加 block 2！不要把 CLAUDE.md / MEMORY.md 拆成独立 block —— 它们是 block 1 的一部分，
    // 因为 Anthropic 只给最多 4 个 cache_control，留两个给 messages 区。
  ],
  ...
}
```

**反模式**（会让 cache 全 miss 的常见错误）：

- 在 `system[1].text` 里拼当前时间戳（秒级或毫秒级），每轮都变 → 每轮 cache miss。正确做法：只放 `2026-04-20` 这种天级时间。
- 在 `system[1].text` 里拼 `turn #N` 计数或 `uuid` → 每轮 miss。
- 在两次请求之间重新 `JSON.stringify(tools)` 但 tool 对象字段顺序不稳定 → schema 字节不同 → cache miss。必须用 **稳定键序** 序列化（JS 用 `JSON.stringify` 保持插入顺序；TypeScript 注意 `Object.keys` 的稳定性）。

## 4.2 tools 的顺序与稳定性

1. **工具定义用常量**，不要每轮现造。
2. **不要根据上下文动态筛选工具**（除非必须）—— 被隐藏的工具造成 tools 数组字节差异，整个 tools 区 cache miss。
3. 如果一定要条件隐藏，尽量用 **权限层** 而不是 **工具过滤** 实现（工具依然出现在 schema 里，只是调用时被拒）。
4. MCP 工具如果频繁变动（比如用户在会话中间 enable/disable MCP server），考虑每个会话 **锁定一份工具快照**。

## 4.3 messages 追加策略

1. **永远只给最后一个 `role:user` 消息的最末 block 打 `cache_control`**（断点 #3）。不要给 assistant 打，不要给中间消息打。
2. 消息数组拼好之后**不要倒序复制或深拷贝** —— JS 里 `structuredClone` 某些环境会重排键序，导致字节不一致。
3. Tool result 过大时（>100KB）用"外置文件指针"（你本地项目已经有这个机制：`docs/transcript_aligned-design.md`、`docs/cache_optimized-plan.md`）。外置后历史消息字节变少，滑动 cache 成本降低。
4. 永远不要"压缩历史消息"除非 token 真的爆了 —— 一旦压缩（rewrite），所有已 cache 的 prefix 都 miss。

## 4.4 命中率自检清单

在 Anthropic SDK 返回的 `usage` 里看四个字段：

| 字段                          | 含义                         | 健康值                 |
| ----------------------------- | ---------------------------- | ---------------------- |
| `input_tokens`                | 新写入的 token（未命中部分） | 每轮只有几百           |
| `output_tokens`               | 生成 token                   | 跟输出长度相关         |
| `cache_read_input_tokens`     | 命中读 token                 | 应该 >> `input_tokens` |
| `cache_creation_input_tokens` | 写 cache token（第一轮才大） | 首轮后稳定在增量       |

**健康度指标**：`cache_read_input_tokens / (cache_read_input_tokens + input_tokens)` 应 **> 0.85**（稳态对话）。低于 0.7 通常意味着：

1. system prompt 有秒级时间戳 → 修掉。
2. tools 数组不稳定 → 固定顺序。
3. 触发了 compact → 扩大 context window 或减小单轮 tool_result。

## 附录 C · Cache绝对不能改的十条 —— 给代码审查用

1. **`system[0]` 身份锚**（"You are Claude Code..."）一个字节不能动。
2. **`system[1]` 正文顺序**：`# System → # Doing tasks → # Executing actions → # Using your tools → # Tone and style → # Text output → # Session-specific → # Committing → # Creating PR → # Other common → # auto memory → # Environment`。
3. **段间空行**：有的段 `# 标题\n正文`（无空行），有的段 `# 标题\n\n正文`（有空行），全部保留原样。
4. **列表缩进**：有的是 ` - `（前一空格），有的是 `- `（无空格），有的是 `  - `（前两空格）。不要"统一"。
5. **全角 / Unicode 字符**：`—`（em-dash）、`🤖`（Claude Code emoji）、`≤`、`·` 都是模板字节，不要 ASCII 化。
6. **tools 数组顺序** 必须在整个会话内稳定。
7. **每个 tool 的 description** 一字节不能改，包括内嵌 `<example>`。
8. **cache_control 只打在 `system[*]` 和 `messages` 的最末 user block 最末 content**，不要撒给其他 block。
9. **`cache_control` 对象本身也要稳定**：`{ type: "ephemeral", ttl: "1h" }` 的键序不要变；要么统一 `{type, ttl}`，要么统一 `{ttl, type}`，但**所有 breakpoint 用同一个序**。
10. **不要用 `structuredClone`、`JSON.parse(JSON.stringify(...))` 之类的手段来"复制"请求 body** —— 键序可能变。需要复制就手写 serializer。
