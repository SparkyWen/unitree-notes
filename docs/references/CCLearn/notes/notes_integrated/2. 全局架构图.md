### 阶段4：迁移执行（Migration Execution）

#### 核心问题：为什么需要在启动时跑迁移？

Claude Code 是一个持续演进的产品，用户的本地配置文件（`~/.claude/` 下的 JSON）保存着**模型偏好、历史设置**等状态。每次版本升级后，旧配置的字段名、默认值可能已经过时甚至废弃。

迁移函数的职责就是：**在进入任何业务逻辑之前，先把用户的本地状态静默升级到当前版本期望的格式。**

------

#### 迁移链的结构模式

```
migrateFennecToOpus()          ← 早期内测版本遗留
migrateLegacyOpusToCurrent()   ← 旧 opus 配置字段重命名
migrateOpusToOpus1m()          ← 模型 ID 升级
migrateSonnet1mToSonnet45()    ← 新版本模型 ID 升级
...（共11个）
```

这是一条**线性迁移链（Linear Migration Chain）**，每个函数对应一次产品迭代的配置变更。

------

#### 每个迁移函数的内部逻辑（通用模式）

typescript

```typescript
// 典型迁移函数结构（伪代码）
async function migrateOpusToOpus1m() {
  const config = await readLocalConfig()         // 读取 ~/.claude/config.json
  
  if (config.model === 'claude-opus-old-id') {   // 检查是否需要迁移
    config.model = 'claude-opus-1m'              // 执行字段变更
    await writeLocalConfig(config)               // 写回
    logMigration('opus → opus-1m')              // 记录（可选）
  }
  // 如果已经是新格式 → 幂等，直接跳过
}
```

**三个关键设计原则：**

| 原则                     | 说明                                               |
| ------------------------ | -------------------------------------------------- |
| **幂等性（Idempotent）** | 重复执行不产生副作用，不会二次迁移                 |
| **静默执行**             | 不打扰用户，失败时降级而非崩溃                     |
| **顺序依赖**             | 必须按版本顺序执行，后一个迁移依赖前一个的输出格式 |

------

#### 为什么放在阶段3之后、阶段5之前？

```
阶段3: 特性门控（Feature Flags 加载完成）
   ↓
阶段4: 迁移执行  ← 此时已知当前功能集，可以安全决策迁移目标
   ↓
阶段5: Commander.js 参数解析（--model 参数读取配置）
```

- **必须在阶段3之后**：迁移的目标模型 ID 可能由 Feature Flag 控制（比如某用户是否开放新模型访问）
- **必须在阶段5之前**：参数解析阶段会读取 `config.model`，此时配置必须已是最新格式，否则 `--model` 默认值会读到废弃的旧 ID

------

#### 真实场景举例

```
用户上次使用 Claude Code v1.2（model: "claude-opus-2024-07")
                    ↓
升级到 v2.0，启动
                    ↓
阶段4 检测到旧 model ID → 自动重写为 "claude-opus-20250301"
                    ↓
阶段5 --model 默认值读取到正确的新 ID
                    ↓
用户无感知，一切正常
```

**如果没有迁移层：** 用户会遇到 "Unknown model ID" 错误，或者被迫手动删除配置文件重新设置。

------

### 阶段8：分流（Traffic Splitting / Mode Dispatch）

#### 这是整个启动链中最关键的决策点

```
阶段8: 分流
    │
    ├── if (-p / --print flag) ────────→ runHeadless()  （无头模式）
    │                                        │
    │                                        ├── QueryEngine.query()
    │                                        ├── drain stdout
    │                                        └── process.exit(0)
    │
    └── else ───────────────────────────→ 交互模式
                                             │
                                             └── 阶段9: launchRepl()
```

------

#### 两条路径的本质差异

##### 路径A：Headless 模式（`-p` flag）

bash

```bash
# 典型调用场景
echo "帮我写一个排序算法" | claude -p
claude -p "解释这个文件" --output-format json
cat error.log | claude -p "分析错误原因"
```

**runHeadless() 的执行模型：**

```
输入（stdin / 参数）
    ↓
QueryEngine.query()         ← 单次 Query-Response 循环
    ↓
drain（等待所有流式 token 输出完毕）
    ↓
stdout 输出（纯文本/JSON）
    ↓
process.exit()              ← 进程结束，无状态保留
```

这是一个**无状态、单次、可管道化**的执行模型，适合：

- CI/CD 脚本集成
- Shell 管道（`| grep | awk`）
- 自动化任务
- 其他程序调用 Claude Code 作为子进程

##### 路径B：交互模式（REPL）

```
进入 React/Ink 渲染循环
    ↓
等待用户输入（事件驱动）
    ↓
多轮对话、状态持久化、UI 组件渲染
    ↓
用户主动退出（Ctrl+C / exit）
```

这是一个**有状态、事件驱动、长生命周期**的执行模型。

------

#### 为什么分流必须放在阶段7之后？

```
阶段6: 工具/命令/MCP 组装完成
阶段7: AppState + Store + 权限上下文初始化完成
         ↓
阶段8: 分流
```

**两条路径都依赖阶段6和7的产物：**

typescript

```typescript
// runHeadless() 需要
runHeadless({
  tools: assembledToolPool,          // 来自阶段6
  commands: getCommands(),           // 来自阶段6
  permissionContext: toolPermCtx,    // 来自阶段7
  store: store,                      // 来自阶段7
  model: resolvedModel,
})

// launchRepl() 同样需要
launchRepl({
  tools, commands, store,            // 同上
  initialState: appState,           // 来自阶段7
})
```

如果分流提前到阶段5，headless 模式会拿不到工具列表，无法执行任何工具调用。

------

#### 分流点的设计意义

```
同一套初始化代价（阶段1-7）
            ↓
      ┌─────┴─────┐
  无头路径      交互路径
（轻量出口）  （完整 UI）
```

这种设计的优雅之处在于：**两条路径共享所有前置初始化，只在最后一刻分叉**。

好处：

1. **代码复用最大化** — 工具注册、权限、认证逻辑只写一次
2. **行为一致性** — headless 和交互模式使用完全相同的工具集和权限模型
3. **测试简化** — 可以用 headless 模式做自动化测试，行为与真实交互完全等价

------

#### 两个阶段的协作关系总结

```
阶段4（迁移）         阶段8（分流）
    │                     │
    │  保证配置格式正确     │  保证路由选择正确
    │                     │
    ▼                     ▼
后续所有阶段        后续执行路径
读到的配置都        与用户意图完全
是最新格式          对齐（脚本 vs 交互）
```

**一句话总结：**

- **阶段4** 是"数据面"的防御层 — 保护后续所有逻辑不被历史数据格式污染
- **阶段8** 是"控制面"的路由层 — 在完整初始化完成后，将执行流量精准导向用户意图的目标路径
