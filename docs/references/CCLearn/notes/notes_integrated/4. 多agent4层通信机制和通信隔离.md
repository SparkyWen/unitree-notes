# 1. Claude Code 多 Agent 通信机制深度解析

> 本文基于 `@anthropic-ai/claude-code@2.1.88` 提取出的源码（`E:\Au_notes\claude_code\source\src`）撰写。
> 目的是把「多 Agent 协作」这件事从 4 个不同的抽象层次讲清楚：
>
> 1. **Tool-level orchestration**（工具级调度）
> 2. **Task-centric communication**（任务中心通信）
> 3. **Swarm / Teammate backend**（群体/队友后端）
> 4. **Bridge / Remote permission**（跨设备桥接）

这 4 层不是平行的「四种方案」，而是**由内到外、由同步到异步、由单进程到跨设备**的 4 个嵌套层次。先看这张总览图：

```
┌────────────────────────────────────────────────────────────┐
│  Layer 4: Bridge  (跨设备 / 跨会话, HTTPS 长轮询 + 子进程)   │
│  ┌──────────────────────────────────────────────────────┐  │
│  │  Layer 3: Swarm / Teammate  (队友，同/跨进程，邮箱)  │  │
│  │  ┌────────────────────────────────────────────────┐  │  │
│  │  │  Layer 2: Task  (Local/Remote 异步任务，磁盘)   │  │  │
│  │  │  ┌──────────────────────────────────────────┐  │  │  │
│  │  │  │  Layer 1: Tool orchestration  (同进程)    │  │  │  │
│  │  │  │  query.ts → StreamingToolExecutor        │  │  │  │
│  │  │  │  → AgentTool → runAgent (sub-generator)  │  │  │  │
│  │  │  └──────────────────────────────────────────┘  │  │  │
│  │  └────────────────────────────────────────────────┘  │  │
│  └──────────────────────────────────────────────────────┘  │
└────────────────────────────────────────────────────────────┘
```

每一层的「通信介质」都不同：

| 层      | 通信载体                           | 序列化                  | 生命周期   | 典型例子                                   |
| ------ | ------------------------------ | -------------------- | ------ | -------------------------------------- |
| Tool   | JS generator yield             | 内存对象                 | 同步     | `Agent(subagent_type: "Explore", ...)` |
| Task   | sidechain JSONL 文件 / HTTPS     | JSON lines           | 异步/可后台 | `run_in_background: true`              |
| Swarm  | 邮箱 JSON 文件 / AsyncLocalStorage | JSON                 | 长驻     | `team_name: "planners", name: "alice"` |
| Bridge | WebSocket/HTTPS 轮询 + 子进程 stdio | control_request JSON | 跨设备    | `claude rc`                            |

下面逐层展开。

## 一、Tool-Level Orchestration —— 同一个 query loop 里的「子生成器」

### 1.1 它要解决的问题

==所有一切的起点是 `query.ts`。Claude 每回合（turn）做的事情就**这四步：**==

1. 把 messages + system prompt + 可用工具池打包，向模型发 `messages.create`。
2. 流式解析返回内容，拆出 `text` 块和 `tool_use` 块。
3. 对每个 `tool_use` 块调度执行，把结果聚成 `tool_result` 块。
4. 把 `tool_result` 追加到 messages，如果还有 tool_use 就循环，否则本 turn 结束。

**Tool-level orchestration 就是第 3 步的实现细节**。关键文件：

- `source/src/query.ts` (~1700 行) — `queryLoop()` 在 L242–280
- `source/src/services/tools/StreamingToolExecutor.ts` — 真正的调度器
- `source/src/tools/AgentTool/AgentTool.tsx` — 当被调度的工具是 `Agent` 时触发
- `source/src/tools/AgentTool/runAgent.ts` — 子 Agent 的 query 生成器

### 1.2 执行细节：一次 `Agent(subagent_type: "Explore", ...)` 的完整过程

#### Step 0 —— 主 query loop 收到 assistant 消息

`query.ts:558–568` 流式读取到 assistant 消息后，扫描其 `content` 数组，找到所有 `content.type === 'tool_use'` 的块。每个块形如：

```json
{
  "type": "tool_use",
  "id": "toolu_01ABC...",
  "name": "Agent",
  "input": {
    "subagent_type": "Explore",
    "prompt": "Find all uses of foo()",
    "description": "Search foo usages"
  }
}
```

#### Step 1 —— 交给 StreamingToolExecutor

`StreamingToolExecutor.ts:40` 定义了这个类，它维护三样东西：

- `toolDefinitions`：当前可用工具（不是全部，可能被权限或 agent 定义限制过）。
- `canUseTool`：权限回调，调用时会走 hooks + permission mode。
- `toolUseContext`：贯穿整个 turn 的上下文（abort controller、appstate、session id 等）。

`addTool(block, assistantMessage)` 把工具入队。注意一点**关键设计**：

```
每个工具有 isConcurrencySafe 布尔
→ true:  可与其他并发安全工具并行
→ false: 独占执行（Agent 工具属于此类，或依赖于之前工具的写入）
```

`processQueue()` 负责根据这个标志串行或并行调度。

#### Step 2 —— executeTool → runToolUse

`StreamingToolExecutor.ts:265–310` 的 `executeTool` 做几件事：

1. `setInProgressToolUseIDs()` 告诉 UI 这个 tool_use_id 正在执行（显示 spinner）。
2. 检查 abort signal。如果用户已按 Esc，直接合成一个 `"Tool use was cancelled"` 错误结果，不跑工具。
3. 调用 `runToolUse()`（定义在 Tool.ts 附近），该函数：
   - 先做参数校验（tool 的 Zod schema）。
   - 走 `canUseTool`（权限 + hook）。
   - 执行 `tool.call(input, context)`。AgentTool 的 `call()` 定义在 `AgentTool.tsx:239–316`。
4. 把 `call()` 返回的 `AgentToolResult` 包装成 `tool_result` 块（`ToolResultBlockParam` 类型）。
5. 状态机迁移：`queued → executing → completed → yielded`。

#### Step 3 —— AgentTool.call() 内部：分岔

`AgentTool.tsx:239–316` 的 call 方法根据参数分三条路：

```ts
if (teamName && name) {
  // 分岔 A：Teammate 模式（见第三章）
  return spawnTeammate({...});
}
if (run_in_background) {
  // 分岔 B：Local async task（见第二章）
  return runAsyncAgentLifecycle({...});
}
// 分岔 C：同步子 agent（本章）
return runAgent({...});
```

##### 分岔 C 最常见：一个同步子 agent 就是一个 子 query loop。`runAgent.ts:248` 定义：

```ts
export async function* runAgent(config, toolUseContext) {
  // 1. 根据 subagent_type 拿到 agent 定义（tools whitelist, system prompt）
  // 2. 构造子 ToolUseContext（共享 abort? 否，给一个 child abort）
  // 3. 调用内部的 query() 生成器 —— 递归！
  for await (const msg of query(subMessages, subToolCtx, ...)) {
    yield msg;                  // 进度事件冒泡到父 loop 的 UI
  }
  return terminalState;         // 最终的 AgentToolResult
}
```

**关键点：子 agent 其实就是同一个 `query()` 函数的递归调用**。差别只在于：

- 它用的是「受限工具集」（由 `subagent_type` 的定义文件指定，通常不包含 Agent 本身，防无限递归）。
- 它有独立的 abort controller，父 abort 会级联，但父继续跑时子可以先结束。
- 它的 messages 不会追加到父 messages，只最终结果（文本摘要）会回传。

#### Step 4 —— 结果回流

子 agent 跑完，`runAgent` 返回一个 `Terminal` 对象（成功/失败/abort）。
`agentToolUtils.ts` 的 `finalizeAgentTool()` 把它打包成：

```json
{
  "status": "completed",
  "content": [
    { "type": "text", "text": "I found 3 usages: ..." }
  ],
  "usage": { "input_tokens": 1234, "output_tokens": 567 }
}
```

被 `StreamingToolExecutor` 写成 `tool_result` 块，返回给 `query.ts` 的 `getCompletedResults()`（L852），最终追加到父 messages 的 user 角色里，开启下一轮 API 调用。

### 1.3 一个完整例子（带 ASCII 时序图）


```
USER: "找出所有用 lodash 的地方，决定是否迁移"
 │
 ▼
MAIN query loop (turn 1)
 │ 发 API → assistant 返回：[text, tool_use(Agent, subagent_type=Explore)]
 │
 ▼
StreamingToolExecutor.addTool(tool_use_block)
 │ isConcurrencySafe? false → 独占
 │
 ▼
executeTool → runToolUse → AgentTool.call()
 │ 无 teamName、无 run_in_background → 走同步 runAgent
 │
 ▼
runAgent (子 generator)
 │ 构造 subAgentContext{ allowedTools: [Grep, Glob, Read, Bash] }
 │ 调用 query(subMessages, subCtx)
 │   │

 │   │ 发 API（模型看到子 system prompt "你是 Explore agent"）
 │   │ assistant 返回 tool_use(Grep pattern="lodash")
 │   │ (递归在这里止住：Explore 的 allowedTools 里没有 Agent)
 │   ▼
 │  runToolUse Grep → 实际执行 ripgrep → 返回 matches
 │  SUB query loop (turn 2)
 │   │ 发 API → assistant 返回 text "Found 15 files..."
 │   │ 无 tool_use → 子 loop 结束

 │
```

## 二、Task-Centric Communication —— 异步、可后台、可跨会话恢复

### 2.1 为什么要有 Task 这一层

Tool-level 的 `runAgent` 是 **同步阻塞** 的：主 loop 必须等子 agent 跑完才能继续。如果子 agent 要花 10 分钟搜整个 monorepo，用户的主对话就卡 10 分钟。

Task 层解决这个：**把 agent 放到后台，让主 loop 立刻返回，用户可以继续做别的事**。并且因为是异步的，它必须：

- 有一个 **agentId** 可以被后续工具引用（TaskGet/TaskOutput/TaskStop/SendMessage）。
- 有 **持久化**，以便 session 重启时恢复状态。
- 有 **进度回报** 机制，让 UI 显示「还在跑第 N 个工具」。

分两种：**LocalAgentTask**（本地异步）和 **RemoteAgentTask**（云端会话）。

### 2.2 LocalAgentTask：在同一 Node 进程里跑的后台 agent

#### 状态结构

`tasks/LocalAgentTask/LocalAgentTask.tsx:116–148`：

```ts
export type LocalAgentTaskState = TaskStateBase & {
  type: 'local_agent',
  agentId: string,                 // UUID，全局引用标识
  prompt: string,
  selectedAgent: string,           // subagent_type
  agentType: string,
  model: string,
  abortController?: AbortController,
  result?: AgentToolResult,        // 完成后有值
  progress?: AgentProgress,        // { toolUseCount, tokens, recentActivities }
  messages?: Message[],            // 重启时从 sidechain 恢复
  isBackgrounded: boolean,
  pendingMessages: string[],       // SendMessage 送进来的排队消息
  evictAfter?: number              // TTL，防止内存泄漏
}
```

#### 磁盘通信：sidechain.jsonl

Task 不依赖内存做通信，它依赖 **磁盘文件**：

```
~/.claude/sessions/{sessionId}/subagents/{agentId}/sidechain.jsonl
```

每一行是一条 `Message`（user/assistant/tool_result），以 UUID 为主键。
作用：

1. **实时读**：主 session 想看子 agent 当前在做什么，读最后 N 行即可。
2. **断线恢复**：session 重启时，根据 UUID 去重合并回 task state.messages。（这也是为什么断了之后能continue恢复）
3. **TaskOutputTool 的后端**：`TaskOutput(taskId)` 直接读这个文件。

#### 完整生命周期例子

用户说 `"启动一个后台 agent 审计所有 API 端点的安全性"`。

```
1. assistant → tool_use(Agent, run_in_background=true, description="Security audit")

2. AgentTool.call() 走 runAsyncAgentLifecycle():
   a) 生成 agentId = uuid()
   b) 创建 LocalAgentTaskState，压入 AppState.tasks[]
   c) fire-and-forget 启动子 query loop（不 await）
   d) 立即返回 { status: "async_launched", agentId, description }

3. 主 query loop 收到 tool_result，告诉用户「已启动后台任务 abc-123」
   用户可以继续聊别的。

4. 后台子 query loop 跑着，每产生一个 message：
   - 写入 sidechain.jsonl
   - 调用 ProgressTracker.updateProgressFromMessage() 累加 tokens/toolCount
   - 通过 emitTaskProgress() 向 SDK event stream 推进度

5. 用户随时可以：
   - TaskList() → 看到 task abc-123 status=running
   - TaskOutput(abc-123) → 读 sidechain 返回当前所有消息
   - SendMessage(abc-123, "也检查 CSRF")
       → 写入 task.pendingMessages
       → 子 agent 下一个 turn 前会被注入为 user message
   - TaskStop(abc-123) → abortController.abort()

6. 子 agent 跑完：
   - completeAgentTask() 标记 terminal
   - result 写入 state
   - sidechain 关闭
   - evictAfter 设为 now + 1h
```

**关键特性：SendMessage 是「邮箱」语义**。消息不是打断子 agent，而是排队，等子 agent 的下一个 turn 开始前，把 pending 消息作为新 user input 注入。这就是「异步双向通信」的实现方式。

### 2.3 RemoteAgentTask：云端长时会话

结构在 `tasks/RemoteAgentTask/RemoteAgentTask.tsx:22–59`：

```ts
export type RemoteAgentTaskState = TaskStateBase & {
  type: 'remote_agent',
  remoteTaskType: 'remote-agent' | 'ultraplan' | 'ultrareview' 
                | 'autofix-pr' | 'background-pr',
  sessionId: string,        // 云端 CCR session id
  log: SDKMessage[],         // 从云端拉下来的消息
  todoList: TodoList,
  reviewProgress?: {...},    // ultrareview 专用
  ultraplanPhase?: 'needs_input' | 'plan_ready'
}
```

#### 通信方式：HTTPS 轮询 + XML 事件

不是内存、不是文件，是 **HTTP**：

```
POST /v1/sessions                 → 创建，返回 sessionId
GET  /v1/sessions/{id}/events     → 增量拉取新消息（with lastEventId）
POST /v1/sessions/{id}/cancel     → TaskStopTool 调用
```

`RemoteAgentTask.tsx:150–250` 的 `pollRemoteSessionEvents()` 在一个独立的定时器里跑，每次把新消息追加到 `log`，并用正则解析 assistant 发出的 `<task-notification>` XML 块：

```xml
<task-notification>
  <status>complete</status>
  <summary>Fixed 3 bugs in auth flow</summary>
  <result>...</result>
</task-notification>
```

看到 `<status>complete</status>` 就认为任务终态，把 `log` 里的 summary 提出来作为 `AgentToolResult`。

#### 本地 vs 远程：同一把工具，两套后端

TaskCreate/TaskGet/TaskList/TaskOutput/TaskStop/TaskUpdate 这六个工具的实现都是 **多态的**：根据 `task.type === 'local_agent' | 'remote_agent'` 走不同后端：

- local → 读写 `AppState.tasks` 里的对象、读 sidechain.jsonl
- remote → 调 CCR HTTP API、读 log 数组

所以对 **模型（LLM）来说，本地和远程任务接口完全一致**。这是把「通信介质」抽象出去的好例子。
### 2.4 深度解析为什么要有local和remote: RemoteAgentTask 的意义：为什么要「把 agent 搬到云上」

#### 1. 先明确：LocalAgentTask 和 RemoteAgentTask 不是「两种等价方案」

很多人会把它俩理解成「本地后台 / 云端后台」这种纯位置差异。实际上它俩解决的是**不同类型的问题**。看源码的这个枚举就很清楚：

```ts
// source/src/tasks/RemoteAgentTask/RemoteAgentTask.tsx:60
const REMOTE_TASK_TYPES = [
  'remote-agent',      // 通用远程 agent
  'ultraplan',         // 深度规划（多轮研究 + 澄清）
  'ultrareview',       // 深度代码审查（多 agent 交叉验证 bug）
  'autofix-pr',        // 自动修复 PR 的 CI 失败
  'background-pr'      // 后台跑通整个 PR 的实现
] as const;
```

这 5 种都是 Local 版本**根本做不了的 workflow**。Local 只能做「你本地能算的事」，Remote 是一整套**托管产品能力**。下面逐个维度展开。

#### 2. 六个「Local 做不了 / 不该做」的理由

##### 理由 ① 生命周期脱离你的本地进程

Local task 的生命周期绑死在当前 Node 进程：

- 你按 Ctrl+C、关终端、关电脑、笔记本休眠 → task 就没了。
- session crash（OOM、未捕获异常）→ task 也没了。
- 重启电脑 → 从 sidechain.jsonl 能恢复状态，但 task 本身**没在跑**。

Remote task 跑在 Anthropic 的服务器上，生命周期独立：

```ts
// RemoteAgentTask.tsx:41
pollStartedAt: number;   // 当前本地 poller 开始观察的时间
                         // 注意是"观察"，不是"启动"，因为 task 早就在云端跑了
```

代码里的这个字段是个关键证据。它刻意区分「task 被创建的时间」和「我（本地）开始轮询它的时间」。因为你完全可以：

1. 昨天 10 点在家启动一个 `ultrareview`
2. 今天 9 点打开 Claude Code，它连上云，看到这个 task 已经跑了 23 小时
3. 继续拉最新进度

L38–40 的注释原文：`"a restore doesn't immediately time out a task spawned >30min ago"` —— 这是作者明确考虑了**跨会话恢复**的证据。

##### 理由 ② 计算密度不同

`ultraplan` 和 `ultrareview` 这类任务有什么特点？看它们的进度字段：

```ts
// RemoteAgentTask.tsx:45-50
reviewProgress?: {
  stage?: 'finding' | 'verifying' | 'synthesizing';
  bugsFound: number;
  bugsVerified: number;
  bugsRefuted: number;
};
```

**`verifying` 和 `refuted` 这两个词很关键**：一个 bug 被 finder agent 报出来后，会有另一个 verifier agent 去独立验证，甚至可能把它推翻（refuted）。这是一个 **多 agent 交叉验证** 的 pipeline，内部可能同时跑几十个子 agent、消耗几百万 tokens。

如果放在本地：

- 你的笔记本要扛起几十个 HTTPS 长连接 + 几十份 context 窗口。
- 你的网络要承受持续的 streaming 流量。
- 你的 token 配额按你的个人 key 算（rate limit 容易打爆）。

放云端：

- 用服务端的高带宽、高并发。
- 用托管的 **rate limit 分摊** 和 **model 专用通道**。
- 你本地只是轮询一个 session endpoint，消耗极低。

##### 理由 ③ 和外部系统的集成需要「服务端身份」

看这两个类型：

```ts
'autofix-pr' | 'background-pr'
```

它们要干的事：

- 监听 GitHub webhooks（你的笔记本不在 webhook 可达范围）
- 推 commit、开 PR、关 PR、comment PR（需要 GitHub App token）
- 订阅 CI 失败事件

这些都需要一个 **always-on 的服务端身份**。让每个用户自己的笔记本都去干这事不现实 —— 不可能要求用户保持电脑常开、不休眠、公网可达、并在本地保管 GitHub App 的私钥。

代码里 `remoteTaskMetadata` 的结构证实了这点：

```ts
// RemoteAgentTask.tsx:65-69
export type AutofixPrRemoteTaskMetadata = {
  owner: string;       // GitHub 组织
  repo: string;        // 仓库名
  prNumber: number;    // PR 号
};
```

##### 理由 ④ 跨设备接力

你的使用场景很可能是：

- 早上通勤时在手机 claude.ai 上启动一个 "review PR #123" 的任务。
- 到公司后打开笔记本，`claude` 一跑，本地就看到这个 task 的进度。
- 午休时用 iPad 查看 bug 列表。

Local task **死死绑在一台机器**。Remote task 则是 session 级别 —— 任意有权限的设备都能 attach 到同一个 `sessionId` 上。这就是 `RemoteAgentTaskState.sessionId` 作为主键的原因。

##### 理由 ⑤ Long-running 语义

```ts
// RemoteAgentTask.tsx:32-35
/**
 * Long-running agent that will not be marked as complete after the first `result`.
 */
isLongRunning?: boolean;
```

这是一个 Local 没有的概念。Long-running agent 会 **一直收反馈、一直迭代**，直到你显式关闭它。例子：

- `background-pr` 类型：跑一个需求 → 收到 CI 反馈 → 自己改 → 再提交 → 再等 CI … 直到 PR 绿。

这种「无限周期」的活儿，本地根本撑不住（睡眠/重启都会中断）；只能跑在云端 24×7 基础设施上。

##### 理由 ⑥ 特殊模型 / 特殊 workflow 只在云端启用

`ultraplan` / `ultrareview` 这类是 **产品级 workflow**，不是单纯「换个更贵的模型」。它们在云端可能用：

- 专用的多 agent 编排模板（Anthropic 内部维护）
- 专用的 system prompt（比本地版本精细很多）
- 专用的 tool set（访问内部代码索引、安全扫描器等）
- 专用的后处理（生成结构化报告）

这些都是服务端资产，本地 runAgent 无法复刻。

#### 3. 通信协议层面：Local vs Remote 的分野

| 维度             | LocalAgentTask                                 | RemoteAgentTask                                       |
| ---------------- | ---------------------------------------------- | ----------------------------------------------------- |
| 存放介质         | 本机 `~/.claude/sessions/`                     | 云端 session 存储                                     |
| 发送命令         | `AbortController` / `SendMessage`（内存+邮箱） | HTTPS POST `/v1/sessions/{id}/...`                    |
| 读进度           | 读 sidechain.jsonl                             | `pollRemoteSessionEvents()` 走 HTTPS                  |
| 解析完成信号     | task.terminalState 标记                        | 从 assistant 消息中 extractTag(`<task-notification>`) |
| 关闭时会发生什么 | 进程退出 = task 死                             | session 继续跑，只是你断开了观察                      |
| 恢复             | 从 AppState + sidechain 重构                   | 从云端拉 log 重构                                     |

`RemoteAgentTask.tsx:19` 的 `pollRemoteSessionEvents` 是这个协议的核心。它本质是一个 **event sourcing**：云端维护一个 ordered event stream，本地只负责从上次的 cursor 位置增量拉取：

```ts
import { archiveRemoteSession, pollRemoteSessionEvents } from '../../utils/teleport.js';
```

注意引入的路径叫 `teleport.js` —— 「传送」。这个命名暗示了它的本质：**把一个异地的 session 状态「传送」到你本地**。

#### 4. 一句话理解

> **LocalAgentTask** 是「我让同一个 Claude 在本地后台多跑一会儿」。
>
> **RemoteAgentTask** 是「我订购 Anthropic 提供的托管 workflow 服务，本地只是一个 dashboard」。
>
> 两者的关系更像是「本地进程 vs SaaS 订阅」，而不是「本地 vs 远程」的同一概念换个位置。

## 三、Swarm / Teammate Backend —— 多个 Agent 长期共存、互相说话

### 3.1 什么是 Agent Swarm？

在前两层，agent 之间的关系是 **父子树形**：一个 coordinator 派单子 agent 出去做活、收结果。子 agent 是 **一次性** 的，做完就销毁。

**Swarm（群体）** 的思想不同：

- 多个 agent **同时长驻**，每个有自己的身份（name、role、allowed tools、自己的历史）。
- 它们之间不是简单的 caller/callee，而是可以 **互相发消息**、**共享某些工件**、**看到彼此的进度**。
- Leader 只是协调者，不是「调用」队友，而是「通知」队友。

比如一个研发团队 swarm：

```
leader (你)
  ├── teammate "alice"  — 只能读代码、跑测试、不能改代码
  ├── teammate "bob"    — 可以改代码、但只在 src/backend/ 下
  └── teammate "carol"  — 只做 code review，禁用 Write/Edit
```

alice 发现 bug → 通过邮箱告诉 bob → bob 修 → carol review → alice 验证。
每个 teammate 都是一个独立的 query loop，有自己的 context 窗口。

### 3.2 为什么 Swarm 和 Teammate 放在一起？

因为在 Claude Code 的实现里，「Swarm」就是「Teammate」的集合。==`utils/swarm/` 目录下全是 teammate 相关代码：==

- `utils/swarm/backends/InProcessBackend.ts`
- `utils/swarm/backends/TmuxBackend.ts`
- `utils/swarm/backends/PaneBackendExecutor.ts`
- `utils/swarm/inProcessRunner.ts`
- `utils/swarm/teamHelpers.ts`
- `utils/swarm/leaderPermissionBridge.ts`
- `utils/teammateMailbox.ts`

==**Swarm 是抽象概念（一群 agent 一起干活），Teammate 是实现单位（群里的一个成员）**。所以代码层面两者合一 —— 你创建一个 swarm 的方式就是陆续 spawn 多个 teammate。==

证据：`AgentTool.tsx:282–316` 当传入 `team_name + name` 两个参数时，才走 teammate 路径：

```ts
if (teamName && name) {
  const result = await spawnTeammate({
    name, prompt, description, team_name: teamName,
    use_splitpane: true,                        // UI: 给这个队友单开一个面板
    plan_mode_required: spawnMode === 'plan',
    model: model ?? agentDef?.model,
    agent_type: subagent_type,
  }, toolUseContext);
  return { status: 'teammate_spawned', ... };
}
```

### 3.3 三种后端 —— 一个队友的三种「肉身」

==Swarm 最精彩的设计是 **后端可插拔**。`utils/swarm/backends/registry.ts` 里维护一个注册表，启动时检测环境（是否在 tmux 里、是否在 iTerm2 里、是否允许同进程），选一个合适的后端。==

#### 后端 A：InProcessBackend —— 同一 Node 进程

`InProcessBackend.ts:38–144`

```ts
export class InProcessBackend implements TeammateExecutor {
  async spawn(config) {
    // 1. 在当前进程里用 AsyncLocalStorage 创建一个隔离域
    const { handle } = await spawnInProcessTeammate(config);
    // 2. 启动队友的 query loop（fire-and-forget）
    startInProcessTeammate(handle);
  }
}
```

这个后端的精髓在 `AsyncLocalStorage`。Node 的这个 API 可以给**每条异步调用链**绑定独立的「thread-local」上下文。Claude Code 用它给每个队友绑定：

- 自己的 AppState（独立的 messages、tools、abort）
- 自己的 permission context
- 自己的日志流

结果是：**在同一 event loop 里并发跑 5 个 query loop，它们的状态互不污染**。

但出现一个问题：队友要执行工具前要征得 **leader** 的授权（因为 leader 是 UI 所在、是和人类对话的地方）。这就是 `leaderPermissionBridge.ts:25–54` 做的事：

```ts
// leader 启动时注册自己的 React setState
registerLeaderToolUseConfirmQueue(setter);

// 队友跑到权限检查时，拿 leader 的 setter
const leaderSet = getLeaderSetToolPermissionContext();
leaderSet({ request: {...}, resolve, reject });
// ↓ leader 的 REPL 弹出确认对话框
// ↓ 人类点 Approve
// ↓ resolve() 被调用
// ↓ 队友的 promise resolve，继续执行工具
```

这叫 **Permission Bridge** —— 权限请求从队友的 AsyncLocalStorage 域穿越到 leader 的 UI 域。**这是「同进程多 agent」能存在的关键胶水**。

#### 后端 B：TmuxBackend —— 不同 tmux pane 里的独立进程

`utils/swarm/backends/TmuxBackend.ts`

```ts
async spawn(config) {
  // tmux split-window -t :0 "claude --team swarm1 --name alice"
  execSync(`tmux split-window ... "claude --team ${team} --name ${name}"`);
}
```

队友是一个 **真正的子进程**，通过 tmux pane 可视化。
它和 leader 不共享内存，怎么通信？—— **邮箱文件**：

```
~/.claude/teams/{team_name}/teammates/{agentId}.json
~/.claude/teams/{team_name}/teammates/{agentId}.inbox.jsonl
```

`utils/teammateMailbox.ts` 定义：

- `writeToMailbox(agentId, message)` — 写一行 JSON
- `readTeammateMailbox(agentId)` — 读所有未读行
- 每 500ms 轮询一次

消息类型：

```json
{"type":"message","from":"leader","text":"alice, 你先跑一下测试"}
{"type":"heartbeat","timestamp":1713000000}
{"type":"result","toolUseId":"...","content":"..."}
```

权限怎么办？—— 各自独立。TmuxBackend 下每个 pane 是完整的 Claude 实例，它会在自己的 pane 里显示权限对话框。人类要到那个 pane 去批准。这是 **权限分散** 模型。

#### 后端 C：PaneBackendExecutor —— iTerm2、Warp 等的抽象父类

`PaneBackendExecutor.ts` 给非 tmux 的终端用（iTerm2 AppleScript、Windows Terminal 等），核心思路和 TmuxBackend 一样：**子进程 + 文件邮箱**，只是 spawn pane 的命令不同。

### 3.4 Coordinator Mode —— Swarm 的一种特化使用

`coordinator/coordinatorMode.ts:36` 定义了一个特殊启动模式：

```ts
export function isCoordinatorMode(): boolean {
  return process.env.CLAUDE_CODE_COORDINATOR_MODE === '1';
}
```

开启后，主 query loop 使用一个特殊 system prompt（L111–369）。大意：

> 你是协调者。不要自己写代码。把工作拆分成可并行的子任务，用 Agent(subagent_type='worker') 派给 worker。worker 跑完后它们的结果会以 `<task-notification>` 块形式出现在你的 user 消息里，带有 `<task-id>`。你综合多个 worker 的结果，给用户回答。

`ASYNC_AGENT_ALLOWED_TOOLS`（L29–35）定义了 worker 的工具集，**不包含 Agent 工具本身**（禁止 worker 再嵌套 spawn）。

Coordinator 模式本质就是：**用 Task 层（背后 LocalAgentTask）+ 特殊 prompt，把 Claude 的主 session 变成一个调度中心**。它用的还是第二章的机制。但它也可以和第三章的 Teammate 结合（coordinator 作为 leader，workers 作为 teammates）。

### 3.5 一个完整的 Swarm 例子

用户说 `"我想要一个 3 人的研发小组：planner/coder/reviewer，长期共存"`。

```
1. /team create devteam
2. Agent(team_name="devteam", name="planner", subagent_type="plan", 
         prompt="做需求分解", model="opus-4")
   → InProcessBackend.spawn()
   → spawnInProcessTeammate() 创建 AsyncLocalStorage 域
   → planner 开始跑
   → AgentTool 返回 { status: "teammate_spawned", agentId: "p-1" }
3. Agent(team_name="devteam", name="coder", subagent_type="general-purpose",
         prompt="待命，接到 planner 指令后实现")
   → 同上，coder 启动
4. Agent(team_name="devteam", name="reviewer", ...)
   → reviewer 启动

现在同一个进程里跑 4 个 query loop: leader + 3 teammates

5. planner 产出设计，通过 SendMessage(coder_id, "开始实现...") 
   → 写 coder 的邮箱
   → coder 下轮 turn 前看到新 user message，开始工作

6. coder 调用 Edit 工具，InProcessBackend 检测到需要权限：
   → 调 leaderPermissionBridge 的 setter
   → leader 的 REPL 弹出 "coder wants to edit src/x.ts, allow?"
   → 人类点允许
   → coder 的 Edit 真正执行

7. coder 完成，给 reviewer 发消息
   → reviewer 读代码、给出评审
   → reviewer 通过邮箱把结果发给 planner 和 coder

8. planner 汇总给 leader（你），leader 用自然语言给你汇报
```

**和第一层 AgentTool 的关键区别**：

| 维度     | Tool-level Agent       | Swarm Teammate       |
| -------- | ---------------------- | -------------------- |
| 生命周期 | 一次调用一次创建销毁   | 长驻，可接消息       |
| 身份     | 匿名                   | 有 name + role       |
| 通信     | 只在结束时返回一个结果 | 运行中可双向收发     |
| 权限     | 随父继承               | 可定制 allowed_tools |
| 上下文   | 子 context 独立但短暂  | 独立且持久           |

### ==3.6 为什么要有三种 Backend：InProcess / Tmux / Pane==

#### 1. 首先澄清一个误区

三种后端不是「三种不同风格的实现给用户选」，而是 **对不同运行环境的适配层**。`registry.ts` 的选择逻辑是：

```
检测当前运行环境 → 能用 InProcess 就用 InProcess → 
否则尝试 Tmux（检测到 TMUX 环境变量）→ 
否则尝试 iTerm2（macOS + iTerm2）→ 
都不行就降级回更简单的模式
```

也就是说，**同一个用户在同一台机器上，在不同 shell 里跑 Claude Code，会自动挑不同的后端**。这是「环境适配」，不是「风格选择」。

#### 2. 三种后端各自适配什么场景

我们先看它们的**物理肉身**有什么差别：

```
InProcessBackend    Tmux / Pane Backend
──────────────     ────────────────────
1 Node.js 进程     多个 Node.js 进程
├─ leader queryLoop  ├─ pane 1: leader
├─ teammate A loop   ├─ pane 2: teammate A
├─ teammate B loop   ├─ pane 3: teammate B  
└─ teammate C loop   └─ pane 4: teammate C
                    （你在终端里看到 4 个分屏）
```

##### 后端 A · InProcessBackend

**适配场景**：用户在任何终端里（哪怕是 IDE 内嵌 terminal、Windows PowerShell、CI 环境）都可以用。不依赖 tmux、不依赖 iTerm2。

**优势**：

- **零启动开销**：不用 fork 进程、不用启动新的 Node runtime。spawn 一个 teammate 就是调一个函数。
- **零 IPC 开销**：teammate 之间共享内存，发消息就是函数调用。
- **无需可视化终端**：在 CI、SSH、VS Code terminal 里都能用。
- **Permission Bridge 简单**：leader 的 UI 直接拿到 teammate 的权限请求（函数回调）。

**劣势**：

- 一个 teammate 崩了（uncaughtException），**整个进程都完蛋**，所有人一起死。
- 共享文件描述符、共享 process.env、共享 cwd，**非状态的东西**容易相互影响。
- leader 的 REPL 要同时显示自己的流 + N 个 teammate 的流，UI 会很拥挤。

##### 后端 B · TmuxBackend

**适配场景**：用户已经在 tmux 会话里跑 Claude Code（`$TMUX` 环境变量存在）。

**做法**：对当前 tmux 会话 `tmux split-window`，在新 pane 里起一个 **完整独立的** `claude --team X --name Y` 子进程。

**优势**：

- **可视化**：每个 teammate 有自己的 pane，你能用眼睛直接看到它在干什么，甚至手动敲字到它的 REPL。
- **进程隔离**：一个 teammate OOM 或者 crash，别的 teammate 不受影响。
- **独立 context**：每个 pane 是独立 CLI 实例，有自己的 AppState、自己的 ink renderer、自己的 stdin。
- **独立日志**：每个 pane 的 stdout 分别滚动，不会混在一起。

**劣势**：

- 重：每个 teammate 一个 Node.js 进程（每个 ~100MB 内存起步）。
- 启动慢：要完整初始化一次 CLI（OAuth、config 加载、hook 注册…大概 1-3 秒）。
- 沟通通过 **邮箱文件**，延迟在百毫秒级。
- 强依赖 tmux 存在。

##### 后端 C · PaneBackendExecutor / ITermBackend

**适配场景**：用户在 iTerm2（macOS 原生高级终端，不用 tmux）里运行。

**做法**：通过 iTerm2 的 AppleScript 或 Python API 创建新 pane，执行一样的 `claude --team X --name Y`。

它和 TmuxBackend **行为几乎一样**，只是「怎么让终端分屏」的 API 不同。所以源码里 `PaneBackendExecutor.ts` 是父类，`ITermBackend.ts` 和 `TmuxBackend.ts` 是两个子类，把「不同终端的分屏原语」抽象掉了。

证据 —— `source/src/utils/swarm/backends/` 目录结构：

```
PaneBackendExecutor.ts   ← 父类：定义"通过某种方式创建 pane + 邮箱通信"的通用流程
TmuxBackend.ts           ← 子类：实现"pane 创建 = tmux split-window"
ITermBackend.ts          ← 子类：实现"pane 创建 = iTerm2 AppleScript"
it2Setup.ts              ← iTerm2 的专属初始化辅助
detection.ts             ← 检测当前环境适合哪个
registry.ts              ← 注册表 + 选择逻辑
```

#### 3. 为什么要三个并存？—— 用户环境的现实分布

Claude Code 的用户画像非常多样：

| 用户类型              | 所在环境                      | 适配的 backend                        |
| --------------------- | ----------------------------- | ------------------------------------- |
| macOS 资深开发者      | iTerm2 裸用                   | **ITerm**                             |
| Linux 工程师 / SRE    | tmux 重度用户                 | **Tmux**                              |
| Windows 用户          | PowerShell / Windows Terminal | **InProcess**                         |
| VS Code / Cursor 用户 | IDE 内嵌 terminal             | **InProcess**                         |
| CI / 脚本里跑         | 无交互终端                    | **InProcess**                         |
| SSH 到服务器          | 只有基础 shell                | **InProcess**（tmux 可用则优先 Tmux） |

如果只有 Tmux Backend：Windows 和 VS Code 用户没法用 Swarm。
如果只有 InProcess Backend：macOS 用户损失了可视化分屏体验。
如果只有 iTerm Backend：Linux 用户没辙。

**所以三种后端的存在，是对「多 Agent 体验」在不同环境下**做渐进降级**的结果**：有条件就给可视化（Pane/Tmux），没条件就吃苦头挤在一个进程里（InProcess）。

#### 4. 它们共享的抽象：TeammateExecutor 接口

三者都实现同一个接口：

```ts
// 简化自 utils/swarm/backends/types.ts
interface TeammateExecutor {
  spawn(config): Promise<SpawnResult>
  sendMessage(agentId, message): Promise<void>
  kill(agentId): Promise<void>
  ...
}
```

上层代码（AgentTool、spawnTeammate）**完全不知道底下是谁**。这就是多态的好处：增加一个新 backend（比如未来 WSL-specific backend），只要实现这个接口就行，不用改调用方。

### 3.7 关键问题：InProcessBackend 同进程跑多个 query loop，为什么不互相污染？

这是全文最烧脑的部分，我们慢慢拆。

#### 1. 为什么这本来**应该**污染

先理解"污染"是怎么发生的。假设你有这样一段传统代码：

```ts
// 伪代码
let currentAgent = null;   // 模块级全局变量

function startAgent(id) {
  currentAgent = id;
  runQueryLoop();
}

function runQueryLoop() {
  while (true) {
    const response = await callAPI();
    logEvent({ agentId: currentAgent, event: response });  // ← 用全局变量
  }
}

// 并发跑两个
startAgent('alice');  // 不 await！
startAgent('bob');    // 不 await！
```

这段代码 **100% 会污染**。为什么？

1. `startAgent('alice')` 执行 → `currentAgent = 'alice'` → 进入 `runQueryLoop` → `await callAPI()` → 让出 event loop。
2. `startAgent('bob')` 执行 → **`currentAgent = 'bob'`** → 进入 `runQueryLoop` → `await callAPI()` → 让出。
3. alice 的 `callAPI()` 先返回 → 恢复执行 → 调 `logEvent` → 读 `currentAgent` → **读到 'bob'** → 事件挂错 agent。

这就是作者在 `agentContext.ts:16–22` 写下的那段注释要解决的问题：

```
WHY AsyncLocalStorage (not AppState):
When agents are backgrounded (ctrl+b), multiple agents can run 
concurrently in the same process. AppState is a single shared state 
that would be overwritten, causing Agent A's events to incorrectly 
use Agent B's context. AsyncLocalStorage isolates each async 
execution chain, so concurrent agents don't interfere with each other.
```

**作者原文翻译**：AppState 是单一共享状态，会被覆盖，导致 Agent A 的事件错误地挂在 Agent B 的 context 上。AsyncLocalStorage 隔离了每条异步执行链，让并发 agent 不互相干扰。

#### 2. AsyncLocalStorage 到底是个什么东西

这是 Node.js 的一个内置 API（`async_hooks` 模块里），心智模型如下：

**想象每个 Promise、每个 setTimeout 回调、每个 fs.readFile 回调，都悄悄背着一个「背包」。**

```ts
import { AsyncLocalStorage } from 'async_hooks';

const als = new AsyncLocalStorage<{ agentId: string }>();

// 在 als.run 里启动一条异步链，这条链上所有后续 await 都会继承这个 store
als.run({ agentId: 'alice' }, async () => {
  await doSomething();        // 这个 await 里 als.getStore() → { agentId: 'alice' }
  await doAnother();          // 这个里也是 { agentId: 'alice' }
  setTimeout(() => {
    als.getStore();            // 还是 { agentId: 'alice' }！尽管 setTimeout 是"脱离"当前栈的
  }, 1000);
});

als.run({ agentId: 'bob' }, async () => {
  await doSomething();        // 这里 als.getStore() → { agentId: 'bob' }
});
```

**关键理解**：两段 `als.run` 是在**同一个 Node 进程、同一个 event loop** 里跑的，它们的 `await` 会互相穿插调度（event loop 就是在各种 pending async 之间切换），但每当一条异步链被恢复执行，它携带的「背包」都是它自己最初被启动时的那个 store。

#### 3. Node 是怎么做到的：AsyncWrap 和 async_hooks

这块说清楚有助于真正理解。底层机制：

1. **Node 给每个异步资源分配一个 asyncId**。Promise、Timer、TCP socket、fs 操作等都是异步资源。
2. **父子关系**：A 内部创建 B，则 B 的 triggerAsyncId = A 的 asyncId。
3. **AsyncLocalStorage 内部维护一棵树**：当 A 创建 B 时，B 自动继承 A 绑定的 store。
4. **当 Node 调度器恢复执行某个异步回调前**，它查这个 callback 对应的 asyncId 绑定了哪个 store，把它设为"当前 store"。
5. 执行结束后恢复到之前的 store。

这一切都是 Node runtime 层面做的，**JavaScript 代码看不到这个切换过程**，感觉就像「store 跟着我的异步调用走」。

所以你写 `als.getStore()`，Node 查"当前正在执行哪个 async 回调"→"这个回调的 store 是什么"→ 返回那个 store。不会串线。

#### 4. Claude Code 里的具体应用

源码里有**三个**独立的 AsyncLocalStorage，每个管一类信息：

| 文件                          | ALS 变量                 | 存什么                                |
| ----------------------------- | ------------------------ | ------------------------------------- |
| `utils/agentContext.ts:93`    | `agentContextStorage`    | agent 身份（分析/遥测用）             |
| `utils/teammateContext.ts:41` | `teammateContextStorage` | teammate 的 agentId / abortController |
| `utils/workloadContext.ts`    | `workloadContextStorage` | workload 类型标记                     |

它们各自负责一类状态。真正 spawn teammate 的代码（`utils/swarm/inProcessRunner.ts`）会把 teammate 的 `runAgent()` 包在 `teammateContextStorage.run(context, () => runAgent(...))` 里。

伪代码大约这样：

```ts
// 简化自 inProcessRunner.ts
async function startInProcessTeammate(handle) {
  const teammateCtx = { agentId, parentId, abortController, ... };
  const agentCtx = { type: 'teammate', agentId, ... };

  // 嵌套的 ALS run：两个 store 同时激活
  await agentContextStorage.run(agentCtx, async () => {
    await teammateContextStorage.run(teammateCtx, async () => {
      // 这里面的所有 await 都会同时持有两个 store
      for await (const msg of runAgent(...)) {
        // 每次从 runAgent yield 出来，ALS 都还在
        processMessage(msg);
      }
    });
  });
}
```

这段代码对每个 teammate 跑一次。每次的 `teammateCtx` 不同。每个 teammate 的整条异步链都持有自己那份 store，**互不可见**。

#### 5. 用一个具体时序图看"为什么不污染"

假设我们在同一进程里 spawn 了 2 个 teammate：alice 和 bob。它们都在查 API。

```
时间轴         Alice 的链                    Bob 的链
─────────      ──────────────────────        ──────────────────────
t=0            als.run({id:'alice'}, async→)
                Alice 执行到 await fetch
                → 让出 event loop
                (背包里装着 'alice')
                
t=1                                          als.run({id:'bob'}, async→)
                                              Bob 执行到 await fetch
                                              → 让出 event loop
                                              (背包里装着 'bob')

t=2            Bob 的 fetch 先返回
                                              Node runtime 看：
                                                这个 callback 属于哪条异步链？
                                                → Bob 的链
                                                → 激活 {id:'bob'} 的 store
                                              Bob 继续执行：
                                                als.getStore() → 'bob' ✓
                                                log({agentId:'bob', ...})
                                                await 下一步
                                              Node runtime 恢复到 Bob 的 store 激活前的状态

t=3            Alice 的 fetch 返回
               Node runtime：
                 这个 callback 属于 Alice 的链
                 → 激活 {id:'alice'} 的 store
               Alice 继续：
                 als.getStore() → 'alice' ✓ 
                 log({agentId:'alice', ...})
               
```

**关键点**：t=2 时 Bob 的 callback 被调用之前，Node runtime 主动帮你切换了"当前 store"。这个切换不是 JS 代码做的，是 runtime 机制。JS 代码完全透明地用 `als.getStore()` 就能拿到正确答案。

#### 6. 那么**什么东西还是会污染**？

ALS **只隔离挂在 ALS 里的状态**。以下东西不在 ALS 保护范围内，共享即污染：

| 共享资源                            | 是否污染   | 为什么                                      |
| ----------------------------------- | ---------- | ------------------------------------------- |
| 模块级 `let currentFoo = ...`       | **会污染** | 写 ALS 外的全局变量就是共享的               |
| `process.env.SOMETHING`             | **会污染** | 进程级环境变量                              |
| `process.cwd()` / `process.chdir()` | **会污染** | cwd 是进程级属性                            |
| 文件系统（同路径并发写）            | **会污染** | 物理资源竞争                                |
| Ink renderer / terminal stdout      | **共享**   | 只有 leader 有 UI，teammate 不直接写 stdout |
| 单例 API client 里的内部 queue      | 取决于实现 | 如果它也用 ALS 或 per-call 参数就 OK        |
| 模块级定时器                        | **会污染** | 定时器回调不一定携带正确 ALS                |

Claude Code 的做法是：**把所有跨 teammate 应该隔离的东西都放进 ALS**，包括：

- `AppState` 的关键字段：不再是全局单例，而是通过 `getAgentContext()` / `getTeammateContext()` 动态解析。
- `AbortController`：每个 teammate 自己的 abort 信号。
- tool use context：权限模式、hook 列表等。
- Analytics metadata：确保每个事件挂对 agent id。

**而需要共享的东西**（文件系统、网络、leader 的 UI），就让它们真的共享，靠别的机制（锁、队列、permission bridge）协调。

#### 7. 一个 corner case：teammate 通过 env var 传递身份的原因

注意 `teammateContext.ts:7-14` 这段注释：

```
Relationship with other teammate identity mechanisms:
- Env vars (CLAUDE_CODE_AGENT_ID): Process-based teammates spawned via tmux
- dynamicTeamContext (teammate.ts): Process-based teammates joining at runtime
- TeammateContext (this file): In-process teammates via AsyncLocalStorage
```

为什么 **Tmux 下的 teammate 用 env var、in-process 的用 ALS**？

- Tmux teammate 是独立进程，ALS 是 Node 进程内的机制，跨进程不存在。但 env var 在 `fork/exec` 时会继承，正好用来传身份。
- in-process teammate 在同进程里共享 env var（一改全改，污染），所以不能用 env var，只能用 ALS。

**同一个逻辑问题（"我是哪个 agent？"）在两种后端下用了两种不同方案**，每种方案都是"该环境下能保证隔离的最省力机制"。这是个相当精妙的工程设计。

#### 8. 小结：为什么不污染的一句话答案

> 因为 **Node 的 AsyncLocalStorage 给每条异步执行链挂了一个隐形"背包"**，event loop 调度切到哪条链就激活哪个背包。Claude Code 把 teammate 的身份、abort、AppState 关键字段都塞进这个背包，所以即便 5 个 query loop 的 await 在同一个 event loop 里你来我往、交错恢复，每次恢复后代码看到的都是"自己那只背包"里的状态，而不是全局共享的最新写入值。

### 3.9 两个问题连起来看

这两个设计（RemoteAgentTask / 三种 Backend）其实在回答**同一个根本问题**：

> **"多 Agent 协作"这件事，在不同部署条件下最合适的实现是什么？"**

答案是一张光谱：

```
「最轻量、最快」                                      「最重量、最强」
          ←————————————————————————————————————————→
InProcess  →  Tmux/Pane  →  LocalTask  →  Bridge  →  RemoteAgent
同进程       多进程同机    本地异步      跨设备      完全云上
  |            |            |            |            |
  |            |            |            |            └─ 托管 workflow，
  |            |            |            |              独立生命周期，
  |            |            |            |              服务端集成
  |            |            |            └─ 本地权力 + 云端 UI
  |            |            └─ 本地后台
  |            └─ 进程隔离 + 可视化
  └─ 零开销
```

**用户需要一个 teammate 做 30 秒的小活**（查文件、跑测试）？InProcessBackend。
**用户需要 4 人团队并行工作并肉眼观察进度**？Tmux/Pane Backend。
**用户需要一个后台任务跑 10 分钟**？LocalAgentTask。
**用户希望在家控制公司机器**？Bridge。
**用户希望云端一直盯着一个 PR 直到合入**？RemoteAgentTask (`background-pr`)。

每一档都是针对一种真实场景，**不能用下一档替代**（下一档太重或不符合语义）、**不能用上一档替代**（上一档不够强）。所以 Claude Code 不是选一个赢家，而是把**整条光谱都实现了**，让框架根据场景自动选。

##### 邮箱读写的并发控制（关键细节）

好几个 teammate 会同时写同一个人的邮箱。怎么防止竞态？

`teammateMailbox.ts:23, 35–41` 用了 **lockfile**：

```ts
import * as lockfile from './lockfile.js'

const LOCK_OPTIONS = {
  retries: {
    retries: 10,
    minTimeout: 5,
    maxTimeout: 100,
  },
}
```

每次写邮箱时：`lockfile.lock(path) → 读 → 改 → 写 → unlock`。
如果另一个进程（或另一个 in-process teammate 的异步链）拿着锁，就指数退避重试，最多 10 次。

这解释了为什么是 **JSON 数组而不是 JSONL**：JSONL 可以并发 append 不冲突，但 JSON 数组必须原子读改写。选数组是因为读的时候 UI 需要随机访问（按 index 标记已读），不是纯消费队列。

##### 消息类型（邮箱里不止聊天）

邮箱里除了普通聊天消息，还承载了协议消息。`teammateMailbox.ts` 里定义了多种：

- `TEAMMATE_MESSAGE_TAG` —— 普通聊天/指令（XML 包装，会以 attachment 形式注入到收件人的下一个 prompt）
- **idle notification** (L392)：teammate 的 Stop hook 触发时发给 leader，告诉它"我空下来了"
- **plan approval request** (L682)：teammate 想退出 plan mode 但需要 leader 批准
- **shutdown request/approved/rejected** (L718/735/753)：关闭握手
- **task assignment** (L951)：leader 派活
- **team permission update** (L980)：leader 广播全组权限变更
- **mode set request** (L1016)：leader 命令某人切换 permission mode

**也就是说，邮箱既是聊天信道，也是 RPC 信道**。它实际上是 teammate 间的**唯一**通信通道（除了 in-process 下的 leaderPermissionBridge 函数回调）。

这是 LocalAgentTask 异步 agent 产出的**原始 stdout/stderr** 输出，不是消息结构化 JSON。


而 `getProjectTempDir()`（`permissions/filesystem.ts:376–378`）：


为什么放 `/tmp`（Windows 上是 `%TEMP%\claude-{uid}\...`）而不是 `~/.claude/`？

- 体积可能很大（一个 agent 跑几小时的完整 stdout），不应该污染家目录。
- 重启机器就自动清掉（符合 "output 本应临时" 的语义）。
- L17–18 的安全注释：tasks 目录的写入用了 `O_NOFOLLOW` 防止 symlink 攻击。

#### 5. Worktree：不在 `.claude` 里

当 teammate 或 subagent 用 `isolation: "worktree"` spawn 时，会创建 **git worktree**（见 `utils/worktree.ts`）。

worktree 的落点**不**在 `.claude/`，而是和你的 repo **同级或指定位置**。典型路径：

```
/path/to/your-repo/                   ← 你的主 checkout
/path/to/your-repo-{agentName}-wt/    ← teammate alice 的 worktree（举例）
```

具体路径记在 `TeamFile.members[].worktreePath` 字段里。

**这个分离很重要**：代码隔离放磁盘上别处（git 的物理隔离），而 teammate 的"状态"文件（config、inbox）留在 `.claude/teams/`。两者关注点分开。

#### 7. 关键洞察

1. **Swarm 的持久化是文件系统级的**。不依赖数据库、不依赖中心服务，靠 `~/.claude/teams/` 目录 + lockfile 协调。所以即使所有 teammate 进程都挂了，重启后从磁盘加载 config.json 就能恢复 team 结构。

2. **Inbox = 跨进程跨设备都一致的通信层**。InProcess teammate 用它，Tmux/Pane teammate 也用它。这是唯一无论后端是什么都成立的通信通道 —— 因为本地文件所有后端都能读。

3. **每个 teammate 的独立对话分两层存**：
   - **Config（身份/元数据）** → `~/.claude/teams/{team}/config.json` 里的 members entry
   - **Transcript（聊天内容）** → `~/.claude/projects/{cwd}/{agentSessionId}.jsonl`
   - 两者通过 `sessionId` 字段关联

1. **Remote 和 Local 的分野在磁盘上也能看到**：Local task 的完整输出在 `/tmp/.../tasks/`，Remote task 的本地只有 meta.json 指针。这就是"Local 是后台进程、Remote 是托管服务"的物理表现。

## 四、Bridge / Remote Permission —— 让云端的 Claude 操控你本地的电脑

### 4.1 为什么需要这一层？

前三层全都在 **一台机器** 上。但有两个真实场景单机不够用：

**场景 A：你人在外地，但代码库在公司工作站上**
你想用手机 claude.ai 问问题，它需要运行 Bash / Read / Edit 去看你工作站的代码。
解法：公司工作站挂一个 **Bridge**，挂号到 Anthropic 的云端。云端 Claude 需要执行工具时，通过这个 Bridge 打到你的工作站。

**场景 B：长时间任务，关电脑也要继续**
比如一个大型重构，你希望 claude.ai 云端会话一直跑着，同时它能在你本地 repo 上做修改。
解法：同上，Bridge 把云端会话和本地 repo 桥起来。

**场景 C：把「危险工具」的权限决定权交还人类**
远程 Claude 要 `rm -rf dist/` 了，它不该自己说了算。Bridge 的 **permission bridge** 机制会把权限请求反向送回云端 Claude，云端给用户弹对话框，用户拍板，才让本地执行。

### 4.2 架构总览

```
[ claude.ai / 云端 Claude session ]       ← 人类通过浏览器交互
         │  HTTPS 长轮询 / SSE
         ▼
[ Anthropic Bridge API  /v1/bridge/... ]
         │
         │  (Bridge 每 1s 拉取 pending 事件)
         ▼
[ 你本地 ]  runBridgeLoop()   ← bridge/bridgeMain.ts
         │  spawn 子进程（沙箱）
         ▼
[ claude --bridge-worker --session-id ... ]
  ↑ stdin JSON line  │ stdout JSON line
  ↓                  │ 实际执行 Bash/Edit/Read
  (双向 stdio pipes)  │
                     ▼
              [ 本地文件系统、git ]
```

### 4.3 具体过程

#### 启动

用户在本地跑 `claude rc` 或 `claude --bridge`（取决于配置）。或者通过 `/register` 界面。

1. `bridge/initReplBridge.ts` 初始化：

   - 从 `~/.claude/.bridgerc`（或类似）读 `environmentId + environmentSecret`。
   - 用这俩去 Anthropic 换一个 JWT，注册本机为某个环境。
   - 启动 `runBridgeLoop()`（`bridge/bridgeMain.ts:141`）。

2. `runBridgeLoop()` 主循环（`bridgeMain.ts:141–200+`）：

   ```ts
   while (!signal.aborted) {
     const events = await api.pollSessionEvents();  // 长轮询 1000ms
     for (const ev of events) dispatch(ev);
     await refreshJwtIfNeeded();
   }
   ```

3. BridgeState 状态机（`bridgeMain.ts:83`）：

   ```
   ready → connected → reconnecting → connected / failed
   ```

   网络断了自动带指数退避重连。

#### 云端发起一个会话

人类在 claude.ai 打开一个「远程 session」，指定要用哪个 environment（= 哪台本地机器）。云端会创建一个 session，给它一个 ID，并往那个 environment 的 Bridge 队列里推一个 `session.start` 事件。

`bridgeMain.ts` 收到事件 → 调 `sessionRunner.ts` 的 `SessionSpawner.spawn()`：

```ts
// sessionRunner.ts:140+
const child = spawn('node', [
  cliPath,
  '--sdk-url', sdkUrl,
  '--session-id', sessionId,
  '--sandbox',                 // 沙箱模式：限 FS、限 shell、限 MCP
  '--bridge-worker',           // 特殊模式
  ...(config.worktree ? ['--worktree', worktreePath] : [])
], {
  env: { ...process.env, OAUTH_TOKEN: ..., MODEL: ... },
  stdio: ['pipe', 'pipe', 'pipe']
});
```

可选 **worktree 隔离**（`utils/worktree.ts`）：创建临时 git worktree，子进程在隔离目录里工作，改动不污染你本地的 main checkout，需要时可以走 PR 合并。

#### 消息往返

云端 Claude 做出 assistant 消息 → 需要执行 Bash → 这个 tool_use 通过云端 API 记下来。
Bridge 拉到这个事件 → 把它作为 `{type: "user_message", ...}` 写进子进程 stdin：

```ts
child.stdin.write(JSON.stringify({
  type: 'tool_use',
  name: 'Bash',
  input: { command: 'ls' },
  tool_use_id: 'toolu_xxx'
}) + '\n');
```

子进程其实是一个 **完整的 Claude CLI 在 `--bridge-worker` 模式下**。它 `stdin` 读入的 tool_use 被它内部的 `StreamingToolExecutor` 调度执行（和第一章一样！），结果从 `stdout` 以 JSON line 输出：

```ts
process.stdout.write(JSON.stringify({
  type: 'tool_result',
  tool_use_id: 'toolu_xxx',
  content: 'file1.txt\nfile2.txt'
}) + '\n');
```

Bridge 读到这行，POST 到云端：`/v1/sessions/{id}/results`。云端 Claude 看到结果，产出下一个 assistant 消息，循环继续。

#### 关键：Permission Bridge

危险工具的权限流：

```
云端 Claude 想执行 Bash("rm -rf dist")
     ↓
本地 bridge worker 子进程收到 tool_use
     ↓
canUseTool 回调触发，但本地 permissions 是 "default = ask"
     ↓
worker 输出 control_request 到 stdout:
  { type: "control_request",
    request: { subtype: "can_use_tool",
               tool_name: "Bash",
               input: {...},
               tool_use_id: "..." } }
     ↓
Bridge 读到，解析 (sessionRunner.ts:29-66 的 onPermissionRequest)
     ↓
Bridge 发 HTTPS POST /v1/sessions/{id}/permission_request
     ↓
云端 session 状态变为 "awaiting permission"
     ↓
人类在 claude.ai 界面上看到对话框："允许执行 Bash('rm -rf dist')?"
     ↓
人类点 Deny
     ↓
云端 POST /v1/sessions/{id}/permission_response {approved: false}
     ↓
Bridge 拉到响应
     ↓
写入子进程 stdin：{ type: "control_response",
                      response: { approved: false, reason: "..." } }
     ↓
worker 的 canUseTool 回调 resolve({ approved: false })
     ↓
Bash 工具不执行，返回 "permission denied"
     ↓
云端 Claude 看到结果，调整策略
```

**这就是 Permission Bridge 的意义**：让权限决定发生在「人类在场的那一端」—— 不管云端、本地哪边决定，只要人在哪里，权限对话框就在哪里。

#### JWT 刷新（跨设备认证）

`bridge/jwtUtils.ts` 维护一个 scheduler：每个 JWT 有 expiresAt，过期前 5 分钟自动用 refreshToken 换新 JWT。失败就把 state 拉回 `reconnecting`，走重连流程。

### 4.4 Bridge vs Swarm Pane Backend：表面像，本质不同

你可能注意到 Bridge 也是「子进程 + JSON 消息」，TmuxBackend 也是。它们的区别：

| 维度             | TmuxBackend（第三章） | Bridge（第四章）       |
| ---------------- | --------------------- | ---------------------- |
| 子进程的「主人」 | leader 是你（人类）   | leader 是云端 Claude   |
| 消息走向         | 文件邮箱，本地        | HTTPS，跨 Internet     |
| 权限决定点       | 本机                  | 云端（让远端人类批准） |
| 存在理由         | 多 agent 并行         | 跨地域、跨设备         |
| 是否需要公网鉴权 | 否                    | 是（JWT）              |

### 4.5 为什么做这件事有意义

1. **解耦 UI 和执行环境**：Claude 的 UI 可以在任何设备（浏览器、手机），算力和文件在你的工作站。
2. **长时会话友好**：你可以关掉浏览器，云端 session 依然在，Bridge 依然挂着，下次回来接着看。
3. **安全边界清晰**：本地 Bridge = 受信环境，云端 = 不受信请求方。Bridge 做的事情是 **代理执行 + 代理权限**，每一个高危操作都强制回到人类。
4. **组合前三层**：Bridge worker 内部仍然是一个完整 Claude，它自己也能用 Agent 工具、spawn Task、组 Swarm。所以 Bridge 是**第一到第三层的跨设备延伸**。

## 五、四层之间的关系与选择

回到文首那张嵌套图，用一个**真实工作流**把四层串起来：

> 你在家，想让 Claude 把公司代码库的一个大需求（重写认证模块）做完。

7. 全程你在家手机上看状态，工作站一边本地 git worktree 隔离、一边在跑活。

## 七、一句话小结

> Claude Code 的多 agent 体系不是「一种多 agent 架构」，而是**四层递进的通信抽象**：
>
> - **Tool-level** 用同进程的子生成器做 context 压缩；
> - **Task** 用磁盘/HTTPS 做异步后台；
> - **Swarm** 用邮箱 + AsyncLocalStorage 做长驻多体；
> - **Bridge** 用 HTTPS + 沙箱子进程做跨设备远程。
>
> 它们共享一个核心组件：`query.ts` 的 query loop。其他三层都是给 query loop 加上「更远的通信介质」和「更强的隔离边界」。




# 2. 答疑1：每一层通信机制的补充答疑
## 问题 1：Tool 层的「JS generator yield / 内存对象序列化」

### 先讲 JS generator

普通函数是 **一次调用，一次返回**；generator 函数是 **一次调用，多次「暂停 - 恢复」**。语法上用 `function*` 声明，函数体内用 `yield` 暂停。

ts

```ts
function* counter() {
  console.log('进入');
  yield 1;            // 暂停点 1，把 1 交出去
  console.log('恢复');
  yield 2;            // 暂停点 2
  console.log('再恢复');
  return 3;           // 结束
}

const g = counter();
g.next();  // 打印"进入"，返回 { value: 1, done: false }
g.next();  // 打印"恢复"，返回 { value: 2, done: false }
g.next();  // 打印"再恢复"，返回 { value: 3, done: true }
```

**`async function\*`（async generator）** 就是上面再加异步能力——`yield` 出去的可以是 Promise，消费端用 `for await (const x of g)` 拿值。

Claude Code 里 `query()`、`runAgent()` 全是 async generator:

ts

```ts
export async function* runAgent(config, ctx) {
  for await (const msg of query(subMessages, subCtx)) {
    yield msg;          // 把子 loop 的每条消息往外「转发」
  }
  return terminalState;
}
```

父 generator 通过 `for await (const msg of runAgent(...))` 消费子 generator yield 出来的消息——**这是子 agent 往父 agent 流式冒泡进度的方式**。

### 再讲「序列化：内存对象」

表里那一栏不是说「存在内存里的对象」，而是说 **不需要真正的序列化**。

「序列化」本来的意思是：把内存里的对象结构，**编码成可跨边界传输的字节流**（JSON 文本、protobuf 二进制、等等）。什么时候需要序列化？跨进程、跨网络、写磁盘——凡是离开当前 V8 堆的时候。

Tool 层的子 generator 和父 generator 跑在 **同一个 Node 进程、同一个 V8 堆** 里，yield 出去的 `msg` 对象只是把 **堆上那个对象的引用** 传给了 `for await` 循环。没有 JSON.stringify，没有拷贝，没有编码解码。

把四层对比一下你就明白这栏在说什么：

| 层              | 通信载体             | 「序列化」那栏的含义                     |
| --------------- | -------------------- | ---------------------------------------- |
| Tool            | generator yield      | **零序列化**——直接传对象引用             |
| Task            | sidechain.jsonl 文件 | 每条消息 `JSON.stringify` 成一行文本写盘 |
| Swarm（跨进程） | mailbox 文件         | JSON 文本                                |
| Bridge          | HTTPS                | JSON body，外加 JWT 等协议头             |

所以「内存对象」是在说 **代价最低、最快、但也最脆弱（进程一挂全没）** 的通信方式。

## 问题 2：sidechain.jsonl 就是硬盘文件吗？怎么通信？

**是的**。路径就在文档里写的那儿：

```
~/.claude/sessions/{sessionId}/subagents/{agentId}/sidechain.jsonl
```

`.jsonl` = **JSON Lines**，文件格式就是「每行一个完整的 JSON 对象」，用 `\n` 分隔。这种格式的好处是 **append-only 友好**——追加一条消息就 `fs.appendFile` 一行，不需要重新解析整个文件。

### 通信方式不完全是「读最后 N 行」

你理解对了一半。实际上有几种读法，取决于谁在读：

1. **子 agent 写**：每产出一条 assistant/user/tool_result message，就追加一行到自己的 sidechain.jsonl。这是单向写入。
2. **TaskOutput 工具读**：当模型或用户调用 `TaskOutput(taskId)` 时，**读全文**，把所有行 parse 成 Message 数组返回（可能再做一步格式化/截断）。
3. **Session 恢复读**：session 重启时，`AppState.tasks[]` 里的 task 对象可能丢了 `messages` 字段（因为它只在内存），这时候 **读全文**、按 UUID 去重、重建到内存。
4. **监控/进度读**：主 UI 想显示「子 agent 正在跑第几个工具」，它其实不直接读 sidechain——看文档 2.2 节末尾，是通过 `ProgressTracker.updateProgressFromMessage()` + `emitTaskProgress()` **在写入的同时** 同步更新内存里的 `progress` 字段（`toolUseCount, tokens, recentActivities`）。主 UI 读内存就够了。

### 关键理解：pendingMessages 是反向通道

Task 层的「双向通信」不对称：

- **子 → 父**：通过 sidechain.jsonl（**磁盘**，append-only）
- **父 → 子**：通过 `task.pendingMessages`（**内存数组**，子 agent 每轮开始前检查并注入）

所以 sidechain **不是一个双向管道**，它只是子 agent 的「日志 + 状态快照」，顺便被父用来查看和恢复。

## 问题 3：Mailbox 到底是硬盘还是内存？

**答案：看后端。Claude Code 有两套并存的机制，名字都叫「mailbox / 通信」但实现完全不同。**

### 后端 A：InProcessBackend（同进程队友）→ 内存 + AsyncLocalStorage

这种场景下，leader 和 teammate 都是 **同一个 Node 进程内的两条异步执行链**。它们通信不需要文件：

- **父 → 子 的消息注入** → 写到子 teammate 的 AppState（内存对象）里的 pendingMessages / inbox 数组
- **子 → 父 的权限请求** → 走 `leaderPermissionBridge`，本质是调一个 React setState，把请求对象塞进 leader 的 UI 队列（内存）
- **隔离机制** → `AsyncLocalStorage`（下一题详解）保证每个 teammate 的「当前 AppState」查询到的是自己的那份

**没有文件参与**。这个后端下，进程挂了所有状态都没了。

### 后端 B：TmuxBackend / PaneBackendExecutor（跨进程队友）→ 硬盘文件

这种场景下，每个 teammate 是一个 **独立的 `claude` 子进程**，跑在独立的 tmux pane 里。它们不共享 V8 堆，内存里怎么塞对象也传不过去。所以只能走 **文件邮箱**：

```
~/.claude/teams/{team_name}/teammates/{agentId}.json       ← 元数据（name、role、pid、状态）
~/.claude/teams/{team_name}/teammates/{agentId}.inbox.jsonl ← 真正的邮箱，append-only
```

通信方式：

1. Leader 要给 alice 发消息 → `writeToMailbox('alice', {type:'message', from:'leader', text:'...'})` → 就是 `fs.appendFileSync(alice.inbox.jsonl, JSON.stringify(msg) + '\n')`。
2. Alice 的进程里有一个 **500ms 轮询器**（`setInterval`），定期调 `readTeammateMailbox('alice')` —— 这是 `fs.readFile` 整个 inbox，跟踪一个 offset 只处理新增的行。
3. 新消息被 parse 出来，作为 user message 注入 alice 自己的 query loop 下一轮。

所以 **mailbox 是磁盘文件**——但 **只在跨进程后端下**。同进程后端根本没有「mailbox」这个实体，只有「内存里的消息队列 + ALS 上下文隔离」。

文档里表 3-30 行写的「Swarm 邮箱 JSON 文件 / AsyncLocalStorage」就是把这两种情况并排写了，斜杠不是「和」而是「或」。

### 为什么要用 500ms 轮询而不是文件监听（inotify/fsevents）？

我的推测（基于通用工程经验）：

- 跨平台一致性：Node 的 `fs.watch` 在 Linux/macOS/Windows 上行为差异巨大，尤其是 Windows 下对 append 的事件支持很弱
- Append-only 语义下 500ms 延迟完全够用（Claude 的决策节奏是秒级）
- 轮询的代码远比事件监听稳定，不会丢事件

## 问题 4：AsyncLocalStorage / async_hooks 的「树」机制

你的理解**方向完全正确**，我把它讲得更精确一点。

### 先澄清：不是"维护一棵完整的树"

更准确的表述是：**每个异步资源在创建时，从它的"触发者"那里继承 store 指针**。没有一个全局的树数据结构真的被 Node 存着。

### 底层机制逐层展开

**第 0 层：异步资源（Async Resource）**

Node 里所有异步操作都是一个 C++ 对象，继承自 `AsyncWrap`。例子：`TCPWrap`（socket）、`TimerWrap`（setTimeout）、`PromiseWrap`（Promise）、`FSReqCallback`（fs 操作）。

每个 AsyncWrap 被创建时会分配两个 ID：

```
asyncId        : 我自己的 ID（唯一递增）
triggerAsyncId : 创建我的那个异步资源的 asyncId（"谁触发的我"）
```

**第 1 层：async_hooks 生命周期钩子**

这是底层 API：

ts

```ts
import { createHook } from 'async_hooks';

createHook({
  init(asyncId, type, triggerAsyncId, resource) { /* 资源刚诞生 */ },
  before(asyncId) { /* 异步回调即将执行 */ },
  after(asyncId)  { /* 异步回调刚执行完 */ },
  destroy(asyncId){ /* 资源被 GC */ },
}).enable();
```

`before / after` 是关键——Node 事件循环在 **调度任何异步回调之前** 会同步触发 `before(asyncId)`，执行完触发 `after(asyncId)`。这是 libuv 和 V8 协作埋下的固定插桩点。

**第 2 层：AsyncLocalStorage 基于此实现**

AsyncLocalStorage (ALS) 其实就是 async_hooks 上面的一层薄封装。它维护一个 `Map<asyncId, Store>`。简化逻辑：

```
init(asyncId, type, triggerAsyncId) {
  // 新资源诞生时，继承"触发者"的 store
  storeMap.set(asyncId, storeMap.get(triggerAsyncId));
}
before(asyncId) {
  // 回调要执行了，把它的 store 设为 "currentStore"
  currentStore = storeMap.get(asyncId);
}
after(asyncId) {
  // 回调结束，恢复
  currentStore = previousStore;
}

als.run(store, fn) {
  // 在 fn 作用域内强制设置 store；fn 内部创建的所有异步资源都会继承这个 store
}
als.getStore() {
  return currentStore;
}
```

**第 3 层：为什么叫"树"**

虽然没有真正的树对象，但逻辑上形成一棵树：

```
   teammate-alice 的 run(storeA, aliceMain) 创建的 Promise chain
                 │
     ┌───────────┼───────────┐
   timer-1    fetch-1     promise-1
     │                       │
   timer-1-cb              .then-cb   ← 全部自动继承 storeA
```

同时 leader 那边：

```
   leader 的 run(storeL, leaderMain) 创建的
                 │
     ┌───────────┘
   UI setState
     │
   React renderer fiber  ← 自动继承 storeL
```

两棵树在同一个事件循环里交错执行，但 `als.getStore()` 永远返回 **当前正在执行的那个回调所在子树的 store**，不会串。

### 回答你的原问题

> 维护了一套树的回调机制？

对的，**逻辑上是树**，**实现上是"每个异步资源持有一个 store 指针 + before/after 时切换 currentStore"**。这套机制：

- Node runtime 层面做（AsyncWrap 在 C++ 层，async_hooks 在 JS 绑定层）
- 对业务代码完全透明（你写 `als.getStore()` 就行）
- 这就是 Claude Code 能在同一 event loop 里跑 5 个并发 query loop 而各自 AppState 不污染的关键

**小警告**：ALS 不是零成本。async_hooks 启用后每个异步资源都有开销。Claude Code 可以用是因为 agent 的瓶颈在 LLM 调用（秒级），ALS 的微秒级开销可以忽略。

# 答疑2：如何实现的多agent在inprocess中的通信隔离？
## 一、先讲 callback（cb）——「以后再做」的那件事

JavaScript 运行在一个 **单线程** 里。这意味着它 **不能停下来等**。如果它等，整个程序就卡死了。

但真实世界里有很多事情要等：

- 读一个文件（等硬盘）
- 发一个网络请求（等服务器）
- 定一个闹钟 5 秒后响（等时间）

JS 不能停下来等，怎么办？**它把「事情做完之后要干嘛」打包成一个函数，交给 Node，然后立刻继续往下跑。Node 在那件事真的做完之后，回头来调用这个函数。**

这个被打包起来、「以后回来再调的函数」就叫 **callback**，缩写 **cb**。「回调」的意思就是「回头再调你」。

js

```js
// 同步的写法 —— 不存在，因为 JS 不能这样等
const data = fs.readSync('foo.txt');  // 会卡住所有东西
console.log(data);

// 真正的写法 —— 用 callback
fs.readFile('foo.txt', (err, data) => {
  // ↑ 这个箭头函数就是 callback / cb
  //   Node 读完文件之后，回头调它
  console.log(data);
});
console.log('这行会先打印');  // 因为 readFile 没卡住
```

所以图里的 **"setTimeout cb"、"fs.read cb"、"fetch cb"** 就是指「当计时器到时间了 / 文件读完了 / 网络请求回来了，**我回头要调的那个函数**」。

------

## 二、Promise —— 更好看的 callback

用多了发现 callback 有个恶心的问题：嵌套。

js

```js
fs.readFile('a.txt', (err, a) => {
  fs.readFile('b.txt', (err, b) => {
    fs.readFile('c.txt', (err, c) => {
      // 俗称「回调地狱」
    });
  });
});
```

于是 JS 发明了 **Promise**：它是一个 **对象**，代表「一件将要完成的事」。你可以用 `.then(cb)` 给它挂 callback，挂多少层都很平。

js

```js
readFile('a.txt')
  .then(a => readFile('b.txt'))     // .then 里传的还是 cb
  .then(b => readFile('c.txt'))
  .then(c => console.log('done'));
```

`.then(...)` 里传进去的那个函数，**本质上还是一个 callback**，只是套了 Promise 这层壳。图里的 **"Promise.then"、"nested .then"** 就是这种 callback。

你还可能见过 `async/await`——那其实是语法糖，底层被编译器拆成 Promise + .then。所以 **await 的后半部分（等着跑的那段）也是一个 callback**。

------

## 三、setTimeout / setImmediate / fetch / fs.read —— 四种「以后再做」

它们都在说「请以后调我的 cb」，差别只在「以后」是多久、什么条件触发：

| API                          | "以后"的含义                          |
| ---------------------------- | ------------------------------------- |
| `setTimeout(cb, 100)`        | 至少等 100 毫秒后                     |
| `setImmediate(cb)`           | 下一轮事件循环开始时（几乎立刻）      |
| `fs.readFile(path, cb)`      | 硬盘把这个文件读完之后                |
| `fetch(url).then(cb)`        | 网络请求响应回来之后                  |
| `Promise.resolve().then(cb)` | 当前同步代码跑完、下一个 microtask 时 |

对 Node 来说，它们在内部 **都是同一类东西**：一个「异步资源（async resource）」。每个异步资源诞生时 Node 都会给它发个号——`asyncId`。图里的 `id 3, id 4, id 5...` 就是这些号。

------

## 四、Event loop —— 那个永远在转的调度员

现在关键来了：Node 有个东西叫 **event loop（事件循环）**，你可以理解为一个 **永不停歇的调度员**，它在干这么一件事：

```
while (还有活没干完) {
  有到期的 timer 回调吗？→ 有就执行
  有已经读完的文件回调吗？→ 有就执行
  有完成的网络请求回调吗？→ 有就执行
  有待跑的 Promise .then 吗？→ 有就执行
  ... 循环往复
}
```

**它每次只能跑一个 callback**（因为 JS 单线程）。它按顺序挑一个，调用它，跑完再挑下一个。

图里底下那条虚线就是在演示这个调度员的某**一次挑选**：

> *Scheduler picks id 9 to run next*

意思是："调度员这一轮从一堆待跑的 callback 里，挑中了 asyncId = 9 那个（nested .then）来跑"。

------

## 五、现在讲 AsyncLocalStorage 和「背包」

你那句**"背包"的比喻太准确了**，我就直接用这个词。

js

```js
const als = new AsyncLocalStorage();

// Leader 那边：
als.run(storeL, () => {
  // 在这个函数内部，「当前背包」= storeL
  setTimeout(() => {
    console.log(als.getStore());  // 还是 storeL
    Promise.resolve().then(() => {
      console.log(als.getStore());  // 依然是 storeL
    });
  }, 100);
});

// Alice 那边：
als.run(storeA, () => {
  // 在这个函数内部，「当前背包」= storeA
  fetch('...').then(() => {
    console.log(als.getStore());  // 是 storeA
  });
});
```

**"背包"里装的是什么？** 随便什么——一般装一个对象 `{ agentId: "alice", role: "reviewer", permissions: [...] }`。在 Claude Code 里装的是 teammate 的 AppState。

### 背包是怎么自动跟着走的？

这就是问题 4 里问的 async_hooks 机制。每个 **异步资源创建的瞬间**，Node 都会记下「此刻正在跑的这条链用的是哪个背包」，把这个引用写进新资源的元数据里。

用图里的例子：

1. `als.run(storeL, leaderMain)` 启动。`asyncId = 1` 的背包是 `storeL`。
2. 在 `leaderMain` 里调用 `setTimeout(cb, 0)` → Node 创建一个计时器资源 `asyncId = 3`。Node 在创建它的瞬间查「我现在在哪条链上跑？」→ 答案是 1 → 把 `storeL` 挂到 3 上。
3. `leaderMain` 里又调用 `fs.readFile(path, cb)` → 创建 `asyncId = 4`，继承 `storeL`。
4. `fs.read cb` 跑起来之后，它内部又写 `Promise.resolve().then(cb)` → 创建 `asyncId = 9`，它的"父亲"是 4，所以 9 也继承 `storeL`。

与此同时 Alice 那边在平行地做同样的事，只不过所有资源挂的背包是 `storeA`。

**这就是图里树形结构的意思**：每个小盒子（异步资源）从它的"触发者"（trigger）那里继承背包。左边紫色那棵树所有节点都挂着 `storeL`；右边青色那棵树所有节点都挂着 `storeA`。它们**在同一个 event loop 里交错执行**，但各自的背包从不串。

## 六、before / after —— 调度员每次切换时的"换背包"动作

<img src="./1. res/asynclocalstorage.png" style="width:100%;" />

现在回答你那句关键的："切到 id 9 storeL 之后就看不到 storeA 的背包了对吧？" **完全正确。** 这一小节讲它是怎么实现的。

问题：event loop 一会儿跑 id 5（Leader 的），一会儿跑 id 6（Alice 的），一会儿跑 id 9（Leader 的）……Node 怎么保证 **每个 callback 跑的时候，`als.getStore()` 返回的是它自己那条链的背包**？

答案：**调度员在每次调 callback 前后，都会做一对小动作**。这就是 `before(asyncId)` 和 `after(asyncId)`。

图的下半部分就是在演示调度员挑中 id 9 之后的完整动作：

```
1. before(9) 被触发
     ├─ Node 查"id 9 挂的背包是哪个？"→ storeL
     └─ 把一个全局变量 currentStore 设为 storeL
       （同时把之前的 currentStore 压栈保存）

2. 真正调用 id 9 的 callback 函数体（图里橙色那块）
     └─ 函数体里写了 als.getStore()
          └─ 这个函数内部就一句话：return currentStore
             → 返回 storeL
          → 看不到 storeA（因为 currentStore 现在就是 storeL）

3. after(9) 被触发
     └─ 把 currentStore 从栈里弹回来，恢复成调 id 9 之前的值
       （这样不会污染下一个 callback）

4. 调度员挑下一个要跑的 callback
     可能是 id 6（Alice 的），那就再来一遍：
     before(6) → currentStore = storeA → 跑 cb → after(6) → 恢复
```

**关键理解**：`als.getStore()` 本质上只是返回一个全局变量 `currentStore`。这个全局变量的值在 **每个 callback 执行前被 Node 偷偷换过**，执行完又换回来。所以从 JavaScript 代码的视角看，背包"跟着自己走"；但物理上其实是**调度员在幕后替你换**。

用一个更形象的比喻：

> 想象一个剧场，只有一个聚光灯（event loop），和一排椅子上坐着很多演员（callback）。每个演员上台前，舞台监督（Node）都先去演员的更衣室给 ta 换上对应的戏服（currentStore = 这个演员的 store），演完立刻换下来，下一个演员再换 ta 的。观众（你的 JS 代码）永远只看到当前这位演员穿着 ta 自己的戏服表演——从不会穿串。

------

## 七、整个图的时序，从头到尾走一遍

现在把图里所有东西串起来，按 event loop 真实的调度顺序走一遍：

**阶段 1：两棵树被建起来**（图的上半部分）

```
t=0ms   主程序调用 als.run(storeL, leaderMain)
        → 创建 id 1，挂 storeL
        leaderMain 里又调 setTimeout → 创建 id 3，挂 storeL
                    又调 fs.readFile → 创建 id 4，挂 storeL
                    又调 Promise.resolve().then → 创建 id 5，挂 storeL
        leaderMain 函数体跑完，但它挂的那些 cb 还没跑

t=0ms   主程序调用 als.run(storeA, aliceMain)
        → 创建 id 2，挂 storeA
        同理，里面挂出 id 6, 7, 8 三个 cb，都挂 storeA
```

此刻 Node 的"待办 callback 队列"里堆着：`[3, 4, 5, 6, 7, 8]`，各自挂着自己的背包。

**阶段 2：event loop 开始跑，一个一个调度**

```
调度员挑 id 5 (Promise.then) ← microtask 优先级高
  before(5) → currentStore = storeL
  跑 cb 函数体 → 里面没再挂新 cb
  after(5) → 恢复

调度员挑 id 8 (Alice 的 Promise)
  before(8) → currentStore = storeA
  跑 cb
  after(8) → 恢复

调度员挑 id 4 (fs.read 完成了)
  before(4) → currentStore = storeL
  跑 cb → 里面写了 Promise.resolve().then(...) 
        → 创建 id 9，此时 currentStore = storeL，所以 id 9 挂 storeL （重点理解）
  after(4) → 恢复

调度员挑 id 7 (Alice 的 setImmediate)
  before(7) → currentStore = storeA
  跑 cb → 里面写了 setTimeout(..., 50)
        → 创建 id 10，此时 currentStore = storeA，所以 id 10 挂 storeA
  after(7) → 恢复

... (id 3, id 6 等也类似)

调度员挑 id 9 (刚才新生的 nested .then)  ← 图里重点演示的这一步
  before(9) → 查 id 9 的背包 → storeL → currentStore = storeL
  跑 cb → 如果里面写 als.getStore()，返回 storeL
  after(9) → 恢复
```

**图下半部分 "before(9) → run → after(9)" 就是在放大展示上面这段**。它告诉你：**id 9 虽然跑得很晚，虽然中间夹了一堆 Alice 的 cb，但它被拉起来跑的瞬间，背包被精确地换回了 storeL，所以它看到的依然是自己那棵树的状态。没有泄漏。**

------

## 八、回到 Claude Code：这一切有什么用？

现在你回头看 InProcessBackend 的代码：

ts

```ts
spawnInProcessTeammate(aliceConfig) {
  const aliceStore = { agentId: 'alice', appState: aliceAppState, ... };
  als.run(aliceStore, () => {
    startAliceQueryLoop();  // 这里面一大堆 await / .then / setTimeout
  });
}

spawnInProcessTeammate(bobConfig) {
  const bobStore = { agentId: 'bob', appState: bobAppState, ... };
  als.run(bobStore, () => {
    startBobQueryLoop();
  });
}
```

Alice 和 Bob 的 query loop **跑在同一个 Node 进程、同一个 event loop 里**，它们的 API 调用、文件读、工具执行全都在交错运行。但是当 Alice 的某个工具执行想查「我是谁？我的 AppState 是什么？」时：

ts

```ts
const ctx = als.getStore();  // 永远返回 Alice 的背包
ctx.appState.messages.push(newMessage);
```

这行代码永远拿到 Alice 自己的 AppState，**不会污染 Bob 的**。这是靠 Node runtime 在每个 callback 前后悄悄换 `currentStore` 实现的。

**如果没有 AsyncLocalStorage**，你就得在每个函数的参数里显式传 ctx，几十层调用栈全部要改。这对 Claude Code 这种有几百个函数的代码库是灾难。ALS 是让「同进程多 agent 并发」变得工程上可行的 **关键胶水**。





你的直觉非常接近了——**栈**确实是关键。但准确说，ALS 用了**两个数据结构配合**：一个是栈（管"当前是谁"），一个是 Map（记"每个异步资源属于谁"）。我把这个"小动作"拆到最细，一行代码一行代码讲。

------

## 一、先把问题讲清楚：到底在防什么污染？

场景：event loop 是一根独木桥，一次只能过一个 callback。

```
队列里等着要跑的 callback：
[ alice-cb-1, bob-cb-1, alice-cb-2, bob-cb-2, alice-cb-3 ]
     ↓          ↓          ↓          ↓          ↓
   需要看到    需要看到    需要看到    需要看到    需要看到
   storeA     storeB     storeA     storeB     storeA
```

它们一个接一个通过独木桥。**每个 callback 在自己跑的时候，调用 `als.getStore()` 必须拿到自己那份 store**。

核心挑战：**`getStore()` 这个函数内部，怎么知道现在是谁在跑？**

答案是：**有一个全局变量 `currentStore`，谁在跑谁就占着它，跑完立刻让出来。**

------

## 二、两个数据结构

### 数据结构 1：Map —— 「谁属于谁」的户口本

js

```js
// Node 内部维护（伪代码）
const resourceToStore = new Map();
// key:   asyncId（异步资源的编号）
// value: store（这个资源属于哪个背包）

resourceToStore:
  3  → storeL
  4  → storeL
  5  → storeL
  6  → storeA
  7  → storeA
  8  → storeA
  9  → storeL   ← 刚才 id 4 的 callback 里创建的，继承了 storeL
```

这个 Map **在异步资源创建时写入**（`init` 钩子），在资源销毁时删除（`destroy` 钩子）。它是静态的档案。

### 数据结构 2：栈 —— 「当前在跑谁」

js

```js
// Node 内部维护（伪代码）
let currentStore = undefined;  // 全局变量：现在谁在独木桥上
const storeStack = [];         // 栈：被打断的人排队等着恢复
```

**`als.getStore()` 做的唯一一件事：**

js

```js
getStore() {
  return currentStore;
}
```

就这一行。它不做任何查找、不做任何树遍历。它只是 **读那个全局变量**。

所以"保证不污染"这件事，**全部的魔法都在于：如何精确地在每个 callback 跑的瞬间，把 `currentStore` 设成正确的值**。

------

## 三、那个"小动作"的完整代码——`before` 和 `after`

这是 Node 在每个 callback 执行前后都要做的两段代码（伪代码，实际在 C++ 里，逻辑完全一样）：

js

```js
// ============ 小动作 1：before(asyncId) ============
// 在 callback 真正执行前被调用
function before(asyncId) {
  // ① 把"现在"的 currentStore 压栈保存
  storeStack.push(currentStore);
  
  // ② 查户口本：这个 asyncId 属于哪个 store？
  const targetStore = resourceToStore.get(asyncId);
  
  // ③ 把 currentStore 换成 targetStore
  currentStore = targetStore;
}

// 现在 callback 开始跑，它内部任何 als.getStore() 都返回 targetStore

// ============ 小动作 2：after(asyncId) ============
// callback 跑完后被调用
function after(asyncId) {
  // ④ 从栈顶弹出之前保存的值，还原
  currentStore = storeStack.pop();
}
```

==**就这四步**。"小动作"就是这四步。我们把每一步掰开再讲。==

------

## 四、为什么要用栈？—— 关键中的关键

你问"栈结构来确保不污染"，对，但栈**不是用来区分 alice 和 bob 的**。栈是用来处理**嵌套**的。

看这个场景：

js

```js
als.run(storeL, () => {           // 进入 storeL 域
  console.log(als.getStore());    // storeL ✓
  
  als.run(storeA, () => {         // 嵌套进入 storeA 域
    console.log(als.getStore());  // storeA ✓
    
    als.run(storeB, () => {       // 再嵌套进入 storeB 域
      console.log(als.getStore());// storeB ✓
    });
    
    console.log(als.getStore());  // 退出 B 后，应该回到 storeA ✓
  });
  
  console.log(als.getStore());    // 退出 A 后，应该回到 storeL ✓
});
```

`currentStore` 只有一个，它得不断被改写。进入新域时要记住旧值，退出时要精确恢复。**这就是栈的典型用法——LIFO（后进先出）对应嵌套的进入/退出。**

用栈演示这段代码执行时 `currentStore` 和 `storeStack` 的变化：

```
开始：       currentStore = undefined,  storeStack = []

进入 storeL: 把 undefined 压栈
             currentStore = storeL,     storeStack = [undefined]

进入 storeA: 把 storeL 压栈
             currentStore = storeA,     storeStack = [undefined, storeL]

进入 storeB: 把 storeA 压栈
             currentStore = storeB,     storeStack = [undefined, storeL, storeA]

退出 storeB: 弹栈 → storeA
             currentStore = storeA,     storeStack = [undefined, storeL]

退出 storeA: 弹栈 → storeL
             currentStore = storeL,     storeStack = [undefined]

退出 storeL: 弹栈 → undefined
             currentStore = undefined,  storeStack = []
```

**栈的功能就是：精确地记住"我进来之前你是谁"，这样我走的时候能把你还原。**

------

## 五、真正回答你的问题：怎么保证 alice 和 bob 不串？

现在把"嵌套栈"的知识 + "户口本 Map"的知识合起来，看两个不相关的 agent 并发时发生了什么。

### 场景

js

```js
// Leader 主程序
als.run(storeL, () => {
  setTimeout(leaderCb, 100);   // 安排一个 leader 的 cb，id = 3
});

als.run(storeA, () => {
  setTimeout(aliceCb, 100);    // 安排一个 alice 的 cb，id = 6
});
```

两个 `als.run` 同步执行完就退出了。此刻：

```
currentStore = undefined
storeStack   = []
resourceToStore = { 3 → storeL, 6 → storeA }
```

队列里躺着两个 cb 等着事件循环来捞：id=3 和 id=6。

### 事件循环捞第一个：id=3

```
before(3) 触发
  ├─ storeStack.push(currentStore)  →  storeStack = [undefined]
  ├─ targetStore = resourceToStore.get(3)  →  storeL
  └─ currentStore = storeL

leaderCb 开始执行
  └─ 它内部写 als.getStore()
       └─ return currentStore  →  storeL ✓

leaderCb 跑完

after(3) 触发
  └─ currentStore = storeStack.pop()  →  undefined
     （storeStack 变回 []）
```

### 事件循环捞第二个：id=6

```
before(6) 触发
  ├─ storeStack.push(currentStore)  →  storeStack = [undefined]
  ├─ targetStore = resourceToStore.get(6)  →  storeA
  └─ currentStore = storeA

aliceCb 开始执行
  └─ 它内部写 als.getStore()
       └─ return currentStore  →  storeA ✓   完全不会看到 storeL

aliceCb 跑完

after(6) 触发
  └─ currentStore = storeStack.pop()  →  undefined
```

**关键观察**：alice 的 cb 跑的时候，**`currentStore` 里物理上只存在 `storeA` 这一个值，`storeL` 根本不在这个变量里**。就算 alice 的代码想访问 storeL 也访问不到——它根本没有 storeL 的引用。

这就是"不会污染"的物理原因：**同一时刻，`currentStore` 里只装一个 store。不存在"两个 store 同时在 currentStore 里"这种状态。** callback 不可能看到别人的 store，因为别人的 store **物理上此刻不在那里**。

------

## 六、那为什么还需要栈呢？（不是两个 agent 的场景，那栈到底救谁？）

很好的追问。纯并发不需要栈——每个 cb 跑完就 pop 回 undefined，不会有嵌套。

**栈是给"在一个 callback 里再触发另一个 store 域"这种嵌套场景用的**。Claude Code 里这种场景真实存在：

js

```js
// Alice 的 query loop 里
als.run(aliceStore, async () => {
  // currentStore = aliceStore
  await someToolExecution();
  
  // 工具执行期间，Claude Code 可能需要临时进入 leader 的权限域
  als.run(leaderPermissionStore, () => {
    // currentStore = leaderPermissionStore
    askLeaderForApproval();
  });
  
  // 权限询问完毕，回来继续 alice 的工作
  // currentStore 必须精确恢复成 aliceStore
  continueAliceWork();  // 这里 als.getStore() 必须还是 aliceStore
});
```

栈在这里救命。没有栈就只能记住一层——进入 leader 域后就再也回不到 alice 域了。

------

## 七、异步嵌套——栈的终极形态

更精妙的是异步跨越 tick 的嵌套：

js

```js
als.run(aliceStore, () => {
  // currentStore = aliceStore
  setTimeout(() => {
    // 这个 cb 跑起来时 —— 100ms 之后，此刻 event loop 已经跑过无数个别的 cb 了
    // currentStore 可能被别人改成任何值
    // 但 Node 保证这个 cb 跑的时候 currentStore 仍然是 aliceStore
    console.log(als.getStore());  // aliceStore ✓
  }, 100);
});
```

原理：这个 setTimeout 创建的时候，`asyncId = 3` 被登记进户口本 → `resourceToStore[3] = aliceStore`（**因为创建它的时候 currentStore = aliceStore，新资源继承当前背包**）。

100ms 后事件循环捞到 id 3 准备跑，`before(3)` 查户口本 → 发现 3 挂的是 aliceStore → 把 currentStore 设成 aliceStore → 跑 cb → `after(3)` 恢复。

**所以"背包跟着异步链走"的秘密是**：

- **创建时快照**（init 钩子把 currentStore 写进户口本）
- **执行时恢复**（before 钩子从户口本查出来，重新设回 currentStore）

栈只管**同步嵌套**的恢复，Map 管**跨异步边界**的传递。两者缺一不可。

------

## 八、浓缩成一张图的心智模型

```
┌─────────────────────────────────────────────────────────────┐
│  全局变量（独木桥上那个人的背包）                            │
│    currentStore = ???                                       │
├─────────────────────────────────────────────────────────────┤
│  栈（上个人的背包，排队等恢复）                              │
│    storeStack = [...]                                       │
├─────────────────────────────────────────────────────────────┤
│  Map 户口本（每个异步资源属于谁）                            │
│    resourceToStore = { id → store, ... }                    │
└─────────────────────────────────────────────────────────────┘

新异步资源诞生：init 钩子把 currentStore 写进户口本
callback 要执行：before 钩子 { 旧值压栈; 从户口本查 → 设新值 }
callback 执行中：als.getStore() 读全局变量
callback 执行完：after 钩子 { 弹栈 → 恢复旧值 }
```

------

## 九、一句话回答你的问题

**你说"栈结构来确保不污染"——这话对一半。更准确的说法是：**

> **隔离靠的是「同一时刻 `currentStore` 这个全局变量里只装一个 store」。栈的作用是精确地在嵌套进入/退出时保存和恢复这个全局变量的值，Map 的作用是让跨越异步边界的 callback 仍然能找回自己该有的 store。三者合力保证了每个 callback 执行的瞬间，`currentStore` 一定是它自己应该看到的那个 store。**

用一个极简的比喻收尾：

> 独木桥（event loop）一次过一个人。每个人来之前，守桥人（before 钩子）都要查档案（Map）看这个人该背什么包，把对应的包递给 ta（设 currentStore），同时把独木桥上原来那个人的包暂存进衣帽间（push 栈）。人过桥后，守桥人（after 钩子）回收 ta 的包，从衣帽间拿回原来那个（pop 栈）。**桥上永远只有一个人、一个包——想穿串也没机会。**



# 答疑3：多进程跨设备之间的通信

对，**ALS 只在同进程（InProcess）场景里有意义**。跨进程、跨网络的场景，隔离机制完全不同——而且其实**更简单、更暴力、也更彻底**。我把四种场景的隔离方式全部展开给你看。

------

## 一、先确立一个大原则：隔离级别是由「共享什么」决定的

不同场景下，agent 之间"物理上共享了什么"，就决定了必须用什么机制来隔离。

```
共享的东西越多 → 需要的隔离机制越精巧
共享的东西越少 → 隔离天然就有了，反而简单
```

四种场景从共享最多到共享最少排列：

| 场景                        | 共享什么                                   | 隔离靠什么                     |
| --------------------------- | ------------------------------------------ | ------------------------------ |
| **同 event loop 多 agent**  | 同一个 V8 堆、同一个 currentStore 全局变量 | **ALS**（换全局变量）          |
| **同进程多线程**（Worker）  | 同一个 Node 进程、不同 V8 堆               | **OS 线程 + 独立 V8 隔离区**   |
| **同机多进程**（Tmux pane） | 同一台机器的文件系统、OS 资源              | **OS 进程边界 + 文件系统路径** |
| **跨机远程**（Bridge）      | 几乎啥也不共享                             | **网络协议 + 认证 + 沙箱**     |

ALS 是最精巧的那一种，因为它要解决**最困难的隔离**——"连进程都不分，就靠软件约定"。下面我从第二种开始讲，难度递减。

------

## 二、同进程多线程（Worker Threads）——V8 隔离区

Node 有一个叫 `worker_threads` 的 API：

js

```js
const { Worker } = require('worker_threads');
const aliceWorker = new Worker('./alice-agent.js');
const bobWorker = new Worker('./bob-agent.js');
```

表面上看是"多线程"，但 Node 的实现不是传统的共享内存多线程。**每个 Worker 有自己完整的 V8 实例**——自己的堆、自己的 event loop、自己的全局变量。

所以 Alice 的 `currentStore` 和 Bob 的 `currentStore` **物理上是两个不同的内存变量**，根本不在同一个地址空间。

### 那它们怎么通信？

既然内存不共享，就不能直接传对象引用（不像同 event loop 那样 yield 一个对象过去）。它们通信靠 **消息传递（message passing）**：

js

```js
aliceWorker.postMessage({ type: 'execute', tool: 'Read', args: {...} });

// alice-agent.js 里
parentPort.on('message', (msg) => {
  // 收到消息，处理
  parentPort.postMessage({ type: 'result', data: ... });
});
```

`postMessage` 发送的对象会被 **结构化克隆（structured clone）**——等价于 `JSON.stringify + JSON.parse`，但支持更多类型（Date、Map、Set、ArrayBuffer）。关键是**拷贝一份过去**，而不是共享引用。

所以隔离是**物理隔离**：你想污染对方都做不到，因为你拿到的对象是你自己堆里的一份拷贝，改它不会影响对方。

Claude Code 没有大面积用 Worker Threads（生态还不够成熟，Node 的大部分生态是为单线程设计的）。但概念上要理解：**这是 ALS 的"硬件升级版"**——不再靠软件约定换背包，而是物理上就给你两个独立的宇宙。

------

## 三、同机多进程（Tmux Backend）——OS 进程 + 文件邮箱

这就是 Claude Code 实际用的 TmuxBackend / PaneBackendExecutor 的场景。

bash

```bash
tmux split-window "claude --team devteam --name alice"
tmux split-window "claude --team devteam --name bob"
```

每个 teammate 是一个**独立的 OS 进程**。alice 的 pid=12345，bob 的 pid=12346。这是 OS 级别的隔离，比 Worker Threads 更彻底：

- 独立的虚拟地址空间（内核保证的，OS kill -9 也无法穿透）
- 独立的文件描述符表
- 独立的环境变量
- 独立的工作目录

**alice 进程想访问 bob 的内存？OS 直接返回 segfault。** 你不需要任何软件约定来"避免污染"——污染在物理上就不可能发生。

### 那它们怎么协作？

既然进程完全隔离，它们得通过 **进程外的东西** 交流。常见选项：

| 机制         | 原理                         | Claude Code 是否用        |
| ------------ | ---------------------------- | ------------------------- |
| 共享文件     | 大家读写同一个磁盘文件       | ✅ 邮箱文件                |
| 管道 / stdio | 父子进程的 stdin/stdout pipe | ✅ Bridge 的 bridge-worker |
| Unix socket  | 本地 IPC socket              | ❌                         |
| TCP / HTTP   | 走本地 localhost 网络        | ❌ 本地不用                |
| 共享内存段   | mmap 同一块内存              | ❌ Node 不好用             |
| 信号         | kill -USR1 这种              | ❌                         |

Claude Code 选了**共享文件**——具体是上次讲过的 `~/.claude/teams/{team}/teammates/{agentId}.inbox.jsonl`。

### 文件邮箱怎么隔离？

这里的"隔离"其实是**命名约定 + 文件系统路径**，比 ALS 粗暴得多：

```
~/.claude/teams/devteam/teammates/
  ├── alice.inbox.jsonl     ← alice 的邮箱，只有 alice 轮询这个
  ├── bob.inbox.jsonl       ← bob 的邮箱，只有 bob 轮询这个
  └── carol.inbox.jsonl     ← carol 的邮箱
```

**每个 agent 的"身份"就是它轮询哪个文件**。不存在"谁的 store 弄错了"这种问题——alice 进程启动时被告知"你是 alice"，它就 `fs.watch('alice.inbox.jsonl')`，从头到尾只看这一个文件。

Leader 想给 alice 发消息？`fs.appendFile('alice.inbox.jsonl', ...)`。想发给 bob？换个路径。**路径本身就是收信人地址**。

### 这里有没有"污染"风险？

理论上有两种：

**1. 写错文件**：Leader 本意发给 alice 却追加到 bob 的邮箱。这不是 OS 能防的，是应用层逻辑错误。Claude Code 的做法是：所有邮箱操作走 `teammateMailbox.ts` 的统一接口，`writeToMailbox(agentId, msg)` 内部拼路径——把容易出错的拼路径操作集中到一个地方。

**2. 并发写**：两个 Leader 进程（理论上）同时往同一个 inbox.jsonl 写。POSIX 保证小于 PIPE_BUF（通常 4096 字节）的 `write()` 系统调用是原子的，而 jsonl 每行通常远小于这个阈值——所以 append-only 的设计本身就避免了交错。这是**用文件格式选择规避并发问题**的经典例子。

**核心对比**：

```
ALS:  靠"软件约定"，多个 store 共用一个 currentStore 变量，靠钩子切换
文件: 靠"物理隔离 + 命名约定"，每人独占一个文件，路径就是身份
```

前者精巧（想不到 Node 能做到这种事），后者踏实（Unix 哲学就这样玩了 50 年）。

------

## 四、跨机远程（Bridge）——网络协议 + 认证 + 沙箱

最外层的场景：云端 Claude 在 Anthropic 服务器上，你本地的 Bridge worker 在你的工作站上，两者隔着公网。

### 共享的东西：几乎没有

- 不同物理机器
- 不同的 OS
- 不同的网络位置
- 不同的用户身份

这种场景下"隔离"根本不是问题——**默认状态就是完全隔离的**。反倒是"怎么让它们安全地通信"才是难题。

### 多层防线，从外到内

**第 1 层：网络协议边界**

双方之间的唯一通道是 HTTPS。所有消息走 JSON over HTTPS：

```
本地 Bridge   <── HTTPS 长轮询 ──>   Anthropic Bridge API   <──>   云端 Claude session
```

本地 Bridge 主动向云端 API 发请求（poll），云端**从不主动连本地**。为什么？因为你的本地机器大概率没有公网 IP（家里 NAT 后面、公司内网里），云端没法主动连过来。**本地 pull，不是云端 push**——这是 Bridge 的基本模型。

**第 2 层：JWT 认证**

每个 Bridge 实例启动时用 `environmentId + environmentSecret` 换一个 **JWT（JSON Web Token）**。之后每次 HTTP 请求都带这个 JWT。服务端通过 JWT 识别"这个请求是哪个 environment 发的"。

```
Bridge → POST /v1/bridge/register { envId, envSecret }
       ← { jwt: "eyJhbGci...", expiresAt: ... }

Bridge → GET /v1/bridge/events
       Headers: Authorization: Bearer eyJhbGci...
       ← { events: [...] }
```

JWT 有过期时间（通常 1 小时），`bridge/jwtUtils.ts` 维护一个 scheduler 在过期前 5 分钟自动刷新。**这保证了"身份"这个维度的隔离**——别人拿不到你的 JWT 就冒充不了你。

**第 3 层：Session ID 作为租户隔离**

云端同一时刻有成千上万个 Bridge 连着（所有用户的所有 environment）。服务端怎么知道某个事件该发给谁？

```
云端状态：
  session-abc123 → { env: env-user1, status: running, events: [...] }
  session-def456 → { env: env-user2, status: running, events: [...] }
  session-ghi789 → { env: env-user1, status: running, events: [...] }

Bridge (env-user1) 发 GET /v1/bridge/events
  ↓
服务端查"env-user1 关联哪些 session" → [abc123, ghi789]
  ↓
只返回这两个 session 的新事件
```

**sessionId 是租户隔离键**。服务端永远只把 A 用户的 session 事件返回给 A 用户的 Bridge。这是**服务端强制的隔离**，不依赖客户端诚实。

**第 4 层：子进程沙箱（最内层）**

就算云端和本地的身份验证都通过了，云端 Claude 让本地执行的命令还是可能作恶（比如 `rm -rf /`）。所以本地 Bridge 不会直接在自己的进程里执行云端的命令，而是 **spawn 一个沙箱子进程**：

ts

```ts
const child = spawn('node', [
  cliPath,
  '--sandbox',          // 沙箱模式
  '--bridge-worker',    // 只处理 Bridge 消息
  '--session-id', sessionId,
  ...(config.worktree ? ['--worktree', worktreePath] : [])
], {
  env: { ...filteredEnv },  // 环境变量被过滤
  stdio: ['pipe', 'pipe', 'pipe']
});
```

沙箱里的限制：

- **文件系统限制**：只能访问配置允许的路径（通常是某个项目目录）
- **Shell 限制**：某些命令被拦截或需要额外权限
- **MCP 限制**：不是所有 MCP server 都暴露给沙箱
- **Worktree 隔离**（可选）：创建临时 git worktree，子进程改动不污染主分支

**第 5 层：Permission Bridge（决策权回人类）**

即使沙箱里能跑 Bash，危险命令（`rm -rf`, `curl | sh`）仍然要走 **Permission Bridge**：

```
云端 Claude 想 rm -rf dist/
      ↓
本地 worker 收到 tool_use
      ↓
worker 的 permission 检查说"需要批准"
      ↓
worker 输出 control_request 到 stdout
      ↓
Bridge 收到，POST /v1/sessions/{id}/permission_request
      ↓
你手机上的 claude.ai 弹对话框
      ↓
你点允许或拒绝
      ↓
回传到 Bridge → worker stdin
      ↓
worker 继续执行或拒绝
```

**这一层不是防"系统污染"，是防"决策被代理"**——高危决策必须有人类签字，不管云端还是本地都做不了主。

------

## 五、对比总结：同一个问题，四种答案

把"两个 agent 之间怎么不互相影响"这个问题，四种场景的答案列清楚：

| 场景               | 内存共享       | 隔离机制               | 通信手段               | 失效后果        |
| ------------------ | -------------- | ---------------------- | ---------------------- | --------------- |
| **同 event loop**  | 是             | ALS 切换全局变量       | 直接传对象引用         | 一个 bug 就串线 |
| **Worker Threads** | 否（独立 V8）  | V8 隔离区              | postMessage 结构化克隆 | 几乎不可能串    |
| **Tmux 多进程**    | 否（独立进程） | OS 进程边界 + 文件路径 | 邮箱 JSON 文件         | 写错路径才会串  |
| **Bridge 跨机**    | 否（独立机器） | 网络协议 + JWT + 沙箱  | HTTPS JSON             | 需要认证被攻破  |

看出规律了吗？**越靠近顶部（共享越多），隔离越依赖"软件正确性"；越靠近底部，隔离越依赖"物理/OS/网络这些硬约束"**。

**ALS 是最脆弱的一层**——如果 Node 的 async_hooks 有 bug，或者某个第三方库没正确传播异步上下文（历史上这种 bug 真的出过），隔离就破了。所以 Claude Code 只在"权衡之下值得"的场景用 ALS（同进程多 agent 避免重启子进程的开销），其他地方都用更暴力的物理隔离。

------

## 六、Claude Code 为什么要支持这么多层？

你可能想问：既然物理隔离更踏实，为什么不全部用多进程/多机？

答案是**性能、资源、用户体验的权衡**：

| 隔离强度       | 启动开销 | 通信开销 | 内存开销   | 适合场景                     |
| -------------- | -------- | -------- | ---------- | ---------------------------- |
| ALS（同 loop） | 0 ms     | 纳秒级   | KB 级      | 几十个短命 teammate 同时在跑 |
| Worker Threads | 50 ms    | 微秒级   | MB 级      | 少量 CPU 密集任务            |
| Tmux 子进程    | 500 ms   | 毫秒级   | 几十 MB    | 用户要可视化看每个 agent     |
| Bridge 跨机    | 秒级     | 十几毫秒 | 服务端资源 | 跨设备、长周期、团队协作     |

**选 ALS**：用户在家起了个小 swarm，想让 3 个 teammate 立刻协作起来，不想看到 3 个终端窗口抢屏幕，也不想等 3 次 Claude 启动（每次几秒）。

**选 Tmux**：用户想**亲眼看到**每个 agent 在干什么（pane 里是 alice 的完整 REPL），愿意用一点内存和启动时间换可见性。

**选 Bridge**：用户不在本地——在手机上、在飞机上、在会议室——但代码、环境变量、git 仓库在工作站上。这不是性能问题，是"算力位置"问题。

**Claude Code 的聪明之处**：让这四种机制**在同一套上层抽象下共存**。`AgentTool.call()` 这个函数，根据参数选择走哪条路：

ts

```ts
if (teamName && name) {
  return spawnTeammate(...);  // 可能 ALS 可能 Tmux，看后端 registry 选的
}
if (run_in_background) {
  return runAsyncAgentLifecycle(...);  // LocalAgentTask
}
return runAgent(...);  // 同步子 generator
```

而在 **Bridge 的 worker 子进程内部**，这套逻辑还在继续运行——它自己可能又 spawn 一个 Swarm、用 ALS 隔离 teammates。所以**四层隔离是嵌套的、可组合的**。

------

## 七、一句话总结

> **ALS 是"同进程多 agent"场景专用的软件级隔离，其他场景根本不需要它——因为 V8、OS、网络已经用物理/硬件/协议的方式把隔离给你做好了。隔离机制的选择，本质上是在回答"我们愿意共享多少东西来换多少性能"这个权衡。**

更直白的版本：

- 同一个事件循环 → ALS（换背包）
- 不同 V8 → 自然隔离（各有各的堆）
- 不同进程 → 自然隔离（各有各的地址空间）
- 不同机器 → 自然隔离（各有各的宇宙）

**越往后越不需要"机制"，只需要"协议"——怎么让两个本来就隔离的东西能说上话**。ALS 难在"明明在同一个宇宙，要装作在不同宇宙"，后面三种难在"明明在不同宇宙，要装作在同一个宇宙"。方向正好相反。



# 答疑4： 底层细节答疑V8堆

## 一、先从最基本的问题开始：变量放在哪儿？

你写 JS 代码的时候：

js

```js
const name = "alice";
const user = { id: 1, role: "admin" };
const numbers = [1, 2, 3, 4, 5];
```

这些值**物理上存在哪里**？

答案是：**进程的内存（RAM）里**。但"进程的内存"内部又分成几个区域，不同的值放不同的地方。理解这个分区，就是理解"堆"的起点。

------

## 二、一个进程的内存布局

当 OS 启动一个进程（比如 `node alice.js`），它给这个进程分配一块虚拟地址空间。这块空间大致长这样：

```
高地址 ┌─────────────────────┐
       │       栈（Stack）     │  ← 函数调用、局部变量、返回地址
       │          ↓            │     （向下增长）
       ├─────────────────────┤
       │                     │
       │      （未分配）       │
       │                     │
       ├─────────────────────┤
       │          ↑            │
       │       堆（Heap）      │  ← 动态分配的对象、数组、字符串
       │                     │     （向上增长）
       ├─────────────────────┤
       │        BSS           │  ← 未初始化的全局变量
       ├─────────────────────┤
       │        Data          │  ← 已初始化的全局变量
       ├─────────────────────┤
       │        Text          │  ← 程序代码（机器指令）
低地址 └─────────────────────┘
```

两个关键区域：**栈（Stack）** 和 **堆（Heap）**。

------

## 三、栈 vs 堆——两种完全不同的内存管理哲学

### 栈（Stack）：纪律严明的办公室

栈的规则非常死板：**后进先出（LIFO）**，只能在顶部添加/删除。

js

```js
function outer() {
  const a = 10;        // ① a 进栈
  inner();             
  // ⑤ inner 返回后，回到这里
}

function inner() {
  const b = 20;        // ③ b 进栈
  const c = 30;        // ④ c 进栈
}                      // ⑤ inner 返回时，b 和 c 一起出栈
```

栈的特点：

- **快**：加减一个指针就行（push = SP++，pop = SP--）
- **自动管理**：函数返回时，它的栈帧自动销毁，不需要手动释放
- **空间有限**：通常几 MB（Node 默认 984KB），递归太深就栈溢出
- **只放小东西**：固定大小的原始值——数字、布尔、指针

### 堆（Heap）：仓库式的动态存储

堆的规则完全不同：**任意时刻可以在任意位置分配/释放**。

js

```js
const user = { name: "alice", age: 30 };
// 这个对象放哪？放堆上
// 栈上只有一个变量 user，它存的是"指向堆里那个对象的地址"（指针）
```

堆的特点：

- **慢**：要找一块合适大小的空闲空间（allocator 算法）
- **手动或 GC 管理**：C/C++ 要手动 free，JS 有垃圾回收器
- **空间大**：可以占用进程地址空间的大部分（GB 级）
- **放大东西**：对象、数组、字符串、函数闭包——所有可变大小、生命周期不确定的东西

------

## 四、用一张图看 JS 变量到底存在哪

js

```js
function createUser() {
  const id = 42;                              // ← 原始值，在栈上
  const name = "alice";                       // ← 字符串，堆上。栈上只有指针
  const user = { id, name, roles: ["admin"] }; // ← 对象，堆上
  return user;                                // ← 返回堆上对象的指针
}

const u = createUser();
```

内存状态：

```
栈（Stack）                    堆（Heap）
┌──────────────────┐           ┌────────────────────────────┐
│ createUser 帧：   │           │                            │
│   id  = 42       │           │  "alice"                   │  ← 字符串对象
│   name → [指针]  │──────────▶│                            │
│   user → [指针]  │──┐        │                            │
├──────────────────┤  │        │  { id: 42,                 │  ← user 对象
│ 主程序帧：        │  └───────▶│    name: [指向 "alice"],    │
│   u → [指针]     │           │    roles: [指向数组] }      │
└──────────────────┘           │                            │
                               │  [1 个元素: "admin"]        │  ← 数组
                               │                            │
                               └────────────────────────────┘
```

栈上的 `user` 和 `u` 只是**指针**——它们存的是"堆里那个对象在哪儿"的地址。真正的对象数据都在堆里。

这就是 JS 里那句著名的话"**对象是引用传递**"的物理原因——你传 `user` 给一个函数，传的其实是栈上那个 8 字节的指针，堆里的对象没动。两个变量指向同一个对象时，修改一个会影响另一个，就是因为它们栈上的指针指向堆里同一块地方。

------

## 五、V8 是什么？

V8 是 Google 写的 **JavaScript 引擎**——把 JS 代码转成机器码并执行的那个东西。

它最初是为 Chrome 浏览器写的，后来 Node.js、Deno、Electron 都用它。Node 本质上就是"**V8 + libuv + 一堆 C++ 绑定的 API（fs, net, http...）**"的组合。

**V8 负责的事**：

- 解析 JS 源代码
- 编译成机器码（JIT）
- 执行机器码
- 管理所有 JS 对象的内存
- 运行垃圾回收器

所以"**V8 堆**"的意思就是：**V8 专门用来存放 JS 对象的那块堆内存**。

每个 V8 实例都有自己的堆。Chrome 每开一个标签页，Node 启动一个进程，就是创建一个新的 V8 实例，有自己独立的堆。

------

## 六、V8 堆的内部结构——不止一块

事情比"就是堆"更精细。V8 为了让垃圾回收跑得快，把堆细分成好几个"代"（generation）：

```
V8 堆
│
├── 新生代（Young Generation）—— ~16 MB，默认
│     │
│     ├── From 空间
│     └── To 空间   （这俩加起来叫 semispace，用于 Scavenge GC）
│
├── 老生代（Old Generation）—— 可以增长到 GB 级别
│     │
│     ├── Old pointer space  （放有引用的老对象）
│     └── Old data space     （放没引用的老对象，如字符串）
│
├── Large object space  （>512KB 的大对象，独立页面）
│
├── Code space  （JIT 编译出来的机器码）
│
└── Map space  （对象的"形状"描述，又叫 hidden class）
```

### 为什么要分代？—— 弱代假说（Weak Generational Hypothesis）

JS 程序里大部分对象"出生不久就死了"——比如 for 循环里的临时变量、函数返回后就不用的中间结果。只有少数对象活得久（全局配置、长期运行的数据结构）。

基于这个观察，V8 的策略是：

**新生代（Young）**：新对象先放这里。用一种叫 **Scavenge** 的 GC 算法——每次 GC 时，把还活着的对象从 From 复制到 To，然后把 From 整个清空。活着的对象很少，所以这种"搬家式"的 GC 非常快（毫秒级）。

**老生代（Old）**：经历过两次 Scavenge 还活着的对象，说明它可能会活很久，被"晋升"到老生代。老生代用 **Mark-Sweep-Compact** 算法——标记所有可达对象、清除不可达的、压缩内存碎片。这个慢（几十毫秒），但好在触发频率很低。

**效果**：99% 的 GC 开销花在占比 1% 的对象上，主要的老对象基本不动。

### 为什么 Claude Code 开发者需要了解这个？

看 Node 启动参数：

bash

```bash
node --max-old-space-size=8192 dist/cli.js
# ↑ 把老生代上限设成 8GB
```

Claude Code 跑长时间的 swarm，几个 teammate 的 messages 数组越长，老生代对象越多。默认 2GB 可能不够。**加这个参数 = 告诉 V8 "允许你的堆长到 8GB"**。

------

## 七、V8 堆是"隔离"的基础——这才是我上次提到它的意义

现在回到我们的主题：agent 隔离。

每个 Node 进程启动时，V8 创建**一个 Isolate**（隔离区）——这是 V8 的一个 C++ 对象，里面包含：

- 一个独立的堆
- 一个独立的 GC
- 一套独立的全局对象（`globalThis`、`Object.prototype` 等）
- 独立的微任务队列

**一个 Isolate 里的 JS 代码完全看不到另一个 Isolate 里的东西**。它们共享的只有一个 OS 进程这个外壳，V8 内部是完全分开的宇宙。

### Worker Threads 就是"多 Isolate"

js

```js
const { Worker } = require('worker_threads');
const w = new Worker('./alice.js');
```

这行代码让 Node 做的事：

1. 在同一个进程里创建一个**新的 V8 Isolate**
2. 给它一个新的堆
3. 新起一个 OS 线程来跑这个 Isolate 的 event loop
4. 加载 `alice.js` 到这个新 Isolate 里执行

主线程和 Worker 线程都在同一个 OS 进程里（同一个 pid），但它们的**堆是物理分离的**——主线程的指针指向主堆的地址，Worker 线程的指针指向 Worker 堆的地址。**你连对方的地址都不知道，想互相访问都无从下手**。

这就是为什么 Worker Threads 之间通信必须用 `postMessage` + 结构化克隆——不能传指针（对方根本解不了你的指针），只能把对象拷贝一份过去。

js

```js
worker.postMessage({ big: largeArray });
//       ↑
//  主堆里 largeArray 的内容被序列化成字节流
//  跨线程传到 Worker
//  Worker 在自己的堆里重建出一个全新的 largeArray
//  两边是两个独立的对象
```

### 对比：同 event loop 里为什么可以直传对象

js

```js
// 同一个 Isolate 里
async function* runAgent() {
  const result = { data: largeArray };
  yield result;  // 只传了 8 字节的指针
}

for await (const msg of runAgent()) {
  // msg 是主 loop 里的变量，指向同一个 result 对象
  // 因为是同一个堆，指针有意义
}
```

同一个 Isolate = 同一个堆 = 指针有意义 = 可以直传对象引用 = 零序列化。这就是我们最早讲的"Tool 层：通信载体 = JS generator yield，序列化 = 内存对象"的物理原因。

------

## 八、一个直观的层次对比

从最隔离到最不隔离：

```
跨机器        ┌────────────┐  ┌────────────┐
              │  机器 A     │  │  机器 B     │
              │  ┌──────┐  │  │  ┌──────┐  │
              │  │进程1 │  │  │  │进程1 │  │
              │  └──────┘  │  │  └──────┘  │
              └────────────┘  └────────────┘
                 ↑ 只能靠网络协议通信

同机多进程    ┌──────────────────────────┐
              │       OS（Linux）         │
              │  ┌──────┐    ┌──────┐    │
              │  │进程1 │    │进程2 │    │
              │  │堆 A  │    │堆 B  │    │
              │  └──────┘    └──────┘    │
              └──────────────────────────┘
                 ↑ 只能靠文件/管道/socket

同进程多线程  ┌──────────────────────────┐
              │        进程（Node）       │
              │  ┌──────┐    ┌──────┐    │
              │  │主线程 │    │Worker│    │
              │  │堆 A  │    │堆 B  │    │ ← 两个独立的 V8 Isolate
              │  └──────┘    └──────┘    │
              └──────────────────────────┘
                 ↑ 只能靠 postMessage

同 Isolate    ┌──────────────────────────┐
              │       V8 Isolate          │
              │   ┌───────────────┐       │
              │   │   同一个堆     │       │
              │   │  alice 对象   │       │
              │   │  bob 对象     │       │ ← 物理上可以互相访问
              │   └───────────────┘       │
              └──────────────────────────┘
                 ↑ ALS 软件层逻辑隔离
```

每一层"隔离强度"的提升都对应着"通信成本"的提升。Claude Code 在不同场景选不同层，就是在这根天平上找平衡点。

------

## 九、一个让你记一辈子的小实验

在你电脑上跑：

bash

```bash
node --expose-gc -e "
  const used = () => (process.memoryUsage().heapUsed / 1024 / 1024).toFixed(1);
  console.log('开始时堆大小:', used(), 'MB');
  
  const huge = [];
  for (let i = 0; i < 1000000; i++) {
    huge.push({ id: i, name: 'user_' + i });
  }
  console.log('分配百万对象后:', used(), 'MB');
  
  huge.length = 0;  // 清空引用
  global.gc();       // 手动触发 GC
  console.log('GC 后:', used(), 'MB');
"
```

你会看到类似：

```
开始时堆大小: 4.2 MB
分配百万对象后: 98.5 MB   ← 100 万个对象占了约 94 MB 堆空间
GC 后: 6.8 MB              ← GC 把它们回收了，堆缩回去
```

这就是**你亲眼看到 V8 堆的样子**：`heapUsed` 就是当前堆里还活着的对象占了多少空间。`global.gc()` 让你主动调 GC（生产环境不该用，调试用）。

更有趣的实验：

bash

```bash
node --expose-gc -e "
  const { Worker } = require('worker_threads');
  const used = () => (process.memoryUsage().heapUsed / 1024 / 1024).toFixed(1);
  console.log('主进程初始堆:', used(), 'MB');
  
  const w = new Worker('setInterval(() => {}, 1000);', { eval: true });
  setTimeout(() => {
    console.log('起 Worker 后主堆:', used(), 'MB');
    // 主堆基本没变 —— 因为 Worker 有自己的堆
    w.terminate();
    process.exit();
  }, 500);
"
```

你会看到起一个 Worker 之后，主进程堆几乎没变（可能多几十 KB 的管理开销），但整个 Node 进程的总内存占用会明显增加——**因为 Worker 在同一进程内但有独立堆**。

## 十、浓缩总结

| 问题                                 | 答案                                                         |
| ------------------------------------ | ------------------------------------------------------------ |
| **堆是什么**                         | 进程虚拟地址空间里专门存"动态分配的、大小不固定的东西"的那块区域 |
| **栈 vs 堆**                         | 栈存原始值和指针（快、自动回收）；堆存对象、数组、字符串（慢、GC 管） |
| **V8 是什么**                        | 执行 JS 代码的引擎，Chrome 和 Node 都用它                    |
| **V8 堆是什么**                      | V8 为 JS 对象专门管理的那部分进程堆内存                      |
| **Isolate 是什么**                   | V8 的"隔离区"，每个 Isolate 有独立的堆和全局对象             |
| **为什么 Worker Threads 能天然隔离** | 每个 Worker 是一个独立 Isolate，有独立的 V8 堆               |
| **为什么同 event loop 能传对象引用** | 同一个 Isolate = 同一个堆 = 指针在这个堆里有意义             |
| **为什么要 ALS**                     | 同一个堆里，两个"逻辑域"共用所有全局变量，必须靠软件约定才能隔离 |

**一句话定位**：

> **堆是"东西放在哪"的问题，V8 堆是 JS 引擎自己管理的那一块，Isolate 是堆和执行环境的打包单位，隔离强度从"同 Isolate"到"跨机器"逐级递增，每一级对应一种 Claude Code 的通信模式。**



# 答疑5：worker为什么CC中用的少？

Worker Threads 是 Node 里一个**非常特殊**的存在——它解决的问题很具体，用错了反而会变慢。我从"为什么需要它"开始讲清楚，然后列出真实的使用场景，最后讲 Claude Code 为什么基本不用它。

------

## 一、先理解它解决的是什么问题——CPU 密集任务

Node 的核心模型是 **单线程事件循环**。这个模型有个前提假设：**你的代码大部分时间在等 I/O**（文件读写、网络、数据库）。在等的时候，线程闲着，可以去处理别的 callback。这就是"异步非阻塞"的美好故事。

js

```js
// I/O 密集场景 —— Node 擅长
fs.readFile('a.txt', cb);   // 发起后线程立刻释放
fetch('https://...');        // 等响应时可以处理别的
db.query('SELECT ...');      // 等结果时不阻塞
```

**但如果你的代码不是在等，而是在算呢？**

js

```js
// CPU 密集场景 —— Node 的噩梦
function findPrimes(max) {
  const primes = [];
  for (let i = 2; i <= max; i++) {
    let isPrime = true;
    for (let j = 2; j * j <= i; j++) {
      if (i % j === 0) { isPrime = false; break; }
    }
    if (isPrime) primes.push(i);
  }
  return primes;
}

app.get('/primes', (req, res) => {
  const result = findPrimes(10_000_000);  // 算 5 秒
  res.json(result);
});
```

这 5 秒里，**整个 Node 进程完全冻结**：

- 其他 HTTP 请求进不来
- setTimeout 的回调不会触发
- 连 console.log('hi') 都要等
- 用户按 Ctrl+C 都可能没反应

为什么？因为事件循环只有一个线程，它此刻正在算素数，没有任何"停下来检查别的 callback"的机会。**JavaScript 没有抢占式调度——一段同步代码开始跑，就要一口气跑完**。

这就是 **Worker Threads 要解决的问题**：让 CPU 密集计算在**另一个 OS 线程**里跑，主线程继续处理 I/O。

------

## 二、Worker Threads 到底是什么

js

```js
const { Worker, isMainThread, parentPort } = require('worker_threads');

if (isMainThread) {
  // 主线程
  const worker = new Worker(__filename);  // 起一个 worker 跑同一个文件
  
  worker.on('message', (result) => {
    console.log('收到结果:', result);
  });
  
  worker.postMessage({ max: 10_000_000 });
  console.log('主线程没被阻塞，可以继续干活');
  
} else {
  // Worker 线程里运行的代码
  parentPort.on('message', ({ max }) => {
    const primes = findPrimes(max);  // 在 worker 里算，不影响主线程
    parentPort.postMessage(primes);
  });
}
```

内部发生了什么：

```
起 Worker 之前，Node 进程：
┌────────────────────────────────────┐
│  pid = 12345                        │
│  ┌──────────────────────────┐      │
│  │  主线程                   │      │
│  │  ├─ V8 Isolate A          │      │
│  │  │   └─ 堆 A（你的代码）    │      │
│  │  └─ event loop A          │      │
│  └──────────────────────────┘      │
└────────────────────────────────────┘

起 Worker 之后：
┌────────────────────────────────────┐
│  pid = 12345（还是同一个进程）       │
│  ┌──────────────────────────┐      │
│  │  主线程                   │      │
│  │  ├─ V8 Isolate A          │      │
│  │  │   └─ 堆 A              │      │
│  │  └─ event loop A          │      │
│  └──────────────────────────┘      │
│  ┌──────────────────────────┐      │
│  │  Worker 线程（新的 OS 线程）│     │
│  │  ├─ V8 Isolate B          │      │
│  │  │   └─ 堆 B（独立）       │      │
│  │  └─ event loop B（独立）   │      │
│  └──────────────────────────┘      │
└────────────────────────────────────┘
         ↕ postMessage（跨 Isolate 通信）
```

**三件同时发生的事**：

1. OS 层：创建一个新的**线程**（通过 pthread_create 或 Windows 对应 API）。这个线程和主线程共享进程的虚拟地址空间——理论上能互相访问内存。
2. V8 层：在这个线程里创建一个**新的 Isolate**。Isolate 有自己的堆、GC、全局对象。
3. Node 层：给这个 Isolate 装上 libuv 的事件循环，让它也能跑异步 API。

**关键**：虽然 OS 线程共享地址空间，但 V8 Isolate **互相不可见**——Isolate A 里的对象在 Isolate B 里根本没法定位。所以表现上就像两个独立的 JS 环境。

------

## 三、和"多进程"的对比——这是理解 Worker 的关键

很多人问："我直接 fork 一个子进程不就行了，为什么要 Worker Threads？"好问题。看这张对比表：

| 维度                 | child_process.fork       | worker_threads              |
| -------------------- | ------------------------ | --------------------------- |
| 隔离单位             | 独立 OS 进程             | 独立 OS 线程（同一进程内）  |
| V8 Isolate           | 独立（每个进程自带一个） | 独立（同进程内多个）        |
| 堆                   | 独立                     | 独立                        |
| 启动时间             | ~50-100 ms               | ~5-15 ms                    |
| 内存开销             | ~30-40 MB/进程           | ~5-10 MB/线程               |
| 通信方式             | IPC（stdio、socket）     | postMessage                 |
| 能共享内存？         | 不能（进程隔离）         | **可以！SharedArrayBuffer** |
| 一个挂了影响另一个？ | 完全不影响               | 整个进程崩溃                |
| CPU 调度             | OS 调度进程              | OS 调度线程（更轻量）       |

核心区别在最后几行：

**Worker Threads 独有能力：共享内存。** 通过 `SharedArrayBuffer`，主线程和 Worker 可以**真正共享一块内存**（不是拷贝），配合 `Atomics` API 做无锁并发。这是 fork 子进程做不到的。

**Worker Threads 的代价：脆弱性。** Worker 里一个未捕获的段错误（比如 native 模块崩了）会把整个进程一起带走，主线程陪葬。多进程就没这问题——子进程崩了主进程照常活。

------

## 四、Worker Threads 的典型使用场景

### 场景 1：CPU 密集计算（经典用例）

图像处理、视频转码、加密解密、压缩、哈希计算、科学计算。

**Sharp 库**（Node 最流行的图像处理库）内部用 libuv 的线程池自动并行化，但如果你自己写 JS 版本的 resize 算法：

js

```js
// server.js 主线程
app.post('/resize', async (req, res) => {
  const result = await runInWorker('./resize-worker.js', req.body);
  res.send(result);
});

// resize-worker.js
const { parentPort } = require('worker_threads');
parentPort.on('message', (imageBuffer) => {
  const resized = manualResizeAlgorithm(imageBuffer);  // 几百毫秒的计算
  parentPort.postMessage(resized);
});
```

主线程响应 1000 个请求的能力完全不受单次 resize 耗时影响。

### 场景 2：PDF / Office 文档解析

解析 PDF、Excel、Word 这类文件，纯 JS 实现（比如 pdf-parse、exceljs）通常是 CPU bound 的。一个大文件解析几秒钟，放主线程就把整个服务卡住。

js

```js
// 典型的文档服务器
app.post('/extract-pdf-text', async (req, res) => {
  // 放主线程：解析一个 100MB PDF 要 3 秒，期间 API 完全不响应
  // 放 Worker：主线程继续接请求，Worker 慢慢解析，解析完回传
  const text = await pdfExtractor.runInWorker(req.file);
  res.json({ text });
});
```

### 场景 3：数据序列化/反序列化大对象

js

```js
const huge = someMassiveObject;  // 500 MB 级别的嵌套对象
const json = JSON.stringify(huge);  
// JSON.stringify 是同步的！这可能冻结主线程几百毫秒
```

把 JSON 序列化丢给 Worker 做。注意这里有个陷阱：**`postMessage` 默认走结构化克隆**（也是拷贝），如果对象太大，克隆本身就很慢。所以要用 `transferList` 把 ArrayBuffer 的所有权直接转移过去（零拷贝）：

js

```js
const buffer = new ArrayBuffer(1024 * 1024 * 500);  // 500 MB
worker.postMessage({ buffer }, [buffer]);  // 第二个参数是 transferList
// 转移后，主线程里的 buffer 就不能用了（所有权已转移）
```

### 场景 4：跑不信任的代码（半沙箱）

你做一个平台，用户提交 JS 代码片段，你要执行它但不想它卡死你的服务。起一个 Worker，设超时，超时就 `worker.terminate()` 强杀。

js

```js
async function runUserCode(code, timeoutMs) {
  const worker = new Worker(code, { eval: true });
  return Promise.race([
    new Promise(resolve => worker.on('message', resolve)),
    new Promise((_, reject) => 
      setTimeout(() => {
        worker.terminate();  // 超时暴力终止
        reject(new Error('timeout'));
      }, timeoutMs)
    )
  ]);
}
```

但要注意：**Worker 不是安全沙箱**。它能访问 `require`、文件系统、网络——只是主线程不被它卡死而已。真正的安全沙箱要用 `vm` 模块 + 更严格的限制，或者干脆隔成独立进程/容器。

### 场景 5：后台任务池（worker pool 模式）

业界最常见的用法：起一个固定大小的 Worker 池（比如 CPU 核心数），把计算任务排队分派。

js

```js
// 用 workerpool 或 piscina 这种库
const Piscina = require('piscina');
const pool = new Piscina({
  filename: './compute-worker.js',
  minThreads: 4,
  maxThreads: 8,
});

app.get('/compute', async (req, res) => {
  const result = await pool.run(req.query);  // 自动分派到空闲 worker
  res.json(result);
});
```

这样你的服务能利用多核 CPU，同时保持主线程 100% 负责 I/O 响应。

### 场景 6：机器学习推理

TensorFlow.js、ONNX Runtime Node 绑定——跑模型推理是 CPU/GPU 密集的，显然不能放主线程：

js

```js
// inference-worker.js
const tf = require('@tensorflow/tfjs-node');
const model = await tf.loadLayersModel(...);

parentPort.on('message', (input) => {
  const output = model.predict(input);  // 几十到几百毫秒
  parentPort.postMessage(output.dataSync());
});
```

（实际上 tfjs-node 底层已经用了 C++ 多线程，但如果你用纯 JS 的 ML 库，Worker 是必须的。）

### 场景 7：实时音视频处理

Web 端这种场景更多（AudioWorklet 本质就是 Worker），Node 端比如实时音频流的 FFT 分析、实时视频帧处理。

------

## 五、什么时候**不**该用 Worker Threads

这是很多人踩坑的地方。**Worker 不是银弹，反而很多场景用了会变慢**。

### 反模式 1：I/O 密集任务

js

```js
// 错误示范
app.get('/users', async (req, res) => {
  const users = await runInWorker(async () => {
    return await db.query('SELECT * FROM users');  // 这是 I/O
  });
  res.json(users);
});
```

数据库查询、HTTP 请求、文件 I/O——这些本来就是非阻塞的！主线程调用 `db.query`，它立刻把实际工作交给 libuv 的 C++ 线程池或 OS，主线程继续干别的。**你丢给 Worker 只是增加了上下文切换和 postMessage 的开销**，没有任何收益。

记住这句话：**Worker 是为了避免 JS 代码卡住事件循环。I/O 操作本来就不卡事件循环。**

### 反模式 2：计算量太小的任务

js

```js
// 错误示范
function addNumbers(a, b) {
  return runInWorker((a, b) => a + b, a, b);  // 疯了
}
```

起 Worker 和 postMessage 本身有毫秒级开销。如果你的计算只要几十微秒，用 Worker 比直接在主线程跑慢 1000 倍。

经验法则：**任务要连续跑够 ~10ms 才值得丢给 Worker**。

### 反模式 3：频繁通信

js

```js
// 错误示范
worker.postMessage({ cmd: 'step1' });
await waitForReply(worker);
worker.postMessage({ cmd: 'step2' });
await waitForReply(worker);
// ...来回 100 次
```

每次 postMessage 都要做结构化克隆 + 跨 Isolate 唤醒。频繁通信的 overhead 会吃掉并行的收益。**应该一次性把所有数据发过去，Worker 一口气算完返回**。

### 反模式 4：需要"共享状态"的场景

Worker 间不能共享普通 JS 对象（堆是隔离的）。如果你的业务需要大量共享状态——比如几个"agent"要访问同一个 AppState——Worker 反而比同 event loop + ALS 麻烦得多。

**这正是 Claude Code 不用 Worker 的主要原因**。

------

## 六、Claude Code 为什么基本不用 Worker Threads

现在回到你关心的领域。Claude Code 里几乎看不到 Worker Threads（我没在源码里看到大规模使用）。为什么？

### 原因 1：它是 I/O 密集，不是 CPU 密集

Claude Code 一个 query loop 的时间都花在哪里？

```
发 API 给 Anthropic  → 网络等待 1-30 秒     ← I/O
流式接收响应         → 网络等待             ← I/O
解析 SSE             → 毫秒级 JS 计算       ← 很轻
执行工具（Read 文件） → 磁盘 I/O             ← I/O
执行工具（Bash）     → 子进程 + 等待输出     ← I/O
执行工具（Grep）     → 子进程 ripgrep        ← I/O
更新 UI（React）     → 毫秒级渲染          ← 很轻
```

**99% 的时间在等 I/O**，剩下 1% 的 JS 计算根本不需要并行。起 Worker 纯粹是浪费资源。

### 原因 2：多 agent 需要共享 leader 的 UI

Claude Code 的 leader 负责：

- 显示权限对话框（React UI）
- 显示 swarm 状态面板
- 处理用户键盘输入
- 维护全局 AppState

如果每个 teammate 是独立 Worker，它们**看不到 leader 的 React 组件、看不到 UI state**。要实现"队友请求权限，leader 弹对话框"就要通过 postMessage 来回传递——比直接用 `leaderPermissionBridge`（函数调用）繁琐得多。

同 event loop + ALS 让这件事变成简单的函数调用：

ts

```ts
// teammate 代码
const leaderSet = getLeaderSetToolPermissionContext();
await new Promise(resolve => {
  leaderSet({ request, resolve });  // 直接塞进 leader 的 React state
});
// 人类点允许
// resolve 被调用
// 代码继续跑
```

用 Worker 的话要变成：

ts

```ts
// teammate worker 里
parentPort.postMessage({ type: 'permission_request', request });
const approval = await waitForReply(/* 一堆相关性 ID 管理 */);
```

而且 `request` 里的 abort signal、context 对象都没法直接传（函数和闭包不能结构化克隆），要拆成纯数据再重建。**工程复杂度爆炸**。

### 原因 3：启动开销

Claude Code 一个 swarm 可能有 5-10 个 teammate。每起一个 Worker 要：

- 创建 OS 线程
- 创建新 V8 Isolate
- 重新加载整个 Node.js runtime
- 重新 require 所有依赖（anthropic SDK、各种工具库等等）

总共可能 **1-3 秒**。而用 ALS 起一个"逻辑 teammate"——就是一个 `als.run(store, fn)` 调用，**几微秒**。

用户的预期是"我喊一声 `/team add alice`，alice 立刻就位"，不是"等 3 秒"。

### 原因 4：工具本身已经跨进程了

Claude Code 的重活已经分散出去了：

- Bash 工具 → 子进程（通过 child_process.spawn）
- Read 工具 → 读文件（libuv 线程池，已经并行）
- Grep 工具 → ripgrep 子进程
- Edit 工具 → 写文件（libuv 线程池）

这些**本来就不会阻塞主线程**。Node 的 I/O 早就是多线程的（libuv 有自己的线程池处理 fs、dns 等），只是对 JS 代码隐藏了这个细节。**再加一层 Worker Threads 是重复造轮子**。

### Claude Code 可能用 Worker 的地方（推测）

看代码的话，可能在这些地方有限使用：

- tokenizer 计算 token 数（如果用纯 JS 实现的 tiktoken，可能几十毫秒的同步计算）
- 大文件 diff/patch 计算（如果 diff 算法是纯 JS 且文件很大）
- 某些代码分析工具内部（比如 tree-sitter parser 如果不走 native）

但这些都是局部优化，不是架构级使用。

------

## 七、Worker Threads 和 Claude Code 四层架构的关系

把 Worker Threads 放回上次那张表：

| Claude Code 场景        | 用了什么                                    | 为什么不用 Worker        |
| ----------------------- | ------------------------------------------- | ------------------------ |
| Tool 层（子 generator） | 同 event loop + yield                       | 不是并发，是调用栈嵌套   |
| Task 层（后台 agent）   | 同 event loop + fire-and-forget + sidechain | I/O 密集，Worker 没收益  |
| Swarm InProcess         | 同 event loop + ALS                         | 需要共享 UI/AppState     |
| Swarm Tmux              | 独立进程 + 文件邮箱                         | 用户要可视化看每个 agent |
| Bridge                  | 独立进程 + HTTPS                            | 需要完整 Claude CLI 能力 |

**看出规律了吗？** Claude Code 对"隔离"的需求要么靠 ALS（软件级）要么靠进程（OS 级），**跳过了 Worker Threads 这一层**。原因是它的场景里 Worker 的核心优势（CPU 并行）用不上，而劣势（启动开销、通信复杂度、共享状态困难）全中。

## 八、一个你可以跑的对比实验

感受一下 Worker 在什么场景真的有用：

js

```js
// save as worker-demo.js, run: node worker-demo.js
const { Worker, isMainThread, parentPort } = require('worker_threads');

function cpuHeavy(n) {
  let sum = 0;
  for (let i = 0; i < n; i++) sum += Math.sqrt(i);
  return sum;
}

if (!isMainThread) {
  parentPort.on('message', (n) => parentPort.postMessage(cpuHeavy(n)));
} else {
  const N = 500_000_000;
  
  // 方案 A：主线程直接算（会卡住事件循环）
  console.time('主线程直接算');
  cpuHeavy(N);
  console.timeEnd('主线程直接算');
  
  // 方案 B：起 4 个 Worker 并行
  console.time('4 个 Worker 并行');
  Promise.all([1, 2, 3, 4].map(() => new Promise((resolve) => {
    const w = new Worker(__filename);
    w.on('message', (r) => { w.terminate(); resolve(r); });
    w.postMessage(N / 4);
  }))).then(() => {
    console.timeEnd('4 个 Worker 并行');
  });
  
  // 证明主线程没被阻塞：方案 B 期间还能打印
  const t = setInterval(() => console.log('主线程活着'), 100);
  setTimeout(() => clearInterval(t), 3000);
}
```

在 4 核及以上的机器上你会看到类似：

```
主线程直接算: 2400 ms    ← 整个期间 setInterval 不响应
4 个 Worker 并行: 700 ms  ← 快了 3.4 倍，且主线程活跃打印了很多次
```

这就是 Worker Threads 的适用场景：**CPU 密集 + 任务可拆分 + 拆分后每块够大（抵消启动开销）**。

## 九、一句话总结

> **Worker Threads 是 Node 为了解决「CPU 密集计算会卡住 event loop」设计的。它给你多个独立的 V8 Isolate，共享同一个进程但互相看不到对方的堆。适合图像处理、文档解析、机器学习、加密等计算型任务；不适合 I/O 型工作流、需要大量共享状态的场景，也不适合启动快的短任务。Claude Code 几乎不用它，因为它的瓶颈是网络 I/O，不是 CPU，而且多 agent 之间需要共享 leader 的 UI 和 AppState——这正好是 Worker 最不擅长的场景。**

------

你理解了 V8 堆 → Isolate → Worker 这条脉络，再去看 Node 文档里各种"threading"、"cluster"、"parallelism"的术语就不会再混了。一个清晰的心智模型：

```
想让 JS 代码不卡事件循环？→ Worker Threads（共享地址空间，独立 Isolate）
想让故障不互相影响？     → child_process.fork（独立进程）  
想让多核利用率最高？      → cluster 模块（多进程共享端口）
想让多 agent 并发协作？    → ALS + 同 event loop（共享堆 + 逻辑隔离）
```
