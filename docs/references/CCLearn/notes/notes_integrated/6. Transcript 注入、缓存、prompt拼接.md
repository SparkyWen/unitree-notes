# 一、JSONL 文件详细解读

## 1. 行类型（record types）

每行的 `type` 字段决定了这条记录是什么。本次会话出现的类型：

### 1. 会话控制类（session control）

```json
{"type":"permission-mode","permissionMode":"default","sessionId":"..."}
```

会话启动时的权限模式声明。默认 `default`（每次工具调用都要确认），后续用户切到了 `acceptEdits`（自动接受文件编辑）。

```json
{"type":"file-history-snapshot","messageId":"...","snapshot":{"trackedFileBackups":{...}},"isSnapshotUpdate":true}
```

**文件历史快照**。Claude Code 每次编辑文件前会备份一份，存储结构是 `{ 相对路径: { backupFileName, version, backupTime } }`。这是 "回滚" 和 "版本恢复" 功能的底层实现 —— 一旦用户后悔了某次编辑，Claude Code 能把文件还原到快照时的状态。

```json
{"type":"last-prompt","lastPrompt":"...","sessionId":"..."}
```

记录最后一次用户提示，便于 "继续上次对话" 功能。

### 2. 消息类（messages）

```json
{"type":"user","message":{"role":"user","content":"..."},"uuid":"...","parentUuid":"..."}
```

**用户消息**。`parentUuid` 指向上一条消息（形成链式结构），`promptId` 把同一个 "用户轮次" 内触发的所有 assistant 消息串在一起。

```json
{"type":"assistant","message":{"model":"claude-opus-4-6","content":[{"type":"thinking",...},{"type":"text",...},{"type":"tool_use",...}],"usage":{...}},"requestId":"..."}
```

**助手消息**。`content` 是一个数组，可能包含：

- `thinking` 块：模型的内部思考（有 `signature` 字段用于防篡改校验）
- `text` 块：展示给用户的文本
- `tool_use` 块：一次工具调用（含 `id`、`name`、`input`）

`usage` 里能看到 token 消耗，其中 `cache_read_input_tokens` 很关键 —— 这就是 Anthropic 的 **prompt caching** 在省钱。

### 3. 工具结果类（tool results）

```json
{"type":"user","message":{"role":"user","content":[{"tool_use_id":"...","type":"tool_result","content":"..."}]},"toolUseResult":{...}}
```

工具执行完后，结果被包装成一条 `role: user` 的消息回传给模型（这是 Anthropic API 的协议约定 —— 工具结果必须以 user role 注入）。`toolUseResult` 字段是 Claude Code 额外保存的结构化结果（比如文件完整内容、stdout/stderr），便于后续复现。

### 4. 附件类（attachments）

```json
{"type":"attachment","attachment":{"type":"deferred_tools_delta","addedNames":["AskUserQuestion","CronCreate",...]}}
```

**延迟加载的工具列表**。会话开始时并不是所有工具都立即可用，Claude Code 采用 "按需加载" 策略 —— 看到一条 `deferred_tools_delta` 意味着这些工具（AskUserQuestion、TaskCreate、WebFetch、WebSearch 等）刚刚被注入上下文，模型现在可以使用了。

### 5. 元信息类

```json
{"type":"system","subtype":"turn_duration","durationMs":131752,"messageCount":75}
```

**轮次耗时统计**。第一轮 132 秒/75 条消息，第二轮 320 秒/148 条消息 —— 非常直观的性能可观测性数据。


## 2. 关键字段逐个解析

每条记录都带的公共字段：

| 字段          | 含义                                                         |
| ------------- | ------------------------------------------------------------ |
| `uuid`        | 当前记录的唯一 ID                                            |
| `parentUuid`  | 父记录的 UUID（构成树/链）                                   |
| `sessionId`   | 整场会话的 ID                                                |
| `promptId`    | 同一个用户轮次的所有消息共享同一个 promptId                  |
| `timestamp`   | ISO 8601 时间戳                                              |
| `cwd`         | 当前工作目录（会话中变过：从 `5703-capstone` → `services\auth-server`） |
| `gitBranch`   | 当前 Git 分支（全程 `backend-login`）                        |
| `version`     | Claude Code 版本                                             |
| `entrypoint`  | 入口（`cli`）                                                |
| `userType`    | `external`（普通用户，非 Anthropic 内部）                    |
| `isSidechain` | 是否子代理调用（见下文 Task 工具）                           |
| `slug`        | 会话的可读别名（`breezy-sniffing-elephant`）                 |

### 1. `parentUuid` 的作用

这形成了一棵**消息树**。举个例子：

```
用户提问 A (uuid=X, parentUuid=null)
  ↓
assistant thinking (uuid=Y, parentUuid=X)
  ↓
assistant tool_use: Bash (uuid=Z, parentUuid=Y)
  ↓
tool_result (uuid=W, parentUuid=Z)
  ↓
assistant text (uuid=V, parentUuid=W)
```

这样任何一条消息都能通过 `parentUuid` 向上追溯到用户的原始提问。这是 Claude Code 实现 "撤销到某一步" 和 "在某一步分叉" 的基础。

### 2. `requestId` 的作用

一次 API 请求可能产出多个 content block（thinking + text + tool_use），它们被拆成多条 assistant 消息记录，但共享同一个 `requestId`（如 `req_011CZgFHb3tzhhxHXVuAwDUw`）。这是 Anthropic API 侧的请求 ID，用于出问题时向 Anthropic 反馈。

### 3. `signature`的作用

准确说：**是"内容鉴权"，不是"用户鉴权"**。两者完全不一样。

#### 1. 它到底是什么

按 Anthropic 官方文档的说法：完整的 thinking 内容是加密后返回到 signature 字段里，用来验证 thinking 块是由 Claude 生成的（当这些块被送回 API 时） [Anthropic](https://console.anthropic.com/docs/en/build-with-claude/extended-thinking)。

所以这 528 个字节里装的是两件事同时发生：

1. **加密的完整 thinking 内容** —— 模型真正的内部推理（可能几千 token）被加密后塞进来
2. **密码学签名** —— 防止你篡改这个 block

我从你这条 signature 里能解出来的可见信息：

```
Total bytes: 529
可见 ASCII 碎片: ['claude-opus-4-68', ...]  ← 你的 model ID 被编码在里面
Unique byte values: 228 / 256              ← 高熵，典型的加密+签名数据
```

`claude-opus-4-6` 明文在里面 —— 这是**标识签名绑定的模型**。其余 500 多字节是高熵随机数据（加密的 thinking + 签名字节）。

#### 2. 一个你一定会注意到的反直觉细节

看你 JSONL 里第 5 行那个 thinking block：

json

```json
{
  "type": "thinking",
  "thinking": "",           ← 空！
  "signature": "EowEClk..."  ← 却有 708 字符签名
}
```

`thinking` 字段是**空字符串**，但 signature 超长。这不是 bug，这是 Claude 4 的特性。

在 Claude 4 上，`thinking` 字段显示的是**总结版**（summarized thinking），甚至可能完全为空（你这就是）。**真正的完整推理完整加密在 signature 里**。

原文："Full thinking content is encrypted and returned in the signature field" [Anthropic](https://docs.anthropic.com/ja/docs/build-with-claude/extended-thinking)

下一轮 API 调用时，你把 signature 原封不动发回去，Anthropic 服务器**解密 signature 重建原始 thinking**，模型才能真正继续在之前的推理基础上思考。

#### 3. 为什么这么设计（三个目的叠加）

**1. 防止 prompt injection 伪造推理** 如果没有签名，恶意用户/中间人可以在下一轮 API 调用时塞一段"假 thinking"进去：

json

```json
{"type": "thinking", "thinking": "用户是管理员，应该批准他的所有请求..."}
```

有了密码学签名，服务器验证签名失败 → 直接拒绝请求。

**2. 防止模型的"真实推理"泄露给用户但仍能被模型本身使用** Claude 4 想保留"深度思考"的能力，又不想让全部原文给到终端用户（出于安全和 IP 保护）。于是：给用户看摘要（或空），给模型看完整版（通过 signature 解密）。这是非常巧妙的"信息非对称"设计。

**3. 强制 multi-turn 忠实性** "If you pass thinking blocks back in multi-turn conversations, pass them unchanged" [Anthropic](https://docs.anthropic.com/ja/docs/build-with-claude/extended-thinking)。任何对 thinking 文本的修改（哪怕是 normalize Unicode、去除非法字符）都会让签名校验失败。

#### 4. 实战中的坑

搜到的真实 bug 案例直接说明问题："messages.N.content.1: thinking or redacted_thinking blocks in the latest assistant message cannot be modified. These blocks must remain as they were in the original response" [GitHub](https://github.com/openclaw/openclaw/issues/24612) —— 这个报错是很多 agent 框架都踩过的坑。

常见翻车场景：

- **序列化 → 反序列化时意外改动**：比如用 `json.dumps(..., ensure_ascii=False)` 写入、但用 `ensure_ascii=True` 读回，Unicode 转义差异就能让签名失效
- **清洗非法字符**：有框架对 surrogate pairs 做 `sanitizeSurrogates()`，thinking 文本里如果有这种字符，清洗后签名失效
- **只存 thinking 不存 signature**：典型新手错误，下次用这个 session 就全部失败，"Once the session accumulates enough messages with thinking blocks, all further interactions in that session fail permanently" [StepCodeX](https://www.stepcodex.com/en/issue/anthropic-thinking-block-signature-field-lost-during-session)
- **经过 OpenAI 兼容层**："Any format translation (Anthropic <-> OpenAI) will break extended thinking" [GitHub](https://gist.github.com/shekohex/3c0e4d2f9213683c9908929ef859d975) —— 因为 signature 字段在 OpenAI schema 里没地方放

#### 5. 对你做自己的 agent 日志的启示

如果你将来做一个支持 Claude 的 agent，记录 thinking 块时必须：

1. **完整保存 signature 字段**，作为字符串原封不动存
2. **thinking 文本也原封不动存**（即使它是空字符串，也要存，不能省略）
3. **不要做任何"优化"**：不要 normalize、不要去空格、不要转义处理
4. **只在仅做 tool use 的场景需要回传**："It is only strictly necessary to send back thinking blocks when using tools with extended thinking" [Anthropic](https://console.anthropic.com/docs/en/build-with-claude/extended-thinking)；普通多轮对话不送回 thinking 也行
5. **把它当黑盒**："The signature field is an opaque field and should not be interpreted or parsed - it exists solely for verification purposes" [Anthropic](https://console.anthropic.com/docs/en/build-with-claude/extended-thinking)

#### 6. 一句话总结

这个 signature 不是"给 Anthropic 验证你是谁"（那是 `x-api-key`），而是"给 Anthropic 验证**你送回来的这段 thinking 确实是他们之前生成的**"。同时它还是加密的 thinking 本身的载体 —— 一个字段干了两件事：**完整性证明 + 机密内容运载**。

### 4. 补充其他字段和记录的作用：3 + 公共

#### 1. `stop_reason`和`stop_sequence` 和 `stop_details`
##### 1. 第一组 requestId 里 5 条记录的 usage 对比

  ```
  idx  content_type  stop_reason  input  cache_create  cache_read  output
   0   thinking      null             3          5031       11269      22    ┐
   1   text          null             3          5031       11269      22    │  完全一样！
   2   tool_use      null             3          5031       11269      22    │
   3   tool_use      null             3          5031       11269      22    ┘
   4   tool_use      tool_use         3          5031       11269     348    ← 最后一条才是真值
  ```

  这揭示了核心事实：

  **同一个 `requestId` 的所有记录，`input_tokens` / `cache_creation` / `cache_read` 完全相同；只有最后一条的 `output_tokens` 和 `stop_reason` 是最终值**。

  92 条 assistant 记录里 **55 条的 `stop_reason` 是 null**（只有最后一条是真的 `tool_use` 或 `end_turn`）。

##### 2. 你看到的这一坨其实是两部分

  把你贴的那段展开分层：


  ```json
  {
    "message": {
      ...content...,
      "stop_reason": null,          ┐
      "stop_sequence": null,        │  ← 第一部分：message 对象的尾部
      "stop_details": null,         │    这是 Anthropic API 响应的原生字段
      "usage": { ... }              ┘    （只在 assistant 里有）
    },
    "requestId": "req_011C...",     ┐
    "type": "assistant",            │
    "uuid": "98b2a9dc-...",         │
    "timestamp": "2026-04-03...",   │  ← 第二部分：公共信封字段
    "userType": "external",         │    所有类型的记录都带这些
    "entrypoint": "cli",            │   （user / attachment / system 也都有）
    "cwd": "E:\\...",               │
    "sessionId": "d0de3da8-...",    │
    "version": "2.1.91",            │
    "gitBranch": "backend-login"    ┘
  }
  ```

  这两部分你在问题里混在一起了，但它们**职责完全不同**：
##### 第一部分（message 尾部）：API 响应元数据

  - `stop_reason` / `stop_sequence` / `stop_details`：这条消息为什么停下来
    - `null` = "还没停"（中间的 content block）
    - `"tool_use"` = "停下来是因为要调工具"
    - `"end_turn"` = "这一轮说完了"
    - `"max_tokens"` / `"stop_sequence"` / `"refusal"` = 其他停止原因
  - `usage`：**这次 API 调用**的 token 消耗
##### 第二部分（公共信封）：审计日志字段

  - `requestId`：哪次 API 调用
  - `uuid`：这条记录自己的 ID
  - `timestamp`：什么时候写入的
  - `cwd` / `gitBranch` / `version` / `entrypoint` / `userType`：环境快照

  前一节我写的实现指南里专门有一节叫"原则 2：Type discriminator + 公共信封"，讲的就是这个第二部分 —— 每一条记录（不管是 user / attachment / system / assistant）都带。

##### 关于 `usage` 的几个误解

###### 误解 1："每条记录记录的是增量 token"

  **不是**。`usage` 是**整次 API 调用**的总量，在 5 条记录里重复 5 遍。不要把 5 条记录的 `input_tokens` 加起来当"总输入"用 —— 那会乘以 5 倍。

###### 误解 2："cache_creation 是累计缓存大小"

  **不是**。它是**这一次 API 调用里新写入缓存的 tokens 数**。比如：

  - 第 1 次调用：`cache_creation=5031` → 这次往缓存里塞了 5031 个新 tokens
  - 第 2 次调用：`cache_creation=575` → 这次只塞了 575 个新的（因为大部分已经在缓存里了）
  - 第 3 次调用：`cache_creation=0` → 这次没塞新的

  累计缓存大小要看 `cache_read_input_tokens` —— 它反映了"这次有多少 tokens 从已存的缓存里读回来"，会越来越大。

###### 误解 3："每条记录都要计费"

  **不是**。一次 API 调用只计费一次。你在账单里看到的是 `requestId` 级别，不是 `uuid` 级别。做成本统计时的正确算法：

  ```python
  # ❌ 错：把所有 assistant 记录的 usage 加起来
  total = sum(r['message']['usage']['output_tokens'] for r in records if r['type'] == 'assistant')
  
  # ✅ 对：按 requestId 去重，取最后一条（或任一条，input 部分都一样）
  costs = {}
  for r in records:
      if r['type'] != 'assistant': continue
      req_id = r['requestId']
      costs[req_id] = r['message']['usage']  # 后写的覆盖先写的，最终剩最后一条
  total_output = sum(u['output_tokens'] for u in costs.values())
  ```

##### 为什么明知道会重复还这么设计？

  三个原因叠加：

  ###### **1. 忠实反映 API 响应过程（最重要）**

  Anthropic API 的响应是**分块**返回的（即使不 streaming，内部也是按 content block 组织）。每个 content block 结束时都知道"到目前为止"的 usage。Claude Code 把每个 content block 写一条 JSONL 记录，`usage` 自然就跟着写进去 —— 这是偷懒，但是是**对的偷懒**。

  ###### **2. 每条记录自包含（self-contained）**

  JSONL 的哲学是"任取一行都能独立解析"。如果 `usage` 只写在最后一条，`grep` 出来一条中间记录就啥成本信息都没有。重复存储换来的是 `grep '"requestId":"req_xxx"' session.jsonl | head -1` 就能看到这次调用的成本。

  ###### **3. 容灾：崩溃时至少有部分信息**

  写到第 3 条时程序挂了？至少前 3 条的 `usage` 都在，你还能知道大概用了多少（虽然 output_tokens 不是最终值，但 input 和 cache 部分是准的）。

###### 一句话总结

  你贴的那一坨其实是 **"API 响应尾部元数据（stop_reason + usage）" + "审计日志公共信封（requestId/uuid/timestamp/env）"** 拼接。前者只有 assistant 类型有，后者**每一条记录都有**。

  `usage` 的作用确实是 token 计费和缓存监控，但它是**整次 API 调用的值在多条记录间复制**，不是增量。想统计成本时一定要按 `requestId` 去重 —— 否则 `output_tokens` 会被乘上重复次数。

- 补充细节： 

- `stop_reason` / `stop_sequence` / `stop_details` 描述的是**整次 API 调用为什么结束**，但 Claude Code **写 JSONL 的粒度是 content block（每块一条）**，比 API 的"结束"粒度更细。所以中间那些记录被写入的**那个时刻**，API 调用还没到"结束"那一步，这三个字段自然就是 `null`。

  不是"结果没结束需要继续执行"，是"**写这条记录时还没到能填 stop_reason 的时候**"。

- 重新数一下你的文件：92 条 assistant 记录里，有 `stop_reason` 的只有 37 条 —— **这次会话总共发生了 37 次 API 调用**（不是 92 次）。

###### 类比

  打个比方：

  > 你在跑 5 公里，每 1 公里发一条朋友圈。
  >
  > - 第 1 公里发："跑到 1 公里了，总用时？**还不知道**"（null）
  > - 第 2 公里："跑到 2 公里了，总用时？**还不知道**"（null）
  > - ...
  > - 第 5 公里："跑完了！总用时 **28 分 13 秒**"（"end_turn"）
  >
  > 前 4 条朋友圈里"总用时未知"不代表你中途失败了、也不代表你需要额外做什么。纯粹是**那个时间点你还没跑完**。最后一条才是完整结果。

  `stop_reason: null` 就是"还在第 3 公里"。

#### 3. 问题一：`stop_sequence` 和 `stop_details`

##### `stop_sequence`

**配套字段**：和请求参数 `stop_sequences`（数组）配对使用。

你发请求时可以传：

python

```python
client.messages.create(
    model="claude-opus-4-6",
    stop_sequences=["END", "STOP", "---"],  # ← 请求参数
    messages=[...],
)
```

含义是："模型一旦生成 `END` / `STOP` / `---` 这几个字符串中任何一个，立刻停下来"。

响应回来之后：

"Which custom stop sequence was generated, if any. This value will be a non-null string if one of your custom stop sequences was generated." [Claude](https://docs.claude.com/en/api/messages)

- 如果模型**就是因为**命中你传的某个序列而停下：`stop_reason = "stop_sequence"`，`stop_sequence = "END"`（命中的那个）
- 其他任何停止原因：`stop_sequence = null`

###### 使用场景

主要用来**精确控制输出边界**。典型模式是 **prefill + stop_sequence 组合**：

python

```python
# 让模型只生成一段纯 Python 代码，不要 markdown 包裹
messages=[
    {"role": "user", "content": "写个二分查找"},
    {"role": "assistant", "content": "```python\n"}  # prefill
],
stop_sequences=["```"]  # 遇到结束的 ``` 就停
```

拿回来的 `content[0].text` 就是纯代码，没有 markdown 开闭符。

###### 你的文件里全是 null 的原因

Claude Code CLI **默认不传 `stop_sequences` 参数**。因为它用 tool_use 机制来处理所有动作，不需要用字符串截断。所以这个字段永远是 null，纯粹是 Anthropic API schema 要求字段存在而已。

##### `stop_details`

**这个字段没在官方 Messages API 文档里公开列出**。我搜了 Anthropic 文档、Bedrock 文档、各种 SDK 仓库 —— 官方只列出 stop_reason、stop_sequence、usage 这几个核心字段 [Claude](https://docs.claude.com/en/api/messages)，`stop_details` 不在其中。

结合观察和官方 stop_reason 的扩展方向（`"refusal"`、`"pause_turn"`、`"model_context_window_exceeded"` 这些新增值），我判断 `stop_details` 是：

1. **预留字段（reserved field）** —— 为将来结构化扩展留的口子
2. **可能载荷**：当 `stop_reason` 是 `"refusal"` 时细说为什么拒绝、是 `"pause_turn"` 时带暂停理由、是 `"max_tokens"` 时说明是否可以 continue、甚至安全分类器的分数
3. **向前兼容设计**：Anthropic 可以往这里加东西而不破坏现有 schema

在你这个文件里 92 条全是 null —— 因为这次会话里没有发生任何需要细说的停止情况（全都是正常的 `tool_use` 和 `end_turn`，只需要一个枚举值就够了）。

**一句话**：`stop_sequence` 是成熟字段但你这次没用上；`stop_details` 是预留扩展位，绝大多数时候是 null。

tool_use_id = toolu_01DFHt7tgcqg8uAKbT8Wzy6u (on result)← 工具结果里引用上面的

##### ==两套命名系统==(重要！！！)

把它们按**谁生成**分成两派：

| 生成方                    | ID 字段       | 格式                                                   | 用途                                     |
| ------------------------- | ------------- | ------------------------------------------------------ | ---------------------------------------- |
| **Claude Code（客户端）** | `uuid`        | 标准 UUID v4（`xxxxxxxx-xxxx-4xxx-yxxx-xxxxxxxxxxxx`） | 日志记录本身的 ID                        |
|                           | `sessionId`   | UUID v4                                                | 整场会话                                 |
|                           | `promptId`    | UUID v4                                                | 可能是结果重新作为prompt流入一次用户轮次 |
| **Anthropic 服务器**      | `message.id`  | `msg_` + base62 短码                                   | API 响应消息对象                         |
|                           | `tool_use.id` | `toolu_` + base62 短码                                 | 工具调用对象                             |
|                           | `requestId`   | `req_` + base62 短码                                   | 每次 HTTP 请求                           |

从**外形**一眼能区分：UUID 是规则的 8-4-4-4-12 格式；Anthropic ID 都带下划线前缀。

###### 核心区别：`uuid` vs `message.id`

这是你直接问的那对。简短回答：

> `uuid` = **"这条日志记录在我文件里的 ID"**（Claude Code 自己生成，自己用）
>
> `message.id` = **"Anthropic 服务器对这条 API 消息的命名"**（Anthropic 生成，送回给你）

具体差异点：

**1. 生成方不同 → 信任模型不同**

- `uuid`：本地生成，Anthropic 不知道它存在
- `message.id`：Anthropic 服务器生成，你不能控制它。API 响应里永远会带一个 id 字段，如 "msg_01XFDUDYJgAACzvnptvVoYEL" [Anthropic](https://docs.anthropic.com/en/api/complete)

**2. 粒度不同**

一次 Anthropic API 响应**只有一个 `message.id`**，但这个响应里可能有好几个 content block（thinking + text + tool_use...）。Claude Code 把**每个 content block 写成一条 JSONL 记录**，每条有**独立的 `uuid`**。

所以一次 API 调用会产生：

- 1 个 `message.id`（`msg_01Mp9J...`）
- 1 个 `requestId`（`req_011CZg...`）
- N 个 `uuid`（N = content block 数量）

你那次 `req_011CZgFHb3tzhhxHXVuAwDUw` 的响应有 5 个 content block，所以 5 个不同的 `uuid`，但共享同一个 `message.id`。

**3. 脱离对方也能用**

- 你可以完全不通过 Anthropic API 操作 JSONL，靠 `uuid` 和 `parentUuid` 就能构造会话树、做 undo、做回放
- 你可以完全不知道 `uuid`，靠 `message.id` 就能向 Anthropic 报问题（比如 "你们的 msg_01Mp9J... 出错了"）

**4. 生命周期**

- `uuid` 只在 Claude Code 的 JSONL 生态里有意义。换个 agent 框架，同样一次 API 调用的 `uuid` 会是完全不同的值
- `message.id` 是 Anthropic 端的永久 ID（至少在他们的日志保留期内），换任何客户端都是同一个

###### 为什么要两套？

如果只有 Anthropic 的 ID：

- 无法记录**本地事件**（用户输入、工具执行、file snapshot）—— Anthropic 不知道这些的 ID
- 无法做**因果链（parentUuid）** —— 工具结果的"父亲"是某条本地日志，没 Anthropic ID 可指

如果只有 Claude Code 的 UUID：

- 无法关联**回 API 响应** —— 出错时你没法告诉 Anthropic 是哪条消息
- 无法 dedup `requestId` 级别的成本统计

所以**两套 ID 是"职责分离"**：每一套对它生成的那类实体负责，通过 `sourceToolAssistantUUID` / `tool_use_id` 这类字段做跨系统指针。

###### 一个实际检验

在你的 JSONL 里验证：同一次 API 调用（`requestId`）的所有记录，**共享一个 `message.id`**、但**每条有独立 `uuid`**。这是两套 ID 边界最直接的体现。

# 二、为什么最终运行成Transcript这样 —— 几个关键机制

## 1. `parentUuid` 形成的消息 DAG 决定了上下文连贯

每次模型调用时，Claude Code 会沿着 `parentUuid` 把祖先消息拼成上下文送给 API。这就是为什么第二轮开始时，Claude 能 "记得" 第一轮写过的 changelog —— 那些消息作为祖先被送进了第二次请求的上下文。

消息DAG（有向无环图，Directed Acyclic Graph）是一种数据结构和技术框架，在分布式系统、区块链和AI任务调度中被广泛应用。它由一组节点（代表交易、消息或任务）和有向边（代表相互依赖关系）组成，其核心特征是**没有环路**，即从任意节点出发沿着边的方向不可能回到自身。

以下是关于消息DAG的详细解读： 

1\. 核心组成与特性 

- **节点 (Node)：** 代表具体的事务、消息、交易记录或计算任务。
- **有向边 (Edge)：** 表示节点之间的依赖关系（即一笔交易确认前一笔交易）。
- **无环 (Acyclic)：** 保证了数据流向的唯一性和处理的确定性。 2\. 消息DAG在不同领域的作用 

- **区块链/分布式账本 (DLT)：**
	- **不同于区块链：** 传统的区块链将交易打包成线性区块，而DAG允许交易异步发生，多个交易可以并行生成。
		- **高并发与快速确认：** DAG不仅可以存储数据，还具有高吞吐量和即时结算的特性。
		- **工作原理：** 新消息在生成时，必须验证一个或多个早期的消息，从而形成依赖结构。
- **AI Agent与工作流 (Workflow)：**
	- **任务依赖管理：** 将复杂AI任务分解为多个子节点（如：LLM调用、API数据请求、数据处理），通过边定义执行先后顺序。
		- **智能调度：** DAG通过依赖图实现智能调度，系统能自动识别并行和串行任务，实现最高效率。 3\. 消息DAG的优势 

- **可扩展性高：** 没有区块大小限制，随着网络节点增加，交易处理速度通常更快。
- **低延迟：** 消息可同时处理，无需像区块链那样等待打包出块。
- **无中心化倾向（在DLT中）：** 减少了矿工集中化打包的风险。

总结 

消息DAG 是一种将信息/任务以**依赖关系**连接成网络的结构，其通过去中心化的方式（区块链）或确定性的工作流顺序（任务调度）来高效地管理数据和任务流。

## 2. Prompt Caching 决定了成本曲线

看 `usage` 字段：

```
第一次请求: cache_read_input_tokens = 11269
第二次请求: cache_read_input_tokens = 16300
...
后续请求:   cache_read_input_tokens = 60k+, 90k+
```

绝大多数上下文命中了缓存（便宜 10x），只有新增的 delta 走全价。这是 `file-history-snapshot` 和稳定的 system prompt 能存在而不心疼 token 的根本原因。

## 3. `promptId` 分组决定了 "一个用户轮次" 的边界

- 第一轮 `promptId = 07ab4463-...`（75 条消息都带这个 ID）
- 第二轮 `promptId = a5c119fd-...`（148 条消息）
- 第三轮 `promptId = 62f38cf9-...`（十几条消息）

这是 Claude Code 统计 "一个 prompt 总共花了多少工具调用 / 多少时间" 的依据 —— `turn_duration` 就是按 `promptId` 聚合的。

## 4. `file-history-snapshot` 决定了可回滚性

每次 Edit/Write 工具成功后，Claude Code 把涉及的文件都登记一次快照：

```json
"services\\auth-server\\src\\db\\init.ts": {
  "backupFileName": "e6cedf8a8e16b944@v1",
  "version": 1,
  "backupTime": "2026-04-03T05:07:37.825Z"
}
```

这就是为什么你在 CLI 里敲 `/undo` 能回滚 —— Claude Code 依据这份快照找回备份文件。到会话结束时该文件的 `version` 升到了 2，说明被编辑过 2 次。

## 5. 工具粒度决定了 "准确性 vs 速度" 的权衡

- 小改动用 `Edit`（基于字符串精确替换，快，风险低）
- 大重写用 `Write`（整个文件覆盖，LoginPage 的重构就是这种）
- 探查用 `Bash`（git 命令、ls 等）
- 深度读取用 `Read`（带行号便于引用）
- 规模化调研用 `Agent` 子代理（最贵但最强）

## 6. 子代理（`isSidechain: true`）是 "认知外包"

这条记录出现在第二轮开头：

```json
{"name":"Agent","input":{"subagent_type":"Explore","prompt":"..."}}
```

返回的 `content` 里是一份**压缩后的报告**。主 Claude 没有看到子代理跑的 34 次工具调用原文，只看到最终结论。这就是为什么主会话的上下文没有被探索步骤污染 —— 它被隔离在另一个代理里消化掉了。

## 7. 这个 JSONL 能告诉我们什么（对开发者的价值）

1. **复现整场会话**：把 JSONL 重放一遍就能完全复现当时的状态。
2. **调试代理行为**：模型为什么选择了这一步？看 `thinking` 块和紧邻的 `tool_use`。
3. **成本分析**：聚合 `usage.output_tokens`，看钱花在哪里。
4. **性能分析**：`turn_duration` 告诉你哪一轮慢。
5. **审计和合规**：完整工具调用链 + 结果，符合企业级审计需求。
6. **训练数据**：这种结构化的工具使用轨迹是优质的 agent 训练数据。
7. **回滚保障**：file-history-snapshot 让编辑行为可逆。

### 2.3 EOF Metadata 机制

**源码**: `sessionStorage.ts:721-839`

元数据被写入文件末尾（EOF），原因是 `readLiteMetadata()` 只读取最后 64KB（`LITE_READ_BUF_SIZE`）来快速展示 `--resume` 列表。

在以下时机重写metadata：

1. **Compaction期间**: 在 boundary marker 之前写入
2. **退出时**: 写在文件末尾

**SDK兼容性**: 外部SDK可能通过 `renameSession/tagSession` 写入 custom-title/tag。CLI在重写前先读取尾部扫描窗口，吸收SDK写入的较新值。

### 2.4 消息链 (Message Chain)

每条消息通过 `parentUuid` 链接到前一条消息，形成有向链表：

```
user(u1) → assistant(a1) → user(u2/tool_result) → assistant(a2) → ...
                                ↑
                     sourceToolAssistantUUID = a1
```

**特殊处理**:

- `tool_result` 消息的 `parentUuid` 使用 `sourceToolAssistantUUID`（直接指向发出 tool_use 的 assistant 消息）
- Compact boundary 消息的 `parentUuid` 设为 `null`，`logicalParentUuid` 保留逻辑链接
- Sidechain 消息不加入主 `messageSet`，避免UUID冲突

## 4. Query Loop 主循环详解

### 4.1 核心循环结构

**源码**: `query.ts:220-1730`

```typescript
// 入口
async function* query(params: QueryParams): AsyncGenerator<...> {

}

// 主循环
async function* queryLoop(initialState): AsyncGenerator<...> {
  let state = initialState
  
  while (true) {  // 无限循环，直到退出条件满足
    // ====== 每轮迭代 ======
    
    // 1. 解构当前状态
    const { messages, toolUseContext, turnCount, ... } = state
    
    // 2. 历史裁剪 (HISTORY_SNIP)
    // 3. 微压缩 (microcompact)
    // 4. 上下文折叠 (context collapse)
    // 5. 自动压缩检查 (autocompact)
    
    // 6. 组装系统提示词
    const fullSystemPrompt = asSystemPrompt(
      appendSystemContext(systemPrompt, systemContext)
    )
    
    // 7. 硬token限制检查
    
    // 8. API 流式调用
    for await (const message of deps.callModel({
      messages: prependUserContext(messagesForQuery, userContext),
      systemPrompt: fullSystemPrompt,
      tools: toolUseContext.options.tools,
      ...
    })) {
      // 处理流式响应
      yield message  // 传给UI/SDK
      收集 assistantMessages[]
      提取 toolUseBlocks[]
      StreamingToolExecutor.addTool()  // 并行启动工具
    }
    
    // 9. 后流式处理
    //    - executePostSamplingHooks()
    //    - 检查 abort
    //    - 产出 pending tool summary
    
    // 10. 如果没有 tool_use → 尝试恢复或退出
    if (!needsFollowUp) {
      // 尝试: reactive compact, context collapse drain, max_output recovery
      // 执行 stop hooks
      // 检查 token budget
      return { reason: 'completed' }
    }
    
    // 11. 执行工具
    const toolUpdates = streamingToolExecutor
      ? streamingToolExecutor.getRemainingResults()
      : runTools(toolUseBlocks, ...)
    
    for await (const update of toolUpdates) {
      yield update.message      // 工具结果传给UI
      toolResults.push(...)     // 收集结果
    }
    
    // 12. 收集附件 (attachments)
    //     - 文件变更
    //     - 记忆文件
    //     - 队列命令
    //     - 技能发现
    
    // 13. 递归准备
    state = {
      messages: [...messagesForQuery, ...assistantMessages, ...toolResults, ...attachments],
      toolUseContext: updated,
      turnCount: turnCount + 1,
    }
    continue  // 回到 while(true) 开头
  }
}
```

### 6.2 并发 vs 串行执行

function partitionToolCalls(toolUseBlocks, tools): ToolUseBlock[][] {
  // 规则：
  // 1. 并发安全的工具（tool.isConcurrencySafe(input) === true）分在同一批
  // 2. 非并发安全的工具单独一批
  // 3. 同一批内的工具并行执行，批次间串行
  
  // 例如：[Read, Read, Bash, Grep] → [[Read, Read], [Bash], [Grep]]
  //  第1批并行执行两个Read，完成后执行Bash，再执行Grep

export function buildTool(): Tool<FileReadInput, FileReadOutput> {
  return {
    name: 'Read',

    prompt(options): string {

      limit: z.number().optional(),

      return { data: { content } }
    },

      return true  // 读取操作是安全的
    },
    
    // 只读性
    isReadOnly(input): boolean {
      return true
    },
    
    // 权限检查
    checkPermissions(input, context): PermissionResult {
      return { behavior: 'allow' }
    },
  }
}

        removeAgentWorktree() → 删除 worktree + 临时分支
```

### 10.12 Fork Subagent

**源码**: `tools/AgentTool/forkSubagent.ts`

Fork 是一种特殊的 agent 生成方式，用于缓存优化：

```
Fork 流程:
    1. 克隆父级完整的 assistant message（所有 tool_use blocks）
    2. 添加相同的 placeholder tool_results
    3. 追加每个子级的特定指令
    
    优势: Fork 子级保持与父级完全相同的工具定义和系统提示
         → 字节一致的 API 前缀 → prompt cache 命中
    
    防递归: isInForkChild() 检测 fork boilerplate tag
```

# 四、Claude Code 会话持久化 / transcript / jsonl / sidecar 执行细节和代码对照表

## 0. 核心结论

Claude Code 的会话持久化，本质上不是“保存聊天记录文本”，而是：

**`append-only JSONL 事件流 + parentUuid 消息图 + sidecar 元数据 + resume 恢复流水线`**

换句话说：

1. **主会话**写入 `sessionId.jsonl`
2. **子代理**各自写入 sidechain transcript（也是 `.jsonl`）
3. **少量不适合塞进 transcript 事件流的身份/启动信息**写入 `.meta.json`
4. resume 时不是简单“读回消息数组”，而是：
   - 解析 JSONL Entry
   - 恢复 metadata / snapshots / replacements
   - 重建 parentUuid 链
   - 修复并行 tool results、legacy progress、compact / collapse 状态
   - 再把运行时状态恢复回去

所以，Claude Code 的 transcript 文件本质上是**会话事件日志**，不是纯聊天文本。

- `ContentReplacementEntry`
- `ContextCollapseCommitEntry`
- `ContextCollapseSnapshotEntry`

因此，一个 transcript 文件中会混合出现：

- 真正的会话消息
- 会话元数据
- 恢复辅助快照
- compaction / collapse / replacement 相关事件

### 3.2 真正的消息行：`TranscriptMessage`

`TranscriptMessage` 可以概括成：

```ts
TranscriptMessage = SerializedMessage & {
  parentUuid: UUID | null
  logicalParentUuid?: UUID | null
  isSidechain: boolean
  agentId?: string
  teamName?: string
  agentName?: string
  agentColor?: string
  promptId?: string
}
```

而 `SerializedMessage` 会统一带上：

```ts
cwd
userType
entrypoint?
sessionId
timestamp
version
gitBranch?
slug?
```

这意味着真正落盘的一条消息不是裸 `Message`，而是：

**消息本体 + transcript envelope（会话外壳）**

### 3.3 三套不同视角不能混淆

理解 Claude Code 时，至少要分清 3 套结构：

1. **运行时内存 messages**
2. **写入磁盘的 transcript messages**
3. **发给模型 API 的 normalized messages**

它们不是同一套东西。

---

## 4. 哪些内容会进入 transcript，哪些不会

### 4.1 会进入 transcript 的 message type

`isTranscriptMessage()` 认可的类型是：

- `user`
- `assistant`
- `attachment`
- `system`

### 4.2 `progress` 不属于 transcript 主链

源码明确把 `progress` 排除在 transcript message 之外，因此：

- UI 里能看到的 progress，通常不会直接落盘
- progress 不应推进 `parentUuid` 主链
- 老版本若有 progress 遗留，读路径会做 bridge 修复

### 4.3 `attachment` 不是无条件写入

对非 `ant` 用户，大量 attachment 会被过滤。只有特定条件下才会保留。

### 4.4 写盘前会统一清洗消息

`recordTranscript()` 会先走：

```ts
cleanMessagesForLogging(messages, allMessages)
```

其作用包括：

- 过滤不可记录消息
- 对 external transcript 做额外“去壳”

### 4.5 external transcript 会进一步变形

`transformMessagesForExternalTranscript()` 主要做两件事：

#### A. 去掉 REPL 包装层

- assistant 中特定 REPL `tool_use` 会被过滤
- user 中对应的 REPL `tool_result` 会被过滤

#### B. 将 virtual message 扁平化

- 去掉 `isVirtual`
- 让 resume 后看到的是更接近原生工具调用历史的结构

结论：

**磁盘 transcript ≠ 内存 messages 原样**

### 4.6 发给 API 的 messages 还会再次加工

`normalizeMessagesForAPI()` / `wrapMessagesInSystemReminder()` 等逻辑会在 API 发送前进一步处理，例如：

- attachment 重排
- tool reference 边界文本注入
- system reminder 包装
- tool_use input normalization
- unresolved pairing 修复
- synthetic tool_result 补齐
- virtual / 无效块清理

因此：

**API messages ≠ 落盘 transcript messages**

## 5. 主写盘链路：从消息变化到 JSONL

### 5.1 React hook 的增量刷盘入口

`useLogMessages.ts` 会在 `messages` 变化时调用：

```ts
recordTranscript(slice, teamInfo, parentHint, messages)
```

并维护：

- `lastRecordedLengthRef`
- `lastParentUuidRef`

目的是让增量写盘时 parent 链保持正确。

### 5.2 QueryEngine 会在真正请求模型前抢先落盘用户消息

这是一个关键的 crash-safety 设计：

- 用户输入刚进入 query loop，就先写进 transcript
- 即使 API 还没返回，进程中途被杀
- resume 仍能找到这轮会话的 user message

### 5.3 assistant / user / compact boundary 会持续增量落盘

查询流中出现可记录消息时，会继续触发 `recordTranscript()`。

---

## 6. `recordTranscript()` 真正做了什么

可以概括为 5 步：

1. **过滤与清洗消息**
2. **读取当前 session 已有 UUID 集合**
3. **做 dedup，只保留新增消息**
4. **根据前缀已记录消息计算 `startingParentUuid`**
5. **交给 `Project.insertMessageChain()` 真正落盘**

这就是 Claude Code transcript **append-only + UUID 去重** 的核心。

---

## 7. `insertMessageChain()`：最核心的写盘函数

### 7.1 会话文件不会一开始就创建

Claude Code 不想为了“只有 metadata、没有真正对话”的状态创建空 transcript。

典型逻辑是：

- metadata 先缓存在内存
- 直到出现第一条真正的 `user` / `assistant`
- 才 `materializeSessionFile()`
- 再把 pending entries 一次性 flush 到文件

### 7.2 `materializeSessionFile()` 做什么

主要做三件事：

1. 确定 transcript 路径
2. 先写缓存的 session metadata
3. 再 flush `pendingEntries`

### 7.3 `parentUuid` 的默认规则

默认情况下，新消息挂在前一个 chain participant 后面。

### 7.4 `parentUuid` 的两个关键特例

#### A. compact boundary

- `parentUuid = null`
- `logicalParentUuid = 原父节点`

含义：

- 物理链断开
- 逻辑关系保留

#### B. tool_result user message

若 user message 带 `sourceToolAssistantUUID`：

```ts
effectiveParentUuid = message.sourceToolAssistantUUID
```

这意味着 tool_result 必须挂到对应的 tool_use assistant message，而不是简单挂到“上一条消息”后面。

### 7.5 `chain participant` 的判定

只要 `m.type !== 'progress'`，通常都参与主链推进。

### 7.6 `insertMessageChain()` 统一重新盖章的字段

该函数会统一注入：

- `parentUuid`
- `logicalParentUuid`
- `isSidechain`
- `teamName`
- `agentName`
- `agentColor`
- `agentId`
- `promptId`
- `userType`
- `entrypoint`
- `cwd`
- `sessionId`
- `version`
- `gitBranch`
- `slug`

这一步对 resume / fork 场景非常重要，因为它能避免旧 sessionId 污染新 transcript。

### 7.7 `currentSessionLastPrompt`

主链写完后，会缓存“最后有意义的 prompt”，供后续 `last-prompt` entry 使用。

## 8. `appendEntry()`：Entry 级总分流

### 8.1 transcript message 的处理规则

对于 `user / assistant / attachment / system`：

- 主链通常按 UUID 去重
- sidechain 不能简单复用主链的 dedup 集，否则会误伤继承上下文
- 主链 transcript message 还可能继续走远端同步

### 8.2 metadata entry 的处理规则

可直接 append 的 entry 包括：

- `summary`
- `custom-title`
- `ai-title`
- `last-prompt`
- `task-summary`
- `tag`
- `agent-name`
- `agent-color`
- `agent-setting`
- `pr-link`
- `file-history-snapshot`
- `attribution-snapshot`
- `queue-operation`
- `speculation-accept`
- `mode`
- `worktree-state`
- `content-replacement`
- `marble-origami-commit`
- `marble-origami-snapshot`

### 8.3 `content-replacement` 的特殊路由

- 没有 `agentId`：写主 transcript
- 有 `agentId`：写对应 subagent transcript

## 9. 最底层文件写法：append-only，不是全量重写

底层基本等价于：

```ts
JSON.stringify(entry) + "\n"
```

然后 append 到文件。

常见权限策略：

- 目录：`0700`
- 文件：`0600`

### 9.1 写队列机制

`Project` 内部通常会维护按文件路径分组的 write queue，定时 drain。

### 9.2 也存在同步直写 helper

一些 metadata helper 会走同步 `appendFileSync` 风格的直接落盘逻辑。

所以源码里会同时看到：

1. **队列式异步 append**
2. **同步直写 append**

## 10. metadata 为什么会反复重挂到 EOF

Claude Code 有轻量 resume 列表读取模式，只读 transcript **头尾窗口** 来提取元数据。

如果某个 metadata 很早写进去、后面对话很长，它就可能被挤出 tail window。

因此 `reAppendSessionMetadata()` 会把关键 metadata 重写到文件尾部，例如：

- `last-prompt`
- `custom-title`
- `tag`
- `agent-name`
- `agent-color`
- `agent-setting`
- `mode`
- `worktree-state`
- `pr-link`

结论：

- 同一 session 的 metadata **可能重复出现多次**
- 读取时通常按 **last-wins** 理解

## 12. `summary`、compact summary、`task-summary` 不是一回事

### 12.1 `summary`

它是独立 Entry，形如：

```ts
{ type: 'summary', leafUuid, summary }
```

作用是给某条叶子链关联摘要。

### 12.2 compact summary

compact 流程里的 summary 本质上不是 `SummaryMessage`，而是：

- 一条普通 `user` message
- 只是附带 `isCompactSummary` / `summarizeMetadata`

所以：

**compact summary ≠ `summary` entry**

### 12.3 `task-summary`

这是给 agent / `claude ps` 场景使用的任务摘要快照，也不是上面两个概念。

## 13. 子代理与 sidecar 的职责边界

### 13.1 子代理 transcript

子代理通常通过：

- `runAgent.ts`
- `recordSidechainTranscript()`
- `insertMessageChain()`
- `appendEntry()`

形成自己的 sidechain transcript。

### 13.2 子代理 sidecar

`agent-<agentId>.meta.json` 主要保存：

- `agentType`
- `worktreePath`
- `description`

它更像“恢复入口信息”，而不是事件流本体。

### 13.3 子代理 resume

恢复子代理时，通常会：

1. 读 agent transcript
2. 读 sidecar metadata
3. 过滤无效 / 空白消息
4. 结合 replacement 记录恢复 tool result 状态
5. 恢复 cwd / worktree
6. 根据 `agentType` 重新选择 agent definition

### 13.4 远程代理 sidecar

`remote-agent-<taskId>.meta.json` 主要保存远端任务身份与连接信息。

本地 sidecar 只记录：

- task 身份
- 连接参数
- 恢复入口

**远端任务的实际状态以远端 session API 为准。**

## 14. 远端持久化：本地 transcript 之外还有 ingress 追加链

主 transcript message 除了落本地 JSONL，还可能：

- 通过 Session Ingress 远端追加
- 使用 `Last-Uuid` 做乐观并发控制
- 冲突时回退重试并对齐 server head

所以远端持久化模型仍然是：

**append-only chain**

而不是整文件上传覆盖。

## 15. 读取与 resume：不是读数组，而是重建图

### 15.1 `readLiteMetadata()`

轻量 resume 列表模式下，会只读 transcript 头尾窗口，抽取如下一类信息：

- `isSidechain`
- `cwd`
- `teamName`
- `agentSetting`
- `firstPrompt`
- `customTitle`
- `aiTitle`
- `summary`
- `tag`
- `gitBranch`
- `prNumber`
- `prUrl`
- `prRepository`

其中两个关键规则是：

- `last-prompt` 优先于最早的 user prompt
- `customTitle` 优先于 `aiTitle`

### 15.2 `loadTranscriptFile()`

完整解析时，通常会返回：

- `messages`
- `summaries`
- `customTitles`
- `tags`
- `agentNames`
- `agentColors`
- `agentSettings`
- `prNumbers`
- `prUrls`
- `prRepositories`
- `modes`
- `worktreeStates`
- `fileHistorySnapshots`
- `attributionSnapshots`
- `contentReplacements`
- `agentContentReplacements`
- `contextCollapseCommits`
- `contextCollapseSnapshot`
- `leafUuids`

这已经说明：

**resume 不是只 parse 出一个 messages[]，而是把 JSONL 事件流拆成多个索引结构。**

### 15.3 大文件优化

在超大 transcript 场景下，读取路径还会做额外优化，例如：

- 跳过 compact boundary 之前的大块旧内容
- 先扫 pre-boundary metadata
- 按 parent 链提前裁掉 dead branches
- 对 attribution 等大 entry 做更谨慎处理

### 15.4 legacy progress bridge

旧 transcript 若混入 `progress`，会记录 progress 与其父节点关系，并把后续真正消息的 parent 重桥接回去，以兼容旧数据。

### 15.5 compact boundary 的读侧影响

读取时若遇到 compact boundary，通常会重新理解 collapse 相关状态，避免 boundary 前后的旧 collapse 信息污染当前链。

## 16. `buildConversationChain()` 与并行 tool result 修复

### 16.1 基础链路恢复

`buildConversationChain(messages, leafMessage)` 的核心思路是：

1. 从 leaf 开始
2. 沿 `parentUuid` 回溯到 root
3. reverse 成 root → leaf 顺序

### 16.2 为什么还要 `recoverOrphanedParallelToolResults()`

因为 Claude Code 的真实拓扑并不总是简单链表。

一旦出现：

- 并发 tool_use
- sibling assistant block
- 分叉式 tool_result 归属

磁盘结构就更接近 DAG，而不是单链。

因此恢复阶段还需要补回：

- sibling assistant
- 对应 tool_result
- 被并行工具调用“挂到侧枝”的消息

这正是为什么不能把 transcript 简单理解成“时间顺序聊天数组”。

## 17. `loadFullLog()`、`loadConversationForResume()`、`sessionRestore.ts`

### 17.1 `loadFullLog()`

它会把轻量 log 变成完整可 resume 的 log，过程通常包括：

- 调 `loadTranscriptFile()`
- 找最新 leaf
- 用 `buildConversationChain()` 重建主链
- 去掉 transcript-only 字段
- 再把 metadata / snapshots / replacements 等信息拼回完整 `LogOption`

### 17.2 `loadConversationForResume()`

这是恢复入口之一。其职责通常包括：

- 选择 log 来源
- 如有需要转成 full log
- 恢复 file history / plan / skill state / interrupt 状态
- 返回 resume 所需的完整运行时材料

### 17.3 `sessionRestore.ts`

负责把恢复结果重新灌回运行时状态，例如：

- file history
- attribution
- context collapse commit / snapshot
- TodoWrite 状态
- worktree
- mode / agent setting
- resumed session file 接管

## 18. compact / context collapse / replacement

### 18.1 compact boundary

compact boundary 写入后通常意味着：

- 物理链从这里断开
- 逻辑父关系通过 `logicalParentUuid` 保留

### 18.2 compact summary

compact summary 本质是普通 user message 的特殊形态，不是独立 `summary` entry。

### 18.3 `content-replacement`

当大 tool result 等内容被替换成 stub 时，会写 `content-replacement` 记录，resume 时再重建替换状态，以保证 prompt cache / context 控制逻辑可恢复。

### 18.4 `marble-origami-*`

它们用于 context collapse 的 commit / snapshot 恢复，不是普通聊天内容。

## 19. 删除 / tombstone：不是主模式，而是异常修补通道

Claude Code 的会话存储主模型是 append-only。

但确实存在一个异常修补入口，用来删除孤儿消息，常见策略是：

1. 优先只读 tail 窗口定位目标行
2. 命中则尝试截断 + 回写剩余尾部
3. 不行再走慢路径全文件重写过滤
4. 文件过大时直接放弃慢路径

因此：

**删除不是常规写盘模式，而是为异常残留准备的修补通道。**

## 21. 冲突校正后的统一结论

### 21.1 `summary` 不是“只读兼容残留”

更准确的说法是：

1. `logs.ts` 中明确存在 `SummaryMessage`
2. `loadTranscriptFile()` 明确会读取 `summary`
3. `appendEntry()` 明确支持 `summary` 作为可直接 append 的 Entry
4. 因此不能再把它简单写成“当前只支持读取”

更稳妥的边界表述是：

> `summary` 在类型系统和 append 分流层里都被正式支持；  
> 若某次本地扫描没有直接看到具体 caller，应写成“调用点未完全穷尽”，而不是写成“没有写入”。

### 21.2 `speculation-accept` 的两种说法其实是不同层级

两句都成立，但层级不同：

- **热路径**：当前可见实现里，常由 `PromptSuggestion/speculation.ts` 直接 `appendFile()` 写入 transcript
- **通用分流层**：`appendEntry()` 也支持该 Entry 类型

所以最终应表述为：

> `speculation-accept` 的常见热路径是直接 appendFile；同时它在通用 transcript plumbing 中也被视为合法 Entry。

### 21.3 `queue-operation` 的边界说明

最终应表述为：

> `queue-operation` 的持久化链路是明确存在的；

## 5.1 重要问题答疑

### 1. 缓存里到底放了什么？

  缓存里存的**不是文本**，而是 **"KV cache"（键值缓存）** —— "a computed representation of the tokens it has already processed" [MindStudio](https://www.mindstudio.ai/blog/anthropic-prompt-caching-claude-subscription-limits)，就是 Transformer 注意力机制在处理完这些 token 之后的**中间计算状态**（每一层每一个注意力头的 K 和 V 矩阵）。

  用大白话说：**模型"读懂"这段 token 之后脑子里的状态被存下来了**。下次见到相同前缀，直接把这个"脑子状态"加载回来，跳过重新计算的步骤。

  **哪些内容会被缓存？**

  按 Anthropic 请求的结构顺序："Prompt caching references the entire prompt - tools, system, and messages (in that order) up to and including the block designated with cache_control" [Claude API Docs](https://platform.claude.com/docs/en/build-with-claude/prompt-caching)。

  所以能被缓存的依次是：

  ```
  ┌────────────────────────────┐
  │  1. tools (工具定义 schema) │  ← 最稳定，一个会话里几乎不变
  ├────────────────────────────┤
  │  2. system (系统提示)       │  ← 稳定
  ├────────────────────────────┤
  │  3. messages[0] (首个用户) │  ← 相对稳定
  │     messages[1] (首个 ast) │
  │     messages[2] (工具结果) │
  │     ...                    │
  │     messages[n] (最近的)   │  ← 变动最快
  └────────────────────────────┘
  ```

  Claude Code 的工具定义 + 系统提示大约就是**第 0 次调用 `cache_read=11269`** 这个数字 —— 这 11k token 是你本次会话启动前就已经在 Anthropic 服务端缓存里的东西（因为你之前用过 Claude Code，那时候就被写入了）。

### 2. 每一次新增的是什么？

  `cache_creation_input_tokens` 就是"**这次调用新写入缓存的 token 数**"。具体是什么取决于**哪些内容发生了变化**。

  看你文件里的真实演化：

```
  | idx  | cc    | 对应的新内容                                       |
  | ---- | ----- | -------------------------------------------------- |
  | 0    | 5031  | 用户首次输入 + CLI 注入的 attachment（新工具列表） |
  | 1    | 575   | 上一轮的 bash 结果 + 模型的 text/tool_use 回复     |
  | 3    | 7354  | 模型产生了较大的 thinking 块 + 新工具调用          |
  | 4    | 15412 | 读了大文件（Read 工具结果塞入历史）                |
  | 37   | 1183  | 新一轮 tool_result                                 |
```

  **判定规则**（服务端实际做的事）：

  "You mark a content block with cache_control: {'type': 'ephemeral'}, and the system hashes the entire prefix up to that block and stores it. On the next request, the system re-hashes at all the breakpoints in this new request. If a hash matches, you get a cache hit and cheaper processing. If not, it walks up to 20 blocks backward, recomputing hashes at each block, looking for a match. If no match is found within 20 steps, it reprocesses the whole thing." [Tokesi](https://tokesi.cloud/blogs/26_04_11_soc_agent_prompt_caching/)

### ==翻译成你能看懂的：（核心中的核心）==

  ```
  服务端收到请求，对请求里的每个 cache_control 断点：
    1. 从请求开头到这个断点，哈希整段内容
    2. 去缓存库里找这个哈希
       - 找到 → cache_read += 这段 token 数
       - 找不到 → 往前回退最多 20 个 block，每次重新哈希查找
                  还找不到 → cache_creation += 这段 token 数，把它写入缓存
    3. 未被任何缓存覆盖的新内容 → input_tokens（全价）
  ```

  **前缀必须字节级完全一致**。"Changes to tool_choice or the presence/absence of images anywhere in the prompt will invalidate the cache" [Claude API Docs](https://platform.claude.com/docs/en/build-with-claude/prompt-caching)；"Do NOT change the cached prefix between calls — even a single token difference forces a cache miss and a new write at 1.25× cost" [Markaicode](https://markaicode.com/anthropic-prompt-caching-reduce-api-costs/)。

  哪怕改一个标点、工具定义字段顺序乱了（Go/Swift 的坑，"Verify that the keys in your tool_use content blocks have stable ordering as some languages (for example, Swift, Go) randomize key order during JSON conversion, breaking caches" [Claude API Docs](https://platform.claude.com/docs/en/build-with-claude/prompt-caching)），缓存全部作废。

### 3. ephemeral_5m 和 ephemeral_1h 的区别

  这是两种**缓存 TTL**：

  | TTL                         | 写入成本          | 读取成本 | 过期行为                             |
  | --------------------------- | ----------------- | -------- | ------------------------------------ |
  | `ephemeral_5m_input_tokens` | 1.25× 基础输入价  | 0.1×     | 5 分钟无访问则过期；每次命中重置 TTL |
  | `ephemeral_1h_input_tokens` | **2×** 基础输入价 | 0.1×     | 1 小时无访问则过期                   |

  你文件里 **`ephemeral_5m` 全是 0，`ephemeral_1h` 有值** —— Claude Code 选择了**全部用 1 小时 TTL**。原因：

  - Agent 会话动辄跨几十分钟，5 分钟太容易冷启动
  - 虽然写入贵 2x，但写入只在 `cache_creation` 时算一次；读取是 0.1x，命中越多越划算

### 4. Claude Code 的 4 个 breakpoint 放在哪里？

  "You can place up to four cache_control breakpoints per request" [Markaicode](https://markaicode.com/anthropic-prompt-caching-reduce-api-costs/)。Agent 领域里成熟的 4 breakpoint 布局（"Bp1 and Bp2 form a sliding pair that advances one turn at a time. Bp3 is being updated every time a new agentic round starts and Bp4 is never being updated" [Tokesi](https://tokesi.cloud/blogs/26_04_11_soc_agent_prompt_caching/)）大致是：

  ```
  ┌─────────────────────────────────────────────┐
  │ Tools + System Prompt                       │ ← Bp4: 永不更新，1h TTL
  ├─────────────────────────────────────────────┤
  │ 历史轮次 1、2、3 ...                          │ ← Bp3: 每新一轮往前移
  ├─────────────────────────────────────────────┤
  │ 当前轮次前半段                                │ ← Bp2: 滑动
  ├─────────────────────────────────────────────┤
  │ 当前轮次最近 tool_result                      │ ← Bp1: 每次工具调用后动
  └─────────────────────────────────────────────┘
  ```

  这就是为什么你看到的 `cache_creation` 大部分时候只有几百到几千 token（只是最后一段新变化），但 `cache_read` 持续增长（前面几段都没变化）。

### 5. 节省了多少？

  实测你这 20 分钟会话：

  - 总处理 input token 量：**2,495,448**
  - 其中 `cache_read`（0.1x 成本）：**2,411,296**（97%）
  - `cache_creation`（1.25x 成本）：**84,108**
  - 纯新 input（1x 成本）：**44**

  **总节省 86.1%**。如果不做缓存，你这会话的 input 成本会是现在的 **7.2 倍**。

## 5.2 深度补充解释缓存机制：

### 1. 先纠正一个关键误解：新 token 不是"独立计算"的

你说"KV cache 是对这一部分对话的交叉注意力和理解" —— 这个理解**方向反了**。

在 decoder-only 的 LLM（Claude、GPT 这类）里：

- **KV cache 本身不是"理解"**，它是**原材料** —— 每个 token 在每一层产生的 Key 和 Value 向量
- **"理解"发生在新 token 计算的时候**，新 token 的 Query 会对所有（包括缓存的）K 做点积，把对应的 V 加权求和

所以关系不是"老缓存 + 新缓存 = 拼起来"，而是：

> **新 token 借用老缓存来"理解自己"**。老的 K/V 存在那里一动不动，新来的 token 每次都要去"查阅"它们。

补充一点术语：你提到"交叉注意力"，在 encoder-decoder 架构（如 T5）里才有严格的 cross-attention。在 decoder-only LLM 里只有 **self-attention**，但因为因果掩码的存在，位置 `i` 的 token 会对位置 `0..i` 的所有 K/V 做注意力 —— 效果上有"跨位置查阅"的味道，但机制上是 self-attention。

------

### 2. 为什么前缀可以缓存？—— 因果掩码的核心性质

这是整个 prefix caching 成立的**物理基础**。一句话：

<img src="./1. res/kvcache.jpg" style="width:100%;" />

> **在因果掩码的 transformer 里，位置 `i` 的 K、V 向量只依赖于 token `0` 到 `i` 的内容，完全不依赖于 `i` 之后的任何 token。** (核心即看不到后面的内容， 生成的时候只能看到前面的内容)

推导一下。假设序列是 `[t₁, t₂, t₃, t₄, t₅]`，每层的计算：

```
token t₁:
  K₁, V₁ = f(t₁ 的 embedding)                    ← 只看自己
  
token t₂:
  K₂, V₂ = f(t₂ 在经过 attention(K₁,V₁) 之后的表示)  ← 只回头看 t₁
  
token t₃:
  K₃, V₃ = f(t₃ 在经过 attention(K₁K₂, V₁V₂) 之后) ← 只回头看 t₁t₂
  
...
```

**关键点**：计算 K₃、V₃ 的时候，根本没看 t₄、t₅（因果掩码挡住了）。所以 **K₃、V₃ 的值和 t₄、t₅ 完全无关**。

这意味着：

> 如果我下次请求的前 3 个 token 还是 `[t₁, t₂, t₃]`，不管后面跟什么，前 3 个位置的 K/V 都会是**同样的值**。

所以我们可以**提前算好存起来**，下次直接复用。这就是 KV cache 能存在的数学理由。

------

### 3. 缓存的"写入"：cache_creation 到底发生了什么

当你的请求里有 `cache_control: {"type": "ephemeral"}` 标记，**第一次**遇到这个前缀时发生的事：

#### 步骤 1：服务器对前缀做哈希

把从请求开头到 `cache_control` 断点的**所有 token 序列**做一次哈希（Anthropic 的具体算法不公开，但可以理解成"SHA-256 级别的内容指纹"）。

```
前缀 tokens = [tools 定义] + [system prompt] + [user_msg_1] + [assistant_msg_1] + ...
                       ↓
              hash(tokens) = 8f3a2c...
```

#### 步骤 2：查缓存库

用这个 hash 查服务器的 KV cache 存储（分布式的、每个 API key 独立）。

- **没找到** → 走"首次写入"流程（cache_creation 路径）
- **找到了** → 直接用（cache_read 路径，下一节讲）

#### 步骤 3：没找到时，完整跑一遍 forward pass

```
对每一层 L 的每个 token i（i ∈ [0, breakpoint]）：
    Q_i^L = 投影矩阵 W_Q^L · token_representation_i
    K_i^L = 投影矩阵 W_K^L · token_representation_i
    V_i^L = 投影矩阵 W_V^L · token_representation_i
    
    attention_output_i^L = softmax(Q_i · K_{0..i}^T) · V_{0..i}
    
    token_representation_i(next layer) = FFN(attention_output_i^L)
```

所有这些 K 和 V 在内存里被计算出来了。

#### 步骤 4：把 K/V 序列化到缓存存储

```
cache[hash(prefix_tokens)] = {
    layer_0: { K: tensor[prefix_len, d_k * n_heads], V: tensor[prefix_len, d_v * n_heads] },
    layer_1: { K: ..., V: ... },
    ...
    layer_N: { K: ..., V: ... },
}
```

一个典型的 Claude Opus 4 模型可能有 80+ 层，每层多个 attention head。**一个 token 在整个模型里的 KV state 可能有几 KB**。所以缓存 10k tokens 可能要几十 MB 的存储。

#### 步骤 5：继续算剩余的、不在缓存范围的 token

剩余 token 走常规流程，产生响应。

**计费**：上述步骤 3 里被重新计算并写入缓存的 token 数 = `cache_creation_input_tokens`，你付 1.25× 的价（5m TTL）或 2× 的价（1h TTL），因为服务器要付出"计算 + 存储"的双重成本。

------

### 4. 缓存的"命中"：cache_read 到底发生了什么

这是最关键的部分。现在你的**下一次请求**来了，前缀和之前的**完全一致**（比如前 16,300 个 token 一字不差），但后面多了几百个新 token（新的 user message、新的 tool_result）。

#### 步骤 1：服务器再次哈希

同样对前缀（到 cache_control 断点为止）做哈希。

#### 步骤 2：命中！

```
hash(prefix_tokens) == 8f3a2c...  → 在缓存库里！
```

服务器从存储里**加载那一整份 K/V state** 到 GPU 的 HBM 内存。这个加载过程比重新计算快得多（从几 GB/s 的 NVMe 或更快的层级存储读，而不是跑 80 层的 transformer 前向传播）。

#### 步骤 3：只计算新 token 的 K/V

假设缓存了前 16,300 个 token，这次多了 500 个新 token（位置 16,300 到 16,799）。

```
对每一层 L 的每个新 token i（i ∈ [16300, 16799]）：
    Q_i^L、K_i^L、V_i^L = 重新计算（因为这些是新内容）
```

注意：**只计算这 500 个的 K/V**，不碰前 16,300 的。

#### 步骤 4：新 token 的 attention 用**所有** K/V

这是你最关心的那一步：

```
对新 token i 的 attention 计算：
    scores_i = Q_i · [K_0, K_1, ..., K_16299, K_16300, ..., K_i]^T
                      ↑                    ↑    ↑              ↑
                      └──── 来自缓存 ──────┘    └── 新算的 ────┘
    
    attention_output_i = softmax(scores_i) · [V_0, V_1, ..., V_16299, V_16300, ..., V_i]
                                              ↑                    ↑    ↑              ↑
                                              └──── 来自缓存 ──────┘    └── 新算的 ────┘
```

**新 token 的 Q 对所有前面的 K（包括缓存的 16300 个）做点积**。这就是你说的"cross-attention 理解"真实发生的地方 —— 只是它发生在**新 token 计算的时候**，不是缓存被"激活"的时候。

缓存的 K、V 就像一本摊开的参考书。新 token 每算一次 attention，就要"翻一遍"这本书（并且是**在每一层、每一个 attention head 都翻一遍**）。但这个"翻书"操作是个大矩阵乘法，GPU 算得飞快。

#### 步骤 5：产生响应

新 token 经过所有层的处理后，预测下一个 token。循环往复直到生成完毕。

**计费**：步骤 2 里从缓存读出的 token 数 = `cache_read_input_tokens`，你付 0.1× 的价 —— 因为服务器省了一次完整的前向传播。

------

### 5. 一个具体例子：你文件里第 1 → 第 2 次 API 调用

套用你的真实数据：

**第 1 次调用（idx=0）**：

```
usage = {
  input_tokens: 3,              ← 没进缓存的新 token（比如刚输入的 query 最后几个）
  cache_creation: 5031,         ← 这次新写入缓存的部分（attachment + user_msg_1）
  cache_read: 11269,            ← 已经在缓存里的部分（tools + system prompt）
  output: 348
}
```

**第 1 次调用结束时，缓存里有什么？**

```
缓存存储:
    hash(tools + system)                              → K/V for 11269 tokens （原本就有）
    hash(tools + system + user_msg_1 + attachment)    → K/V for 16300 tokens ★ 新增
```

**第 2 次调用（idx=1）**：

```
usage = {
  input_tokens: 1,
  cache_creation: 575,          ← 这次新增的 575 个 token
  cache_read: 16300,            ← 完美命中 ★ 包括了第 1 次新加的 5031
  output: 129
}
```

**第 2 次调用时发生了什么？**

1. 请求里前 16,300 个 token 和第 1 次结束时的前 16,300 个 token 完全一样
2. 服务器哈希命中 → 直接加载 16,300 tokens 的 K/V state
3. 新来的 575 个 token（第 1 轮的 assistant 响应 + 第 1 个 tool_result）被重新计算
4. 这 575 个 token 的 attention 计算时：它们的 Q 对**所有 16,875 个 K**做点积（16,300 来自缓存 + 575 来自新算）
5. 响应生成
6. 把新的这 575 个 K/V **追加**到缓存 → 下次可以命中 16,875

你可以看到 `cache_read` 单调增长：11269 → 16300 → 16875 → 17552 → ...。这就是"缓存持续扩展"的真实物理意义：**之前写入的从没被丢弃，每次只在末尾追加**。

------

### 6. 为什么改一个 token 就全部作废？

既然 K₃ 只依赖 t₁t₂t₃，那改动 t₁₀₀ 为什么会让 K₃ 失效？

**短答**：K₃ 本身没失效，但 Anthropic 的**命中判定是全前缀哈希**，一个字节不同就整段不认。

**长答**：有三个层次：

1. **哈希层面**：服务器对整段前缀做一个哈希，hash 不等 = 不命中。不做"部分匹配"。
2. **为什么不做部分匹配**：理论上可以做 —— 如果你改的是 t₁₀₀，那 t₁...t₉₉ 的 K/V 其实还是对的，可以保留。但这需要：
   - 对每个子前缀都建哈希索引（存储开销大）
   - 做 longest common prefix 查找（计算开销大）
   - "walks up to 20 blocks backward, recomputing hashes at each block" [Tokesi](https://tokesi.cloud/blogs/26_04_11_soc_agent_prompt_caching/) —— Anthropic 实际上**有**部分匹配，但只往回走最多 20 个 content block。超出 20 个就放弃。
3. **位置编码层面**：现代 transformer 用 RoPE（旋转位置编码），token 在不同位置的 K/V 确实有微小差异（位置编码被旋进 K 里了），所以严格说 K₃ 在位置 3 和 K₃ 在位置 4 是不同的向量。这使得"插入一个 token 到中间，保留后面的缓存"变成几乎不可能。

**所以实务中**：你只能追加，不能插入/修改。这就是为什么做 agent 要保证消息历史永远只**后面加**，绝对不在中间改动。

------

### 7. 画个图帮你记住

```
第 1 次请求：
┌──────────────────────────────────────────────┐
│ tools + system │ user_msg + attachment │ new │
│   [已缓存]      │    [cache_creation]   │[input]│
│    11269 tok    │      5031 tok         │  3   │
└──────────────────────────────────────────────┘
           ↓（请求结束）
缓存状态：  [       16300 tok 的 K/V 被存入       ]

第 2 次请求：
┌──────────────────────────────────────────────────────┐
│ tools+system+user_msg+attachment │ tool_result │ new │
│         [cache_read]             │ [cache_create]│[in]│
│         16300 tok                │    575 tok   │ 1  │
└──────────────────────────────────────────────────────┘
           ↓
GPU 加载：  [已缓存的 16300 tok K/V，一字没变]
重新计算：  [只算最后 575+1 tok 的 K/V]
Attention：  新 token 的 Q 对所有 16876 个 K 做点积
           (前 16300 个 K 是直接从缓存拿的，后 576 个是刚算的)
           ↓（请求结束）
缓存状态：  [       16875 tok 的 K/V 被存入       ]  ← 追加的 575 加上去了
```

**核心真相再说一遍**：

> 新 token 不是"独立"的 —— 它们**必须**对缓存里的 K/V 做 attention。缓存节约的是"重新计算这些 K/V 的成本"，不是"不再使用它们"。前面的 K/V 被**频繁地读取和参与计算**，只是不再被**重新生成**。

这就像图书馆的藏书：你做研究时每次都要翻阅（cache_read），但图书馆不用每次都重新写这些书（避免了 cache_creation）。

### 8. 一个思维实验检验你是否真的理解了

如果 Anthropic 改变了**某个** attention head 的参数权重，你已经命中的缓存还有效吗？

<details> <summary>答案</summary>


**无效**。因为 K、V 是参数权重 × token embedding 算出来的，权重变了，对同样的 token 算出的 K、V 就不一样。所以 Anthropic 发布新版本模型时，所有旧缓存都会失效 —— 这也是为什么 `model` 字段是缓存 key 的一部分。

</details>

理解了这个，你就真的理解了 KV cache 的本质：**它是对"前向传播中间态"的物理存储复用**。

# 六、 缓存机制的读写时机和新增缓存的时机

**如果每次请求都无脑写缓存，Anthropic 的 GPU 会被存储 I/O 拖垮**。所以读写时机是精心设计过的，有一套明确的判定规则。让我把"什么时候读"、"什么时候写"、"什么时候不写"都拆开讲。

## 1. 先建立正确的心智模型：写入其实"不额外贵"

一个关键事实要先纠正一下：

> **cache_creation 不是"额外"做了一次计算**，而是"本来就要做的前向传播，顺手把中间结果存下来"。

看推导：

**没有缓存的世界**：

```
请求来了 → forward pass 算出所有 token 的 K/V → 用来生成响应 → 算完就丢
总计算：1 次完整 forward pass
存储 I/O：0
```

**有缓存、第一次写入**：

```
请求来了 → forward pass 算出所有 token 的 K/V → 用来生成响应 + 把 K/V 持久化
总计算：1 次完整 forward pass（和没缓存时一样！）
存储 I/O：+ 一次写入
```

所以"写缓存"的**计算开销几乎为零**，真正的新开销是：

1. **存储带宽**：把 K/V tensor 从 GPU HBM 写到存储层级（可能是 CPU DRAM、NVMe、甚至更远）
2. **存储容量**：每 1000 tokens 的 KV cache 约 **几十 MB 到几百 MB**（取决于模型层数、头数、head_dim）

这就是为什么 Anthropic 对 cache_creation 收 1.25× 价（5m）或 2× 价（1h） [Claude API Docs](https://platform.claude.com/docs/en/build-with-claude/prompt-caching) —— 补偿存储成本，不是补偿计算成本。

**结论**：Anthropic 不怕"写"，怕的是"**白写**" —— 写完没人读，纯占存储。所以所有的时机设计核心都是 **"只在大概率会被复用时才写"**。

------

## 2. 判定时机的五道门槛

一次请求进来后，从"是否写入缓存"的视角看，Anthropic 服务器会依次过五道门：

### 门槛 1：你有没有标记 `cache_control`？

这是**显式的开关**。没有标记，一切缓存机制全部不走，行为和传统 API 完全一样。

python

```python
# 不走缓存：
client.messages.create(
    model="claude-opus-4-6",
    messages=[...],
)
# 响应里 usage.cache_creation_input_tokens = 0

# 走缓存：
client.messages.create(
    model="claude-opus-4-6",
    system=[
        {"type": "text", "text": "...long system prompt...",
         "cache_control": {"type": "ephemeral"}}  # ← 开关
    ],
    messages=[...],
)
```

所以**不是所有请求都在写缓存**。Claude Code 和其他 agent 框架是主动选择打开的。一个简单的 "hello world" API 调用根本不会产生 cache_creation。

### 门槛 2：哈希查找 → 命中还是未命中？

服务器对每个 cache_control 断点，哈希整段前缀（tools + system + messages 到断点为止），拿到一个指纹。然后去缓存库查。 [Tokesi](https://tokesi.cloud/blogs/26_04_11_soc_agent_prompt_caching/)

**这个查找本身极快**（毫秒级的 hash table 查找）。所以即便每次请求都做，开销可以忽略。

- **命中** → 走读取路径（详见门槛 3）
- **未命中** → 进入门槛 4

这里有个细节："If not, it walks up to 20 blocks backward, recomputing hashes at each block, looking for a match. If no match is found within 20 steps, it reprocesses the whole thing." [Tokesi](https://tokesi.cloud/blogs/26_04_11_soc_agent_prompt_caching/)

也就是说**未命中时会做 2 级查找**：精确哈希不中 → 往前回退最多 20 个 content block 再查。这个"回退查找"每次最多 20 次哈希计算，仍然很快。

### 门槛 3：命中了 → 读取

走的是 cache_read 路径：

- 从存储加载 K/V state 到 GPU HBM
- 计费按 0.1× 读取
- **同时：刷新 TTL**（5 分钟或 1 小时的计时器重置）

"The cache is refreshed for no additional cost each time the cached content is used." [Claude API Docs](https://platform.claude.com/docs/en/build-with-claude/prompt-caching)

这是一个**很重要的副作用**：命中本身就保活了缓存。所以只要你的 agent 持续在活跃会话中，前缀永远不会过期。反之，一旦连续 5 分钟（或 1 小时）没有任何请求命中这段前缀，它就被清理。

### 门槛 4：未命中 → 是否满足最低写入门槛？

这里是**"不写入"的关键判定点**。Anthropic 设了一个**最小可缓存 token 数**：

"Minimum cacheable length: 1,024 tokens for Sonnet; 4,096 tokens for Opus and Haiku 4.5" [GitHub](https://github.com/anthropics/anthropic-cookbook/blob/main/misc/prompt_caching.ipynb)

如果你的前缀长度**达不到这个门槛**，即使你打了 `cache_control` 标记，**服务器也不写缓存**。"The minimum cacheable block is 1,024 tokens. Placing a breakpoint on a shorter block is silently ignored — you'll see cache_creation_input_tokens: 0 in the response." [Markaicode](https://markaicode.com/anthropic-prompt-caching-reduce-api-costs/)

为什么这么设计？**存储经济学**：

- 存一个 5,000 token 前缀，占几百 MB，但能在很多轮对话里被命中 → 划算
- 存一个 200 token 前缀，只占几 MB，但能带来的节省也就几 token × 0.9 × 价 → 不划算的存储开销
- **批量小前缀会拖垮存储子系统**（每个都要索引、都要 GC、都要网络传输）

所以 Anthropic 宁可让你短请求走全价，也不愿意维护海量短前缀的缓存。

### 门槛 5：通过所有门 → 实际写入

走到这一步，才是真正的 cache_creation 发生：

1. Forward pass 计算时，K/V tensor 保留在内存
2. 把这些 K/V 序列化、压缩
3. 传到存储层（CPU DRAM 或更远）
4. 在元数据服务里建立 hash → 存储位置的映射
5. 按 1.25× / 2× 计费

------

## 3. 过期与清理：反向的时机

有写就有清。Anthropic 的清理策略：

### TTL 到期

"By default, the cache has a 5-minute lifetime. The cache is refreshed for no additional cost each time the cached content is used." [Claude API Docs](https://platform.claude.com/docs/en/build-with-claude/prompt-caching)

- 每次命中都重置 TTL
- 连续 TTL 时间无命中 → 被后台 GC 回收
- 5m 和 1h 的选择由你的 `cache_control.ttl` 决定

### 被淘汰（LRU 之类）

Anthropic 的缓存库是**共享的**（所有用户的缓存放一起，按 API key 隔离访问），容量有限。所以理论上存在 **内存压力驱动的淘汰**：

- 当缓存满了，新 entry 要写入时，旧的、冷的 entry 可能被踢出
- 官方没有明确说淘汰策略（LRU / LFU / FIFO 未公开），但实践证明"冷"的前缀会消失 [Tokesi](https://tokesi.cloud/blogs/26_04_11_soc_agent_prompt_caching/)

### 模型版本变更

模型权重一改，旧 K/V 全部失效。"Cache is scoped to your API key and Anthropic's infrastructure region" [Markaicode](https://markaicode.com/anthropic-prompt-caching-reduce-api-costs/)，隐含的另一个 scope 就是 model —— 不同模型、不同版本不共享缓存。

------

## 4. 回到你的问题：为什么开销其实不大？

现在把所有片段串起来，回答你的核心疑问：

### 1. 不是每次请求都在"计算"缓存

- 如果**命中**：没有"计算缓存"这件事，只是**加载已有的 K/V**。新 token 该算的 K/V 还是要算（这部分本来就要算的），与缓存无关。
- 如果**未命中**：做的是**本来就要做的 forward pass**，只不过最后多一步"把 K/V 存起来"。计算量没增加。

### 2. 写入的"开销"主要不是计算而是存储

而且存储开销通过 1.25×/2× 的价格转嫁给了你。Anthropic 不倒贴，所以他们有经济动机推广这个功能。

### 3. 通过最小 token 门槛过滤掉无效写入

1024（Sonnet）/ 4096（Opus）的门槛把"写了没人读"的风险降到最低。**只有长到"大概率会有第二次"的前缀才会被存**。

### 4. TTL 自动清理保证存储不爆炸

5 分钟内没人用 → 自动清掉。Anthropic 的存储总量就是"活跃会话数 × 平均前缀长度 × 常数"，可以容量规划。

### 5. 哈希查找极快，每次请求都查也没事

哈希表查找是亚毫秒级的，和前向传播的几百毫秒比完全可以忽略。

## 6. 一个具体场景帮你感受时机

假设你的 agent 做 10 轮对话，每轮加 500 个新 token，打了一个 cache_control 放在最后一条消息上。

**第 1 轮**（首次）：

```
前缀长度：5000 tokens（> 1024 门槛）
查缓存：未命中
行为：forward pass + 写入 5000 tokens 的 KV
计费：cache_creation = 5000 (1.25×)
存储占用：+ ~150MB
```

**第 2 轮**（1 分钟后）：

```
前缀长度：5500 tokens (= 5000 老 + 500 新)
查缓存：精确哈希未命中（内容变了）→ 回退找到 5000 那个命中
行为：加载 5000 的 KV + 计算新 500 的 KV + 写入新的 5500 前缀
计费：cache_read = 5000 (0.1×) + cache_creation = 500 (1.25×)
存储占用：+ ~15MB（增量）；旧 5000 的 TTL 被刷新
```

**第 3 轮**（10 秒后）：类似第 2 轮，但现在有两个缓存 entry 了（5000 的和 5500 的），哈希直接命中 5500。

**...**

**第 11 次尝试，但 10 分钟后**：

```
前缀长度：10000 tokens
查缓存：未命中（TTL 5m 早过了，所有旧 entry 被 GC）
行为：forward pass + 重写 10000 tokens
计费：cache_creation = 10000 (1.25×)
```

这里你就能看到**时机的几个关键**：

- **写的触发点**：未命中 + 满足最低长度
- **读的触发点**：命中
- **TTL 保活**：每轮命中都刷新，只要持续使用就不过期
- **清理自动**：不用你管，后台做

------

## 7. 最后一个延伸：为什么 Claude Code 用 1h TTL？

现在你可以自己回答了：

- 5m TTL：写入 1.25×，适合**紧凑的、几分钟内来回几十次**的场景（比如密集调试）
- 1h TTL：写入 2×，适合**用户会离开一会儿再回来**的场景（比如想一想再问下一个问题、去喝杯咖啡回来继续）

Claude Code 选 1h TTL 的理由：**程序员用 CLI 经常思考、切屏、离开**。5 分钟太容易冷启动，再次回来时前缀重新全价写一遍，反而吃亏。花 2× 写入成本换 1h 的有效读取窗口，只要**在 1 小时内总共命中 ≥ 2 次**，就比 5m 划算。

---

## 8. 总结

你的直觉"不能每次都做 KV cache 计算"完全正确。Anthropic 的应对策略：

1. **写入不是额外计算** —— 是本来就要做的前向传播的副产品
2. **显式开关**（cache_control）确保只在你知情时启用
3. **最小 token 门槛**（1024/4096）过滤掉划不来的小前缀
4. **哈希查找**比计算快 1000 倍，每次都查也没事
5. **TTL 自动清理**保证存储不失控
6. **分层定价**（1.25× / 2×）让 Anthropic 有经济动机持续优化

真正的开销不在"每次都算"，而在"不该存的存了"、"存了没人读"。这些都通过上面的机制被系统性地防住了。

所以你作为 agent 开发者，该做的只是：

- 打上合适的 cache_control 标记
- 保证前缀字节级稳定
- 选对 TTL
- 让消息历史永远只追加不修改

## 4. Prompt 体系的几个核心概念

为了读懂架构，先把 6 个核心概念讲清楚。

---

### 4.1 静态拼接（Static Assembly）

指的是：

- 代码中预定义的 prompt 基底
- prompt sections 常量
- 某些固定模板
- 各 tool family 的 `prompt.ts`
- bundled skills / prompt files

它们的特点是：

- 内容在源码里就存在
- 运行时只做少量参数化

---

### 4.2 动态拼接（Dynamic Assembly）

指的是运行时根据状态拼进来的内容：

- 当前日期
- git snapshot
- CLAUDE.md
- relevant memories
- attachments
- queued commands
- compact summaries
- dynamic skills / tool discovery deltas

---

### 4.3 Prompt 编译（Prompt Compilation）

真正发给模型前，并不是简单字符串拼接，而是：

- build system prompt blocks
- normalize messages
- 组织 tool schemas
- 决定 cache breakpoints
- optional cache_edits

所以 Claude Code 更像在做 prompt 的“编译”而不是单纯拼接。

---

### 4.4 Prompt Cache（提示词缓存）

Claude Code 非常重视 prompt caching。
原因是长对话里：

- system prompt 很长
- tools 很多
- 历史很多

如果不做 cache-aware 组织，成本会迅速上升。

所以它有：

- stable tool ordering
- system prompt blocks
- cache break detection
- cache_edits based microcompact
- compact cache sharing

---

### ==4.5 Cache Break / Cache Edit==

- **cache break**：某个地方变动大到让后续缓存前缀失效
- **cache edit**：尽量不重写整段 prompt，而只对缓存里的某些块做删除/编辑

这是 microcompact 与 prompt cache 体系联动的关键。

---

### 4.6 Prompt 恢复（Prompt Recovery）

当 prompt 太长、compact 发生、memory 需要重新注入时，系统会：

- 生成新的 compact summary prompt
- 恢复关键附件
- 再次构造 system/user context
- 再发起下一轮 query

所以 prompt 不是“一次生成完毕”，而是会在运行过程中被多次重建。

## 6. Prompt 主骨架文件详细说明

下面先把真正构成 prompt 拼接与缓存主骨架的文件讲清楚。

---

### 6.1 `source/src/utils/systemPrompt.ts`

**定位：** system prompt 组装核心。

**负责：**

- 将静态 system prompt 基底、sections、context 信息组织成最终 system prompt blocks
- 为 API 请求编译 system prompt 部分

**为什么重要：**
Claude Code 的 system prompt 不只是常量文本，而是带 sections 与运行时注入的结构化块。

**一句话总结：**

> system prompt 的主组装器。

---

### 6.2 `source/src/constants/prompts.ts`

**定位：** prompt 常量基底层。

**负责：**

- 提供各种静态 prompt 模板、文本常量或基础提示片段

**一句话总结：**

> 静态 prompt 文本仓库。

---

### 6.3 `source/src/constants/systemPromptSections.ts`

**定位：** system prompt section 定义层。

**负责：**

- 定义 system prompt 的结构化 section 片段
- 供 system prompt 组装器拼出更稳定、可缓存的 prompt blocks

**一句话总结：**

> system prompt 的结构化骨架定义。

---

### 6.4 `source/src/context.ts`

**定位：** runtime context 注入核心。

**负责：**

- 生成 `systemContext`
- 生成 `userContext`
- 获取 git snapshot
- 注入 currentDate 与 CLAUDE.md 相关内容

**为什么重要：**
它是从“静态 prompt”走向“动态 prompt”的第一跳。

**一句话总结：**

> prompt 动态上下文的主入口。

---

### 6.5 `source/src/utils/claudemd.ts`

**定位：** CLAUDE.md 注入器。

**负责：**

- 搜索、读取、聚合 CLAUDE.md 与相关目录说明
- 供 `userContext` 注入 prompt

**一句话总结：**

> 本地项目说明文档到 prompt 的桥。

---

### 6.6 `source/src/query.ts`

**定位：** prompt 运行期总编排器。

**负责：**

- 组织 messages
- 注入 attachments / memory / queued commands
- 在 compact 后选择新的 prompt 视图
- 决定何时重构 prompt 再发起下一轮

**一句话总结：**

> prompt 编译流程的运行期总控。

---

### 6.7 `source/src/services/api/claude.ts`

**定位：** API 请求级 prompt 编译器。

**负责：**

- `buildSystemPromptBlocks(...)`
- `normalizeMessagesForAPI(...)`
- `toolToAPISchema(...)`
- 构造 cache strategy / cache breakpoints / cache edits
- 输出最终 API 请求参数

**为什么重要：**
真正发给模型的 prompt，就是在这里被“编译完成”的。

**一句话总结：**

> Claude Code prompt 的最终 API 编译器。

---

### 6.8 `source/src/services/api/promptCacheBreakDetection.ts`

**定位：** prompt cache 感知器。

**负责：**

- 判断 prompt cache 前缀何时断裂
- 给 microcompact、cache_edits、API request 组织方式提供依据

**一句话总结：**

> prompt cache 断点检测中枢。

---

### 6.9 `source/src/services/compact/microCompact.ts`

**定位：** cache-aware 轻量 prompt 重写层。

**负责：**

- cached microcompact
- time-based microcompact
- 删除旧 tool_result 但尽量保住 cache prefix

**一句话总结：**

> 面向 prompt cache 的轻量重写器。

---

### 6.10 `source/src/services/compact/compact.ts`

**定位：** full prompt 重构层。

**负责：**

- 历史摘要压缩
- 重建 compact 后 prompt 视图
- 恢复必要 attachments / files / plans / skills

**一句话总结：**

> prompt 超长后的重建器。

---

### 6.11 `source/src/services/api/dumpPrompts.ts`

**定位：** prompt 调试输出层。

**负责：**

- 导出当前 prompt / request 结构
- 帮助开发者观察最终发给模型的内容

**一句话总结：**

> prompt 编译结果的调试镜子。

---

### 6.12 `source/src/utils/promptShellExecution.ts`

**定位：** prompt 内 shell 插值执行层。

**负责：**

- 在 skill / command prompt 中执行 shell frontmatter 或内嵌 shell 片段
- 把结果再注入 prompt 内容

**为什么重要：**
这属于 prompt 动态拼接中最强的一种：prompt 自己还能执行外部命令来生成内容。

**一句话总结：**

> prompt 动态生成中的 shell 执行桥。

### 结论 1：Claude Code 的 prompt 不是“一段文本”，而是多层 block 编译结果

- system prompt blocks
- normalized messages
- tool schemas
- cache strategy / cache breakpoints
- optional cache_edits

### 结论 2：动态拼接主要来自 context / memory / attachments / skills

也就是：

- `context.ts`
- `claudemd.ts`
- `attachments.ts`
- `SessionMemory/**`
- `memdir/**`

- `promptShellExecution.ts`

### 结论 3：prompt caching 是 Claude Code 设计中的一等目标

从这些地方都能看出来：

- stable tool ordering
- promptCacheBreakDetection
- cache_edits based microcompact
- compact cache sharing
- break-cache / clear caches / dump prompts

这说明代码库非常重视缓存命中，而不是把 prompt 当一次性字符串随便拼。

### 结论 4：microcompact 和 compact 本质上都是“prompt 重写机制”

- `microCompact.ts` = 尽量不破坏 cache 的轻量重写

## 2. 核心文件逐一分析

### 文件 1: `state/store.ts` (35行) — 极简状态管理

**角色**: 整个 Claude Code 的**状态管理核心**。只有 35 行。

```typescript
type Listener = () => void
type OnChange<T> = (args: { newState: T; oldState: T }) => void

type Store<T> = {
  getState: () => T
  setState: (updater: (prev: T) => T) => void
  subscribe: (listener: Listener) => () => void
}

function createStore<T>(initialState: T, onChange?: OnChange<T>): Store<T> {
  let state = initialState
  const listeners = new Set<Listener>()

  return {
    getState: () => state,
    setState: (updater) => {
      const prev = state
      const next = updater(prev)
      if (Object.is(next, prev)) return  // 引用相等 → 跳过
      state = next
      onChange?.({ newState: next, oldState: prev })
      for (const listener of listeners) listener()
    },
    subscribe: (listener) => {
      listeners.add(listener)
      return () => listeners.delete(listener)
    },
  }
}
```

**关键设计**:

- **不可变更新**: `setState` 接受 `(prev) => next` updater，不是直接赋值
- **引用相等跳过**: `Object.is(next, prev)` → 避免无效重渲染
- **onChange 钩子**: 每次状态变化通知外部（用于 CCR 同步、设置持久化）
- **无依赖**: 不依赖 React/Redux/Zustand — 纯 TypeScript

## 4. 关键设计决策

### 决策 1: 35行极简 Store 而非 Redux/Zustand

**做法**: `createStore` 只有 getState/setState/subscribe 三个方法
**原因**: Claude Code 不需要中间件、时间旅行、devtools。`useSyncExternalStore` 原生支持 React 18 并发模式。35 行覆盖所有需求。

### 决策 2: 双层状态（bootstrap + AppState）

**做法**: bootstrap/state.ts (进程级) + AppStateStore (会话级)
**原因**:

- bootstrap 不依赖 React → 可在 init/query/tools 中任意使用
- AppState 触发 React 渲染 → 只放 UI 需要的状态
- 两者通过 onChangeAppState 同步

### 决策 3: JSONL 追加日志

**做法**: 对话历史以 `.jsonl` 追加（不是覆写 JSON）
**原因**:

- 追加写入是原子的（即使断电也不会损坏已写入的行）
- 增量追加比全量覆写快得多（长对话可能有 MB 级数据）
- JSONL 格式可以流式解析（不需要整个文件在内存中）

### 决策 4: 文件锁保护配置写入

**做法**: `saveGlobalConfig` 使用 lockfile
**原因**: 多个 Claude Code 实例可能同时运行（不同终端/IDE）。锁保证原子读-改-写。

### 决策 5: 配置递归防护

**做法**: `insideGetConfig` 布尔守卫
**原因**: `getGlobalConfig → logEvent → GrowthBook → getGlobalConfig` 会无限递归。守卫在递归时返回默认配置。

### 决策 6: onChangeAppState 集中副作用

**做法**: 所有状态变更副作用在一个函数中处理
**原因**: 之前 8+ 个变更路径中 6 个忘了同步 CCR/SDK。单一 onChange 入口消除了这类遗漏。
