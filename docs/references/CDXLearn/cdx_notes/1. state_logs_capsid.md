# 2. `logs_2.sqlite-wal`：`logs_2` 的写前日志，不是普通日志文件

这个文件大小约 **4.5 MB**。它不是人类可读日志，而是 SQLite 的 **Write-Ahead Log**。

它的作用是：

```
Codex 写日志
   ↓
先写入 logs_2.sqlite-wal
   ↓
之后 checkpoint
   ↓
再合并进 logs_2.sqlite 主库
```

SQLite 官方解释，WAL 模式下，commit 可以通过追加 WAL 完成，不必立刻写入主数据库；多个事务可以追加到同一个 WAL 文件，之后再 checkpoint 回主库。

你这个文件很重要，因为我发现一个关键现象：

## 你的主库单独打开会像“损坏”，但配上 WAL 后是正常的

我实际测试：

| 打开方式                                                     | 结果                                                         |
| ------------------------------------------------------------ | ------------------------------------------------------------ |
| 只打开 `logs_2(1).sqlite`                                    | `integrity_check` 显示大量异常，部分查询报 `database disk image is malformed` |
| 把它重命名/复制成 `logs_2.sqlite`，并配上 `logs_2.sqlite-wal` | `integrity_check = ok`                                       |

这说明：

> **你的 `logs_2(1).sqlite` 并不是一定真的坏了，而是它需要对应的 `logs_2.sqlite-wal` 一起恢复完整状态。**

为什么会这样？
 因为 SQLite 要求 WAL 文件和主库文件同名规则严格对应：

```
logs_2.sqlite
logs_2.sqlite-wal
logs_2.sqlite-shm
```

但是你上传后文件名变成了：

```
logs_2(1).sqlite
logs_2.sqlite-wal
logs_2(1).sqlite-shm
```

这里主库和 WAL 名字不完全匹配。很可能是 Windows / 浏览器上传时自动给主库加了 `(1)`，但 WAL 保持了原始名字。所以单独打开 `logs_2(1).sqlite` 时，SQLite 找不到正确的 WAL，就会读到一个不完整的主库状态。

# 3. `logs_2(1).sqlite-shm`：WAL 的共享内存索引文件，可以再生成

这个文件大小 **32 KB**。它是 SQLite WAL 模式下的 **shared-memory file**。

作用不是保存业务数据，而是：

- 帮 SQLite 快速定位 WAL 中的页面；
- 协调多个连接同时读写；
- 做锁和读写状态管理；
- 提高 WAL 查询性能。

SQLite 官方说，`-shm` 文件的目的只是给多个进程访问同一 WAL 数据库时提供共享内存；它没有持久内容，并且在 WAL recovery 时可以从 WAL 重新创建。

所以：

| 问题                          | 回答                                                      |
| ----------------------------- | --------------------------------------------------------- |
| `-shm` 能不能单独打开？       | 基本不能，没意义                                          |
| `-shm` 是日志吗？             | 不是                                                      |
| `-shm` 丢了会不会必然丢数据？ | 通常不会                                                  |
| 能不能删除？                  | Codex 完全关闭后通常可以重新生成，但不要在 Codex 运行时删 |
| 真正重要的是谁？              | 主库 `.sqlite` + `.sqlite-wal`                            |

- 主库看起来不完整；
- 查询报 `database disk image is malformed`；
- 日志时间线缺失。

------

## `-shm` 相对最不重要

Codex 完全关闭后，`-shm` 通常可以再生成。但仍然不建议在 Codex 运行时删。

# 二、`logs_2.sqlite-wal` 到底是什么？

## 1. 它不是“普通日志文件”

`logs_2.sqlite-wal` 不是你可以直接打开读的文本日志。它是 SQLite 的 **Write-Ahead Log**，中文可以叫：

```
写前日志
预写日志
滚动前向日志
```

它属于 SQLite 数据库机制，不属于 Codex 自己随便定义的文本格式。

SQLite 官方对 WAL 的解释是：传统 rollback journal 会先保存旧数据，然后直接改主数据库；而 WAL 反过来，主数据库先保持不变，所有新变化先追加到 WAL 文件中，commit 只需要在 WAL 里追加一个提交记录即可。这样读者可以继续读旧主库，写者可以继续把新内容追加到 WAL。

------

## 2. 为什么 Codex 的 `logs_2.sqlite` 需要 WAL？

因为 Codex 的日志写入是 **高频、小事务、持续追加** 的。

你这次上传的 `logs_2` 里有接近 7000 条日志，级别包括：

```
TRACE / DEBUG / INFO / WARN / ERROR
```

Codex 执行时会不停发生这些事件：

```
启动 app / CLI
读取配置
创建 thread
连接模型 API
接收 streaming response
调用工具
运行 shell command
记录 approval
创建子 agent
关闭子 agent
写 token usage
记录错误 / warning
写 analytics 失败信息
```

如果每一条日志都直接改 `logs_2.sqlite` 主库，会有几个问题：

| 问题              | 没有 WAL 时的麻烦 |
| ----------------- | ----------------- |
| 写入频繁          | 每次写主库都更重  |
| UI/后台同时读日志 | 读写容易互相阻塞  |
| 崩溃恢复          | 写到一半更难恢复  |
| 顺序日志追加      | 主库随机写更重    |
| 多连接访问        | 需要更复杂锁控制  |

WAL 的优势就是：**先追加，不急着改主库**。

所以执行时更像这样：

```
Codex 内部事件发生
    ↓
写一条 logs 记录
    ↓
SQLite 不一定立刻改 logs_2.sqlite
    ↓
先追加到 logs_2.sqlite-wal
    ↓
等合适时机 checkpoint
    ↓
再把 WAL 中的内容合并回 logs_2.sqlite
```

SQLite 官方也明确说，WAL 模式多了一个 checkpoint 步骤；checkpoint 就是把 WAL 里追加的事务转移回主数据库。默认情况下，SQLite 会在 WAL 达到一定阈值时自动 checkpoint。

------

## 3. “最近未合并”是什么意思？

你之前看到我说：

```
logs_2.sqlite-wal = logs_2 最近未合并的写入内容
```

这里的“未合并”不是“未提交”。

这点非常重要。

它的状态是：

```
已经 commit 了
但是还没有 checkpoint 合并进 logs_2.sqlite 主库
```

换句话说：

| 状态                       | 是否已经生效？ | 在哪里？       |
| -------------------------- | -------------- | -------------- |
| 未 commit                  | 没生效         | 事务内部       |
| 已 commit，但未 checkpoint | 已经生效       | WAL 文件       |
| 已 checkpoint              | 已经生效       | 主库 `.sqlite` |

所以，`logs_2.sqlite-wal` 里面的内容不是临时草稿，而可能是 **已经正式提交的数据库内容**。

SQLite 官方明确说，WAL 文件是数据库持久状态的一部分；如果数据库文件和 WAL 文件分离，之前已经提交的事务可能丢失，数据库甚至可能表现为损坏。

简单说：

# 三、`logs_2.sqlite-shm` 到底是什么？

## 1. SHM 是 WAL 的索引，不是数据库内容

`logs_2.sqlite-shm` 是：

```
shared memory file
wal-index file
```

它不是日志内容本身，也不是业务数据。

SQLite 官方说，WAL 模式数据库活跃时通常由三个文件描述状态：主数据库 `X`、写前日志 `X-wal`、wal-index 文件 `X-shm`。

官方还明确说，`-shm` 文件并不真正作为普通文件使用，而是被数据库客户端 mmap 成共享内存，用来协调数据库访问，并缓存 WAL 里 frame 的位置，从而快速定位内容。

------

## 2. 为什么 WAL 还需要 SHM？

因为 WAL 里面不是简单的“第 1 行日志、第 2 行日志”。

SQLite 的底层不是按“行”读写，而是按 **page** 读写。你的 WAL 文件头显示 page size 是：

```
4096 bytes
```

也就是说，WAL 里保存的是一帧一帧的数据库页变更：

```
WAL frame 1 -> 修改了数据库 page 12
WAL frame 2 -> 修改了数据库 page 9
WAL frame 3 -> 又修改了 page 12
WAL frame 4 -> 修改了 page 50
...
```

当 SQLite 要读取某一页时，它要回答一个问题：

```
我要读 page 12。
主库里有 page 12。
WAL 里可能也有 page 12 的更新。
那么最新有效版本在哪里？
```

如果没有索引，SQLite 可能要反复扫描 WAL：

```
从 WAL 开头扫到结尾
找 page 12 的最后一次有效更新
```

这很慢。

所以 `-shm` 做的是：

```
WAL frame 索引
page number -> WAL frame 位置
锁状态
读者 end mark
checkpoint 状态
```

SQLite 官方文档说明，`-shm` 里的 hash table 用来快速回答：“给定数据库页号 P 和最大 WAL frame M，找到不超过 M 的最新 frame”。

------

## 3. Codex 为什么需要这个？

因为 Codex 不是一个“单线程写完就退出”的简单脚本。

它运行时可能同时有：

```
TUI / App 正在读状态
后台 logger 正在写 logs
agent runtime 正在写事件
子 agent 正在写子 thread 状态
app-server / debugger 可能读状态
checkpoint 可能正在发生
```

你可以把它理解成：

```
logs_2.sqlite        = 账本主册
logs_2.sqlite-wal    = 最新流水暂存册
logs_2.sqlite-shm    = 流水索引 + 柜台排队规则 + 锁
```

没有 `-shm`，SQLite 就更难高效回答：

```
谁在读？
谁在写？
当前读者能看到 WAL 的哪一段？
checkpoint 能不能安全合并？
某个 page 的最新版本在哪个 WAL frame？
```

------

## 4. 没有 `logs_2.sqlite-shm`，哪里不行？

这个也要分情况。

### 情况 A：数据库没有在运行

如果 Codex 完全退出，并且下次 SQLite 有写权限，它通常可以重新生成 `-shm`。

所以：

```
静态备份时，shm 不如 wal 重要
```

SQLite 官方也说，`-shm` 不包含数据库内容，也不需要用于崩溃恢复；第一个连接到空闲数据库的客户端通常会截断或重建它。

------

### 情况 B：数据库正在运行

如果 Codex 正在使用这个库，你删掉 `-shm`，可能会导致：

```
SQLite 锁状态混乱
读写连接失去协调
正在读的连接和正在写的连接互相冲突
checkpoint 失败或 SQLITE_BUSY
日志查询变慢
Codex 内部状态读取失败
```

尤其是 Windows 上，文件锁和 mmap 行为更敏感。

------

### 情况 C：只读环境下打开 WAL 数据库

这点非常关键。

SQLite 官方说，新版本可以打开只读 WAL 数据库，但需要满足条件之一：`-wal` 和 `-shm` 已经存在且可读，或者目录允许创建它们，或者用 immutable 参数打开。

也就是说，如果你把数据库复制到一个只读目录：

```
有 logs_2.sqlite
有 logs_2.sqlite-wal
没有 logs_2.sqlite-shm
目录又不允许创建 shm
```

那么 SQLite 可能连读都读不了。

所以 `-shm` 虽然不是数据本体，但在某些场景下是 **打开数据库所必需的协调文件**。

------

## 5. WAL 和 SHM 的区别一句话

| 文件                | 是否包含数据库内容     | 丢失后果                             | 是否可重建   |
| ------------------- | ---------------------- | ------------------------------------ | ------------ |
| `logs_2.sqlite-wal` | 是，可能包含已提交事务 | 可能丢日志、库不完整、读出旧状态     | 不能随便重建 |
| `logs_2.sqlite-shm` | 否，不包含业务数据     | 运行时并发/只读打开/锁协调可能出问题 | 通常可重建   |

最重要的一句：

> **WAL 是“数据变化本身”；SHM 是“找到这些变化并协调并发访问的索引和锁”。**

# 四、`cap_sid` 到底是什么？

## 1. 它不是 SQLite，也不是日志

你上传的 `cap_sid` 是一个很小的 JSON 文件，结构大致是：

```
{
  "workspace": "S-1-5-...",
  "readonly": "S-1-5-...",
  "workspace_by_cwd": {
    "某个工作目录": "S-1-5-...",
    "另一个目录": "S-1-5-..."
  }
}
```

这里我不展开你的具体 SID 和路径，避免泄露本机环境信息。

它的关键词是：

```
workspace
readonly
workspace_by_cwd
S-1-5-...
```

`S-1-5-...` 是 Windows 里常见的 SID 风格标识。结合 Codex Windows sandbox 机制，可以非常明确地推断：

> **`cap_sid` 是 Codex 为 Windows sandbox 记录的“能力 / 权限边界 / 工作区目录映射”。**

------

## 2. 为什么 Codex 需要这个？

因为 Codex 不是普通聊天机器人，它会真的运行命令：

```
git status
npm test
python script.py
mkdir
写文件
读项目文件
调用构建工具
```

所以它必须回答一个安全问题：

```
这个命令能不能读这个文件？
能不能写这个目录？
能不能访问工作区外面？
要不要问用户批准？
```

OpenAI 官方文档说明，Codex 本地会使用操作系统强制执行的 sandbox，通常把 agent 限制在当前 workspace 内，并用 approval policy 控制何时需要停下来请求用户确认。

官方 Windows 文档也说明，Codex 在 Windows 原生运行时会使用 Windows sandbox，阻止 agent 在工作目录外写文件，并在没有用户批准时阻止网络访问。

------

## 3. `cap_sid` 在这个过程中扮演什么角色？

可以这样理解：

```
Codex 的权限判断
│
├─ 逻辑层：
│   ├─ sandbox_mode = workspace-write
│   ├─ approval_policy = on-request
│   ├─ 当前 cwd 是什么
│   └─ 哪些目录是 writable roots
│
└─ Windows 执行层：
    ├─ 用 Windows sandbox / token / ACL / capability SID 限制进程
    ├─ 给 workspace 分配可写能力
    ├─ 给 readonly 区域分配只读能力
    └─ 用 cap_sid 记录这些能力 ID 和目录映射
```

官方文档说，在 `workspace-write` 模式下，Codex 可以读文件、在 workspace 内编辑、在边界内运行常规本地命令；如果要超出边界，则需要审批。

所以 `cap_sid` 很可能就是 Windows 下把这种抽象权限落地到 OS 层时需要的映射文件：

```
workspace 权限能力 SID
readonly 权限能力 SID
某个 cwd 对应的 workspace capability SID
```

注意：OpenAI 公开文档没有逐字段说明 `cap_sid` 的内部格式，所以这里对它的具体字段含义属于基于文件内容和官方 sandbox 机制的推断。但从字段名和 SID 格式看，它的用途非常清楚：**本机 sandbox 权限边界映射**。

------

## 4. 没有 `cap_sid`，哪里不行？

也分情况。

### 情况 A：Codex 能重新生成它

如果你关闭 Codex 后删除 `cap_sid`，下次 Codex 可能会重新初始化 sandbox，并重新生成类似映射。

这种情况下不一定灾难。

------

### 情况 B：Codex 正在运行，你删除它

这可能导致：

```
当前 session 的 sandbox 权限映射丢失
后续 shell command 无法正确判断 workspace 边界
本来应该允许的工作区写入变成失败
本来应该只读的目录边界无法识别
Codex 更频繁请求 approval
Windows sandbox 初始化失败
某些命令直接报 permission denied / access denied
```

------

### 情况 C：Codex 不能重新建立 sandbox 映射

比如：

```
权限不足
Windows sandbox setup 被企业策略阻止
ACL / SID 创建失败
工作目录迁移了
配置和实际目录不一致
```

那没有 `cap_sid` 就会更严重。

可能表现为：

```
Codex 无法安全启动 agent mode
shell command 无法进入 sandbox
workspace-write 模式不可用
只能退回 read-only 或要求更多 approval
```

Windows 官方文档提到 Codex 的 preferred native sandbox 会使用 dedicated lower-privilege sandbox users、filesystem permission boundaries、firewall rules 和 local policy changes；fallback sandbox 则使用 restricted Windows token 和 ACL-based filesystem boundaries。

这就解释了为什么它需要一个类似 `cap_sid` 的文件：**它需要把“抽象的工作区权限”绑定到 Windows 本地安全身份和文件系统权限边界上。**

------

## 5. `cap_sid` 对执行安全的核心意义

没有 `cap_sid`，最严重的问题不是“模型不能回答”，而是：

```
Codex 无法可靠证明：
这个命令真的被限制在 workspace 内
这个命令真的不能乱写用户目录
这个命令真的没有绕过只读边界
```

所以它属于 **安全执行基础设施**。

简单说：

| 文件                | 服务对象                 |
| ------------------- | ------------------------ |
| `logs_2.sqlite-wal` | 数据库一致性             |
| `logs_2.sqlite-shm` | 并发读写协调             |
| `cap_sid`           | Windows sandbox 权限边界 |
| `history.jsonl`     | 用户 prompt 历史体验     |

# 五、`history.jsonl` 到底是什么？

## 1. 它不是完整会话 transcript

你上传的 `history.jsonl` 只有 4 条记录，每条结构是：

```
{
  "session_id": "...",
  "ts": 1777375561,
  "text": "用户输入的 prompt"
}
```

它保存的是：

```
你在 Codex 输入过的 prompt
输入发生在哪个 session
输入时间戳
```

它不保存完整执行过程，比如：

```
模型完整回答
工具调用细节
shell 输出
文件 diff
approval 结果
子 agent 完整消息
完整上下文
```

所以它不是完整 session 文件。

------

## 2. 那完整会话在哪里？

完整会话通常在：

```
~/.codex/sessions/...
```

或者 Codex 当前配置的 `CODEX_HOME/sessions/...` 下。

Codex 官方文档说明，Codex 会本地保存 transcripts，让你可以 resume 之前的线程；`codex resume` 可以打开最近的交互会话，`codex resume <SESSION_ID>` 可以指定某个 session ID 恢复。

所以要分清：

```
history.jsonl
    = 你输入过什么 prompt

sessions/*.jsonl
    = 这次会话完整发生了什么

state_5.sqlite
    = 哪些 session 存在、标题、cwd、模型、token、父子 agent 关系、rollout_path 等索引

logs_2.sqlite
    = Codex 内部运行日志
```

------

## 3. 为什么还要有 `history.jsonl`？

因为 prompt 历史和完整会话 transcript 是两个不同需求。

### 需求 1：快速找回你以前输入过的 prompt

Codex CLI 官方文档提到，交互模式中可以用方向键恢复之前的 draft text，也可以用 `Ctrl+R` 搜索 prompt history。

这就需要一个轻量文件：

```
history.jsonl
```

否则每次按 ↑ 或 Ctrl+R，Codex 都要去扫完整 sessions transcript：

```
sessions/2026/04/28/xxx.jsonl
sessions/2026/04/27/xxx.jsonl
sessions/2026/04/26/xxx.jsonl
...
```

这会慢，也复杂。

------

### 需求 2：只保存“输入历史”，避免读取完整 transcript

`history.jsonl` 很轻：

```
一行 = 一次用户输入
```

这比完整 transcript 简单很多。

完整 transcript 可能包含：

```
模型长回答
工具结果
shell 输出
diff
错误堆栈
文件内容片段
approval metadata
```

如果 Codex 只是想帮你找回上一条 prompt，它不需要解析这么多东西。

------

### 需求 3：跨 session 的 prompt 复用

你这个文件里有 4 条记录，但它们分布在 3 个 session：

```
session A：生成 AGENTS.md
session B：分析 hackathon idea
session B：保存建议到 docs/suggestion_codex.md
session C：测试两个子 agent
```

这说明 `history.jsonl` 是横跨 session 的输入历史，而不是单个 session 的完整记录。

------

# 六、没有 `history.jsonl`，整体执行有什么影响？

## 1. 当前任务通常还能跑

没有 `history.jsonl`，Codex 仍然可以：

```
启动
读取仓库
调用模型
运行工具
写文件
执行命令
创建 session
记录 state
写 logs
```

所以：

> **`history.jsonl` 不是 Codex 执行任务的核心依赖。**

它不是 sandbox，不是状态索引，也不是完整上下文。

------

## 2. 但是这些体验会受影响

如果没有 `history.jsonl`，可能影响：

| 功能                           | 影响         |
| ------------------------------ | ------------ |
| ↑ / ↓ 找回之前输入             | 找不到或变少 |
| Ctrl+R 搜索 prompt history     | 搜不到       |
| 快速复用旧 prompt              | 不方便       |
| 看“我之前问过什么”             | 不完整       |
| 某些 UI 的 prompt history 展示 | 可能为空     |

Codex 官方文档明确提到交互模式里可以用 `Up/Down` 恢复之前 draft text，用 `Ctrl+R` 搜索 prompt history。

------

## 3. resume 会不会受影响？

这点非常重要：

```
resume 主要依赖 sessions transcript + state 索引
不是主要依赖 history.jsonl
```

Codex 官方文档说 resume 会重新打开之前的 thread，并保留原始 transcript、plan history 和 approvals。

所以如果只有 `history.jsonl`，你不能完整恢复一次 session。

反过来，如果你删了 `history.jsonl`，但 `sessions/*.jsonl` 和 `state_5.sqlite` 还在，理论上之前的 session 仍然可能被 resume。

也就是说：

```
history.jsonl 丢了
    ↓
prompt 输入历史丢了

sessions/*.jsonl 丢了
    ↓
完整会话上下文丢了

state_5.sqlite 丢了
    ↓
Codex 可能找不到会话索引

logs_2.sqlite 丢了
    ↓
排障日志丢了
```

# 七、从一次完整 Codex 执行角度串起来

下面这张图最关键。

假设你输入：

```
请分析这个代码库，并调用两个子 agent
```

Codex 运行链路大概是：

```
1. 启动 Codex
   ↓
2. 读取 CODEX_HOME 下的配置和本地状态
   ↓
3. 判断当前 cwd / workspace
   ↓
4. 加载 sandbox 权限边界
      └─ cap_sid 参与 Windows 权限映射
   ↓
5. 创建或恢复 thread
      └─ state_5.sqlite 记录 thread 元数据
   ↓
6. 记录你的输入 prompt
      └─ history.jsonl 追加一行
   ↓
7. 创建完整 session transcript
      └─ sessions/.../*.jsonl 持续记录完整对话和事件
   ↓
8. agent 开始运行
      ├─ 读文件

      └─ 写结果
   ↓
9. 执行过程中的内部事件持续写日志
      └─ logs_2.sqlite

   ↓
10. Codex 结束
      ├─ checkpoint WAL 到主库
      ├─ 清理或保留 wal/shm
      ├─ 更新 state
      └─ session 可 resume
```

# 八、这几个文件分别缺失时，具体哪里会坏？

## 1. 没有 `logs_2.sqlite-wal`

| 场景                            | 后果                     |
| ------------------------------- | ------------------------ |
| Codex 正常关闭后已经 checkpoint | 可能没事                 |
| Codex 未正常关闭                | 最近日志丢失             |
| WAL 中有已提交事务              | 主库状态不完整           |
| 复制数据库时漏掉 WAL            | 数据库可能看起来损坏     |
| 需要排查错误                    | 关键 ERROR/WARN 可能消失 |

你这次文件属于：

```
WAL 仍然很重要，不能单独丢
```

------

## 2. 没有 `logs_2.sqlite-shm`

| 场景                    | 后果                      |
| ----------------------- | ------------------------- |
| 数据库空闲且可写        | 通常可重建                |
| Codex 正在运行          | 锁协调/并发访问可能出问题 |
| 只读目录打开 WAL 数据库 | 可能打不开                |
| 多连接读写日志          | 更容易 busy / 失败 / 变慢 |

一句话：

```
SHM 丢了通常不丢数据，但可能让 WAL 数据库无法正常并发工作。
```

------

## 3. 没有 `cap_sid`

| 场景                         | 后果                         |
| ---------------------------- | ---------------------------- |
| 下次可重新初始化 sandbox     | 可能自动重建                 |
| 正在运行时删除               | 当前权限边界可能异常         |
| Windows sandbox 初始化失败   | 命令执行可能失败             |
| workspace/read-only 映射丢失 | Codex 不知道哪些目录可写     |
| 安全边界不可验证             | 需要更多 approval 或拒绝执行 |

一句话：

```
cap_sid 丢了不是“上下文丢失”，而是“本机安全执行边界可能失效或需要重建”。
```

------

## 4. 没有 `history.jsonl`

| 场景             | 后果                           |
| ---------------- | ------------------------------ |
| 当前任务执行     | 通常不影响                     |
| prompt 历史搜索  | 受影响                         |
| ↑ / ↓ 找回旧输入 | 受影响                         |
| Ctrl+R 搜索历史  | 受影响                         |
| resume 完整会话  | 主要不靠它                     |
| 完整上下文恢复   | 靠 sessions transcript，不靠它 |

一句话：

```
history.jsonl 丢了，Codex 还能干活，但你找回旧 prompt 的体验会下降。
```

------

# 九、最容易误解的地方

## 误解 1：`-wal` 是临时文件，所以可以删

不完全对。

更准确是：

```
-wal 可能是临时存在的，但里面可能包含已提交、尚未合并进主库的数据。
```

SQLite 官方明确说 WAL 是数据库持久状态的一部分，复制或移动数据库时应该带上 WAL；如果分离，已提交事务可能丢失，数据库可能损坏。

------

## 误解 2：`-shm` 没有数据，所以完全没用

也不对。

更准确是：

```
-shm 不保存业务数据，但保存 WAL 索引和锁协调信息。
```

它不负责“恢复数据”，但负责“高效、安全地读写 WAL”。

------

## 误解 3：`history.jsonl` 是会话记录

不是。

它是：

```
prompt 输入历史
```

不是：

```
完整对话 transcript
```

完整 transcript 是 resume 的关键，官方文档说 resumed run 会保留原 transcript、plan history 和 approvals。

------

## 误解 4：`cap_sid` 是普通缓存

不建议这么理解。

它更像：

```
Windows sandbox 权限边界的本地映射文件
```

删除后可能可以重建，但它服务的是安全执行，不是普通 UI 缓存。

------

# 十、最终总结表

| 文件                | 解决的问题                                      | 没有它会怎样                                       | 是否可删                          |
| ------------------- | ----------------------------------------------- | -------------------------------------------------- | --------------------------------- |
| `logs_2.sqlite-wal` | 保证日志库高频写入、事务提交、崩溃恢复          | 未 checkpoint 的日志丢失，数据库可能不完整         | 不要单独删                        |
| `logs_2.sqlite-shm` | WAL 并发读写协调、快速索引 WAL frame、锁管理    | 运行时可能 busy / 变慢 / 只读打开失败              | Codex 关闭后通常可重建            |
| `cap_sid`           | Windows sandbox 的 workspace/read-only 权限映射 | 权限边界重建失败、命令执行失败、approval 增多      | 不建议手动删                      |
| `history.jsonl`     | 保存用户 prompt 输入历史                        | 不能方便搜索/复用旧 prompt，但当前执行通常不受影响 | 可备份后删，但会丢 prompt history |

# 十一句话彻底讲透

如果用一句最底层的话概括：

```
logs_2.sqlite-wal 解决“写入先安全落盘，不阻塞读者”的问题；
logs_2.sqlite-shm 解决“多个连接如何快速、正确、并发地读 WAL”的问题；
cap_sid 解决“Codex 在 Windows 上如何把抽象 sandbox 权限落实到真实 OS 权限边界”的问题；
history.jsonl 解决“用户如何快速找回和复用过去输入的 prompt”的问题。
```

如果从 Codex 整体执行看：

```
cap_sid 保证 agent 被关在安全边界里；
history.jsonl 记录你输入过什么；
state_5.sqlite 记录有哪些会话和会话索引；
sessions/*.jsonl 记录完整会话上下文；
logs_2.sqlite + wal + shm 记录 Codex 自己运行时发生了什么。
```

所以它们不是重复的，而是分别负责：

```
安全边界
用户输入历史
会话索引
完整上下文
运行日志
数据库一致性
并发读写
崩溃恢复
```







> **Codex 用 `.sqlite` 主要不是为了“存储和检索整个代码库文件内容”，而是为了存储本地状态、会话索引、线程元数据、运行日志、父子 agent 关系等结构化数据。真正的大规模代码文件查找，更多依赖工具层，比如 `rg/ripgrep`、文件读取、shell 命令、项目结构探索，而不是简单把整个仓库塞进 SQLite 里做检索。**

------

# 1. Codex 为什么会用 `.sqlite`？

因为 Codex 本质不是普通聊天工具，而是一个 **本地运行的 coding agent**。它会：

```
启动 CLI / Desktop / App Server
读取当前 repo
创建 thread
记录会话状态
调用模型
调用工具
运行 shell
修改文件
创建子 agent
记录 approval
保存 resume 信息
写运行日志
关闭 / 恢复 session
```

这些内容不是纯文本流水账，而是大量 **结构化状态**。例如：

| 数据类型        | 适合 SQLite 的原因                               |
| --------------- | ------------------------------------------------ |
| thread 列表     | 可以按时间、项目路径、归档状态查询               |
| session 元数据  | 可以保存 title、cwd、model、token、rollout_path  |
| 子 agent 关系   | 可以建 `parent_thread_id → child_thread_id` 关系 |
| 日志记录        | 可以按 level、target、thread_id、时间范围筛选    |
| app/server 状态 | 可以事务化更新，避免写一半损坏                   |
| resume 索引     | 可以快速找到对应 session transcript              |

官方 Codex CLI 文档说明，Codex 可以读取 repository、修改文件、运行命令，并且会把 transcripts 本地保存，用于之后 resume 继续之前的 thread。

------

# 2. 为什么不用纯 JSONL 全部保存？

其实 Codex **不是不用 JSONL**。它是混合设计：

```
SQLite
    = 结构化索引 / 状态 / 日志 / metadata

JSONL
    = 大型会话 transcript / rollout / 输入历史 / 流式事件记录
```

你可以理解成：

```
state_5.sqlite
    负责回答：有哪些会话？属于哪个 cwd？标题是什么？rollout 文件在哪里？

sessions/*.jsonl
    负责保存：这次会话完整发生了什么？

logs_2.sqlite
    负责记录：Codex 自己运行时出了什么内部事件？

history.jsonl
    负责保存：用户过去输入过哪些 prompt？
```

GitHub 社区里也有人报告过类似结构：`state_5.sqlite` 里有 thread 元数据，真正的 rollout transcript 在 `~/.codex/sessions/.../rollout-*.jsonl`，如果索引不同步，最近 session 可能在可见历史里消失。 Reddit 上也有人提到，即使 SQLite metadata 存在，Desktop app 通常仍然需要 `threads.rollout_path` 指向的 backing transcript JSONL 文件才能显示完整会话。

所以 Codex 的设计不是：

```
全部放 SQLite
```

而更像：

```
SQLite 做索引和状态
JSONL 做长 transcript 和事件流
```

------

# 3. SQLite 相比 JSONL 的关键优势

## 3.1 JSONL 适合追加，不适合复杂查询

JSONL 很适合这种场景：

```
{"ts": "...", "event": "user_message", "text": "..."}
{"ts": "...", "event": "tool_call", "tool": "shell"}
{"ts": "...", "event": "assistant_message", "text": "..."}
```

优点是：

- 顺序追加简单；
- 每行独立；
- 出错时容易人工修复；
- 适合 transcript；
- 适合流式写入。

但它不擅长：

```
按 cwd 找所有 thread
按 archived 状态过滤
按 thread_id join 子 agent
按更新时间排序
按 title 搜索
批量更新归档状态
事务性更新多个表
快速统计 logs level
```

如果全靠 JSONL，Codex 每次打开历史列表可能要扫大量文件：

```
sessions/2026/04/28/xxx.jsonl
sessions/2026/04/27/xxx.jsonl
sessions/2026/04/26/xxx.jsonl
...
```

这对 Desktop sidebar / resume / thread list 会很慢。

------

## 3.2 SQLite 适合本地结构化状态

SQLite 是一个嵌入式数据库，不需要额外启动服务。对 Codex 这种本地 CLI / Desktop agent 来说非常合适：

| 能力         | 为什么对 Codex 有用             |
| ------------ | ------------------------------- |
| 单文件数据库 | 容易放在 `~/.codex`             |
| 无服务依赖   | 不需要用户安装 Postgres / MySQL |
| ACID 事务    | 防止状态写一半                  |
| B-tree 索引  | 快速查 thread、logs、cwd、time  |
| SQL 查询     | 方便筛选、排序、join            |
| 跨平台       | Windows / macOS / Linux 都能用  |
| WAL 模式     | 读写可以并发，适合日志持续写入  |

SQLite 官方说明，WAL 模式下 writer 追加写 WAL，reader 可以同时读取；但是同一时间只有一个 writer。 这正适合 Codex 这种“本地单用户、多读、少量持续写”的应用。

------

# 4. 为什么不是全部放进一个 `.sqlite`？

因为完整 transcript 可能非常大。社区里有人提到 legacy Codex 本地有 269 个 `.jsonl` sessions，其中单个 session 超过 180MB；也有人报告 Codex Desktop 在少数超大历史会话存在时，typing、scrolling、thread switching 都会变慢。

如果把完整大 transcript 全塞进 SQLite，会遇到几个问题：

| 问题        | 解释                                   |
| ----------- | -------------------------------------- |
| 数据库膨胀  | 大量长文本会让 DB 快速变大             |
| VACUUM 成本 | 删除历史后不一定自动释放磁盘           |
| 写锁竞争    | 大库写入、checkpoint、读取会更重       |
| UI 加载压力 | Desktop 可能过度 hydrate 历史          |
| 迁移困难    | schema 变更和大 BLOB / TEXT 迁移更麻烦 |

GitHub issue 中有用户报告 `state_5.sqlite` 和 `logs_1.sqlite` 长期使用后异常膨胀，导致写锁竞争、重复写缓存错误，甚至 app restart loop；其中还提到 SQLite 删除后不自动释放空间，需要 `VACUUM`。这是社区报告，不等于官方确认的所有环境通病，但它说明 SQLite 本地状态如果缺少清理机制，确实会在长期使用下变成性能瓶颈。

所以更合理的设计就是：

```
小而结构化的数据：SQLite
大而顺序追加的数据：JSONL
真正代码文件内容：留在 repo 文件系统里，用工具搜索和读取
```

------

# 5. 那 `.sqlite` 对“大规模文件检索”友好吗？

要分三种情况。

------

## 情况 A：检索 Codex 的 thread / logs / metadata

**友好。**

比如你要查：

```
SELECT * FROM threads WHERE cwd = 'E:\Au_projects\0-openai-hackathon';
SELECT * FROM logs WHERE level = 'ERROR';
SELECT * FROM thread_spawn_edges WHERE parent_thread_id = '...';
```

这种结构化查询，SQLite 非常适合。

如果建了合适索引，查询速度会很好。

------

## 情况 B：检索大量文本内容，但用了 SQLite FTS5

**可以友好，但要专门设计。**

SQLite 官方有 FTS5 全文搜索扩展，专门用于在大量 documents 中高效搜索包含某些 term 的文档。FTS5 还支持把索引建立在外部内容上，避免简单重复存储所有原文。

如果 Codex 想做一个本地代码索引，理论上可以设计成：

```
files 表
    id
    path
    mtime
    hash
    language
    size

chunks 表
    file_id
    chunk_id
    start_line
    end_line
    text

fts_index 虚拟表
    path
    symbol
    text
```

然后用：

```
SELECT path, snippet(...)
FROM code_fts
WHERE code_fts MATCH 'authentication token refresh';
```

这种情况下 SQLite 对本地全文检索是可以用的。

但问题是：

> **你目前看到的 Codex `state_5.sqlite` / `logs_2.sqlite` 不是这个用途。它们不是大型代码全文索引库。**

------

## 情况 C：直接把整个大型代码库塞进普通 SQLite 表，然后用 `LIKE '%xxx%'`

**不友好。**

如果只是：

```
SELECT * FROM file_contents WHERE content LIKE '%auth middleware%';
```

那对大规模代码库会很差，因为：

- `LIKE '%xxx%'` 很难用普通索引；
- 大量长文本扫描成本高；
- ranking 不好；
- snippet 不好；
- 代码语义无法理解；
- rename / polyglot / 跨文件逻辑无法解决。

所以答案是：

```
SQLite 不是天然的大规模代码语义检索方案。
SQLite + FTS5 可以做本地全文检索。
SQLite + vector extension 可以做轻量语义检索。
但 Codex 当前本地 SQLite 更像状态库和日志库，不是默认的代码语义索引库。
```

------

# 6. Codex 实际上怎么找代码？

从官方和社区资料看，Codex 更倾向于 **agentic search**：

```
模型判断要找什么
    ↓
调用 shell / rg / find / cat / sed / python
    ↓
读取相关文件
    ↓
继续缩小范围
    ↓
编辑 / 测试 / 验证
```

官方 use case 文档强调，理解大代码库时应该让 Codex trace request flow、识别模块、指出下一步该读哪些文件；并建议你给出相关文件、目录或 feature area，scope 越具体，回答越具体。

社区和 issue 里也能看到 Codex 对 `rg/ripgrep` 的依赖痕迹。例如有 issue 报告 Codex 调用了 `rg` 做文件操作但后台进程没有退出；另一个 issue 中 Codex 给出的 best practice 是“使用 `rg` 和 `rg --files`，不要用慢的 grep/ls -R”。 Reddit 用户也建议安装 `git`、`rg/ripgrep`、formatter、linter、test runner，并强调大 repo 中最省 token 的做法是给 Codex 精确文件和清晰验证循环，而不是让它漫游整个 repo。

这说明 Codex 的代码检索不是简单：

```
SQLite 里查一条语义向量
```

更像：

```
模型 + 文件系统 + ripgrep + shell + 局部读取 + 迭代推理
```

------

# 7. Codex 为什么不默认做一个“全仓库 SQLite 语义索引”？

我认为主要有 7 个原因。

------

## 7.1 成本问题

构建全仓库索引要做：

```
扫描所有文件
过滤 node_modules / dist / .git / vendor
切 chunk
算 hash
识别语言
提取 symbol
可能生成 embedding
写入索引
监听文件变化
增量更新
清理删除文件
处理 rename
```

对大 repo 来说，这本身就是一个重任务。

------

## 7.2 语义索引并不总是比 `rg` 好

代码检索和普通知识库检索不同。代码里很多需求是精确查找：

```
函数名
变量名
类名
路由路径
错误信息
配置 key
SQL 表名
API endpoint
环境变量
日志字符串
```

这些场景 `rg` 非常强。

比如你要找：

```
frontend.healthcheck.ready
```

语义向量未必比：

```
rg "frontend.healthcheck.ready"
```

更好。

------

## 7.3 语义检索容易“看起来相关，但改错地方”

代码修改要求非常精确。语义检索可能找出概念相关但不是实际调用链上的文件。
 这会导致 agent：

```
读了看似相关的文件
错过真正入口
编辑了错误模块
测试失败
浪费 token
```

GitHub 上也有 Codex enhancement issue 明确提出希望加入 semantic codebase indexing，因为当前缺少 first-class semantic search 时，在中大型代码库中会依赖 grep 或文件名启发式；这也反过来说明该能力至少当时并不是 Codex CLI 的默认核心能力。

------

## 7.4 文件变化太频繁

coding agent 运行时会不断改文件：

```
写代码
改测试
生成 build artifact
格式化
安装依赖
生成 lockfile
```

如果有全量索引，就必须做增量同步。否则索引很快 stale。

------

## 7.5 隐私和磁盘占用

如果默认把全部代码内容、embedding、chunk 存本地数据库，用户可能会担心：

```
源码副本在哪里？
能不能清理？
是否包含密钥？
索引会不会上传？
数据库多大？
```

保持“代码仍在文件系统，Codex 按需读取”更简单透明。

------

## 7.6 SQLite 的单 writer 限制

SQLite 官方说明，SQLite 支持无限多个同时 reader，但同一时刻只允许一个 writer；很多场景没问题，因为 writer 很快完成，但高并发写入应用可能需要其他方案。

如果 Codex 同时：

```
写日志
写 state
写 session index
写代码索引
写 embedding index
写文件变更监听结果
```

SQLite 单 writer 就可能成为瓶颈。

------

## 7.7 大库维护问题

SQLite 理论上可以很大。官方 limits 页面说，默认 4096-byte page size 下最大数据库约 17.5TB，最大 page size 下可到约 281TB。

但理论最大值不代表适合把所有内容都放进去。SQLite 官方也提醒，如果考虑这种极大数据库，应考虑 client/server 数据库，因为 SQLite 是单文件存储，文件系统本身也会限制单文件大小。

对 Codex 来说，大型代码仓库更合理的方式是：

```
源文件留在原地
索引只保存必要 metadata
搜索用 rg / AST / LSP / 外部索引
读取时按需进入上下文
```

------

# 8. 所以 Codex 的 `.sqlite` 是“检索友好”还是“不友好”？

结论要精确：

| 场景                         | SQLite 是否友好 | 解释                                         |
| ---------------------------- | --------------- | -------------------------------------------- |
| 查 thread / session metadata | 很友好          | 结构化查询、排序、过滤、join                 |
| 查 logs                      | 友好            | 可以按 level、target、time、thread_id 查     |
| resume 会话索引              | 友好            | 快速找到 rollout_path                        |
| 存完整 transcript            | 一般            | 大长文本可能导致 DB 膨胀，所以 JSONL 更合适  |
| 全文搜索历史 prompt          | 可以            | 但需要 FTS 或外部索引                        |
| 搜索整个代码库文本           | 取决于实现      | SQLite FTS5 可以，但普通表 + LIKE 不好       |
| 语义检索大型代码库           | 不够            | 需要 embedding/vector/AST/LSP/agentic search |
| 高频多 writer 写入           | 不理想          | SQLite 单 writer，可能锁竞争                 |

所以最准确的说法是：

> **Codex 用 SQLite 是为了本地状态检索友好，不是为了默认承担整个代码库的大规模语义检索。**

------

# 9. 为什么这套设计合理？

因为 Codex 运行中有三类完全不同的数据：

## 第一类：结构化、经常查询、需要更新的数据

例如：

```
threads
thread_spawn_edges
agent_jobs
logs
remote enrollments
dynamic tools
```

适合：

```
SQLite
```

------

## 第二类：长文本、顺序追加、按 session 回放的数据

例如：

```
完整对话
tool call trajectory
assistant 输出
shell output
diff
approval event
```

适合：

```
JSONL
```

------

## 第三类：项目源代码

例如：

```
.py
.ts
.java
.md
.sql
config files
tests
```

适合：

```
留在文件系统
用 rg / find / git / AST / LSP 按需查
```

也就是说，Codex 的架构更像：

```
SQLite：索引层
JSONL：轨迹层
File System：源代码真相层
Tools：检索和执行层
Model：推理和决策层
```

------

# 10. 大规模文件情况下，Codex 真正的瓶颈在哪里？

不是单纯 “SQLite 好不好”，而是下面几个瓶颈叠加：

------

## 10.1 上下文窗口瓶颈

仓库可以很大，但模型一次不能无限读所有文件。
 所以 Codex 必须做：

```
先搜索
再筛选
再读取局部
再推理
再验证
```

这就是为什么 `rg`、README、AGENTS.md、测试命令很重要。

------

## 10.2 搜索召回瓶颈

如果用户问得很抽象：

```
帮我修复用户登录偶尔失败的问题
```

Codex 不知道应该先搜：

```
login
auth
session
token
refresh
middleware
cookie
oauth
```

这时候没有语义索引确实会慢。

------

## 10.3 历史会话膨胀瓶颈

长期使用后，历史和日志会膨胀。官方 advanced config 现在提供了 `history.max_bytes`，当 history 文件超过上限时，会丢弃最旧记录并 compact，保留最新记录。

这说明官方也意识到本地历史不能无限膨胀。

------

## 10.4 SQLite 清理瓶颈

如果日志表删除了旧行，但没有 VACUUM，磁盘文件可能仍然很大。社区 issue 已经报告过这类长期膨胀和锁竞争问题。

------

# 11. 如果你要让 Codex 更适合大项目，应该怎么做？

你要把重点放在 **减少搜索空间** 和 **增强工具层**，而不是纠结它为什么用了 SQLite。

## 11.1 必须安装 / 确认 `rg`

```
rg --version
```

大项目里，`rg` 是最关键工具之一。社区里也反复建议 Codex 使用 `rg` / `rg --files` 替代慢的 grep/ls-R。

------

## 11.2 写好 `AGENTS.md`

里面应该告诉 Codex：

```
# Project Map

- frontend app: apps/web
- backend API: services/api
- auth module: services/api/src/auth
- database migrations: packages/db/migrations
- tests: pnpm test / pytest

# Search Rules

- Do not search node_modules, dist, build, .next, coverage
- For auth bugs, start from services/api/src/auth and middleware
- For frontend routing, start from apps/web/src/routes

# Verification

- Run pnpm lint
- Run pnpm test --filter ...
```

这比让 Codex 自己在大 repo 里漫游高效很多。

------

## 11.3 明确告诉 Codex 搜索范围

不要只说：

```
解释这个代码库
```

更好是：

```
请只分析 services/api/src/auth 相关登录流程，先用 rg 找 route、middleware、token、session，然后给我调用链和关键文件，不要读取 node_modules 和 dist。
```

------

## 11.4 对超大 repo，可以自己加索引

如果你真的想做“代码库级别搜索友好”，可以自己建一层：

```
SQLite FTS5：适合本地关键词全文搜索
ripgrep：适合精确字符串 / regex
tree-sitter：适合符号、函数、类结构
LSP：适合定义跳转 / 引用
vector DB：适合语义召回
hybrid search：关键词 + symbol + vector
```

我个人建议你如果研究 Codex harness，可以设计成：

```
第一层：rg 精确搜索
第二层：AST / tree-sitter symbol index
第三层：SQLite FTS5 文本索引
第四层：embedding/vector semantic index
第五层：agent 根据任务动态选择工具
```

这样比“只用 SQLite”或“只用向量库”都更合理。

# 12. 最终结论

## 为什么 Codex 用 `.sqlite`？

因为它需要一个本地、轻量、跨平台、可事务化、可查询的结构化状态库。它适合保存：

```
thread metadata
resume index
cwd / title / model / token usage
subagent parent-child relation
logs
app state
```

------

## `.sqlite` 对大规模文件检索友好吗？

**对 metadata 友好，对完整代码语义检索不够。**

更精确地说：

```
SQLite + 普通表：
    适合结构化状态，不适合大规模全文搜索

SQLite + FTS5：
    可以做本地全文搜索，但需要专门索引设计

SQLite + vector extension：
    可以做轻量语义搜索，但不是 Codex 当前本地 state/log SQLite 的主要用途

Codex 实际代码检索：
    更依赖 rg / shell / 文件系统 / agentic search / 按需读取
```

------

## 为什么这套架构合理？

因为 Codex 把不同数据放在了不同位置：

```
SQLite
    = 状态和索引

JSONL
    = 完整会话轨迹

File system
    = 真实代码库

rg / shell / tools
    = 大规模代码搜索和验证

模型
    = 判断该搜什么、读什么、改什么、测什么
```

这是一种典型的 agent 架构取舍：
 **不要把所有东西都塞进数据库；数据库只保存需要快速查询和一致性维护的状态，代码内容仍然让工具按需搜索和读取。**

# 4. `.jsonl` 是什么？

`.jsonl` 叫 **JSON Lines**。

它不是一个完整的大 JSON，而是：

```
一行 = 一个 JSON 事件
```

大概长这样：

```
{"type":"user_message","content":"..."}
{"type":"assistant_message","content":"..."}
{"type":"tool_call","name":"shell","args":{...}}
{"type":"tool_result","content":"..."}
```

所以你打开后会看到很多行，每一行都是一次事件。

它比把所有内容塞到 SQLite 里更适合记录长 transcript，因为：

- 可以边运行边追加写入；
- 不需要频繁改写大字段；
- 工具输出很长时更容易流式保存；
- 文件损坏时通常只影响局部；
- 方便按 session 单独管理；
- SQLite 只需要保存路径索引。

你贴出来这两行：

- 独立 thread id；
- 独立 rollout JSONL；
- 独立初始 prompt；
- 独立运行过程；
- 独立模型配置；
- 通过 `parent_thread_id` 关联回父 agent。

所以你之前怀疑的点基本成立：

> Codex 的 subagent 更像是独立 session / thread，通过父子关系关联，而不是全部塞进父 transcript 的一层嵌套结构里。

```
  id,
  rollout_path,
  substr(initial_user_message, 1, 120) AS message_preview
FROM threads
ORDER BY created_at DESC;
```

如果报错说没有 `initial_user_message`，说明列名不是这个。你先运行：

```
PRAGMA table_info(threads);
```

然后把真实列名替换进去。

也可以先简单用：

```
SELECT *
FROM threads
ORDER BY created_at DESC;
```

# 9. 你贴出来这组数据说明了什么？

你的这组数据至少说明了 5 件事：

## 1. Codex 每次任务都会生成一个独立 rollout JSONL

例如：

```
rollout-2026-04-28T21-27-26-019dd3d8-12b6-7651-bb0d-d992a4d652b5.jsonl
```

这就是完整执行记录。

------

## 2. Codex 会把首条用户指令复制进 SQLite

比如：

```
现在我的docs 路径下有2025-2026-idea.md和2026hackathon.md...
```

这让 Codex 可以快速展示历史任务标题、搜索历史任务，而不用每次打开大 JSONL 文件。

------

## 3. Codex 会记录当前工作目录

例如：

```
E:\Au_projects\0-openai-hackathon
```

这说明 Codex session 是和 repo / workspace 强绑定的。

------

## 4. Codex 会记录 sandbox 和 approval 配置

例如：

```
{"type":"workspace-write","writable_roots":["C:\\Users\\Helios\\.codex\\memories"],"network_access":false}
```

以及：

```
on-request
```

这说明这次任务运行时：

- 有 workspace-write 权限；
- 网络不可用；
- 需要时才请求 approval；
- writable root 包含 `C:\Users\Helios\.codex\memories`。

------

## 5. 子 agent 是独立 thread

这两条：

```
Anscombe explorer
Huygens explorer
```

说明 Codex 创建了两个子 agent，并分别记录成独立 thread。

这对你研究 harness 很重要，因为它证明了：

```
父 agent 负责分配任务
子 agent 拥有独立上下文
父子之间通过 thread_spawn metadata / rollout 返回结果关联
```

# 10. 最重要的结论

你现在看到的结构可以概括成这样：

```
state_5.sqlite
  └── threads 表
        ├── 保存每个 session 的索引信息
        ├── 保存 rollout JSONL 文件路径
        ├── 保存首条用户指令
        ├── 保存工作目录 / 模型 / provider / CLI 版本
        ├── 保存 sandbox / approval policy
        └── 保存 subagent 的父子关系 metadata

sessions/YYYY/MM/DD/rollout-xxx.jsonl
  └── 保存完整执行 transcript
        ├── user message
        ├── assistant message
        ├── tool call
        ├── tool result
        ├── file operation
        ├── shell command
        ├── subagent response
        └── final answer

logs_2.sqlite
  └── 保存更底层的日志 / 运行记录 / process 相关信息
```

所以你要继续深入研究的话，下一步不是继续只看 `state_5.sqlite`，而是应该：

1. 用 `threads` 表找到目标 session；
2. 复制 `rollout_path`；
3. 打开对应 `.jsonl`；
4. 分析每一行事件；
5. 再对照 `logs_2.sqlite` 看底层日志。
