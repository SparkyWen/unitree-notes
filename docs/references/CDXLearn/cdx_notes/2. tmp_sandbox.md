它不是一个普通项目源码包，而是 **Codex 本地运行状态目录的一部分**，里面主要有：

```

cache/
log/

```

| 顶层目录    | 作用                                          | 文件数 | 目录数 | 未压缩大小 |

| `.sandbox/` | 沙箱命令执行审计日志                          | 1      | 1      | 9 KB       |

| `cache/`    | 已解析/已发现工具 schema 缓存                 | 1      | 2      | 约 432 KB  |

# 1. 最核心结论

这个压缩包记录的是一次 Codex 运行过程中的本地状态：

```
启动 Codex
  ↓
加载 .tmp/plugins 中的本地插件仓库
  ↓
尝试远程同步插件 / app / connector 信息
  ↓
远程接口多次 403，所以回退到本地已有快照
  ↓
生成或使用 cache/codex_apps_tools/...json 中的工具 schema 缓存
  ↓
启动会话、子 agent、shell 工具
  ↓
shell 命令通过 sandbox 执行，并写入 .sandbox/sandbox.log
  ↓
Codex 主程序运行过程写入 log/codex-tui.log
  ↓
关闭会话，日志和缓存仍然留在磁盘上
```

所以你问的几个关键问题，可以先给结论：

| 问题                                 | 结论                                                         |
| ------------------------------------ | ------------------------------------------------------------ |
| 为什么同时有 `tmp` 和 `.tmp`？       | 它们不是同一个用途。`.tmp` 是 Codex 内部隐藏式临时/可刷新资源区，本包里主要放插件仓库；`tmp` 是普通运行临时区，本包里只有空的 `arg0/`。 |
| `.tmp` 是不是 session 中间文件？     | 不是简单的“当前 session 临时文件”。这里的 `.tmp/plugins` 是一个可复用的插件仓库镜像，会跨会话存在。 |
| `tmp` 是不是 session 中间文件？      | 更像普通短生命周期 scratch 区，但本包里 `tmp/arg0/` 是空目录，没有可分析中间文件。 |
| `cache` 里是什么？                   | 是 Codex apps / connector 工具定义缓存，具体是 118 个工具的 JSON schema，不是用户聊天内容。 |
| `log` 记录什么？                     | `log/codex-tui.log` 记录 Codex 主程序、插件加载、工具调用、模型连接、session 生命周期、warning/error 等。 |
| `.sandbox` 是什么？                  | 是 shell 命令执行沙箱/审计日志区。这个包里只有 `sandbox.log`，记录了 Codex 调用 PowerShell 执行了哪些命令、何时开始、何时成功。 |
| session 结束后 `.sandbox` 会清除吗？ | 从这个压缩包看，**没有在 session 结束时自动清空**。日志在关闭后仍然存在。是否后续轮转/清理，要看 Codex 的清理策略，但本包不能证明“session 一结束就删除”。 |

# 3. 为什么要同时设计 `tmp` 和 `.tmp`？

## 3.1 这两个目录不是重复设计

你的压缩包中：

```
.tmp/
  plugins/
  plugins.sha

tmp/
  arg0/
```

它们用途明显不同。

`.tmp` 里面有完整插件仓库：

```
.tmp/plugins/
  .git/
  .agents/
  plugins/
  README.md
  .gitignore

.tmp/plugins.sha
```

而 `tmp` 里面只有：

```
tmp/arg0/
```

并且是空目录。

所以：

```
.tmp = Codex 内部可刷新资源区
tmp  = 普通运行临时 scratch 区
```

------

## 3.2 `.tmp` 为什么前面有点？

`.tmp` 里的点不是文件扩展名，而是目录名的一部分。

在跨平台软件里，前缀点号通常表达：

```
这是内部目录，不希望用户直接编辑
```

在 Unix/macOS/Linux 里，点号开头的目录默认隐藏。Windows 不一定因为点号自动隐藏，但这种命名仍然有很强的语义：

```
.codex/.tmp = Codex 自己管理的内部临时目录
```

它的作用不是给用户放东西，而是给 Codex 放：

- 下载/同步下来的插件仓库
- 可刷新但可复用的运行资源
- 插件 marketplace 元数据
- skill 文档
- app connector 配置
- MCP 配置
- 插件图标、资源、脚本
- Git 元数据

------

## 3.3 `tmp` 为什么没有点？

`tmp` 更像普通运行临时区。这个压缩包里只看到：

```
tmp/arg0/
```

而且为空。

`arg0` 这个名字通常让人想到“启动参数 / 第 0 个参数 / launcher 参数槽位”。但这个包里没有更多文件，所以只能稳妥地说：

```
tmp/arg0/ 是运行过程中创建的空临时目录。
```

不能根据这个包断言它一定做了什么。

------

## 3.4 为什么不把所有东西都放进一个 `tmp`？

从程序设计角度，分开非常合理：

| 目录               | 生命周期               | 内容性质         | 是否可以重建    | 设计原因               |
| ------------------ | ---------------------- | ---------------- | --------------- | ---------------------- |
| `.tmp/plugins`     | 较长，可跨 session     | 插件仓库镜像     | 可以重拉/重同步 | 避免每次启动都下载插件 |
| `.tmp/plugins.sha` | 较长                   | 插件版本指针     | 可以重建        | 快速判断插件版本       |
| `cache/`           | 中等，可跨 session     | 工具 schema 缓存 | 可以重建        | 减少重复解析/远程请求  |
| `tmp/`             | 短                     | 普通临时文件     | 通常可删除      | 存放一次性运行 scratch |
| `.sandbox/`        | session / 命令审计相关 | 命令执行日志     | 删除会丢审计    | 追踪 shell 执行        |
| `log/`             | 较长                   | 主程序日志       | 删除会丢诊断    | 排查问题               |

如果全部混在 `tmp` 里，会有几个问题：

1. **清理策略冲突**
    普通临时文件可以随时删，但插件仓库删掉后，离线或远程 403 时 Codex 可能无法加载插件。
2. **可复用资源和短期 scratch 混杂**
    `.tmp/plugins` 是可以长期复用的“临时仓库镜像”，不是一轮对话里的 scratch 文件。
3. **安全边界不清晰**
    `.sandbox` 的日志和普通临时文件不同，它有审计价值。
4. **启动性能下降**
    如果每次 session 结束都清 `.tmp/plugins`，下一次启动就要重新同步或重新扫描大量插件。
5. **离线/远程失败时没有 fallback**
    你的日志里恰好出现多次远程 403。Codex 仍能继续工作，很大程度依赖本地已有插件/工具快照。

# 4. `.tmp` 目录详细解释

------

## 4.1 `.tmp/plugins.sha`

内容是：

```
6807e4de4d8ceceefb51abd9e4ba3269030352c4
```

这是一个 40 位十六进制字符串，形式上非常像 Git commit SHA。

同时 `.tmp/plugins/.git/logs/HEAD` 里显示：

```
clone: from https://github.com/openai/plugins.git
```

并且 `.git/config` 里有：

```
url = https://github.com/openai/plugins.git
```

所以 `.tmp/plugins` 是从：

```
https://github.com/openai/plugins.git
```

克隆下来的本地插件仓库快照，`plugins.sha` 大概率用于记录当前本地插件仓库对应的版本。

从运行角度，它的作用类似：

```
Codex 启动
  ↓
查看 .tmp/plugins.sha
  ↓
判断本地插件仓库是否已经是目标版本
  ↓
如果是，就直接加载
  ↓
如果不是，尝试同步/更新
```

## 4.2 `.tmp/plugins/.git/`

这里是插件仓库的 Git 元数据。

里面包括：

```
.git/config
.git/HEAD
.git/index
.git/logs/
.git/objects/pack/
.git/refs/
.git/shallow
```

最大的文件是：

```
.tmp/plugins/.git/objects/pack/pack-d994a203d59ac89dad3b2be9dece420733b9e0ba.pack
```

大小约 7.7 MB。

这说明插件仓库是一个浅克隆或压缩后的 Git pack 存储。它的作用：

1. 记录插件仓库来源。
2. 让 Codex 可以更新插件仓库。
3. 让本地文件和版本号对应。
4. 避免把插件当作完全散乱的临时文件管理。

这不是用户项目 Git 仓库，而是 Codex 本地的插件资源仓库。

## 4.6 `.codex-plugin/plugin.json` 是什么？

这是每个插件的 manifest，即插件清单。

例如 GitHub 插件：

```
{
  "name": "github",
  "version": "0.1.0",
  "description": "Inspect repositories, triage pull requests and issues...",
  "skills": "./skills/",
  "apps": "./.app.json",
  "interface": {
    "displayName": "GitHub",
    "shortDescription": "Triage PRs, issues, CI, and publish flows",
    "category": "Coding",
    "capabilities": [
      "Interactive",
      "Write"
    ],
    "composerIcon": "./assets/github-small.svg",
    "logo": "./assets/github.png"
  }
}
```

从程序运行角度，Codex 启动或刷新插件时会读取这些 `plugin.json`，然后得到：

| 字段                              | 作用                                      |
| --------------------------------- | ----------------------------------------- |
| `name`                            | 插件内部 ID                               |
| `version`                         | 插件版本                                  |
| `description`                     | 插件说明                                  |
| `skills`                          | skill 目录位置                            |
| `apps`                            | app connector 配置位置                    |
| `mcpServers`                      | MCP server 配置位置                       |
| `interface.displayName`           | UI 展示名                                 |
| `interface.category`              | UI 分类                                   |
| `interface.capabilities`          | 插件能力，例如 Read / Write / Interactive |
| `interface.defaultPrompt`         | UI 中的 starter prompt                    |
| `interface.logo` / `composerIcon` | 图标资源                                  |

你的日志里有 manifest 校验 warning：

```
ignoring interface.defaultPrompt: prompt must be at most 128 characters
path=C:\Users\Helios\.codex\.tmp\plugins\plugins\build-ios-apps\.codex-plugin/plugin.json

ignoring interface.defaultPrompt: maximum of 3 prompts is supported
path=C:\Users\Helios\.codex\.tmp\plugins\plugins\plugin-eval\.codex-plugin/plugin.json
```

这说明 Codex 启动时确实扫描了这些插件 manifest，并校验字段规则。

# 5. `cache` 目录详细解释

`cache` 里只有一个真实文件：

```
cache/codex_apps_tools/48ee4282bc45634d2af85fcd9b8aac5784685376.json
```

大小约 432 KB。

这个 JSON 的顶层结构是：

```
{
  "schema_version": 2,
  "tools": [
    ...
  ]
}

也就是说它缓存了：

| 字段               | 作用                                       |
| ------------------ | ------------------------------------------ |

| `tool_name`        | 内部工具名                                 |
| `tool_namespace`   | 工具命名空间                               |
| `tool.name`        | 暴露给模型/工具路由层的名称                |
| `tool.title`       | UI/展示标题                                |
| `tool.description` | 工具能力描述                               |
| `inputSchema`      | 工具参数 JSON schema                       |

## 5.2 为什么要缓存工具 schema？

因为工具 schema 对 Codex 很重要。

当模型需要调用工具时，它必须知道：

```
有哪些工具
每个工具叫什么
每个工具需要什么参数
参数类型是什么
哪些参数必填
工具大概做什么
```

如果每次启动都重新从远程 connector 拉取全部 schema，会有问题：

1. 启动慢。
2. 离线或远程失败时不可用。
3. 每轮对话重复解析浪费资源。
4. 工具列表变化时难以判断是否要刷新。

所以设计为：

```
远程或本地发现工具
  ↓
整理成标准 JSON schema
  ↓
写入 cache/codex_apps_tools/<hash>.json
  ↓
后续快速读取
```

这个文件名：

```
48ee4282bc45634d2af85fcd9b8aac5784685376.json
```

是 40 位十六进制，很像内容哈希或缓存 key。它大概率用于表达：

```
这批工具 schema 的某个版本/指纹
```

如果工具定义变化，就可以生成新的 hash 文件，避免错用旧 schema。

## 7.4 session 结束后 `.sandbox` 会不会清除？

你的问题是：

> 是不是如果当前 session 没关，这里面就保存了中间文件？当 session 结束就清除？

根据这个压缩包，答案是：

```
不能这么理解。
```

原因：

1. `log/codex-tui.log` 里有 shutdown 记录：

```
Shutting down Codex instance
```

1. `.sandbox/sandbox.log` 仍然存在于压缩包中。
2. `.sandbox` 里面没有看到“中间文件”，只看到命令审计日志。
3. `tmp/arg0/` 也是空的。
4. `.tmp/plugins` 和 `cache` 明显是跨 session 可复用内容。

所以更准确的生命周期判断是：

| 目录           | session 结束是否必然清除？     | 本包证据                            |
| -------------- | ------------------------------ | ----------------------------------- |
| `.sandbox/`    | 不一定                         | session 结束后 `sandbox.log` 仍存在 |
| `tmp/`         | 可能可清理，但本包没有有效内容 | 只有空 `arg0/`                      |
| `.tmp/plugins` | 不应每次 session 结束就清      | 里面是插件仓库镜像                  |
| `cache/`       | 可重建，但不一定清             | 工具 schema 缓存仍存在              |
| `log/`         | 通常不会 session 结束即清      | `codex-tui.log` 保留 shutdown 记录  |

# 9. `log` 和 `.sandbox` 为什么要分开？

它偏向：

```

## 9.2 `.sandbox/sandbox.log`

记录的是：

```

```

它偏向：

| 问题                                     | 看哪个日志             |
| ---------------------------------------- | ---------------------- |

# 10. 哪些内容可以删？哪些不建议乱删？

从工程角度：

| 目录/文件              | 是否可以删                | 后果                                               |
| ---------------------- | ------------------------- | -------------------------------------------------- |
| `tmp/`                 | 通常可以在 Codex 关闭后删 | 本包里为空，影响很小                               |
| `cache/`               | 可以删，但会重建          | 下次启动可能变慢，远程失败时可能少一些本地工具信息 |
| `.sandbox/sandbox.log` | 可以删，但会丢审计        | 无法追踪之前执行过哪些命令                         |
| `log/codex-tui.log`    | 可以删，但会丢诊断        | 无法排查之前的错误                                 |
| `.tmp/plugins`         | 不建议随便删              | 如果远程同步失败，插件列表/skills 可能无法加载     |
| `.tmp/plugins.sha`     | 不建议单独删              | 可能导致 Codex 判断插件版本异常或重新同步          |

最安全的原则：

```
Codex 正在运行时不要删除这些目录。
Codex 关闭后：
  tmp/ 可以优先清
  log/ 可以按需归档或清理
  cache/ 可以让它重建
  .tmp/plugins/ 除非明确要重拉插件，否则不要随便删
```

# 11. 对你几个问题逐条回答

## 11.1 为什么要有 `tmp` 和 `.tmp`？

因为它们生命周期和内容性质不同。

```
.tmp:
  Codex 内部隐藏资源区
  本包中主要是插件仓库镜像
  可跨 session 复用
  不应每轮会话结束就删

tmp:
  普通运行临时区
  本包中只有空的 arg0/
  更像短生命周期 scratch
```

------

## 11.2 为什么这样设计？

为了分离：

1. 可复用内部资源。
2. 普通临时文件。
3. 工具 schema 缓存。
4. 主程序日志。
5. 沙箱命令审计。

这样设计可以让 Codex：

```
启动更快
远程失败时仍能工作
日志更容易排查
临时文件更容易清理
插件仓库更容易版本化
沙箱执行更容易审计
```

------

## 11.3 `cache` 里内容是什么？

是：

```
Codex apps 工具 schema 缓存
```

具体文件：

```
cache/codex_apps_tools/48ee4282bc45634d2af85fcd9b8aac5784685376.json
```

里面有：

```
schema_version: 2
tools: 118 个
```

工具分布：

```
GitHub: 86
Outlook Email: 31
Coursera: 1
```

它的作用是让 Codex 知道当前可以调用哪些 app 工具，以及每个工具需要哪些参数。

------

## 11.4 `log` 记录什么？

`log/codex-tui.log` 记录：

```
插件同步失败
manifest 校验 warning
app list 加载失败和 fallback
session 初始化
MCP 初始化
模型 websocket 连接
工具调用
子 agent 调度
apply_patch 内容
shutdown
错误和 warning
```

这是主程序诊断日志。

------

## 11.5 `log` 文件夹在执行过程中如何实现记录？

从日志格式看，Codex 使用类似 Rust `tracing` 的结构化日志方式：

```
时间戳
日志级别
模块名
span 信息
事件内容
耗时信息
```

例如：

```
INFO session_loop{thread_id=...}:submission_dispatch{...}:turn{...}: codex_core::client: new
```

这表示日志不是随便打印字符串，而是按模块、session、turn、tool call 形成层级 span。

------

## 11.6 `.sandbox` 到底是什么？

在这个包里：

```
.sandbox = shell 命令沙箱审计目录
```

它记录了 Codex 通过 PowerShell 执行了哪些命令。

它不等于项目目录，也不等于所有中间文件目录。

------

## 11.7 当前 session 没关时，`.sandbox` 里会保存中间文件吗？

本包无法证明 `.sandbox` 会保存“所有中间文件”。

本包只能证明：

```
.sandbox/sandbox.log 保存 shell 命令审计
```

没有看到其他中间文件。

------

## 11.8 session 结束后 `.sandbox` 会清除吗？

从这个压缩包看：

```
没有立即清除。
```

因为日志里已经有 shutdown，而 `.sandbox/sandbox.log` 仍然存在。

所以不能说：

```
session 一结束 .sandbox 就清空
```

更准确是：

```
它至少在这次快照中保留到了 session 结束之后。
是否后续轮转/清理，取决于 Codex 的本地清理策略。
```

------

# 12. 一句话总结

这个压缩包展示的是 Codex 的本地运行支撑系统：

```
.tmp/plugins 负责本地插件仓库和 skill 资源
cache 负责 app/tool schema 快速加载
log 负责主程序运行诊断
.sandbox 负责 shell 命令执行审计
tmp 是普通临时 scratch，本包里基本没用上
```

最关键的理解是：

```
.tmp 不是普通临时垃圾目录；
它在这个包里承担了“本地插件仓库镜像”的作用。

cache 不是用户数据；
它是工具 schema 缓存。

.sandbox 不是项目文件区；
它是命令执行审计区。

log 不是 shell 输出；
它是 Codex 主程序的内部运行轨迹。
```
