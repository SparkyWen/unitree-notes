# Codex 与 Claude Code transcript 风格深度对比

> 生成日期：2026-04-28（Australia/Sydney）  
> 对比对象：用户提供的 `claude_transcript.zip` 与 `codex_transcript.zip`，并结合公开官方文档与 Codex 开源源码核对。  
> 结论重点：**Claude Code 更像“主会话 JSONL + sidechain/subagent JSONL + 大输出外置文件”的文件系统分层；Codex 更像“每个 agent/thread 一个 rollout JSONL”的事件流模型，父子关系不靠目录分层，而靠 thread id、spawn/wait/close 事件和 session metadata 关联。**

---

## 0. 一句话总览

你观察到的方向基本是对的，但需要拆成两个层面：

1. **持久化 transcript 层面**：
   - **Claude Code**：在这份样本里明显有“主会话目录 → `subagents/` → `tool-results/`”的文件系统分层。大工具输出被 spill 到 `tool-results/*.txt`，JSONL 里只留 `<persisted-output>`、路径和预览。
   - **Codex**：在这份样本里没有把子 agent 放到父目录下，而是三个平级 `rollout-*.jsonl`。但它不是没有父子关系：子 rollout 的 `session_meta.payload.source.subagent.thread_spawn.parent_thread_id` 记录了父 thread，主 rollout 也记录了 `spawn_agent`、`wait_agent`、`close_agent` 事件。

2. **模型实时上下文层面**：
   - **不要把“transcript 文件里有什么”直接等同于“下一次模型请求完整注入了什么”。** 两者通常不同。
   - Claude 的大输出外置后，模型看到的是 preview/path 这类压缩呈现，而不是无条件看到完整 txt。
   - Codex 通过 `ContextManager` 生成 model-visible history：工具输出会按 truncation policy 截断；长线程会触发 compaction，用 handoff summary 替换活跃历史。subagent 的噪声工作一般只把最终 summary/status 回传到主 thread，而不是把子 agent 全量工具轨迹注入主 thread。

这个样本里的 Claude transcript 是非常典型的“Anthropic message block + 本地运行时元数据”混合体：

```text
rollout-2026-04-28T21-56-43-019dd3f2-e18e-7750-bafd-0c662d6230c8.jsonl  # 子 agent A
rollout-2026-04-28T21-56-48-019dd3f2-f5ab-7a70-8ef9-5a1d193323dd.jsonl  # 子 agent B
```

关键统计：

| 文件 | 行数 / 大小 | 角色 |

| `019dd3f1-a808-...` | 95 行 / 115,193 bytes | 主 thread |
| `019dd3f2-e18e-...` | 22 行 / 49,769 bytes | 子 agent A / nickname `Anscombe` / role `explorer` |

| payload.type | 数量 |
|---|---:|

| `function_call` | 16 |
| `function_call_output` | 16 |
| `message` | 12 |
| `reasoning` | 8 |

Codex 这个样本是非常典型的“event-sourced rollout trace”：

## 2. 工具调用记录风格对比

### 2.1 Claude Code：assistant 发 `tool_use`，user 回 `tool_result`

Claude 的 transcript 更接近 Anthropic Messages API 的语义结构：

```json
{
  "type": "assistant",
  "message": {
    "role": "assistant",
    "content": [
      {
        "type": "tool_use",
        "id": "toolu_...",
        "name": "Bash",
        "input": { "command": "..." }
      }
    ]
  }
}
```

随后工具结果作为 `user` message 的 `tool_result` block 回到模型：

```json
{
  "type": "user",
  "message": {
    "role": "user",
    "content": [
      {
        "type": "tool_result",
        "tool_use_id": "toolu_...",
        "content": "..."
      }
    ]
  },
  "toolUseResult": {
    "stdout": "...",
    "stderr": "...",
    "interrupted": false
  }
}
```

在你给的 Claude 样本中，主会话发生了 3 个工具调用：

| 工具 | 次数 | 结果 |
|---|---:|---|
| `Bash` | 2 | 列出 writer agent skills 与 skill 目录 |
| `Agent` | 1 | 启动 writer 子 agent，并在主会话收到最终稿 |

子 agent 中发生了 1 个工具调用：

| 工具 | 次数 | 结果 |
|---|---:|---|
| `Read` | 1 | 读取 `SKILL.md`，输出过大，spill 到 `tool-results/*.txt` |

### 2.2 Codex：模型 item + 运行时 event 并行记录

Codex 的工具调用生命周期在 transcript 中会拆得更细：

1. 模型产生 `function_call`：

```json
{
  "type": "response_item",
  "payload": {
    "type": "function_call",
    "name": "shell_command",
    "arguments": "{...}",
    "call_id": "call_..."
  }
}
```

2. 运行时执行工具，并记录 runtime event，例如 shell 命令完成：

```json
{
  "type": "event_msg",
  "payload": {
    "type": "exec_command_end",
    "call_id": "call_...",
    "exit_code": 0,
    "aggregated_output": "...",
    "duration": "..."
  }
}
```

3. 再以 `function_call_output` 的形式把模型可见结果放回历史：

```json
{
  "type": "response_item",
  "payload": {
    "type": "function_call_output",
    "call_id": "call_...",
    "output": "Exit code: 0\nWall time: ...\nOutput:\n..."
  }
}
```

在你给的 Codex 主 rollout 中，比较重要的工具有：

| 工具名 | 用途 |
|---|---|
| `update_plan` | 维护计划状态 |
| `spawn_agent` | 启动子 agent |
| `wait_agent` | 等待子 agent 结果 |
| `close_agent` | 关闭子 agent thread |
| `shell_command` | 执行本地 PowerShell 命令 |
| `apply_patch` | 写入/修改文件 |

Codex 的一个显著特点是：**工具调用的“模型输出”和“宿主运行时事件”都被记录**。这让 transcript 可审计性更强，但也让 JSONL 行类型更多、更像系统事件流，而不像 Claude 那种消息树。

## 3. Subagent / 子 agent 记录方式对比

### 3.1 Claude Code：sidechain 文件系统分层非常明显

Claude 样本中，主会话用 `Agent` 工具启动 writer 子 agent：

- 主 JSONL 中有 `Agent` 的 `tool_use`。
- 主 JSONL 中有 `Agent` 的 `tool_result`，内容是子 agent 最终输出。
- 子 agent 自己的完整执行过程在 `subagents/agent-ab41c2302c7dd3e69.jsonl`。
- `agent-ab41c2302c7dd3e69.meta.json` 记录：

```json
{"agentType":"writer","description":"张雪峰式选校建议"}
```

Claude 的子 agent JSONL 行有：

```json
"isSidechain": true,
"agentId": "ab41c2302c7dd3e69"
```

这说明 Claude 的持久化结构天然把 sidechain/subagent 看成主 session 的附属物。它不仅在逻辑上是子会话，在文件系统上也放在主 session 目录下。

### 3.2 Codex：每个 agent 是一个独立 thread / rollout

Codex 样本里，主 thread 通过 `spawn_agent` 产生两个新 thread：

| 子 agent | thread id | nickname | role |
|---|---|---|---|
| A | `019dd3f2-e18e-7750-bafd-0c662d6230c8` | `Anscombe` | `explorer` |
| B | `019dd3f2-f5ab-7a70-8ef9-5a1d193323dd` | `Huygens` | `explorer` |

主 rollout 里有：

```json
{
  "type": "collab_agent_spawn_end",
  "sender_thread_id": "019dd3f1-a808-7930-a4ce-5773e3ae9fea",
  "new_thread_id": "019dd3f2-e18e-7750-bafd-0c662d6230c8",
  "new_agent_nickname": "Anscombe",
  "new_agent_role": "explorer"
}
```

子 rollout 的 `session_meta` 中则有反向链接：

```json
{
  "source": {
    "subagent": {
      "thread_spawn": {
        "parent_thread_id": "019dd3f1-a808-7930-a4ce-5773e3ae9fea",
        "depth": 1,
        "agent_nickname": "Huygens",
        "agent_role": "explorer"
      }
    }
  }
}
```

所以你的“Codex 没有分层？”可以更准确地说成：

> 在这个 zip 里，Codex **文件系统上没有父目录/子目录式分层**；但它有**事件与元数据层面的逻辑分层**。父子关系靠 thread id、`parent_thread_id`、`depth`、spawn/wait/close 事件来重建。

这与 Claude 的差异很大：

| 维度 | Claude Code | Codex |
|---|---|---|
| 子 agent 存储 | 主 session 目录下 `subagents/agent-*.jsonl` | 独立 `rollout-*.jsonl`，与主 rollout 平级 |
| 父子关系 | 目录结构 + `isSidechain` + `agentId` | `parent_thread_id` + `depth` + spawn/wait/close events |
| 主会话看到什么 | `Agent` 工具最终结果 | `wait_agent`/`close_agent` 返回的 completed status / summary |
| 子 agent 内部工具轨迹是否进主会话 | 不进；在子 JSONL | 不进；在子 rollout |
| 是否更适合多 agent 并行 | 可并行，但结构偏“sidechain” | 结构天然接近 multi-thread orchestration |

## 4. 大量工具调用结果怎么办？核心问题拆解

你问的关键问题是：

> Codex 这种工具调用和 subagents 都是单独 JSONL，遇到大量工具结果怎么办？是压缩了再注入主 transcript，还是别的做法？

要分 **Claude** 和 **Codex**，也要分 **transcript 持久化** 与 **模型上下文注入**。

### 4.1 Claude Code：大输出外置到 `tool-results/`，JSONL 留 preview/path

你给的 Claude 样本里，子 agent 读取 `SKILL.md` 后，JSONL 里的 `tool_result` 不是全文，而是：

```text
<persisted-output>
Output too large (8.7KB). Full output saved to: .../tool-results/toolu_01P4D4SH1FtBAbfEd3EyneDE.txt

Preview (first 2.0KB):
...
</persisted-output>
```

也就是说：

- 完整输出保存到：`tool-results/toolu_01P4D4SH1FtBAbfEd3EyneDE.txt`
- JSONL 中只保存：提示、路径、前 2KB 预览。
- 子 agent 后续如果需要完整内容，可以再通过工具按需读取文件或定位片段；但不会把 8.7KB 全部无条件塞进主会话。

这正好对应 Claude 官方 `.claude` 目录说明：

- `projects/<project>/<session>.jsonl` 是 full conversation transcript。
- `projects/<project>/<session>/tool-results/` 用来放 large tool outputs spilled to separate files。

### 4.2 Claude Code：subagent 的上下文隔离天然减少主上下文污染

Claude Code/Agent SDK 文档对 subagent 的描述非常明确：

- 子 agent 的上下文窗口从 fresh 开始。
- 它不会继承父会话历史或父会话工具结果。
- 父 agent 收到的是子 agent 最终 message 作为 `Agent` 工具结果。

这意味着 Claude 在面对“海量探索/读取/搜索”时的推荐做法是：

1. 让 subagent 去读很多文件、跑很多命令。
2. 子 agent 内部 transcript 保存完整过程。
3. 主会话只接收子 agent 最终 summary。
4. 如果工具输出本身巨大，则再走 `tool-results/` spill。

因此，Claude 的策略可以概括成：

> **文件系统外置大输出 + 子 agent 隔离探索噪声 + compaction 摘要长会话。**

### 4.3 Codex：样本中没有外置 `tool-results/`，工具结果内嵌 rollout，但 model-visible history 会截断

你给的 Codex 样本没有看到 `tool-results/` 目录。shell 输出、`wait_agent` 返回、`apply_patch` 返回都在各自 rollout 的 `function_call_output` 或 `event_msg` 中。

但是这不等于 Codex 会把所有输出永久完整注入模型。Codex 开源源码里 `ContextManager` 的逻辑很关键：

- 它记录的是 history item。
- `record_items(..., policy)` 时会调用 `process_item`。
- 对 `FunctionCallOutput` 和 `CustomToolCallOutput` 会调用 `truncate_function_output_payload(...)`。
- `for_prompt(...)` 会 normalize history，然后返回实际发送给模型的 prompt history。

换句话说，Codex 的核心处理不是“把大工具结果压缩成 summary 再注入主 transcript”，而是更接近下面的链路：

```text
工具原始输出
  ↓
运行时事件/rollout 记录（用于审计、恢复、UI）
  ↓
ContextManager 生成 model-visible history
  ↓
对工具输出按 truncation policy 截断
  ↓
活跃上下文太大时触发 compaction，生成 handoff summary
  ↓
用 summary + 最近/必要信息替换当前活跃 history
```

注意这里有两个不同概念：

| 概念 | 是否等价于 transcript？ | 作用 |
|---|---|---|
| rollout JSONL | 否，只是持久化/审计记录 | 记录发生过什么 |
| model-visible history | 否，是从 history 构造出来的请求上下文 | 决定模型下一步实际看到什么 |
| compaction replacement history | 否，是长上下文时的替换视图 | 让模型继续工作但丢弃/摘要旧细节 |

所以回答你的原问题：

> Codex 一般不是“把每个大工具结果摘要后再注入主 transcript”。更准确是：**工具输出进入对应 thread 的 rollout/history；进入模型上下文前会被截断/规范化；主 thread 只拿到 subagent 的结果摘要/status；长线程接近上下文上限时，再整体 compaction 成 handoff summary 替换活跃历史。**

### 4.4 Codex：compaction 是线程级 handoff summary，不是每个工具结果的局部摘要

Codex 的 compaction prompt 很短，目标是生成 handoff summary，包括：

- 当前进度和关键决策。
- 重要上下文、限制、用户偏好。
- 还要做什么。
- 继续任务需要的关键数据、例子、引用。

源码中 `run_compact_task_inner_impl` 的关键行为是：

1. 克隆当前 history。
2. 用 compact prompt 让模型生成 summary。
3. 收集 user messages。
4. 构造 compacted history：保留一部分用户消息 + summary。
5. `replace_compacted_history(...)` 替换当前活跃历史。

因此 compaction 更像：

```text
旧长上下文
  → 生成任务交接摘要
  → 用“有限用户消息 + 摘要 + 必要初始上下文”替换活跃 history
```

它不是：

```text
每个 tool_result → 单独摘要 → 作为压缩 tool_result 注入主 transcript
```

这点非常重要。否则你会误以为 Codex 在 transcript 层做了精细压缩，其实它主要是在 **model-visible history** 与 **context checkpoint** 层做管理。

## 5. Codex 的“平级 rollout”为什么看起来没有分层？

### 5.1 这是 thread-first，而不是 session-directory-first

Claude 的文件组织像这样：

```text
session/
├── main.jsonl
├── subagents/
└── tool-results/
```

Codex 的文件组织在你这个样本中像这样：

```text
rollout-parent.jsonl
rollout-child-A.jsonl
rollout-child-B.jsonl
```

这背后的设计风格不同：

| 风格 | Claude Code | Codex |
|---|---|---|
| 持久化基本单位 | session + sidechain | thread / rollout |
| 多 agent 模型 | 父 session 的 sidechain | 多 thread orchestration |
| 文件系统关系 | 层级目录 | 平级文件 + metadata graph |
| 重建父子树靠什么 | 路径 + `agentId` | `parent_thread_id` + spawn/wait/close events |

这不是“Codex 没有分层”，而是：

> Codex 的分层不体现在目录树，而体现在事件图和 thread graph。

### 5.2 主 rollout 不吞子 rollout 的内部工具结果

主 Codex rollout 对子 agent 的记录大致是：

1. `spawn_agent`：生成新 thread id。
2. `collab_agent_spawn_end`：记录新 agent nickname/role/prompt。
3. `wait_agent`：等待一个或多个 child thread。
4. `collab_waiting_end` / `function_call_output`：返回 child 的 completed summary。
5. `close_agent`：关闭 child thread。

主 rollout 里看到的是子 agent 的 final/status 文本，不是子 agent 的所有 `shell_command` 输出。

子 agent 自己的 shell 输出在自己的 rollout 里。例如：

- 子 A 执行 `Get-ChildItem -Force`、`Get-ChildItem -Force docs`、`git status --short`。
- 子 B 执行 `Get-Content README.md`、`Get-Content AGENTS.md`、`git log --oneline -5`。

主 thread 最终只拿到 A/B 的中文总结，然后写报告。

这与 Codex 官方 subagent 概念吻合：把 noisy intermediate output 移出主 thread，返回 summaries。

## 6. Claude 与 Codex 在“上下文污染”上的不同治理方式

### 6.1 Claude：显式外置 + sidechain 隔离

Claude Code 的治理方式更直观：

```text
大输出 → tool-results/*.txt
子任务 → subagents/*.jsonl
主会话 → 只拿最终 tool_result / summary
长会话 → compaction / rewind / hooks re-inject
```

优点：

- 人类打开目录就能看出层次。
- 大输出文件非常好定位。
- 子 agent 的生命周期和主会话关系明确。
- 适合做 transcript 可视化、复盘、审计。

缺点：

- 文件系统对象更多。
- 如果子 agent 多，目录会变复杂。
- 大输出虽然外置，但仍可能产生敏感数据落盘风险。
- 如果 preview 不够，模型可能需要二次读取。

### 6.2 Codex：事件流 + truncation + compaction + thread graph

Codex 的治理方式更系统化/运行时化：

```text
每个 agent/thread → 一个 rollout event stream
工具输出 → function_call_output / runtime event
模型上下文 → ContextManager 规范化与截断
多 agent → spawn/wait/close 协同
长会话 → context compaction replacement history
```

优点：

- 很适合并行 agent 与 thread 级 orchestrator。
- 父主 thread 不被子 agent 内部工具噪声污染。
- event stream 可以还原 runtime 细节，如 token_count、exec_command_end、collab events。
- compaction 是在活跃上下文层处理，不依赖目录结构。

缺点：

- 人肉读 JSONL 难度更高。
- 没有目录分层时，必须写解析器按 thread id 重建树。
- 大工具输出如果只靠截断，可能丢掉中间关键信息；最好让命令输出重定向到文件，再让模型按需读取关键片段。
- transcript、history、prompt 三者边界更容易被误解。

---

## 7. “大工具结果”在实际使用中的最佳实践

### 7.1 对 Claude Code

建议：

1. **让大探索任务进 subagent**
   - 比如“读完整代码库并找出测试薄弱点”，不要让主会话直接读所有文件。
   - 主会话只保留结论、路径、证据摘要。

2. **让工具输出天然可分页**
   - 不要 `cat huge.log`。
   - 用 `rg`、`sed -n`、`head/tail`、结构化过滤，避免大输出直接进入 transcript。

3. **对需要长期保留的信息写入项目文件，而不是依赖 transcript**
   - 例如 `docs/investigation-summary.md`、`MEMORY.md`、`CLAUDE.md`。
   - compaction 后再注入更可靠。

4. **用 hooks 或 compact instructions 指定必须保留的信息**
   - 例如修改文件列表、测试命令、未解决 bug、关键约束。
   - Claude 官方也建议可在 compaction 后 re-inject critical context。

### 7.2 对 Codex

建议：

1. **把会制造噪声的任务显式交给 subagents**
   - Codex 官方强调 subagents 需要显式触发。
   - Prompt 要写清楚：spawn 几个、每个负责什么、等待所有结果、返回什么摘要格式。

2. **不要让 shell 工具直接吐海量文本到 stdout**
   - 更好的模式是：

```bash
some_long_command > /tmp/result.log 2>&1
rg "ERROR|FAILED|panic" /tmp/result.log
sed -n '120,220p' /tmp/result.log
```

   - 这样 Codex 不会只拿到被截断的大段输出，而是拿到精确片段。

3. **让 subagent 交付“证据化摘要”**
   - 不要只说“检查完了”。
   - 要求子 agent 返回：结论、关键路径、命令、证据片段、风险、下一步。

4. **长任务主动 compact 或开新 thread**
   - Codex 自动 compaction 可以续航，但多次 compaction 后摘要误差会累积。
   - 如果任务阶段明显切换，开新 thread 并带上 handoff summary 往往更稳。

5. **写一个 rollout 解析器**
   - 对 Codex transcript 分析，最好按 `session_meta.payload.id`、`parent_thread_id`、`spawn_agent`、`wait_agent`、`close_agent` 重建 tree。
   - 不要只按文件名排序，否则你会觉得“没有分层”。

## 8. 两者 transcript 风格的核心差异表

| 维度 | Claude Code | Codex |
|---|---|---|
| 文件形态 | session JSONL + 子目录 | 每个 thread 一个 rollout JSONL |
| 行结构 | message-centric，每行多为 user/assistant/system/attachment | event-centric，顶层 `type` + `payload.type` |
| 工具调用表达 | `tool_use` / `tool_result` block | `function_call` / `function_call_output` / runtime events |
| 运行时元数据 | 顶层 `toolUseResult`、`uuid`、`parentUuid`、`isSidechain` | `event_msg`、`turn_context`、`token_count`、`exec_command_end` |
| 子 agent 存储 | `subagents/agent-*.jsonl` | 独立 `rollout-*.jsonl` |
| 子 agent 关系 | `agentId` + 目录关系 | `parent_thread_id` + spawn/wait/close events |
| 大输出处理 | `tool-results/*.txt` 外置 + JSONL preview/path | 样本中内嵌；模型可见 history 通过 truncation policy 截断；长线程 compaction |
| 主上下文污染控制 | subagent summary + tool-results spill + compaction | subagent thread summary + output truncation + compaction |
| 人类可读性 | 结构直观，目录层次清楚 | 信息丰富但需要解析器 |
| 审计粒度 | 消息链/工具结果清楚 | runtime event 更细，如 token、exec、collab 状态 |

## 9. 回答你的几个具体判断

### 9.1 “Codex 的工具调用和 subagents 都是单独 JSONL 文件吗？”

不完全。

- 工具调用不是单独 JSONL 文件；它们是各自 thread 的 rollout JSONL 里的 `response_item` / `event_msg` 行。
- subagent 在这个样本中确实是独立 rollout JSONL 文件。
- 主 agent 和子 agent 的工具调用分别在各自的 rollout 文件里。

### 9.2 “Codex 还没有分层吗？”

文件系统上：这个样本确实没有像 Claude 那样的 `subagents/` 层级。  
逻辑上：有分层，靠这些字段和事件：

- `session_meta.payload.id`
- `session_meta.payload.source.subagent.thread_spawn.parent_thread_id`
- `depth`
- `agent_nickname`
- `agent_role`
- 主 thread 的 `spawn_agent` / `wait_agent` / `close_agent`
- `collab_agent_spawn_end` / `collab_waiting_end` / `collab_close_end`

### 9.3 “大量工具结果怎么办？压缩了再注入主 transcript 吗？”

最准确答案：

- **Claude Code**：大输出会 spill 到 `tool-results/*.txt`，JSONL/model-visible result 里放 preview/path；子 agent 的内部工具轨迹不进主会话，主会话拿 final result/summary；长会话再 compaction。
- **Codex**：工具输出记录在对应 rollout，但进入模型上下文前会经过 context manager 的截断/规范化；subagent 的内部工具轨迹不直接注入主 thread，主 thread 只通过 `wait_agent` 获得 completed summary/status；长线程触发 compaction 后，活跃 history 被 handoff summary 替换。

所以不是简单的“压缩了再注入主 transcript”。更像：

```text
Claude:
大工具输出 → 外置文件 + preview/path
子 agent 内部噪声 → 子 transcript
主会话 → 子 agent final summary
长上下文 → compaction summary

Codex:
工具输出 → 当前 thread rollout/history
主模型可见 history → truncation/normalization
子 agent 内部噪声 → 子 rollout
主 thread → wait_agent summary/status
长上下文 → compaction replacement history
```

## 10. 如果你要做 transcript 分析器，建议的数据模型

### 10.1 Claude Code 解析模型

建议用这个结构：

```ts
type ClaudeSession = {
  sessionId: string;
  mainJsonl: ClaudeLine[];
  subagents: Record<string, {
    meta: ClaudeSubagentMeta;
    jsonl: ClaudeLine[];
  }>;
  toolResults: Record<string, string>; // tool_use_id -> full text path/content
};
```

解析重点：

- 用 `uuid` / `parentUuid` 建主链。
- 用 `isSidechain` 和 `agentId` 识别 sidechain。
- 用 `tool_use.id` 与 `tool_result.tool_use_id` 配对。
- 用 `persistedOutputPath` 或 `<persisted-output>` 解析外置大输出。
- 用 `toolUseResult` 读取结构化 stdout/stderr/status。

### 10.2 Codex 解析模型

建议用这个结构：

```ts
type CodexThread = {
  threadId: string;
  parentThreadId?: string;
  depth?: number;
  nickname?: string;
  role?: string;
  rolloutPath: string;
  events: CodexLine[];
  calls: Record<string, CodexToolCall>;
  outputs: Record<string, CodexToolOutput>;
  children: string[];
};
```

解析重点：

- 先扫所有 rollout，读取 `session_meta.payload.id`。
- 如果 `session_meta.payload.source.subagent.thread_spawn.parent_thread_id` 存在，则建立 parent-child edge。
- 再扫主 rollout 的 `spawn_agent` / `collab_agent_spawn_end`，补充 nickname、role、prompt。
- 用 `call_id` 配对：
  - `function_call` ↔ `function_call_output`
  - `custom_tool_call` ↔ `custom_tool_call_output`
  - `event_msg.exec_command_end` 作为 runtime evidence。
- `wait_agent` 的 output/status 是父 thread 实际接收到的子 agent 摘要。

### 10.3 Codex parent-child 重建伪代码

```python
threads = {}

for rollout in rollout_files:
    meta = first_line_with_type(rollout, "session_meta")
    tid = meta["payload"]["id"]
    threads[tid] = {"path": rollout, "children": []}

    spawn = meta["payload"].get("source", {}).get("subagent", {}).get("thread_spawn")
    if spawn:
        parent = spawn["parent_thread_id"]
        threads[tid]["parent"] = parent
        threads[tid]["depth"] = spawn.get("depth")
        threads[tid]["nickname"] = spawn.get("agent_nickname")
        threads[tid]["role"] = spawn.get("agent_role")

for tid, t in threads.items():
    parent = t.get("parent")
    if parent in threads:
        threads[parent]["children"].append(tid)
```

## 11. 设计哲学上的差别

### Claude Code 的哲学

Claude Code 的 transcript 更像：

> “把一次主对话作为中心，sidechain 是它的附属；大输出是主对话/sidechain 的附属文件。”

这对人类非常友好，因为目录就是语义。你打开目录就知道哪个是主会话、哪个是子 agent、哪个是工具大输出。

### Codex 的哲学

Codex 的 transcript 更像：

> “每个 agent 都是一个可独立恢复/审计的 thread；父子关系是事件图，不是目录树。”

这对多 agent orchestration 更自然，因为所有 agent 都是 thread，主 agent 只是其中一个 coordinator。代价是人类需要解析器才能把树还原出来。

---

## 12. 结论

最终结论可以压缩成 6 条：

1. **Claude Code 的 transcript 更 message-centric，Codex 更 event-centric。**
2. **Claude 的 subagent 在文件系统上分层，Codex 的 subagent 在 thread graph 上分层。**
3. **Claude 大工具输出在样本中明确 spill 到 `tool-results/*.txt`，JSONL 留 preview/path。**
4. **Codex 样本中工具输出内嵌 rollout，但模型可见上下文由 ContextManager 处理，会截断工具输出，并在长线程时 compaction。**
5. **两者都不应该理解成“主 transcript 永远塞满所有工具结果”。主会话通常只保留必要摘要/结果，尤其是 subagent 场景。**
6. **如果你要复盘或构建工具，Claude 可以按目录树解析；Codex 必须按 `thread_id + parent_thread_id + call_id + collab events` 重建逻辑树。**

## 0. 三份文件的角色关系

三份文件都是 **JSONL**：每一行是一条独立 JSON 记录。所有记录外层都有：

```json

  "timestamp": "...Z",
  "type": "...",
  "payload": { "...": "..." }

```

## 1. 总体结构：JSONL 的四类顶层记录

顶层 `type` 只有四种：

| 顶层路径 | type 值         | 作用                                                         | 是否有 `payload.type` |
| -------- | --------------- | ------------------------------------------------------------ | --------------------- |
| `$.type` | `session_meta`  | 整个 transcript / session 的元数据。包括线程 ID、cwd、来源、模型提供方、base instructions、git 信息；子 agent 文件还会记录父线程 ID、agent 昵称和角色。 | 否                    |
| `$.type` | `turn_context`  | 本轮运行上下文。包括 turn_id、cwd、日期、时区、审批策略、沙箱策略、权限 profile、模型、协作模式、用户/仓库指令、截断策略等。 | 否                    |
| `$.type` | `response_item` | 模型上下文里的“消息/推理/工具调用/工具返回”等条目。它更接近会被放进模型 conversation history 的结构。 | 是                    |
| `$.type` | `event_msg`     | runtime / UI / 执行器侧事件。它记录任务开始结束、用户消息、agent 可见消息、token/rate limit、shell 执行结束、subagent spawn/wait/close、patch 应用结束等。 | 是                    |

| 子 agent A |              1 |              1 |              12 |           8 |
| 子 agent B |              1 |              1 |              12 |           8 |

## 2. 所有不同层次下的 `type` 类型

本节按 JSON 路径分层说明。重点是：同名字段 `type` 在不同路径下语义不同，不能混为一谈。

---

### 2.1 顶层 `$.type`

| `$.type`        | 含义                              | 典型 payload                                                 |
| --------------- | --------------------------------- | ------------------------------------------------------------ |
| `session_meta`  | session / transcript 初始化元数据 | `id`、`timestamp`、`cwd`、`originator`、`cli_version`、`source`、`model_provider`、`base_instructions`、`git`；子 agent 还有 `agent_nickname`、`agent_role` |
| `turn_context`  | 当前 turn 的执行上下文            | `turn_id`、`cwd`、`current_date`、`timezone`、`approval_policy`、`sandbox_policy`、`permission_profile`、`model`、`collaboration_mode`、`user_instructions`、`truncation_policy` |
| `response_item` | 对话/模型项目                     | `payload.type` 可以是 `message`、`reasoning`、`function_call`、`function_call_output`、`custom_tool_call`、`custom_tool_call_output` |
| `event_msg`     | runtime 事件                      | `payload.type` 可以是 `task_started`、`user_message`、`agent_message`、`token_count`、`exec_command_end`、`collab_*`、`patch_apply_end`、`task_complete` 等 |

---

### 2.2 `$.payload.type`：`response_item` 下的类型

当顶层是 `response_item` 时，`payload.type` 表示“模型上下文条目类型”。本组样本里有六种：

| 顶层            | `payload.type`            | 作用                                                    | 核心字段                                  | 备注                                                         |
| --------------- | ------------------------- | ------------------------------------------------------- | ----------------------------------------- | ------------------------------------------------------------ |
| `response_item` | `message`                 | 一条对话消息。可来自 `developer`、`user`、`assistant`。 | `role`、`content`、可选 `phase`           | `content` 是数组，内部还有 `input_text` / `output_text`。assistant 消息常与 `event_msg.agent_message` 成对出现。 |
| `response_item` | `reasoning`               | 模型推理状态记录。                                      | `summary`、`content`、`encrypted_content` | 样本中 `summary` 为空数组，`content` 多为 `null`，真正内容在 `encrypted_content`，不可直接读。 |
| `response_item` | `function_call`           | 模型请求调用普通工具。                                  | `name`、`arguments`、`call_id`            | `arguments` 是 JSON 字符串，不是已展开对象。工具包括 `update_plan`、`spawn_agent`、`shell_command`、`wait_agent`、`close_agent`。 |
| `response_item` | `function_call_output`    | 普通工具调用结果，按 `call_id` 回填。                   | `call_id`、`output`                       | `output` 是字符串。有时是普通文本，有时是 JSON 字符串，例如 `wait_agent` 返回的 `status`。 |
| `response_item` | `custom_tool_call`        | 自定义工具调用。                                        | `status`、`call_id`、`name`、`input`      | 样本中用于 `apply_patch`。`input` 是 patch 原文。            |
| `response_item` | `custom_tool_call_output` | 自定义工具调用结果。                                    | `call_id`、`output`                       | 样本中用于 `apply_patch` 的返回，`output` 是 JSON 字符串，含 `metadata.exit_code`、`duration_seconds`。 |

### 2.3 `$.payload.type`：`event_msg` 下的类型

当顶层是 `event_msg` 时，`payload.type` 表示 runtime 层发生了什么。它不是普通聊天消息，而是执行系统/CLI 的事件日志。

| 顶层        | `payload.type`           | 作用                                                 | 核心字段                                                     | 样本中的位置/特点                                            |
| ----------- | ------------------------ | ---------------------------------------------------- | ------------------------------------------------------------ | ------------------------------------------------------------ |
| `event_msg` | `task_started`           | 一个任务 turn 开始。                                 | `turn_id`、`started_at`、`model_context_window`、`collaboration_mode_kind` | 三个 transcript 各一次。                                     |
| `event_msg` | `user_message`           | runtime 记录用户输入。                               | `message`、`images`、`local_images`、`text_elements`         | 与 `response_item.message role=user` 相关，但不是同一层。    |
| `event_msg` | `token_count`            | token / rate limit 状态。                            | `info`、`rate_limits`                                        | 主 agent 多次出现，子 agent 各 3 次。                        |
| `event_msg` | `agent_message`          | agent 对外可见消息。                                 | `message`、`phase`、`memory_citation`                        | `phase` 可为 `commentary` 或 `final_answer`。通常也会有对应的 `response_item.message role=assistant`。 |
| `event_msg` | `exec_command_end`       | shell 命令执行完成事件。                             | `call_id`、`turn_id`、`command`、`cwd`、`parsed_cmd`、`stdout`、`stderr`、`aggregated_output`、`exit_code`、`duration`、`formatted_output`、`status` | 只在主 agent 文件中出现 6 次；子 agent 的 shell 输出只表现为 `function_call_output`，未出现 `exec_command_end` 事件。 |
| `event_msg` | `collab_agent_spawn_end` | 子 agent 创建完成/进入 pending 状态。                | `call_id`、`sender_thread_id`、`new_thread_id`、`new_agent_nickname`、`new_agent_role`、`prompt`、`model`、`reasoning_effort`、`status` | 主 agent 中出现 2 次，对应两个子 agent。                     |
| `event_msg` | `collab_waiting_end`     | `wait_agent` 等待结束，返回一个或多个子 agent 状态。 | `sender_thread_id`、`call_id`、`agent_statuses`、`statuses`  | 主 agent 中出现 2 次。关键字段是 `status.completed`。        |

#### 3.2.4 `event_msg.agent_message` 与 `response_item.message` 的关系

样本里，assistant 的可见输出通常出现两条：

- `event_msg.agent_message`：runtime / UI 事件，便于界面显示和任务日志记录。

#### 3.2.5 `function_call` / `function_call_output`

普通工具调用使用这对结构：

```json
{

  "name": "shell_command",
  "arguments": "{\"command\":\"...\",\"workdir\":\"...\",\"timeout_ms\":30000}",

```

```json
{
  "type": "function_call_output",
  "call_id": "call_xxx",
  "output": "Exit code: 0\nWall time: ...\nOutput:\n..."
```

注意：

- `arguments` 是 JSON 字符串，需要二次 `json.loads` 才能变成对象。
- `output` 也是字符串，不保证是 JSON。shell 输出是格式化文本；`spawn_agent`、`wait_agent`、`close_agent` 的输出则是 JSON 字符串。
- `call_id` 是请求与结果之间的主键。

#### 3.2.6 `custom_tool_call` / `custom_tool_call_output`

这里 `changes.<file>.type = add` 表示新增文件。

## 5. 子 agent 结果注入主 agent：是否精炼/蒸馏？

这是本次分析的核心结论。

### 5.1 结论

**就这三份文件而言，主 agent 没有收到子 agent 的完整 transcript，也没有收到子 agent 的全部工具调用结果。**

主 agent 收到的是每个子 agent 的最终状态对象，核心字段是：

```json
{
  "completed": "子 agent 的最终回答文本"
}
```

更精确地说：

1. 子 agent 自己运行完整任务，内部有自己的 `session_meta`、`turn_context`、`function_call`、`function_call_output`、`reasoning`、`agent_message`、`task_complete`。
2. 子 agent 结束时，其最终回答出现在子 transcript 的：
   - `event_msg.payload.type = agent_message` 且 `phase = final_answer`
   - `response_item.payload.type = message` 且 `role = assistant`、`phase = final_answer`
   - `event_msg.payload.type = task_complete` 的 `last_agent_message`
3. 主 agent 调用 `wait_agent` 后，runtime 把这个最终回答作为 `status.completed` 返回给主 agent。
4. runtime 还额外生成一条 `response_item.message(role=user)`，内容是 `<subagent_notification>...</subagent_notification>`，其中包了一份同样的 `status.completed`。
5. 主 agent 后续调用 `close_agent` 时，又以 `previous_status.completed` / `status.completed` 的形式重复返回同一最终回答。

因此：

- **不是**“把子 agent 的所有调用结果全部注入主 transcript”。
- **也没有观察到 runtime 在注入边界上再次做独立蒸馏/摘要**。
- ==注入内容与子 agent 的最终回答文本一致；如果这个文本看起来像摘要，那是子 agent 自己最终回答已经总结了它的工作，而不是主 agent transcript 注入时把完整子 transcript 自动压缩成摘要。==
- 从主 agent 视角看，它拿到的是“子 agent 最终状态/最终回答”，不是“子 agent 全量历史”。

### 5.2 注入链路的实际形态

#### 第一步：主 agent 创建子 agent

主 transcript 中先出现：

```json
{
  "type": "function_call",
  "name": "spawn_agent",
  "arguments": "{...}",
  "call_id": "call_xxx"
}
```

runtime 随后记录：

```json
{
  "type": "collab_agent_spawn_end",
  "sender_thread_id": "主线程 ID",
  "new_thread_id": "子线程 ID",
  "new_agent_nickname": "Anscombe 或 Huygens",
  "new_agent_role": "explorer",
  "prompt": "发给子 agent 的任务提示",
  "model": "gpt-5.5",
  "reasoning_effort": "high",
  "status": "pending_init"
}
```

再给模型一个 `function_call_output`：

```json
{
  "type": "function_call_output",
  "call_id": "call_xxx",
  "output": "{\"agent_id\":\"子线程 ID\",\"nickname\":\"...\"}"
}
```

这里主 agent 只知道子 agent 的 ID / 昵称，不知道它内部之后会执行哪些工具。

#### 第二步：主 agent 等待子 agent

主 transcript 中：

```json
{
  "type": "function_call",
  "name": "wait_agent",
  "arguments": "{\"targets\":[\"子线程 ID\"],\"timeout_ms\":120000}",
  "call_id": "call_xxx"
}
```

runtime 产生：

```json
{
  "type": "collab_waiting_end",
  "sender_thread_id": "主线程 ID",
  "call_id": "call_xxx",
  "agent_statuses": [
    {
      "thread_id": "子线程 ID",
      "agent_nickname": "...",
      "agent_role": "explorer",
      "status": {
        "completed": "子 agent 最终回答文本"
      }
    }
  ],
  "statuses": {
    "子线程 ID": {
      "completed": "子 agent 最终回答文本"
    }
  }
}
```

然后返回给模型：

```json
{
  "type": "function_call_output",
  "call_id": "call_xxx",
  "output": "{\"status\":{\"子线程 ID\":{\"completed\":\"子 agent 最终回答文本\"}},\"timed_out\":false}"
}
```

#### 第三步：runtime 注入 `<subagent_notification>`

在 `wait_agent` 返回之后，主 transcript 中出现额外的用户侧消息：

```json
{
  "type": "message",
  "role": "user",
  "content": [
    {
      "type": "input_text",
      "text": "<subagent_notification>\n{\"agent_path\":\"子线程 ID\",\"status\":{\"completed\":\"子 agent 最终回答文本\"}}\n</subagent_notification>"
    }
  ]
}
```

这条非常关键：它说明子 agent 的结果是以“用户侧通知”的形式注入主 agent 的模型上下文。通知里仍然只有 `agent_path` 和 `status.completed`，没有子 agent 的完整工具调用历史。

#### 第四步：关闭子 agent 时重复返回状态

主 agent 后续调用 `close_agent`：

```json
{
  "type": "function_call",
  "name": "close_agent",
  "arguments": "{\"target\":\"子线程 ID\"}",
  "call_id": "call_xxx"
}
```

runtime 记录：

```json
{
  "type": "collab_close_end",
  "receiver_thread_id": "子线程 ID",
  "receiver_agent_nickname": "...",
  "receiver_agent_role": "explorer",
  "status": {
    "completed": "子 agent 最终回答文本"
  }
}
```

并返回：

```json
{
  "type": "function_call_output",
  "call_id": "call_xxx",
  "output": "{\"previous_status\":{\"completed\":\"子 agent 最终回答文本\"}}"
}
```

这仍然是最终状态的重复，不是完整 transcript 注入。

### 5.3 精确比对结果

在这三份样本中，主 agent 中下列位置的文本与子 agent 自己的最终回答完全一致，只是 JSON 字符串层面会有转义差异：

| 子 agent       | 子 transcript 中的最终文本                                   | 主 transcript 中的对应注入位置                               | 是否全文一致 |
| -------------- | ------------------------------------------------------------ | ------------------------------------------------------------ | ------------ |
| A / `Anscombe` | `event_msg.agent_message phase=final_answer`；`task_complete.last_agent_message` | `collab_waiting_end.statuses[agent_id].completed`；`function_call_output.output.status[agent_id].completed`；`<subagent_notification>.status.completed`；`collab_close_end.status.completed`；`close_agent.previous_status.completed` | 是           |
| B / `Huygens`  | `event_msg.agent_message phase=final_answer`；`task_complete.last_agent_message` | 同上                                                         | 是           |

这说明注入边界采用的是 **最终回答 passthrough / 状态传递**，而不是把子 transcript 的所有事件展开进主 transcript。

| 是否收到 `<subagent_notification>`     | 有                                                           | 没有                                                  |
| 是否有 `apply_patch`                   | 有，表现为 `custom_tool_call` + `patch_apply_end`            | 没有                                                  |
| 是否有 `exec_command_end` runtime 事件 | 主样本中有 6 次                                              | 两个子样本中没有；子样本只记录 `function_call_output` |
| 行数                                   | 95                                                           | 各 22                                                 |
| 角色                                   | orchestrator / 汇总者 / 写文件者                             | isolated worker / read-only explorer                  |

## 8. 几个容易误解的结构点

### 8.1 `event_msg` 不是 `response_item`

两者经常成对出现，但用途不同：

| 现象                      | `event_msg`        | `response_item`                                            |
| ------------------------- | ------------------ | ---------------------------------------------------------- |
| assistant 说话            | `agent_message`    | `message role=assistant`                                   |
| shell 工具结束            | `exec_command_end` | `function_call_output`                                     |
| patch 工具结束            | `patch_apply_end`  | `custom_tool_call_output`                                  |
| 子 agent spawn/wait/close | `collab_*_end`     | 对应的 `function_call_output` 或 `<subagent_notification>` |

可以把 `event_msg` 理解为 runtime 日志，把 `response_item` 理解为模型上下文/对话项目。

### 8.2 `function_call.arguments` 和 `function_call_output.output` 常常是“字符串里的 JSON”

例如：

```json
"arguments": "{\"targets\":[\"019...\"],\"timeout_ms\":120000}"
```

这不是对象，而是字符串；要解析内部参数，需要二次解析。

同理：

```json
"output": "{\"status\":{...},\"timed_out\":false}"
```

也是字符串里的 JSON。

### 8.3 `<subagent_notification>` 是注入主 agent 上下文的包装

它出现在：

```text
response_item.payload.type = message
response_item.payload.role = user
content[0].type = input_text
content[0].text = "<subagent_notification> ... </subagent_notification>"
```

这说明子 agent 结果被包装成用户侧输入块提供给主 agent，而不是作为工具原始输出之外的完整 transcript。

### 8.4 子 agent 的最终回答会在多个地方重复

同一段子 agent 最终回答文本，在不同层中反复出现：

- 子 transcript 的 `event_msg.agent_message phase=final_answer`
- 子 transcript 的 `response_item.message role=assistant phase=final_answer`
- 子 transcript 的 `event_msg.task_complete.last_agent_message`
- 主 transcript 的 `collab_waiting_end.status.completed`
- 主 transcript 的 `function_call_output.output.status[agent_id].completed`
- 主 transcript 的 `<subagent_notification>.status.completed`
- 主 transcript 的 `collab_close_end.status.completed`
- 主 transcript 的 `close_agent` 返回 `previous_status.completed`

这是一种状态传播和日志冗余，不代表多个独立结果。

## 9. 可以用于解析这类 transcript 的推荐模型

如果要程序化解析，建议按以下层级建立数据模型：

```text
TranscriptFile
├─ records: TranscriptRecord[]
│  ├─ timestamp
│  ├─ top_type: session_meta | turn_context | response_item | event_msg
│  └─ payload
│     ├─ SessionMetaPayload
│     ├─ TurnContextPayload
│     ├─ ResponseItemPayload
│     │  ├─ MessageItem
│     │  ├─ ReasoningItem
│     │  ├─ FunctionCallItem
│     │  ├─ FunctionCallOutputItem
│     │  ├─ CustomToolCallItem
│     │  └─ CustomToolCallOutputItem
│     └─ EventPayload
│        ├─ TaskStartedEvent
│        ├─ UserMessageEvent
│        ├─ TokenCountEvent
│        ├─ AgentMessageEvent
│        ├─ ExecCommandEndEvent
│        ├─ CollabAgentSpawnEndEvent
│        ├─ CollabWaitingEndEvent
│        ├─ PatchApplyEndEvent
│        ├─ CollabCloseEndEvent
│        └─ TaskCompleteEvent
```

解析子 agent 关系时，建议用：

```text
child.session_meta.payload.source.subagent.thread_spawn.parent_thread_id
    == parent.session_meta.payload.id
```

解析工具调用链时，建议用：

```text
response_item.function_call.call_id
    == response_item.function_call_output.call_id
    == event_msg.exec_command_end.call_id / collab_*_end.call_id / patch_apply_end.call_id
```

解析子 agent 注入时，建议用：

```text
parent response_item.message(role=user)
  content[].text contains <subagent_notification>
    JSON.agent_path = child thread id
    JSON.status.completed = child final answer
```

## 10. 最终回答用户关心的三个问题

### 问题 1：所有不同层次下的 `type` 类型有什么作用？

完整列表如下：

| 层级路径                                                     | type 值                                                      |
| ------------------------------------------------------------ | ------------------------------------------------------------ |
| `$.type`                                                     | `session_meta`、`turn_context`、`response_item`、`event_msg` |
| `$.payload.type` under `response_item`                       | `message`、`reasoning`、`function_call`、`function_call_output`、`custom_tool_call`、`custom_tool_call_output` |
| `$.payload.type` under `event_msg`                           | `task_started`、`user_message`、`token_count`、`agent_message`、`exec_command_end`、`collab_agent_spawn_end`、`collab_waiting_end`、`patch_apply_end`、`collab_close_end`、`task_complete` |
| `$.payload.content[].type`                                   | `input_text`、`output_text`                                  |
| `$.payload.sandbox_policy.type`                              | `workspace-write`                                            |
| `$.payload.permission_profile.type`                          | `managed`                                                    |
| `$.payload.permission_profile.file_system.type`              | `restricted`                                                 |
| `$.payload.permission_profile.file_system.entries[].path.type` | `special`、`path`                                            |
| `$.payload.parsed_cmd[].type`                                | `unknown`                                                    |
| `$.payload.changes.<file>.type`                              | `add`                                                        |

详细作用已在第 2 节逐项解释。

### 问题 2：子 agent 结果注入主 agent 时，是否经过精炼/蒸馏，还是全部注入？

结论：**没有把子 agent 的完整 transcript / 全部工具调用结果注入主 agent。**

主 agent 收到的是子 agent 的最终状态文本 `status.completed`。该文本与子 agent 自己的最终回答一致。换句话说：

- 子 agent 内部工具调用结果保留在子 agent 自己的 transcript 中。
- 主 agent transcript 中只出现子 agent 的最终回答文本。
- 没有观察到 runtime 在注入时再次自动摘要完整子 transcript。
- 但从数据量角度看，它确实是“只注入最终结果”，不是“全量历史注入”。

### 问题 3：transcript JSONL 的结构框架包含哪些内容？

结构框架可以概括为：

```text
JSONL file
└─ line records
   ├─ timestamp
   ├─ type
   │  ├─ session_meta      # 文件/session 元数据
   │  ├─ turn_context      # 本轮上下文、沙箱、权限、模型、仓库指令
   │  ├─ response_item     # 模型上下文条目：消息、推理、工具调用、工具结果
   │  └─ event_msg         # runtime 事件：任务、用户消息、agent 消息、token、shell、patch、协作 agent
   └─ payload
      ├─ message/content/role/phase
      ├─ reasoning/encrypted_content
      ├─ function_call/name/arguments/call_id
      ├─ function_call_output/call_id/output
      ├─ custom_tool_call/input
      ├─ custom_tool_call_output/output
      ├─ task_started/task_complete
      ├─ token_count/rate_limits
      ├─ exec_command_end/stdout/stderr/exit_code/status
      ├─ collab_agent_spawn_end/new_thread_id/prompt/status
      ├─ collab_waiting_end/statuses/status.completed
      ├─ collab_close_end/status.completed
      └─ patch_apply_end/changes
```

最重要的设计点是：**一份 transcript 同时记录“模型看到/产生的 response item”和“runtime 执行层 event message”。两者交织在同一个 JSONL 文件里，通过 `timestamp`、顺序和 `call_id` 关联。**
