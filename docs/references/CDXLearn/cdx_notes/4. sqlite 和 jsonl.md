我会先区分两类来源：**OpenAI 官方文档/源码**和**社区讨论/代码阅读**。重点不是泛泛介绍 SQLite，而是解释 Codex 里“会话记录、SQLite 索引/日志、持久化记忆文件”在运行时各自承担什么角色。

目前看到一个关键点：**OpenAI 官方文档明确承认 `~/.codex`、`history.jsonl`、`~/.codex/memories/`、`AGENTS.md` 的机制**，但没有把 `state_5.sqlite / logs_2.sqlite / session_index.jsonl / rollout JSONL` 的内部 schema 当作稳定公开 API 来文档化。所以我会把“官方确定”和“社区/issue 反推”分开讲。

Thought for 51s

下面是我刚刚实时查到后整理出的结论。**核心判断：Codex 现在不是“只靠模型记忆上下文”，而是用了多层本地状态系统：JSONL 保存真实会话流，SQLite 保存结构化索引/日志/状态，`AGENTS.md` 和 `~/.codex/memories/` 才是更接近“持久化记忆”的东西。**

------

# 1. 先给结论：Codex 的本地持久化大概分 4 层

| 层级                  | 典型文件                                | 作用                                                         | 是否是真正“记忆”            |
| --------------------- | --------------------------------------- | ------------------------------------------------------------ | --------------------------- |
| **会话原始记录层**    | `~/.codex/sessions/.../rollout-*.jsonl` | 保存一条线程的真实事件流：用户消息、模型回复、工具调用、状态事件等 | 不是智能记忆，是 transcript |
| **会话索引/元数据层** | `state_5.sqlite`、`session_index.jsonl` | 记录 thread id、标题、cwd、是否归档、rollout 路径、更新时间等，用于 sidebar / resume / project grouping | 不是记忆，是索引数据库      |
| **诊断日志层**        | `logs_2.sqlite`、`logs_2.sqlite-wal`    | 保存 app-server / 网络 / streaming / tool / debug 日志       | 不是记忆，通常不是会话内容  |
| **持久化记忆层**      | `AGENTS.md`、`~/.codex/memories/`       | 给未来 session 注入稳定规则、项目约定、偏好、历史总结        | 这是更接近“memory”的部分    |

OpenAI 官方文档明确说，Codex 的本地状态默认放在 `CODEX_HOME`，也就是通常的 `~/.codex`，里面常见 `config.toml`、`auth.json`、`history.jsonl`、日志和缓存等文件；同时官方 troubleshooting 文档也明确说，session transcripts 在 `$CODEX_HOME/sessions`，归档会话在 `$CODEX_HOME/archived_sessions`。

------

# 2. `sessions/rollout-*.jsonl`：它更像“真实会话录像带”

`rollout-*.jsonl` 是最关键的原始会话 payload。社区 issue 里多次提到：即使 SQLite 里有 metadata，Codex Desktop/CLI 通常仍然需要 `threads.rollout_path` 指向的 JSONL 文件，才能真正恢复和渲染会话。一个 Reddit 复盘也提到：如果 SQLite metadata 还在，但 backing transcript 文件不在预期的 `~/.codex/sessions/...` 路径下，UI 仍然可能什么都显示不出来。这个说法不是官方 schema 文档，但和多个 GitHub issue 的本地排查结论一致。

可以这样理解：

```
rollout JSONL = 真正的聊天/工具执行事件流
state_5.sqlite = 这条会话在哪里、叫什么、属于哪个项目、是否归档
session_index.jsonl = 这条会话的人类可读名称/快速 resume 名称
```

所以：**如果只有 SQLite，没有 rollout JSONL，通常不能完整恢复会话；如果只有 rollout JSONL，没有索引，理论上数据还在，但 UI / resume 可能找不到。**

------

# 3. `state_5.sqlite`：不是“语义记忆库”，而是会话元数据库

目前官方没有公开完整 `state_5.sqlite` schema 作为稳定 API。但从多个 GitHub issue 的本地排查看，`state_5.sqlite` 里至少会存 thread 级 metadata，例如：

| 字段/概念            | 作用                                              |
| -------------------- | ------------------------------------------------- |
| `id` / thread id     | 唯一线程 ID                                       |
| `title`              | 线程标题                                          |
| `cwd`                | 当前项目/工作目录，用于按项目分组                 |
| `rollout_path`       | 指向真实 transcript JSONL                         |
| `archived`           | 是否归档                                          |
| `source`             | 来源，例如 CLI / VS Code / Desktop                |
| `updated_at`         | 更新时间，用于排序                                |
| `thread_spawn_edges` | 父子 agent / subagent 关系，社区 issue 中多次提到 |

一个近期 GitHub issue 直接描述：本地 `threads` 表里有 recent user-facing thread，`rollout_path` 指向存在的 `~/.codex/sessions/.../rollout-*.jsonl`，但 `session_index.jsonl` 没同步，导致历史列表缺失；预期行为是 `session_index.jsonl`、`state_5.sqlite` 和 rollout JSONL 应该保持一致。

所以 `state_5.sqlite` 的本质是：

> **Codex 的本地会话状态表 / sidebar 索引表 / resume 元数据表，不是向量数据库，也不是让模型直接“理解历史”的长期记忆。**

------

# 4. `session_index.jsonl`：小但很关键，像“线程名字索引”

`session_index.jsonl` 看起来很小，但它经常决定 `codex resume --all` 显示什么名字，以及 `codex resume "<thread_name>"` 能不能通过名字找到对应会话。

社区 issue 里有一个非常典型的现象：`state_5.sqlite` 的 `threads.title` 和 `session_index.jsonl` 的 `thread_name` 可能不同步；有用户发现修改 SQLite title 不一定影响 picker，但更新 `session_index.jsonl` 里的 `thread_name` 后，picker 和 name-based resume 才正常。另一个 issue 直接指出 `/rename` 更新了 `session_index.jsonl`，但没有同步更新 SQLite 的 `threads.title`，导致“append-only session index”和 SQLite metadata 出现 split-brain。

所以它大概承担这个角色：

```
thread id  →  human-readable thread_name  →  resume / picker display
```

这也是为什么你看到 Codex 本地状态不像 Claude 那种单一 transcript，而是多个文件配合。

------

# 5. `logs_2.sqlite`：更像结构化运行日志，不是会话正文库

`logs_2.sqlite` 经常被误解成“保存所有聊天内容的数据库”。但从近期 GitHub issue 看，它更像 **app-server / extension 的结构化诊断日志库**。有 issue 报告 streaming 时 `app-server` 会持续写入 `~/.codex/logs_2.sqlite-wal`，并且里面有 TRACE / INFO / DEBUG / WARN 等日志级别；该 issue 的 workaround 还明确说 `logs_2.sqlite` 只包含 internal diagnostic logs，丢失它通常不等于丢失 conversation history。

它可能记录：

| 内容                     | 例子                                           |
| ------------------------ | ---------------------------------------------- |
| 网络/streaming 日志      | websocket、responses API、连接池事件           |
| app-server 状态          | thread/start、thread/resume、shutdown、archive |
| memory 后台任务          | 是否触发 memory extraction / consolidation     |
| token / request 相关诊断 | 模型请求、cwd、时间段等                        |

有一个 2026 年 4 月 issue 还显示，用户在 `logs_2.sqlite` 里查到了 background memory subsystem 的模型请求，`cwd` 是 `~/.codex/memories`，说明 memory 生成可能会在后台跑模型调用。

------

# 6. `*-wal` 和 `*-shm`：这是 SQLite WAL 模式，不是 Codex 独有设计

你看到的：

```
state_5.sqlite-wal
state_5.sqlite-shm
logs_2.sqlite-wal
logs_2.sqlite-shm
```

这是 SQLite 的 Write-Ahead Logging 机制。

SQLite 官方解释：WAL 文件用于实现 atomic commit 和 rollback；它和主数据库在同一目录，名字是在数据库文件后加 `-wal`。如果最后一个连接没有干净关闭，WAL 文件可能继续留在磁盘上，下次打开数据库时再清理。`-shm` 是 WAL 模式下多个连接共享的 memory index 文件，用于协调并快速定位 WAL frames；它不包含持久数据库内容。

所以：

| 文件           | 作用                                 | 能不能删                           |
| -------------- | ------------------------------------ | ---------------------------------- |
| `*.sqlite`     | 主数据库                             | 不能随便删                         |
| `*.sqlite-wal` | 最近还没 checkpoint 回主库的事务记录 | 不建议手删，尤其 Codex 正在运行时  |
| `*.sqlite-shm` | WAL 共享内存索引                     | 不包含核心数据，但不建议运行中手删 |
| checkpoint 后  | WAL 内容合并回主库                   | 干净关闭后可能自动消失             |

这就是你之前问的 `logs_2.sqlite-wal = 最近未合并写入内容`、`logs_2.sqlite-shm = WAL 临时共享内存索引` 的根本原因。

------

# 7. `history.jsonl`：它不是新 Desktop sidebar 的唯一来源

官方 Advanced Config 文档说，Codex 默认会把本地 history 写到 `CODEX_HOME`，例如 `~/.codex/history.jsonl`；也可以通过 `[history] persistence = "none"` 禁用，或者用 `history.max_bytes` 限制大小，超限后会丢弃最旧条目并压缩文件。

但结合官方 troubleshooting 和社区 issue，目前更合理的理解是：

```
history.jsonl
= CLI / local history persistence 的一部分
≠ Desktop/VS Code 所有线程恢复的唯一真实来源
```

因为官方同时明确说 session transcripts 在 `$CODEX_HOME/sessions`，而 GitHub issue 里也反复出现：能否恢复一条会话，通常要同时看：

```
~/.codex/state_5.sqlite
~/.codex/session_index.jsonl
~/.codex/sessions/.../rollout-*.jsonl
```

------

# 8. `AGENTS.md`：这是确定性“项目长期规则”，比 memories 更可靠

OpenAI 官方明确说，Codex 会在开始工作前读取 `AGENTS.md`。它会构建 instruction chain：先读 global scope，即 `~/.codex/AGENTS.override.md` 或 `~/.codex/AGENTS.md`；再从项目根目录一路走到当前工作目录，每层读取 `AGENTS.override.md`、`AGENTS.md` 或 fallback 文件。

所以 `AGENTS.md` 的角色是：

```
稳定、显式、可版本控制的项目规则
```

比如：

```
# Repository Guidelines

- Always run npm test after modifying frontend files.
- Prefer pnpm.
- Do not change database migrations without confirmation.
```

它和 `memories/` 的区别是：

| 项目           | `AGENTS.md`          | `~/.codex/memories/`           |
| -------------- | -------------------- | ------------------------------ |
| 谁写           | 人写/团队写          | Codex 后台生成                 |
| 稳定性         | 高                   | 中等，可能延迟、可能总结不完整 |
| 是否适合强规则 | 适合                 | 不适合作唯一规则来源           |
| 是否可进入 Git | 项目级可进入 Git     | 通常不要手工依赖/共享          |
| 作用           | 每次启动注入明确指导 | 从历史 thread 提取可复用上下文 |

------

# 9. `~/.codex/memories/`：这才是官方意义上的“持久化记忆文件”

OpenAI 官方 Memories 文档说，Memories 默认关闭；启用后，Codex 可以把之前 eligible prior threads 里的有用上下文转成本地 memory files。Codex 会跳过 active 或 short-lived sessions，会对生成的 memory 字段做 secret redaction，并且不是每个 thread 结束立刻更新，而是在 thread idle 一段时间后后台更新。官方还说主 memory files 位于 `~/.codex/memories/`，包括 summaries、durable entries、recent inputs 和 supporting evidence；这些文件应被视为 generated state，不建议把手工编辑它们作为主要控制方式。

也就是说，memory 生成流程大概是：

```
历史 thread / rollout JSONL
        ↓
后台 memory extraction model
        ↓
~/.codex/memories/ 下的 summaries / durable entries / evidence
        ↓
未来新 session 启动时，根据配置决定是否注入
```

相关配置包括：

```
[features]
memories = true

[memories]
generate_memories = true   # 是否允许从新 thread 生成记忆
use_memories = true        # 是否在未来 thread 使用已有记忆
```

官方配置引用中也列出了 `memories.generate_memories`、`memories.use_memories`、`memories.disable_on_external_context`、`memories.extract_model`、`memories.consolidation_model` 等键。

# 10. 为什么 Codex 要用 SQLite，而不是只靠 JSONL 或模型自己检索？

我的判断是：**SQLite 不是为了让模型“语义理解历史”，而是为了让客户端、CLI、Desktop、VS Code extension 可以稳定、快速、事务化地管理本地状态。**

## 10.1 JSONL 适合保存事件流，但不适合做复杂状态查询

JSONL 很适合：

```
一行一个事件
追加写入
崩溃后容易恢复
保留完整 transcript
```

但它不适合：

```
按 cwd 查所有线程
按 updated_at 排序
过滤 archived = 0
通过 thread_id 快速找到 rollout_path
维护 parent-child subagent 关系
按账号 / provider / source 分组
```

这些更适合 SQLite。

## 10.2 SQLite 适合保存“当前状态”和索引

例如：

```
select id, title, cwd, rollout_path, updated_at
from threads
where archived = 0
order by updated_at desc;
```

这类需求如果靠扫描几百个甚至几千个 JSONL 文件，会很慢。事实上，有 GitHub issue 报告 `codex resume` 在很多本地 sessions 下会变慢；该 issue 的 source inspection 认为 picker 仍会 stat 很多 rollout 文件并读取 heads，即使 SQLite DB 存在。

这说明 Codex 当前实现可能还没有完全把所有 resume/list 都优化成纯 SQLite 查询，但设计方向上 SQLite 仍然是更适合做 metadata/index 的。

## 10.3 模型不能当“状态数据库”

模型可以理解历史，但不能负责：

```
保证 thread id 唯一
保证 rename 和 archive 事务一致
保证 power loss 后恢复
保证 sidebar 排序稳定
保证不重复显示同一 session
保证跨进程并发读写安全
```

这些是数据库/文件系统该做的事情，不是 LLM 该做的事情。

# 11. 为什么会出现“SQLite 有、JSONL 有，但 UI 还是不显示”？

因为 Codex 现在看起来有多个状态来源，且不同入口可能读不同组合：

```
Desktop sidebar
CLI resume
VS Code task picker
Cloud-synced Desktop history
Local-only threads
```

社区 issue 里反复出现的问题包括：

| 问题                                                     | 可能原因                                           |
| -------------------------------------------------------- | -------------------------------------------------- |
| session 存在但 sidebar 不显示                            | UI thread listing / grouping / project binding bug |
| `state_5.sqlite` 有 row，但 `session_index.jsonl` 没同步 | index stale                                        |
| `session_index.jsonl` 有名字，但 SQLite title 旧         | rename split-brain                                 |
| `rollout_path` 指向的 JSONL 不存在                       | metadata 有，但正文 payload 缺                     |
| Windows 路径被改成 `\\?\...`                             | cwd/path normalization 导致项目分组分裂            |
| Desktop 新版 cloud sync 不认本地手工 SQLite patch        | 本地 cache 不是 account-owned cloud thread         |

OpenAI Community 上一个 2026 年 4 月 27 日帖子提到，新 Codex Desktop app 似乎使用 cloud-synced thread history 给 Desktop sidebar 做历史，并用本地 SQLite `orbit.db` 做缓存；手工往 `orbit.db` 注入记录并不能创建合法的 account-owned cloud thread id，sync layer 可能会清除或拒绝这些记录。这个是用户观察，不是官方承诺，但对解释“为什么手工改 SQLite 不一定生效”很有价值。

# 12. 一句话理解 Codex 的完整运行链路

你可以把 Codex 的本地持久化理解成下面这条链：

```
用户打开 Codex / CLI / VS Code
        ↓
读取 ~/.codex/config.toml、auth、AGENTS.md
        ↓
如果开启 memories，读取 ~/.codex/memories/
        ↓
创建或恢复 thread
        ↓
state_5.sqlite 写 thread 元数据
        ↓
session_index.jsonl 写 thread name / resume index
        ↓
sessions/.../rollout-*.jsonl 追加真实会话事件
        ↓
logs_2.sqlite 记录 app-server / streaming / tool / memory 诊断日志
        ↓
SQLite WAL 暂存事务，checkpoint 后合并进主 DB
```

# 13. 对你最重要的实践建议

## 备份时，不要只备份一个 SQLite

至少备份：

```
~/.codex/config.toml
~/.codex/auth.json              # 注意敏感
~/.codex/state_5.sqlite*
~/.codex/logs_2.sqlite*
~/.codex/session_index.jsonl
~/.codex/sessions/
~/.codex/archived_sessions/
~/.codex/memories/
~/.codex/AGENTS.md
```

其中最重要的是：

```
sessions/ + state_5.sqlite + session_index.jsonl
```

## 不要在 Codex 运行时手工改 SQLite

因为 WAL 模式下，真正的新写入可能还在：

```
state_5.sqlite-wal
logs_2.sqlite-wal
```

直接改主 DB，可能和 WAL 中未 checkpoint 的内容冲突。

## 真正想让 Codex “长期记住规则”，优先写 `AGENTS.md`

`memories/` 是辅助回忆层，不适合作唯一规则来源。官方也明确建议 required team guidance 应该放在 `AGENTS.md` 或 checked-in documentation，而不是只依赖 memories。

# 最核心的回答

**Codex 的 SQLite 不是“模型记忆库”，而是本地状态数据库。**

**Codex 的持久化记忆分两种：**

1. **显式记忆**：`AGENTS.md`
    你写什么，它稳定注入什么，最可靠。
2. **生成式记忆**：`~/.codex/memories/`
    Codex 从历史 thread 中后台总结出来，未来可能注入，但不是强规则来源。

**而 `state_5.sqlite + session_index.jsonl + sessions/rollout JSONL` 是“会话恢复系统”，不是 memory 系统。**
 它们解决的是：这条会话是谁、在哪里、叫什么、属于哪个项目、如何恢复、正文文件在哪。
