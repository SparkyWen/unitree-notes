## 0. 先给结论：Codex 的多 agent 通信不是 Claude Code 的同构系统

Codex 和 Claude Code 都有“多 agent”能力，但它们的实现中心完全不同：

```text
Claude Code 多 agent 核心：
  Tool 调度 + Task 对象 + Mailbox 文件/队列 + Swarm backend + Remote bridge

Codex CLI / codex-rs 多 agent 核心：
  Thread / Session + Submission Queue / Event Queue + AgentControl + AgentRegistry
  + Op::InterAgentCommunication + in-memory Mailbox + Rollout/StateDB 持久化

OpenAI Agents SDK 多 agent 核心：
  Runner loop + Handoffs + Agent.as_tool() + Session/Conversation state
```

也就是说：

> **Codex CLI 的多 agent 本质是“多个 CodexThread / Session 之间通过 Op 队列、AgentControl 控制面、AgentPath/ThreadId 寻址、Mailbox 投递、状态 watch 与 rollout 持久化连接起来”。**

而 OpenAI Agents SDK 的多 agent 不是一个后台 thread / mailbox swarm 系统，而是一个应用层编排 SDK：

> **Agents SDK 的多 agent 本质是“同一个 Runner loop 中的 agent 切换（handoff）或把 agent 包装成 tool 的嵌套调用”。**

OpenAI 的基础 `openai-python` / `openai-node` SDK 是 REST / Responses / Realtime API 客户端，不是多 agent 编排框架；多 agent 编排主要在 OpenAI Agents SDK 和 Codex CLI / Codex App 产品层实现。OpenAI Python SDK README 将其描述为 OpenAI REST API 的库，Node SDK README 也描述为 OpenAI REST API 的 JS/TS 库。citeturn811058search2 citeturn811058search0

## 2. 总体层次图：Codex 多 agent 的 7 层

Codex 的多 agent 机制不像你给的 Claude 示例那样天然分成“Tool / Task / Swarm / Bridge”四层；Codex 更像是：

> **每个 agent = 一个 Codex thread/session；
>  多 agent 通信 = model-visible tools → AgentControl → ThreadManager/SQ → per-session mailbox/status → rollout/SQLite 持久化。**

## 3. Codex 的核心通信不是“agent 调 agent 函数”，而是“线程会话之间送 Op”

### 3.1 Protocol Queue：Submission Queue / Event Queue

Codex 的高层接口是一个 queue pair：

```text
Client / TUI / App
    │
    │  Submission { id, op, trace }
    ▼
Submission Queue / tx_sub
    │
    ▼
Session submission_loop
    │
    ├── Op::UserInput
    ├── Op::UserTurn
    ├── Op::InterAgentCommunication
    ├── Op::Interrupt
    ├── Op::ExecApproval
    ├── Op::RequestPermissionsResponse
    ├── Op::DynamicToolResponse
    ├── Op::Review
    └── Op::Shutdown
    │
    ▼
Agent turn / tool execution / model call
    │
    ▼
Event Queue / rx_event
    │
    ├── EventMsg::AgentMessage
    ├── EventMsg::ItemStarted / ItemCompleted
    ├── EventMsg::ExecCommandBegin / End
    ├── EventMsg::CollabAgentSpawnBegin / End
    ├── EventMsg::CollabAgentInteractionBegin / End
    ├── EventMsg::CollabWaitingBegin / End
    ├── EventMsg::CollabCloseBegin / End
    ├── EventMsg::CollabResumeBegin / End
    └── EventMsg::TurnComplete / Error / Warning
    │
    ▼
Client / TUI / App
```

`Codex` struct 内部持有：

```rust
pub struct Codex {
    pub(crate) tx_sub: Sender<Submission>,
    pub(crate) rx_event: Receiver<Event>,
    pub(crate) agent_status: watch::Receiver<AgentStatus>,
    pub(crate) session: Arc<Session>,
    pub(crate) session_loop_termination: SessionLoopTermination,
}
```

`Codex::spawn()` 创建 bounded submission channel、unbounded event channel、Session、status watch，然后 `tokio::spawn` 一个 `submission_loop`。这意味着每个 Codex thread/session 都有自己的输入队列、输出事件队列和状态 watch。fileciteturn34file0

### 3.2 Op 是 Codex agent 的“控制消息总线”

在多 agent 场景里最关键的 Op 有两类：

```rust
Op::UserInput { items, ... }
Op::InterAgentCommunication { communication }
```

`InterAgentCommunication` 的结构是：

```rust
pub struct InterAgentCommunication {
    pub author: AgentPath,
    pub recipient: AgentPath,
    pub other_recipients: Vec<AgentPath>,
    pub content: String,
    pub trigger_turn: bool,
}
```

其中：

- `author`：发送者 agent path。
- `recipient`：接收者 agent path。
- `content`：消息内容。
- `trigger_turn`：是否立即唤醒目标 agent 开始一个 turn。

这就是 Codex V2 多 agent 消息和任务分派的核心数据结构。fileciteturn6file0

## 4. AgentControl：Codex 多 agent 的控制面

`AgentControl` 是 Codex 多 agent 里最关键的对象。源码注释明确说：

- `AgentControl` 被每个 Session 持有。
- 它提供 spawn 新 agent 和 inter-agent communication 的能力。
- 一个 root thread/session tree 中最多创建一次。
- 同一个 `AgentControl` 会被传给从 root 派生出的所有 sub-agent。
- registry 作用域是 root thread，而不是整个 ThreadManager。fileciteturn17file0

可以把它理解成 Codex 多 agent 的“共享控制平面”：

```text
Root Session
  └── SessionServices.agent_control: AgentControl
          │
          ├── AgentRegistry        记录 live agents / paths / nicknames / limits
          ├── Weak<ThreadManager>  创建/查找/移除 CodexThread
          ├── spawn_agent_*        创建子 agent thread
          ├── send_input           向目标 thread 送 Op::UserInput
          ├── send_inter_agent_communication
          ├── interrupt_agent
          ├── close_agent
          ├── resume_agent_from_rollout
          └── subscribe_status

Child Session A
  └── 共享同一个 AgentControl

Child Session B
  └── 共享同一个 AgentControl
```

### 4.1 AgentControl 不是业务 agent，而是控制面句柄

`AgentControl` 不直接执行模型推理；它做的是：

1. 根据配置创建新的 CodexThread / Session。
2. 注册 agent metadata。
3. 维护 agent tree。
4. 将输入操作送到目标 thread 的 submission queue。
5. 订阅目标状态。
6. 关闭 / 恢复 agent。
7. 处理 forked context 与 rollout 恢复。

核心方法索引：

| 方法 | 作用 |
|---|---|
| `spawn_agent_with_metadata()` | 创建 agent thread 并返回 `LiveAgent` |
| `spawn_agent_internal()` | 真实 spawn 实现 |
| `spawn_forked_thread()` | 基于父 rollout fork 子 thread |
| `send_input()` | 对目标 agent 发送 `Op::UserInput` 或其他 Op |
| `send_inter_agent_communication()` | 对目标 agent 发送 `Op::InterAgentCommunication` |
| `interrupt_agent()` | 发送 `Op::Interrupt` |
| `close_agent()` | 关闭 agent 及 live descendants |
| `shutdown_live_agent()` | 关闭单个 live agent |
| `resume_agent_from_rollout()` | 从 rollout 恢复 agent 及 open descendants |
| `subscribe_status()` | 订阅目标 agent 的 `AgentStatus` watch |
| `list_agents()` | 列 live agent tree |
| `resolve_agent_reference()` | 把 AgentPath reference 解析成 ThreadId |

这些方法都在 `codex-rs/core/src/agent/control.rs`。fileciteturn17file0

## 5. AgentRegistry：多 agent 的寻址、命名和限制

Codex 不只用 UUID / ThreadId；V2 增加了更像路径树的 `AgentPath`。

`AgentRegistry` 管理：

```rust
struct ActiveAgents {
    agent_tree: HashMap<String, AgentMetadata>,
    used_agent_nicknames: HashSet<String>,
    nickname_reset_count: usize,
}

pub(crate) struct AgentMetadata {
    pub(crate) agent_id: Option<ThreadId>,
    pub(crate) agent_path: Option<AgentPath>,
    pub(crate) agent_nickname: Option<String>,
    pub(crate) agent_role: Option<String>,
    pub(crate) last_task_message: Option<String>,
}
```

它解决的问题：

1. **限制数量**：`reserve_spawn_slot(max_threads)` 控制一个 session tree 中最多能 spawn 多少 sub-agents。
2. **限制深度**：`next_thread_spawn_depth()` / `exceeds_thread_spawn_depth_limit()` 防止无限嵌套 spawn。
3. **路径寻址**：`agent_id_for_path()`、`resolve_agent_reference()` 让 `target` 可以不是裸 ThreadId，而是相对/绝对 AgentPath。
4. **nickname 分配**：从 `agent_names.txt` 或 role 配置中挑昵称，避免 UI 上全是 UUID。
5. **last task message**：记录最近任务摘要，供 `list_agents` 展示。

`AgentRegistry` 源码明确说它用于限制 Codex 多 agent 能力，目前限制每个用户 session 的 sub-agent / thread 总数，而且它被同一 user session 中所有 agents 共享，因为 `AgentControl` 是共享的。fileciteturn31file0

### 6.1 V1 spawn_agent 全流程

源码路径：

```text
codex-rs/core/src/tools/handlers/multi_agents/spawn.rs
```

流程图：

```text
Model calls spawn_agent
    │
    ▼
SpawnAgentHandler.handle()
    │
    ├── parse arguments
    │   ├── message / items
    │   ├── agent_type
    │   ├── model
    │   ├── reasoning_effort
    │   └── fork_context
    │
    ├── parse_collab_input()
    │   └── message/items → Op::UserInput
    │
    ├── child_depth = next_thread_spawn_depth(parent_session_source)
    │   └── exceeds_thread_spawn_depth_limit ? error
    │
    ├── send EventMsg::CollabAgentSpawnBegin
    │
    ├── build_agent_spawn_config(parent base instructions, turn)
    │   ├── clone effective parent config
    │   ├── set model/provider/reasoning/developer instructions
    │   ├── apply approval policy
    │   ├── apply sandbox / cwd
    │   └── apply permission profile
    │
    ├── if fork_context:
    │   ├── reject agent_type/model/reasoning overrides
    │   └── SpawnAgentForkMode::FullHistory
    │
    ├── else:
    │   ├── apply requested model override
    │   └── apply role config
    │
    ├── session.services.agent_control.spawn_agent_with_metadata(...)
    │   ├── config
    │   ├── initial Op
    │   ├── SessionSource::SubAgent(ThreadSpawn)
    │   └── SpawnAgentOptions { fork_mode, environments }
    │
    ├── fetch child config snapshot / nickname / role / status
    │
    ├── send EventMsg::CollabAgentSpawnEnd
    │
    └── return { agent_id, nickname }
```

V1 spawn 的返回值主要是 `agent_id`，也就是 `ThreadId` 字符串。fileciteturn10file0

### 6.2 V1 send_input：按 ThreadId 发输入

源码路径：

```text
codex-rs/core/src/tools/handlers/multi_agents/send_input.rs
```

流程：

```text
Model calls send_input(target, message/items, interrupt?)
    │
    ├── parse target → ThreadId
    ├── parse message/items → Op::UserInput
    ├── if interrupt: agent_control.interrupt_agent(target)
    ├── emit CollabAgentInteractionBegin
    ├── agent_control.send_input(target, Op::UserInput)
    ├── status = agent_control.get_status(target)
    ├── emit CollabAgentInteractionEnd
    └── return { submission_id }
```

这个版本是“直接给目标 thread 的 submission queue 追加输入”，不是 mailbox 语义。fileciteturn11file0

### 6.3 V1 wait_agent：等目标 agent 进入 final status

源码路径：

```text
codex-rs/core/src/tools/handlers/multi_agents/wait.rs
```

流程：

```text
Model calls wait_agent(targets, timeout_ms)
    │
    ├── parse targets → Vec<ThreadId>
    ├── timeout clamp(min, max)
    ├── emit CollabWaitingBegin
    ├── for each target:
    │      agent_control.subscribe_status(target)
    │      └── watch::Receiver<AgentStatus>
```

## 9. Full-history fork：Codex 如何复制父上下文

Codex 子 agent 的 fork 不等于把父对象引用传给子 agent。源码里是通过父 thread 的 rollout 文件 materialize / flush 后，读取 rollout item，再筛选可保留项，最后 fork 新 thread。

关键路径：

```text
codex-rs/core/src/agent/control.rs
```

关键函数：

```rust
spawn_forked_thread()
keep_forked_rollout_item()
```

`keep_forked_rollout_item()` 的过滤规则很重要：

| Rollout item 类型 | fork 是否保留 |
|---|---:|
| system message | 是 |
| developer message | 是 |
| user message | 是 |
| assistant final answer | 是 |
| reasoning | 否 |
| local shell call | 否 |
| function call | 否 |
| tool search call | 否 |
| function/tool output | 否 |
| custom tool call/output | 否 |
| web search / image generation / compaction call | 否 |
| turn context | 否 |
| compacted / event / session meta | 是 |

这说明 Codex 的 fork 不是“复制完整低层 tool trace”，而是复制对模型有意义的会话历史，尤其会剔除工具调用细节和 runtime turn context，让 child 重新建立自己的运行环境。fileciteturn17file0

### 9.1 FullHistory fork 的特殊限制

错误提示含义是：full-history forked agents 会继承 parent agent type、model、reasoning effort；如果想改 role/model/reasoning，就不要 full-history fork。fileciteturn9file0 fileciteturn20file0

这就是 Agents SDK 的多 agent 基础：**handoff 不是并行后台 agent，而是 current_agent 的切换**。fileciteturn52file0

### 13.3 Handoff：agent 接管会话

源码路径：

```text
openai-agents-python/src/agents/handoffs/__init__.py
openai-agents-python/src/agents/run_internal/turn_resolution.py
```

`Handoff` 结构：

```python
@dataclass
class Handoff(Generic[TContext, TAgent]):
    tool_name: str
    tool_description: str
    input_json_schema: dict[str, Any]
    on_invoke_handoff: Callable[[RunContextWrapper[Any], str], Awaitable[TAgent]]
    agent_name: str
    input_filter: HandoffInputFilter | None = None
    nest_handoff_history: bool | None = None
    strict_json_schema: bool = True
    is_enabled: bool | Callable = True
```

默认 handoff tool name 是：

```text
transfer_to_<agent_name>
```

默认 handoff description 是：

```text
Handoff to the {agent.name} agent to handle the request. {handoff_description}
```

官方文档也说明 handoff 被表示成 tools，模型调用 handoff tool 后，SDK 会切换到目标 agent。fileciteturn49file0 citeturn947573search0

#### Handoff 执行流程

```text
Runner loop current_agent
    │
    ├── get_handoffs(current_agent)
    │      ├── Agent item → handoff(agent)
    │      └── Handoff item → keep
    │
    ├── model response contains tool call: transfer_to_X
    │
    ├── process_model_response()
    │      └── processed_response.handoffs = [ToolRunHandoff]
    │
    ├── execute_tools_and_side_effects()
    │      └── if run_handoffs:
    │            execute_handoffs()
    │
    ├── execute_handoffs()
    │      ├── if multiple handoffs: ignore later ones
    │      ├── new_agent = handoff.on_invoke_handoff(ctx, args)
    │      ├── append HandoffOutputItem
    │      ├── hooks.on_handoff(...)
    │      ├── apply input_filter or nest_handoff_history
    │      └── return NextStepHandoff(new_agent)
    │
    └── Runner loop sets current_agent = new_agent
           and continues next turn
```

`execute_handoffs()` 会处理多 handoff 冲突：如果一个响应里出现多个 handoff，只接受第一个，其他 handoff 输出“Multiple handoffs detected, ignoring this one.”。fileciteturn51file0

### 13.4 Handoff input_filter / nest_handoff_history：上下文隔离点

`HandoffInputData` 包含：

```python
input_history
pre_handoff_items
new_items
run_context
input_items
```

默认情况下，新 agent 会看到整个 conversation history；但可以用：

```text
input_filter
nest_handoff_history

```

来改写下一个 agent 看到的输入。源码还说明 server-managed conversations 不支持 handoff input filters；如果使用 `conversation_id`、`previous_response_id` 或 `auto_previous_response_id`，SDK 会禁用或拒绝某些 handoff history 过滤行为。fileciteturn49file0 fileciteturn51file0

### 13.5 Agent.as_tool：agent 作为工具被另一个 agent 调用

源码路径：

```text
openai-agents-python/src/agents/agent.py
```

`Agent.as_tool()` 的文档明确区分它和 handoff：

| 维度 | Handoff | Agent.as_tool |
|---|---|---|
| 输入 | 新 agent 通常接收 conversation history | 子 agent 接收生成出来的 tool input |
| 控制权 | 新 agent 接管 conversation | 原 agent 等子 agent 输出后继续 |
| 返回 | 切换 current_agent | 作为 FunctionTool 返回 tool output |
| 典型用途 | routing / escalation / specialist 接管 | 子任务查询 / summarizer / classifier / evaluator |

`as_tool()` 内部创建一个 `FunctionTool`，其执行函数 `_run_agent_impl()` 会解析 tool JSON input，然后调用：

```python
Runner.run(starting_agent=self, input=resolved_input, ...)
```

或在 streaming 模式下调用：

```python
Runner.run_streamed(starting_agent=self, input=resolved_input, ...)
```

并把嵌套 run 的结果作为 tool output 返回给父 agent。源码还特意创建 fresh `ToolContext`，避免和父 run 共享 approval state。fileciteturn46file0

#### Agent.as_tool 时序图

```text
Parent Agent Runner loop
    │
    ├── model sees child_agent_as_tool
    ├── model calls tool child_agent_as_tool(input_json)
    │
    ├── FunctionTool._run_agent_impl()
    │      ├── parse JSON input
    │      ├── validate structured params
    │      ├── build resolved_input
    │      ├── create nested context
    │      ├── Runner.run(child_agent, resolved_input)
    │      │      └── child agent has its own loop
    │      ├── extract output
    │      └── return FunctionToolResult
    │
    ├── Parent receives tool result
    └── Parent model runs again or finalizes
```

### 13.6 Agents SDK 与 Codex CLI 多 agent 的根本区别

| 维度 | Codex CLI / codex-rs | OpenAI Agents SDK |
|---|---|---|
| agent 实体 | CodexThread / Session | Python/TS Agent object |
| 通信载体 | Op / Submission Queue / Mailbox | Runner loop items / tool outputs / handoff items |
| 并行后台 | 支持多个 thread/session；agent_jobs 支持多 worker | SDK 本身主要是顺序 Runner loop；并行需要应用代码自己 orchestrate |

## 17. 最关键的设计细节

### 17.1 Codex 用 ThreadId / AgentPath，而不是直接 agent object 引用

V1 主要用 ThreadId，V2 加入 AgentPath。这让 agent 可以用类似路径的方式引用其他 agent：

```text
/root
/root/planner
/root/planner/reviewer
/root/worker-1
```

`resolve_agent_target()` 先尝试把 target 解析成 ThreadId，失败后再走 AgentPath reference resolution。fileciteturn30file0

### 17.2 V2 的 message 和 task 只差一个 bit：trigger_turn

```text
send_message   → trigger_turn=false
followup_task  → trigger_turn=true
```

这一个字段决定目标 agent 是否立即开始一个 turn。这个设计很简洁：消息和任务共用一个 envelope，只是 delivery mode 不同。fileciteturn22file0

### 17.3 wait_agent 在 V2 中是“等待消息”，不是“等待 worker 完成”

V1 wait 有 targets，等 status final。V2 wait 没有 targets，等当前 session 的 mailbox seq 变化。这意味着 V2 的协作模型更接近“actor inbox”：agent 等待别人给自己发消息。fileciteturn12file0 fileciteturn24file0

### 17.4 子 agent 继承的是 runtime-effective config，不是静态配置文件

`build_agent_spawn_config()` / `apply_spawn_agent_runtime_overrides()` 会从当前 `TurnContext` 继承：

- model provider
- model slug
- reasoning effort
- reasoning summary
- developer instructions
- compact prompt
- approval policy
- shell environment policy
- sandbox executable
- cwd
- permission profile

源码注释明确说这些值由 live turn 决定，不是 persisted config；如果直接 clone stale config，child agent 可能和 parent 在 approval policy、cwd、sandbox 上不一致。fileciteturn9file0

### 17.5 full-history fork 会过滤 tool traces

Codex fork 会保留系统、developer、user、assistant final answer 等高层 history，但丢掉 reasoning、function/tool calls、tool outputs、turn context 等低层 runtime traces。这个设计类似“复制对话语义，而不是复制执行噪音”。fileciteturn17file0

### 17.6 AgentControl 被所有子 agent 共享，所以 registry 是 session-tree 级别

这避免了每个 child 自己维护一套不一致的 agent tree。所有 agents 共享同一控制面，才能做到：

- parent 能找到 child。
- child 能找 sibling / parent。
- close agent 能关闭 descendants。
- resume 能恢复 open child edges。
- list_agents 能看到统一 tree。

fileciteturn17file0 fileciteturn31file0

### 17.7 Codex open CLI 没有 Claude 那种 tmux/iTerm teammate backend

Claude 笔记中 Swarm backend 包括 in-process、tmux、iTerm、pane backend 等多种“肉身”。fileciteturn1file9

Codex 开源 CLI 的 multi-agent 核心不是 pane backend，而是 `ThreadManagerState` + 多个 CodexThread / Session。公开 Codex App / Cloud 产品层有 sandbox / worktree / parallel agents，但这部分完整后端调度不能仅从 `codex-rs/core` 还原。citeturn947573search1 citeturn947573search4

## 20. 一句话复盘

Codex 的多 agent 通信不是一个简单的“调用子 agent 函数”。它是：

```text
Thread / Session 作为 agent 实体
+ Submission Queue / Event Queue 作为基本协议
+ AgentControl 作为共享控制面
+ AgentRegistry 作为 agent tree / path / nickname / limit 管理
+ Op::InterAgentCommunication 作为 agent-to-agent envelope
+ Mailbox 作为 V2 queued message / trigger-turn inbox
+ watch::Receiver<AgentStatus> 作为状态同步机制
+ rollout / state DB 作为 fork / resume / job persistence
```

而 OpenAI Agents SDK 的多 agent 则主要是：

```text
Runner loop
+ Handoff = 当前 agent 切换给另一个 agent 接管
+ Agent.as_tool = 把子 agent 包成 FunctionTool，父 agent 等 tool output 后继续
+ Session / RunState = conversation history 与中断恢复
```

这两个体系可以互补：Codex 更像“工程 agent runtime / thread graph”，Agents SDK 更像“应用层 agent workflow 编排”。





下面这份分析基于我检索到的 **OpenAI Codex 公开仓库源码快照**与官方 Codex 文档。当前官方文档明确说明：Codex 现在默认支持 subagent 工作流，可以并行 spawn 专门 agent，也支持用户自定义 agent TOML；运行时由 Codex 负责 spawn、路由 follow-up、wait、close 等编排。

# 0. Codex 多 agent 通信总预览图

------

# 1. Layer 1：单个 agent 的 Codex loop

## 1.1 基本结构：Codex 是 SQ/EQ 队列模型

Codex 协议文件开头就写明，它使用：

> **SQ / EQ pattern**：Submission Queue / Event Queue。

`codex-rs/protocol/src/protocol.rs` 定义了 `Submission`，里面有：

```
pub struct Submission {
    pub id: String,
    pub op: Op,
    pub trace: Option<W3cTraceContext>,
}
```

而 `Op` 是所有进入一个 Codex thread/session 的操作入口，例如：

- `Op::UserInput`
- `Op::UserTurn`
- `Op::UserInputWithTurnContext`
- `Op::InterAgentCommunication`
- `Op::Interrupt`
- `Op::Shutdown`

源码里明确把 `Op::InterAgentCommunication` 作为一种 submission operation，说明 agent-to-agent 消息不是直接“函数调用另一个模型”，而是先变成一个 `Op` 投递到目标 thread 的 SQ。

## 1.2 每个 agent 是一个独立 Codex thread/session

`codex-rs/core/src/session/mod.rs` 里的 `Codex` struct 包含：

```
pub struct Codex {
    pub(crate) tx_sub: Sender<Submission>,
    pub(crate) rx_event: Receiver<Event>,
    pub(crate) agent_status: watch::Receiver<AgentStatus>,
    pub(crate) session: Arc<Session>,
}
```

这说明每个 Codex thread 都有自己的 submission 队列、event 队列、状态 watch channel、session 对象。`Codex::spawn` 会创建新的 `Session`，再启动后台 `submission_loop`。

从 OpenAI 官方“Unrolling Codex agent loop”文章看，Codex 的基本 agent loop 是：模型请求 tool call，Codex 执行工具并把 tool output 加回上下文，然后继续请求模型，直到 assistant message 完成；文章还说明 Codex 当前发送的是基于 Responses API 的请求，重点 payload 是 `instructions`、`tools`、`input`。

## 1.3 多 agent 的本质

多 agent 并不是在一个 model response 内部启动多个 JS generator 那种“同进程子 generator”；在 Codex 里：

```
root agent = root Codex thread/session
subagent  = another Codex thread/session
communication = parent/peer thread 向目标 thread 的 submission queue 投递 Op
```

这点非常重要，因为它解释了为什么 Codex 的 subagent **天然是 thread 级别的对象**，不是一个可以无限复用的“角色实例模板”。

# 2. Layer 2：model-visible multi-agent tools

这一层是模型能看到、能调用的工具面。

官方文档说，Codex 会负责 spawning、routing follow-up、waiting、closing，并把结果整合回主 agent。
 源码里这个工具面分两套：**v1** 和 **v2**。

------

## 2.1 工具注册入口

`codex-rs/tools/src/tool_registry_plan.rs` 里根据 config 决定启用哪套工具：

```
if config.collab_tools {
    if config.multi_agent_v2 {
        spawn_agent
        send_message
        followup_task
        wait_agent
        close_agent
        list_agents
    } else {
        spawn_agent
        send_input
        resume_agent
        wait_agent
        close_agent
    }
}
```

这就是 v1/v2 的关键分叉。

`codex-rs/core/src/tools/spec.rs` 再把这些 tool spec 绑定到具体 handler：

- v1: `multi_agents::SpawnAgentHandler`, `SendInputHandler`, `ResumeAgentHandler`, `WaitAgentHandler`, `CloseAgentHandler`
- v2: `multi_agents_v2::SpawnAgentHandler`, `SendMessageHandler`, `FollowupTaskHandler`, `WaitAgentHandler`, `CloseAgentHandler`, `ListAgentsHandler`

------

## 2.2 v1 工具：ThreadId 导向

v1 是“按 agent id / thread id 通信”。

| v1 tool        | 作用                   | 地址形式                  |
| -------------- | ---------------------- | ------------------------- |
| `spawn_agent`  | 创建新 subagent        | 返回 `agent_id`           |
| `send_input`   | 给已有 agent 发输入    | `target = agent_id`       |
| `resume_agent` | 按 id 恢复已关闭 agent | `id = agent_id`           |
| `wait_agent`   | 等指定 agents 完成     | `targets = [agent_id...]` |
| `close_agent`  | 关闭 agent             | `target = agent_id`       |

`create_send_input_tool_v1` 的描述甚至明确提示：如果任务依赖之前上下文，应该用 `send_input` 复用 agent。`create_resume_agent_tool` 也明确说可以 resume previously closed agent by id。

这意味着：**v1 其实有显式复用工具。**

------

## 2.3 v2 工具：AgentPath / task_name 导向

v2 是“按任务路径通信”，例如：

```
/root/reviewer
/root/planners/alice
/root/implementers/frontend
```

v2 的 tool spec 里，`spawn_agent` 必填：

```
task_name
message
```

并说明：如果当前 agent 是 `/root/task1`，spawn `task_3` 得到 canonical name `/root/task1/task_3`。其他 agent 要跨树通信时，需要用 canonical name。

v2 tool 面如下：

| v2 tool         | 作用                           | 是否触发目标 agent 新 turn      |
| --------------- | ------------------------------ | ------------------------------- |
| `spawn_agent`   | 创建命名 task agent            | 是，初始任务会进入目标          |
| `send_message`  | 给目标发字符串消息             | 否，只入邮箱                    |
| `followup_task` | 给目标发任务消息               | 是；忙则排队                    |
| `wait_agent`    | 等任意 live agent mailbox 更新 | 不返回内容，只返回 wait summary |
| `close_agent`   | 关闭 agent 和 descendants      | 关闭                            |
| `list_agents`   | 列出 live agents               | 只列 live                       |

源码里 `create_send_message_tool` 的描述是 “without triggering a new turn”，而 `create_followup_task_tool` 的描述是 “trigger a turn in the target”。

# 3. Layer 3：AgentControl / ThreadManager / Registry 控制面

这是 Codex 多 agent 的核心层。

------

## 3.1 AgentControl 是 root session tree 内共享的控制面

`codex-rs/core/src/agent/control.rs` 的注释非常关键：

- `AgentControl` 是 multi-agent ops 的 control-plane handle。
- 每个 session 通过 `SessionServices` 持有它。
- 它提供 spawn 和 inter-agent communication。
- 它应该在一个 root session tree 内共享，使 registry 作用域是 root thread，而不是整个 ThreadManager。

结构上：

```
pub(crate) struct AgentControl {
    manager: Weak<ThreadManagerState>,
    state: Arc<AgentRegistry>,
}
```

也就是说：

```
AgentControl
  ├─ Weak<ThreadManagerState>  → 操作 live Codex threads
  └─ Arc<AgentRegistry>        → 维护当前 root tree 的 live agent map / limits
```

------

## 3.2 spawn_agent 的真实执行流

以 v2 `spawn_agent` 为例，执行链是：

```
model calls spawn_agent
  ↓
multi_agents_v2/spawn.rs parses args
  ↓
build_agent_spawn_config(parent base instructions, turn context)
  ↓
apply role / model / reasoning / runtime overrides
  ↓
construct SessionSource::SubAgent(ThreadSpawn { parent_thread_id, depth, agent_path, ... })
  ↓
AgentControl::spawn_agent_with_metadata
  ↓
AgentControl::spawn_agent_internal
  ↓
ThreadManagerState::spawn_new_thread_with_source / fork_thread_with_source
  ↓
new Codex thread/session
  ↓
AgentRegistry registers path/id/role/nickname
  ↓
AgentControl::send_input or send InterAgentCommunication to child
```

v2 `spawn.rs` 里先解析：

- `message`
- `task_name`
- `agent_type`
- `model`
- `reasoning_effort`
- `fork_turns`

然后计算 child depth，检查 `agent_max_depth`，构造 `thread_spawn_source(..., Some(task_name))`，再调用 `spawn_agent_with_metadata`。如果初始输入是纯文本，并且 spawn source 有 agent path，它会把初始任务包装成：

```
Op::InterAgentCommunication {
    communication: InterAgentCommunication::new(
        parent_path,
        recipient,
        Vec::new(),
        prompt,
        true,
    )
}
```

这就是 v2 初始任务为什么天然也是“agent 邮件”。

------

## 3.3 ThreadManager：真正创建 thread/session

`codex-rs/core/src/thread_manager.rs` 里 `ThreadManagerState` 维护：

```
threads: Arc<RwLock<HashMap<ThreadId, Arc<CodexThread>>>>
thread_created_tx: broadcast::Sender<ThreadId>
```

并提供：

```
send_op(thread_id, op)
spawn_new_thread_with_source(...)
fork_thread_with_source(...)
resume_thread_from_rollout_with_source(...)
remove_thread(...)
```

`send_op` 本质上就是：

```
let thread = self.get_thread(thread_id).await?;
thread.submit(op).await
```

也就是把 `Op` 投递到目标 thread 的 submission queue。

------

## 3.4 AgentRegistry：live agent 树和限制

`codex-rs/core/src/agent/registry.rs` 定义了 `AgentRegistry`：

```
pub(crate) struct AgentRegistry {
    active_agents: Mutex<ActiveAgents>,
    total_count: AtomicUsize,
}

struct ActiveAgents {
    agent_tree: HashMap<String, AgentMetadata>,
    used_agent_nicknames: HashSet<String>,
    nickname_reset_count: usize,
}
```

`AgentMetadata` 保存：

```
agent_id: Option<ThreadId>,
agent_path: Option<AgentPath>,
agent_nickname: Option<String>,
agent_role: Option<String>,
last_task_message: Option<String>,
```

核心点：

1. `reserve_spawn_slot(max_threads)` 控制总 subagent 数。
2. `reserve_agent_path(agent_path)` 会检查路径是否已存在。
3. 如果路径已存在，会报错：

```
agent path `{agent_path}` already exists
```

1. `live_agents()` 只返回 live、非 root agent。
2. `release_spawned_thread(thread_id)` 会从 live tree 删除 agent，并递减 count。

这直接解释了你观察到的现象：

> **v2 里同一个 `task_name` / `AgentPath` 在 live registry 中不能重复 spawn；关闭后 registry 删除，路径又不再代表一个 live agent。**

# 4. Layer 4：v2 mailbox / named routing 通信层

v2 的最大变化就是：从 `ThreadId` 通信变成 `AgentPath` 命名路由 + mailbox。

------

## 4.1 InterAgentCommunication 协议结构

`protocol.rs` 定义：

```
pub struct InterAgentCommunication {
    pub author: AgentPath,
    pub recipient: AgentPath,
    pub other_recipients: Vec<AgentPath>,
    pub content: String,
    pub trigger_turn: bool,
}
```

也就是说，一封 agent 消息至少包含：

```
author     谁发的
recipient  主收件人
content    正文
trigger    是否唤醒目标 agent 开始处理
```

并且 `Op` 里有专门的：

```
Op::InterAgentCommunication { communication }
```

这就是 v2 的 agent-to-agent 消息 envelope。

------

## 4.2 mailbox 实现

`codex-rs/core/src/agent/mailbox.rs` 非常短，但很关键：

```
pub(crate) struct Mailbox {
    tx: mpsc::UnboundedSender<InterAgentCommunication>,
    next_seq: AtomicU64,
    seq_tx: watch::Sender<u64>,
}

pub(crate) struct MailboxReceiver {
    rx: mpsc::UnboundedReceiver<InterAgentCommunication>,
    pending_mails: VecDeque<InterAgentCommunication>,
}
```

它做三件事：

1. `send()`：把 `InterAgentCommunication` 放进 `mpsc`。
2. 每次 send 都增加 `seq`，并通过 `watch::Sender<u64>` 通知 waiters。
3. receiver 侧可以：
   - `has_pending()`
   - `has_pending_trigger_turn()`
   - `drain()`

因此 v2 mailbox 的真实载体是：

```
tokio mpsc unbounded channel + VecDeque pending_mails + watch seq number
```

不是磁盘邮箱，也不是 HTTP。

------

## 4.3 send_message vs followup_task

两个工具共用 `message_tool.rs`，只差 delivery mode：

```
send_message   → MessageDeliveryMode::QueueOnly
followup_task  → MessageDeliveryMode::TriggerTurn
```

`send_message` 会构造 `InterAgentCommunication`，但把 `trigger_turn` 改成 false；`followup_task` 则保持 true。然后统一调用：

```
agent_control.send_inter_agent_communication(receiver_thread_id, communication)
```

源码里还做了几个保护：

- `resolve_agent_target` 先把 target 解析成 live `ThreadId`
- `followup_task` 不允许给 root agent 派任务
- `interrupt=true` 时先 `interrupt_agent`
- 发送前后会 emit interaction begin/end event

`send_message.rs` 和 `followup_task.rs` 只是很薄的 wrapper。

------

## 4.4 v2 wait_agent 等的是 mailbox 更新，不是直接等最终内容

v1 的 `wait_agent` 是等指定 targets 的 final status。

v2 的 `wait_agent` 不接受 targets。它做的是：

```
let mut seq_rx = session.subscribe_mailbox_seq();
if session.has_pending_mailbox_items() { ... }
else wait seq_rx.changed() until timeout
```

返回：

```
{
  "message": "Wait completed" | "Wait timed out",
  "timed_out": true | false
}
```

也就是说 v2 `wait_agent` **只告诉模型“邮箱有更新了”**，并不直接返回子 agent 最终内容；内容会通过 mailbox / history / notification 进入当前 agent 可见上下文。

------

## 4.5 session 如何处理 InterAgentCommunication

`session/handlers.rs` 中：

```
pub async fn inter_agent_communication(
    sess: &Arc<Session>,
    sub_id: String,
    communication: InterAgentCommunication,
) {
    let trigger_turn = communication.trigger_turn;
    sess.enqueue_mailbox_communication(communication);
    if trigger_turn {
        sess.maybe_start_turn_for_pending_work_with_sub_id(sub_id).await;
    }
}
```

这说明：

```
Op::InterAgentCommunication 到达目标 session
  ↓
enqueue_mailbox_communication
  ↓
如果 trigger_turn=true
    maybe_start_turn_for_pending_work
  否则只是 pending mail
```

所以：

- `send_message`：只排队，不启动新 turn。
- `followup_task`：排队，并尝试启动目标 agent 新 turn。
- 如果目标 agent 正忙，后续消息会等它空闲后处理。

# 5. Layer 5：fork / resume / rollout / SQLite / batch jobs

这一层决定“能不能跨 session 复用”。

------

## 5.1 fork_context / fork_turns：spawn 时复制父上下文

v1 有 `fork_context: bool`。

v2 用 `fork_turns`：

```
none
all
positive integer string, e.g. "3"
```

`multi_agents_v2/spawn.rs` 默认是 `all`，也就是全量 fork。源码里：

```
"all" => Some(SpawnAgentForkMode::FullHistory)
"none" => None
"3" => Some(SpawnAgentForkMode::LastNTurns(3))
```

如果 full fork，则禁止同时传 `agent_type/model/reasoning_effort` overrides。

`AgentControl::spawn_forked_thread` 会：

1. 找到 parent rollout path。
2. flush parent rollout。
3. 读取 `RolloutRecorder::get_rollout_history`。
4. 如果是 `LastNTurns(n)`，先截断。
5. 过滤出适合 fork 的 items。
6. 调用 `fork_thread_with_source` 创建子 thread。

测试里也验证了 fork 后只保留父 thread 的用户消息和 assistant final answer，会过滤掉 reasoning、inter-agent message、usage hints 等不适合复制的内容。

------

## 5.2 rollout JSONL 与 SQLite state_db

Codex 的 thread 持久化由两部分组成：

```
rollout JSONL: 详细历史
SQLite state_db: thread metadata / spawn edges / jobs / indexes
```

`state/src/runtime/threads.rs` 里可以看到 `threads` 表保存：

- `id`
- `rollout_path`
- `source`
- `agent_nickname`
- `agent_role`
- `agent_path`
- `model_provider`
- `model`
- `reasoning_effort`
- `cwd`
- `title`
- etc.

而 `thread_spawn_edges` 表保存：

```
parent_thread_id
child_thread_id
status = open | closed
```

并提供：

```
upsert_thread_spawn_edge
set_thread_spawn_edge_status
list_thread_spawn_children_with_status
list_thread_spawn_descendants_with_status
find_thread_spawn_child_by_path
find_thread_spawn_descendant_by_path
```

这非常重要：**SQLite 已经有按 canonical agent_path 找子 agent thread 的能力，但当前 v2 resolver 主要查的是 live registry。**

状态枚举只有：

```
Open
Closed
```



------

## 5.3 v1 resume_agent：源码里确实有恢复机制

v1 的 `resume_agent.rs` 做的是：

```
if status == NotFound:
  build_agent_resume_config
  agent_control.resume_agent_from_rollout(config, receiver_thread_id, thread_spawn_source)
```

也就是说 v1 可以按 `ThreadId` 从 rollout 恢复已关闭 agent。

`AgentControl::resume_agent_from_rollout` 又会：

1. 读取 thread id 对应 rollout。
2. 恢复该 agent。
3. 查 SQLite 里 open descendants。
4. 递归恢复 open descendants。

所以 Codex 并不是完全没有复用/恢复设计；问题在于：

> **v2 工具面没有暴露 `resume_agent`，而 v2 的 `resolve_agent_target` 只解析 live agent。**

------

## 5.4 v2 当前缺的不是持久化数据，而是“按 path 恢复 live agent”的工具/控制流

`agent_resolver.rs` 当前逻辑是：

```
if target is ThreadId:
    return ThreadId
else:
    agent_control.resolve_agent_reference(session.conversation_id, &turn.session_source, target)
```

而 `resolve_agent_reference` 是通过 `AgentRegistry` 解析 live path。

这意味着：

```
/root/reviewer live     → 可 resolve，可 followup_task
/root/reviewer closed   → registry 已删除，不可 resolve
/root/reviewer persisted in SQLite → 目前 v2 resolver 不自动查 state_db 恢复
```

这就是你感觉“spawn 出来的子 agent 不能复用”的主要源码原因。

------

## 5.5 Batch jobs 是另一条多 agent 批处理通道

除了 collab tools，Codex 还有 `agent_jobs_tools`：

- `spawn_agents_on_csv`
- `report_agent_job_result`

工具 spec 说明：每个 CSV row spawn 一个 worker sub-agent，worker 必须调用 `report_agent_job_result`，主调用会阻塞到所有行完成并导出 CSV。

`agent_jobs.rs` 中，每个 pending item 会：

1. 构造 worker prompt。
2. 调用 `agent_control.spawn_agent_with_metadata(...)`。
3. 把 `thread_id` 写入 job item。
4. 通过 `subscribe_status` 等 worker 完成。
5. 如果 worker 没 report result，则按失败处理。

这层不是“固定 team”，而是“高并发一次性 worker pool”。

官方文档也说明 `spawn_agents_on_csv` 会按 CSV 行启动 worker，并要求每个 worker 调用 `report_agent_job_result`。


# 7. 你观察到的“spawn 出来的子 agent 好像不能复用”——源码级解释

结论分三种情况。

------

## 7.1 live agent 是可以复用的

如果 subagent 还 live，没有 close，也没有 session tree 退出：

### v1

用：

```
send_input(target = agent_id, ...)
```

v1 工具描述明确鼓励在依赖上下文时复用 agent。

### v2

用：

```
followup_task(target = "reviewer", message = "继续审这个模块")
```

或者：

```
followup_task(target = "/root/reviewer", message = "继续")
```

`followup_task` 会发 `InterAgentCommunication`，并 `trigger_turn=true`。

如果只是想留言，不启动 turn：

```
send_message(target = "reviewer", message = "FYI ...")
```

这会 queue-only，不唤醒目标。

------

## 7.2 spawn_agent 本身不是 reuse；每次 spawn 都是新 thread

`spawn_agent` 的语义是创建新 Codex thread/session。
 `AgentControl::spawn_agent_internal` 会 reserve slot、创建/fork thread、注册 metadata、再发送初始 input。

所以如果模型每次都调用：

```
spawn_agent(task_name="reviewer", ...)
```

那它是在请求新 agent，而不是“找已有 reviewer”。

在 v2，如果已有 `/root/reviewer` live，再 spawn 同名还会被 `AgentRegistry::reserve_agent_path` 拒绝，因为路径已存在。

------

## 7.3 closed / 跨 session 的 v2 agent 当前不能自然按 name 复用

这是你真正卡住的点。

当前 v2：

```
list_agents      → 只列 live agents
resolve target   → live registry
followup_task    → 必须 resolve 到 live ThreadId
close_agent      → 关闭并从 registry release
```

v2 没有 model-visible `resume_agent`。
 虽然 SQLite 已经保存了 `agent_path`，并且有 `find_thread_spawn_descendant_by_path`，但 v2 resolver 没有自动把 closed `/root/reviewer` 从 rollout 恢复成 live thread。

所以准确说：

```
Codex subagent 可以 live reuse；
v1 可以 by id resume closed agent；
v2 当前不能 by stable task_name 自动恢复 closed/persisted agent。
```

------

# 8. 不改源码时，怎样尽量做“固定 agent team”

如果你只是想在一个 Codex session 内有固定队伍，当前就能做：

## 8.1 定义自定义 agents

官方文档说可以在：

```
~/.codex/agents/
.codex/agents/
```

放 TOML 文件，包含：

```
name = "reviewer"
description = "..."
developer_instructions = "..."
```

也可以继承或覆盖 model、sandbox、MCP、skills 等设置；custom agent 会覆盖同名 built-in。

源码里 `agent/role.rs` 负责 role layer 加载与应用：

- built-in roles: `default`, `explorer`, `worker`
- user-defined roles: `config.agent_roles`
- spawn 时 `apply_role_to_config(config, role_name)` 把角色配置作为高优先级 layer 插入配置。

## 8.2 在 root 开局一次性 spawn 固定 task_name

例如让 root 做：

```
spawn_agent(task_name="planner", agent_type="planner", message="你是团队 planner，保持上下文，等待后续任务。")
spawn_agent(task_name="reviewer", agent_type="reviewer", message="你是团队 reviewer，保持上下文，等待后续审查任务。")
spawn_agent(task_name="implementer", agent_type="worker", message="你负责实现任务，等待后续任务。")
```

之后只用：

```
followup_task(target="planner", message="规划 X")
followup_task(target="reviewer", message="审查 Y")
followup_task(target="implementer", message="实现 Z")
```

## 8.3 不要 close team members

`close_agent` 的工具描述明确说不用时 close，但如果你要固定 team，就不要在中途 close。

限制：

- 这只保证当前 root session tree 内 live reuse。
- Codex 进程退出、root thread 被恢复后，v2 team 不会自动按 path 复活。
- 长期 live agent 会消耗内存、token、状态管理资源。
- 默认 `[agents] max_threads` / depth 会限制队伍大小；官方文档给出的默认是 `max_threads = 6`，`max_depth = 1`。

# 9. 如果要实现“可持久化固定 agent team”，应该怎么改源码

下面给你一个源码级改造方案。重点是：**不要重写整个多 agent 系统**，而是把 v2 的 `AgentPath` 与已有 SQLite/rollout resume 能力接起来。

------

## 9.1 目标语义

你想要的应该是：

```
team member = stable logical agent
  name/path: /root/team/reviewer
  role: reviewer
  thread_id: 可变，但最好恢复旧 thread_id
  context: 来自之前 rollout
  state: live / persisted-open / closed / archived
```

理想工具行为：

```
ensure_agent(task_name="reviewer", agent_type="reviewer")
  if /root/reviewer live:
      return existing
  else if /root/reviewer persisted in state_db:
      resume from rollout
      return resumed
  else:
      spawn new
      return new

followup_task(target="reviewer", message="...")
  if live:
      send
  else if persisted and auto_resume enabled:
      resume then send
  else:
      error
```

------

## 9.2 最小侵入方案：给 v2 加 `resume_agent` 或 `ensure_agent`

### 改动文件 1：`codex-rs/tools/src/agent_tool.rs`

增加一个 v2 tool spec，例如：

```
pub fn create_resume_agent_tool_v2() -> ToolSpec
```

参数建议：

```
{
  "target": "relative or canonical task name",
  "message": "optional message to send after resume",
  "trigger_turn": true
}
```

或者更推荐直接做：

```
create_ensure_agent_tool()
```

参数：

```
{
  "task_name": "reviewer",
  "agent_type": "reviewer",
  "message": "optional initial/followup task",
  "fork_turns": "none|all|3",
  "reuse_policy": "live_or_resume_or_spawn"
}
```

原因：`resume_agent` 只恢复已有；`ensure_agent` 才适合固定 team。

当前 `agent_tool.rs` 已经有 v1 `create_resume_agent_tool`，但没有 v2 版。

------

### 改动文件 2：`codex-rs/tools/src/tool_registry_plan.rs`

在：

```
    if config.multi_agent_v2 {

    }

```

的 v2 分支加入：


### 改动文件 3：`codex-rs/tools/src/lib.rs`

### 改动文件 5：新增 `codex-rs/core/src/tools/handlers/multi_agents_v2/ensure_agent.rs`

伪代码：

```
pub struct EnsureAgentHandler;

impl ToolHandler for EnsureAgentHandler {
    async fn handle(&self, invocation: ToolInvocation) -> Result<FunctionToolOutput, FunctionCallError> {
        let args: EnsureAgentArgs = parse_arguments(...)?;

        let parent_path = AgentPath::from_session_source(&turn.session_source)
            .unwrap_or_else(AgentPath::root);

        let canonical_path = parent_path.join(&args.task_name)?;

        // 1. 如果 live，直接返回
        if let Some(thread_id) = session.services.agent_control
            .agent_id_for_path(&canonical_path)
            .await
        {
            maybe_send_followup(thread_id, args.message).await?;
            return ok_existing(canonical_path, thread_id);
        }

        // 2. 如果 state_db 有 persisted path，resume
        if let Some(thread_id) = find_persisted_agent_by_path(session, root_thread_id, &canonical_path).await? {
            let config = build_agent_resume_config(...)?;
            let live = session.services.agent_control
                .resume_agent_from_rollout(config, thread_id, reconstructed_source)
                .await?;

            maybe_send_followup(live.thread_id, args.message).await?;
            return ok_resumed(canonical_path, live.thread_id);
        }

        // 3. 否则 spawn new
        spawn like multi_agents_v2/spawn.rs
    }
}
```

## 9.3 关键新增能力：AgentControl 按 path 查找/恢复

### 改动文件 6：`codex-rs/core/src/agent/control.rs`

新增类似：

```
pub(crate) async fn ensure_agent_for_path(
    &self,
    config: Config,
    root_thread_id: ThreadId,
    parent_session_source: &SessionSource,
    agent_path: AgentPath,
    role: Option<String>,
    spawn_or_resume_options: ...
) -> Result<LiveAgent>
```

逻辑：

```
1. registry.agent_id_for_path(path)
   → live: return LiveAgent

2. state_db.find_thread_spawn_descendant_by_path(root_thread_id, path)
   → exists:
       resume_single_agent_from_rollout(...)
       register metadata with same agent_path
       mark edge Open
       return LiveAgent

3. not exists:
       spawn_agent_with_metadata(...)
```

为什么这可行？

因为 SQLite 已经提供了：

```
find_thread_spawn_child_by_path
find_thread_spawn_descendant_by_path
```

且 `threads` 表已经保存了 `agent_path`, `agent_role`, `agent_nickname`。

------

## 9.4 修复 resume 时的 metadata / path 保留

当前 `resume_agent_from_rollout` 用的是 thread id。你需要确认并强化：

```
resume 时从 state_db.get_thread(thread_id) 读 agent_path/role/nickname
register_spawned_thread 时写回 AgentMetadata
```

如果某处 fallback 构造：

```
SessionSource::SubAgent(SubAgentSource::ThreadSpawn {
    parent_thread_id,
    depth,
    agent_path: None,
    agent_nickname: None,
    agent_role: None,
})
```

就要改成使用 SQLite metadata 里的：

```
agent_path
agent_nickname
agent_role
```

否则恢复后 registry 里没有稳定 path，`followup_task("reviewer")` 仍然找不到。

------

## 9.5 修改 resolver：让 v2 target 可以 lazy resume

### 改动文件 7：`codex-rs/core/src/agent/agent_resolver.rs`

当前 resolver 只做：

```
ThreadId::from_string(target)
or agent_control.resolve_agent_reference(...)
```

你可以扩展为两种模式：

```
resolve_agent_target_live_only(...)
resolve_agent_target_or_resume(...)
```

然后：

- `send_message` 可以 live-only，避免悄悄启动旧 agent。
- `followup_task` 可以 `or_resume`，因为它本来就是触发任务。
- `close_agent` 可以 live-only 或 persisted-aware，取决于你是否允许 close persisted open edge。
- `list_agents` 可以增加 `include_persisted=true`。

当前 resolver 文件很小，改造点清晰。

------

## 9.6 修改 list_agents：区分 live / persisted

### 改动文件 8：`codex-rs/core/src/tools/handlers/multi_agents_v2/list_agents.rs`

当前只调用：

```
agent_control.list_agents(...)
```

也就是 live agents。

建议 schema 增加：

```
{
  "path_prefix": "...",
  "include_persisted": true,
  "status_filter": "live|open|closed|all"
}
```

返回：

```
{
  "agents": [
    {
      "agent_name": "/root/reviewer",
      "lifecycle": "live",
      "thread_id": "...",
      "agent_status": "completed",
      "last_task_message": "...",
      "agent_role": "reviewer"
    },
    {
      "agent_name": "/root/planner",
      "lifecycle": "persisted_open_not_loaded",
      "thread_id": "...",
      "agent_status": "not_loaded"
    }
  ]
}
```

这样 root agent 才知道哪些 team member 可以 resume。

------

## 9.7 修改 close_agent：不要把 team member 永久失联

### 当前行为

`close_agent` 会：

1. 设置 spawn edge status = Closed。
2. shutdown live agent。
3. registry release。
4. descendants 一起关。

如果你要固定 team，有两种策略：

### 策略 A：close = unload, not retire

新增参数：

```
{
  "target": "reviewer",
  "mode": "unload|retire"
}
```

- `unload`：关闭 live thread，但保持 edge `Open`，表示 team member 仍属于团队，可 resume。
- `retire`：设置 edge `Closed`，表示不再自动恢复。

### 策略 B：新增 `suspend_agent`

保持 `close_agent` 原语不变，新增：

```
suspend_agent(target)
```

语义：

```
flush rollout
shutdown live thread
release registry
keep thread_spawn_edge Open
```

这样 `ensure_agent` 可以重新加载它。

------

如果你要“固定 agent team”的产品化体验，建议加一个 team 配置层。

例如：


# 10. 推荐改造路线

## 路线 1：最小可用，适合你现在实验

实现：

```
ensure_agent
followup_task auto-resume
list_agents include_persisted
suspend_agent
```

不新增 team manifest，只靠 task path：

```
/root/planner
/root/reviewer
/root/implementer
```

优点：

- 改动小。
- 复用现有 `AgentPath`、rollout、SQLite。
- 与 v2 语义一致。

------

## 路线 2：产品化固定 team

在路线 1 上增加：

```
agent_teams config
auto_start / auto_resume
member role/model/sandbox policy
team-aware UI
```

优点：

- 用户体验好。
- 不依赖模型每次自己记得 spawn 谁。
- 可以启动时自动 materialize team。

------

## 路线 3：全局跨 root session team

这个更复杂，因为现有 `agent_path` 是 root tree 内路径：

```
/root/reviewer
```

如果你要“所有项目共享一个 reviewer agent”，需要新建全局 team table，例如：

```
agent_team_members(
  team_name TEXT,
  member_name TEXT,
  thread_id TEXT,
  cwd TEXT,
  role TEXT,
  updated_at INTEGER,
  lifecycle TEXT
)
```

但我不建议第一步就做这个。Codex 当前设计更偏向：

```
一个 root thread tree 内的 subagents
```

不是“全局常驻人格进程”。

# 12. 最核心判断

Codex 当前多 agent 机制的本质是：

```
不是“固定 agent team first”
而是“root thread 按需 spawn thread-shaped subagents”
```

所以：

- **live subagent 可以复用**：v1 用 `send_input`，v2 用 `followup_task`。
- **spawn 不是复用**：每次 spawn 都是在创建新 thread。
- **v1 有 by-id resume**：`resume_agent`。
- **v2 有 stable path，但缺 by-path resume 工具/控制流**。
- **SQLite 已经保存 agent_path 和 spawn edge**，因此实现持久化 fixed team 不需要推倒重来，关键是把 v2 resolver / ensure_agent / list_agents / close semantics 接到 state_db + rollout resume 上。
