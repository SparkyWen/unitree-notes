# 05 — Medical Safety and Privacy

Date: 2026-04-29

This document is the safety contract for CareNote. It is enforced
across three layers: **prompt** (every agent prompt forbids the
behaviours below), **schema** (every output schema requires the right
provenance fields), and **reducer** (deterministic code in
`VisitStateReducer` that rejects anything the schema didn't already
reject). All three must hold; any one of them alone is insufficient.

## 1. Medical safety boundary

CareNote is forbidden from doing any of the following, regardless of
input:

1. Producing a **diagnosis** ("you have pneumonia", "this is likely a
   bacterial infection").
2. Producing a **prescription** ("take 500 mg of X", "you should add Y
   to your regimen").
3. Recommending **starting**, **stopping**, or **changing** a
   medication.
4. Judging whether the **doctor is correct or incorrect**.
5. **Inferring missing medical fields** (drug name, dose, frequency,
   timing, duration). If a field is missing it stays missing and is
   marked as such.
6. **Triaging** an emergency. Any apparent emergency content is
   redirected to "contact a doctor / urgent care / local emergency
   number". CareNote does not say "this is mild" or "this is severe".
7. Producing free-form medical advice that does not cite
   `source_turn_ids`.

Permitted patterns:

- "The transcript recorded that the doctor mentioned X." (citation
  required.)
- "This medication has missing dose information; please confirm with
  the doctor or pharmacist."
- "If symptoms feel severe, please contact a doctor or urgent care."
  (no triage opinion attached.)

## 2. Privacy boundary

All visit data lives in:

| Storage | Scope | Lifetime |
|---|---|---|
| Postgres (Clariose DB) | application data | until user deletes |
| Filesystem `~/.codex/sessions/...` | Codex thread rollouts (per role) | until role thread reset |
| Redis | TranscriptEventBus + queue caches | ephemeral (TTL ≤ 24h) |
| Browser local state | live transcript display | tab close |

We do not export to any third party. The only outbound network calls
from the harness are to `api.openai.com` (Realtime + Codex) and only on
an explicit user-initiated path.

## 3. Consent flow

Before the visit starts:

1. The user sees a single consent screen with four checkboxes:
   - "I understand that my voice will be sent to OpenAI Realtime for
     transcription."
   - "I understand transcripts and analysis will be stored on this
     server."
   - "I understand drafts must be confirmed by me before they become
     reminders or memory."
   - "I have the consent of others present in the room to record." (if
     applicable)
2. The user checks one toggle: "Save raw audio (default off)."
3. The user picks the language.
4. Only then is **Start Visit** enabled.

`visits.consent_recorded` and `visits.raw_audio_saved` are set at this
step and recorded for audit.

## 4. Raw audio policy

Default: **not saved**. The Realtime session does not produce a
recording on our side; audio flows browser → OpenAI. To save raw audio
we would need a separate `MediaRecorder` upload, which is **out of MVP
scope** and gated behind the consent toggle.

If a future iteration enables raw audio:

- The recording is encrypted at rest with a per-visit key.
- Deletion of the visit deletes the recording.
- Audio is never sent anywhere except the same server's storage.

## 5. Transcript policy

- Transcripts are stored in `transcript_turns` keyed by
  `(visit_id, item_id)`.
- They are deleted with the visit.
- They are **redacted** in infrastructure logs unless
  `DEBUG_CARENOTE_PHI=true` (default false).
- They are **never** sent to family without an explicit user share
  action.
- They are visible to the harness — the harness needs to read them to
  do its job.

## 6. Family sharing policy

Family-facing summary is generated by the `family_summary` role and is
**displayed to the user** in the End-Visit UI. It is not auto-sent to
anyone. The user can copy or share it from their device using their
own messaging apps.

## 7. Deletion / export policy

- `DELETE /api/visits/:id` is a hard delete in Postgres for that
  visit's rows: `transcript_turns`, `agent_runs`, `extracted_facts`,
  `draft_tasks`, `memory_candidates`, `safety_flags`. It does **not**
  delete confirmed `memory_entries` (those have their own deletion
  flow).
- `DELETE /api/memory/:id` deactivates a confirmed memory entry
  (`active = false`) and purges it from search results. Hard delete
  is `DELETE /api/memory/:id?hard=true`.
- `GET /api/visits/:id/export` returns a JSON dump for the user's
  records.

## 8. Audit logging policy

`agent_runs` is the primary audit trail for harness behaviour. It
records:

- `team_id`, `visit_id`, `role`, `thread_id`, `runtime`.
- Input JSON (sanitised; transcript text included only if
  `DEBUG_CARENOTE_PHI=true`).
- Raw output, parsed output, validation status, errors.
- Timestamps.

Permission decisions and consent toggles are written to a separate
`audit_log` table (already present in the Clariose base):

- `consent_recorded` event.
- `raw_audio_saved` toggle changes.
- Draft task confirm / reject events with the user id.
- Memory candidate confirm / reject events.
- Visit delete events.

## 9. Reminder confirmation policy

- `medication_reminder_draft` outputs always carry
  `requires_user_confirmation = true` and
  `confirmation_status = "pending"`. The reducer enforces this
  regardless of model output.
- `POST /api/visits/:id/draft-tasks/:tid/confirm` is the only path that
  promotes a draft to a confirmed reminder. The endpoint requires:
  - the draft is in `pending` status; and
  - the request body explicitly carries the user-confirmed values for
    the reminder (the user can edit before confirming).
- Confirmed reminders are written to `reminders` (the existing Clariose
  table). They never auto-fire on the medical content; the user's
  reminder list is the actor.

## 10. Memory confirmation policy

- `memory_update` outputs always carry
  `requires_user_confirmation = true`. Reducer enforces.
- `POST /api/visits/:id/memory-candidates/:cid/confirm` promotes a
  candidate to `memory_entries` with `active = true`.
- Memory entries can be edited or deactivated from the user's memory
  page; deactivation is reversible, hard delete is not.
- The `MemoryRetrievalService` only returns active, confirmed
  entries (`allowed_memory_status = "confirmed_only"`).

## 11. PHI logging policy

- All log statements that include transcript text, fact text,
  reminder body, or memory content **must** route through a
  `redact()` helper that returns `[REDACTED]` unless
  `DEBUG_CARENOTE_PHI=true`.
- The default log line for a transcript turn is:
  `turn completed visit=vis_... item=itm_... len=137`. No content.
- Codex `agent_runs.input_json` and `agent_runs.raw_output` may contain
  transcript text; that is intentional (audit trail) but the columns
  are not exported in any default API response.

## 12. Network surface of the harness

The Codex runtime is started with `networkAccessEnabled = false` and
`sandboxMode = "read-only"`. The agent therefore cannot:

- make HTTP calls;
- run shell commands;
- write to the filesystem;
- exfiltrate data via tool calls.

The only network egress is the SDK's call to OpenAI's Codex backend
itself, which we accept as the price of using Codex.

## 13. Emergency-redirect rule

If transcript content matches obvious emergency keywords (chest pain,
severe bleeding, suicidal ideation, anaphylaxis), the
`safety_clarification` role emits a `safety_flags` entry of type
`possible_emergency`, severity `high`, with
`recommended_user_action = "Please contact a doctor or your local
emergency service."` The reducer **does not triage**; it simply
elevates this safety flag in the UI.

We do not maintain a list of emergency keywords in code — the role's
prompt instructs it to be conservative. This is intentional: keyword
lists fail closed (false negatives) while a model + prompt + schema
fail open (false positives that are corrected by the user).

## 14. Forbidden development practices

Do not:

- Hard-code drug names, doses, or interaction rules into reducers.
- Add a "diagnosis confidence" column anywhere.
- Add a "the doctor is wrong" output type.
- Pre-confirm drafts on behalf of the user.
- Bypass the guardrail to "just ship the demo".

If a deadline forces a shortcut, mark the agent's
`compliance_guardrail` to `is_safe = false` instead of removing the
check.

## 15. Threat model (brief)

| Threat | Mitigation |
|---|---|
| Prompt injection in transcript causes diagnosis output | Compliance guardrail role + reducer rules. |
| Model invents a dose | Reducer forces `needs_user_confirmation`; UI displays "missing fields" prominently. |
| Operator log scraping | PHI redaction by default; `DEBUG_CARENOTE_PHI` is a tripwire. |
| Codex thread contains historical patient data | Threads are reset on prompt/schema bump; operator `reset_all` empties them. |
| Stolen ephemeral Realtime token | Token is short-lived; per-visit; cannot bind a different visit. |
| `OPENAI_API_KEY` leak | Server-only env, never sent to client; `.env` gitignored; documented in README. |
| Family sees data they shouldn't | No automatic share; user must initiate. |

## 16. Disclaimers in user-facing output

Every `final_visit_summary` payload includes a fixed disclaimer string,
in the user's language. The English copy:

> This summary is for memory and organization only. It is not
> diagnosis or treatment advice. Please confirm medication, dose,
> timing, and follow-up instructions with your doctor or pharmacist.

The Chinese copy:

> 本摘要仅用于回顾与整理，不构成诊断或治疗建议。请就药物、剂量、用药
> 时间和复诊安排，与医生或药师再次确认。

The disclaimer is part of the schema, not optional prose — the
reducer rejects a final summary that does not include it.
