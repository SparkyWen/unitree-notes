# MuJoCo G1 Terrain Test Scene — Design

Date: 2026-05-07
Branch: feature/terrain
Repo: unitree-notes

## Goal

Add a new MuJoCo scene file alongside the existing G1 scene that introduces
multiple terrain types (slopes, stairs, scattered obstacles, rough ground,
Perlin height field) for stress-testing the trained walking policy. **Do not
modify the existing clean scene** — leave `scene_29dof.xml` and `g1_29dof.xml`
untouched. The new scene must be opt-in.

## Constraints

- Existing files MUST be byte-identical after this change:
  - `unitree_mujoco/unitree_robots/g1/scene_29dof.xml`
  - `unitree_mujoco/unitree_robots/g1/g1_29dof.xml`
  - `unitree_mujoco/unitree_robots/g1/scene.xml` (the legacy obstacle course)
  - `unitree_mujoco/unitree_robots/g1/height_field.png`
  - `unitree_mujoco/unitree_robots/g1/unitree_hfield.png`
- Default behavior of `simulate_python/unitree_mujoco.py` MUST be unchanged
  (still loads the clean `scene_29dof.xml`). Loading the terrain scene is
  opt-in via a flag.
- The trained G1 walking policy must not collide with terrain at startup.
  The known failure mode (documented in `simulate_python/config.py`) is
  that legacy `scene.xml` places obstacles at the origin, so the policy
  contacts geometry while the elastic band is still suspending the robot
  and the robot destabilises before any controller is running.
- Floor friction/condim must remain `friction="1.5 0.05 0.005" condim="6"
  priority="1"` to preserve the QA5 fix (heel-strike pivot bug).

## Non-Goals

- Re-tuning the policy for terrain. We assume the existing 4.6/policy is
  what runs; this scene merely exposes it to terrain.
- Procedural/randomised terrain at sim-launch time. The terrain is generated
  once into a static XML so the simulation is deterministic.
- Touching `simulate/` (the C++ simulator) or any other robot (go2/h1/etc.).
  Scope is G1 only.

## Files Added

| Path | Purpose |
|---|---|
| `unitree_mujoco/unitree_robots/g1/scene_29dof_terrain.xml` | New scene; `<include file="g1_29dof.xml"/>` plus a worldbody full of terrain geoms. Generated by the script below. |
| `unitree_mujoco/unitree_robots/g1/terrain_perlin.png` | Perlin height-field PNG generated by `terrain_generator.AddPerlinHeighField`. Distinct filename so it does not overwrite the legacy `height_field.png` referenced by `scene.xml`. |
| `unitree_mujoco/terrain_tool/g1_terrain_config.py` | A configuration script that imports `terrain_generator.TerrainGenerator` and adds the seven terrain features below. Re-running this script regenerates the XML and PNG with whatever parameters the user has tweaked. |

## Files Modified

`unitree_mujoco/simulate_python/config.py` — add `USE_TERRAIN` flag at the
top of the file (default `False`) and branch the G1 scene path on it:

```python
USE_TERRAIN = False  # set True to load the four-direction terrain test scene

if ROBOT == "g1":
    if USE_TERRAIN:
        ROBOT_SCENE = "../unitree_robots/g1/scene_29dof_terrain.xml"
    else:
        ROBOT_SCENE = "../unitree_robots/g1/scene_29dof.xml"

    ROBOT_SCENE = "../unitree_robots/" + ROBOT + "/scene.xml"
```

The existing inline comment about scene.xml/scene_29dof.xml stays. Add a

## Layout (top-down)

```
                         +Y (north)
                            │
                 stairs ▲ 8 steps × 0.10 m
                 init (0, +4, 0)
                            │
  rough ground              │              slope 10° → slope 15° → Perlin hfield
  8×8 cube grid             │              boxes at +3, +5;  hfield at +7.5
  init (-4, -1, 0)      (0, 0)  ───────►   along +X axis
                       G1 spawn                                        +X (east)
                       2 m clean radius
                            │
                            ▼
                 scattered obstacles
                 boxes/cylinders, y ≈ -4
                         -Y (south)
```

The +Y / -Y / -X / +X arms are independent; the robot needs to be walked
into one of them to encounter terrain. Origin ±2 m is intentionally empty
so the elastic band's descent and the policy's startup happen on flat
ground exactly the way they do in `scene_29dof.xml`.

## Terrain Parameters

All values are passed to the corresponding `terrain_generator` API.

> **Size convention (important).** `AddBox`, `AddGeometry`, and
> `AddRoughGround` accept the `size` (or `box_size`) argument as
> **full edge length** and halve it internally before writing it to the
> MJCF (`geo.attrib["size"] = list_to_str(0.5 * np.array(size))`). All
> sizes below are stated as full edge lengths to match how the API is
> called. For cylinders the convention used by this tool is
> `size=[diameter, full_length]`.

### East (+X): two ramps and a Perlin field

| Item | API | Parameters |
|---|---|---|
| Ramp 1 (10°) | `AddBox` | `position=[3.0, 0.0, 0.155]`, `euler=[0.0, 0.1745, 0.0]`, `size=[1.5, 1.0, 0.05]` |
| Ramp 2 (15°) | `AddBox` | `position=[5.0, 0.0, 0.218]`, `euler=[0.0, 0.2618, 0.0]`, `size=[1.5, 1.0, 0.05]` |
| Perlin hfield | `AddPerlinHeighField` | `position=[7.5, 0.0, 0.0]`, `euler=[0,0,0]`, `size=[1.0, 1.0]`, `height_scale=0.08`, `negative_height=0.05`, `image_width=128`, `img_height=128`, `smooth=80.0`, `output_hfield_image="terrain_perlin.png"` |

Each ramp's center z = sin(θ)·half_length + cos(θ)·half_thickness, with
half_length = 0.75 m and half_thickness = 0.025 m (these are the resulting
half-extents after `AddBox` halves the `size=[1.5, 1.0, 0.05]` argument).
This puts the lowest corner of the tilted slab exactly on the ground
(z=0). `terrain_generator` does not auto-compute this; the script passes
the literal z numbers above.

Perlin parameter names follow `terrain_generator.AddPerlinHeighField`'s
signature exactly (`img_height`, `smooth`, `output_hfield_image`) — the
upstream `readme.md` uses different names but the function uses these.

### North (+Y): stairs

| API | Parameters |
|---|---|
| `AddStairs` | `init_pos=[0.0, 4.0, 0.0]`, `yaw=0.0`, `width=0.25`, `height=0.10`, `length=1.0`, `stair_nums=8` |

(`width` here is the per-step depth in meters, matching the
`terrain_generator.py` parameter name; total run = 8 × 0.25 = 2.0 m, top
step at z = 0.80 m.)

### South (-Y): scattered obstacles

Four geoms placed by hand via `AddBox` / `AddGeometry` so the robot has
to navigate around them:

| Item | API | Parameters |
|---|---|---|
| Low box | `AddBox` | `position=[0.5, -3.5, 0.10]`, `euler=[0,0,0]`, `size=[0.40, 0.40, 0.20]` |
| Tall box | `AddBox` | `position=[1.2, -4.0, 0.20]`, `euler=[0,0,0.5]`, `size=[0.30, 0.30, 0.40]` |
| Cylinder 1 | `AddGeometry` | `position=[0.0, -4.5, 0.15]`, `euler=[0,0,0]`, `size=[0.24, 0.30]`, `geo_type="cylinder"` |
| Cylinder 2 | `AddGeometry` | `position=[1.5, -5.0, 0.30]`, `euler=[0,0,0]`, `size=[0.20, 0.60]`, `geo_type="cylinder"` |

Resulting half-extents after the API halves `size`: low box 0.20×0.20×0.10
(40 cm × 40 cm × 20 cm cube), tall box 0.15×0.15×0.20 yawed 0.5 rad,
cylinders radius 0.12 / height 0.30 and radius 0.10 / height 0.60.

### West (-X): rough ground

| API | Parameters |
|---|---|
| `AddRoughGround` | `init_pos=[-4.0, -1.0, 0.02]`, `euler=[0,0,0]`, `nums=[8, 8]`, `box_size=[0.08, 0.08, 0.08]`, `box_euler=[0,0,0]`, `separation=[0.20, 0.20]`, `box_size_rand=[0.02, 0.02, 0.02]`, `box_euler_rand=[0.10, 0.10, 0.0]`, `separation_rand=[0.0, 0.0]` |

`AddRoughGround` writes each cube's center at
`local_pos + init_pos` where `local_pos.z = -box_size[2]/2` (i.e. -0.04
for `box_size[2]=0.08`). With `init_pos[2]=0.02` the resulting cube
centres sit at z = -0.02, half-extent 0.04, so cubes extend roughly z ∈
[-0.06, +0.02] — tops poke above the floor by ~2 cm (more where size
randomisation grows the cube or rotation tilts it). `box_euler_rand=
[0.10, 0.10, 0.0]` adds ±5.7° per-cube tilt for irregularity.

Grid spans x ∈ [-4, ~-2.4], y ∈ [-1, ~+0.6] after the 0.20 m × 8-step
spacing. Closest cube to origin sits ~2.5 m away in the worst case.

## Workflow

First time / when re-tuning:

```bash
conda activate unitree
pip install noise opencv-python      # one-time deps for terrain_generator
cd unitree_mujoco/terrain_tool
python g1_terrain_config.py
# → writes ../unitree_robots/g1/scene_29dof_terrain.xml
# → writes ../unitree_robots/g1/terrain_perlin.png
```

To switch into the terrain scene: edit one line in
`unitree_mujoco/simulate_python/config.py`:

```python
USE_TERRAIN = True
```

Then launch as normal (`python unitree_mujoco.py`). The robot still spawns
on clean ground at origin; press the joystick / keyboard commands to walk
into one of the four arms to test the policy on that terrain.

To switch back, set `USE_TERRAIN = False`. No regeneration needed — the
clean scene file is never touched.

## Stability Considerations

- **Origin clearance.** No terrain geom is placed within 2 m of the origin
  in either x or y. The closest item is the stairs init at (0, +4, 0) and
  the first ramp at (+3, 0). The elastic band's startup descent and the
  default-pose holding PD seeded by `UnitreeSdk2Bridge` therefore behave
  identically to the clean scene for the first few seconds.
- **Floor unchanged.** `scene_29dof_terrain.xml` includes `g1_29dof.xml`
  and declares the floor with the same `friction="1.5 0.05 0.005"
  condim="6" priority="1"` settings as `scene_29dof.xml`. This preserves
  the QA5 fix.
- **Perlin amplitude.** `height_scale=0.08` keeps the Perlin field below
  the policy's typical foot-clearance margin; the field is also placed
  7.5 m away so the robot must walk to reach it (and the operator can
  abort before contact).
- **No randomisation at runtime.** The XML is static; rerunning the
  generator is the only source of variation, and the seed is whatever
  `terrain_generator.py` uses internally — deterministic across runs.

## Testing / Verification

This spec is a build-time generation; runtime testing is manual.

1. **Generation succeeds** — running `g1_terrain_config.py` produces the
   XML and the PNG without errors.
2. **MuJoCo loads the scene** — `mujoco.MjModel.from_xml_path` on the
   generated file returns a valid model (we will run a quick load-only
   check inside the implementation step).
3. **Policy startup unchanged** — with `USE_TERRAIN=True`, after the
   elastic band lowers the robot to ground, the robot stands in the same
   default pose with no terrain contact. Visual check via mjpython
   `viewer`.
4. **Walks into terrain on command** — manual: command forward velocity
   along +X, observe ramp climb; same for other arms. Out of scope to
   automate.

## Out-of-Scope / Future Work

- Difficulty presets (easy / medium / hard) — currently the script is the
  preset; if needed later, expose top-level constants in
  `g1_terrain_config.py`.
- Multiple terrain scenes (e.g. one per terrain type) — possible later by
  parametrising the script with a `--zones` argument; not needed now.
- Adding terrain scenes for other robots (go2/h1/etc.) — the existing
  upstream `terrain_tool/scene.xml` already covers go2-style use; G1 is
  the only one with the policy-stability constraint.
