# g1_v1 — Vision Risk Gate (autonomous-mode confirm reduction)

**Status:** Design — awaiting user review before implementation plan.
**Owner:** Sparky / g1_brain.
**Date:** 2026-05-07.
**Related:** `docs/audio-control-update01.md`, `docs/architecture.md`, `g1_brain/safety/supervisor.py`.

---

## 0. Problem statement

Today the operator can pick one of three `run_mode`s:

| `run_mode` | Behaviour | Pain point |
|---|---|---|
| `observe` | All motion blocked. | Useful only for headless dry-runs. |
| `confirm` | **Every** motion call (`walk`, `turn`, `gesture`, …) prints a terminal y/N prompt. | Voice operator cannot reach the keyboard mid-conversation. A "walk 10 m" turns into one approval; OK. A "turn 180° + walk + wave" turns into 3+ approvals; tedious. |
| `active` | Motion runs unattended once the 11 safety rules pass. | The 11 rules are mechanical (whitelist, FSM, watchdog, parameter clamp, ground-constraint geometry); they do not reason **semantically** about the image. A coffee cup on the path, a child standing 1 m ahead, an open stairwell — all of these can pass the existing rules. Operator is nervous and ends up babysitting the terminal anyway. |

**Operator goal (verbatim):** *"the model should use its own video stream + GPT-5.5 to quickly judge whether the current behaviour carries risk. If it does not, execute without my consent. If it does, ask me."*

This is **a philosophy, not a new mode** — the gate is orthogonal to `run_mode`.

## 1. Solution at a glance

Add a **Vision Risk Gate** as a horizontal capability inside `SafetySupervisor`:

* Just before the legacy "confirm prompt" step, take the latest head-camera JPEG and ask GPT-5.5 (`vision_model: "gpt-5.5"`, already wired in `va_demo.VisionClient`) one question: *given this action and this first-person view, is it safe to proceed?*
* If GPT-5.5 says **SAFE**: short-circuit out of the supervisor — no terminal prompt, regardless of `run_mode` (so both `active` and `confirm` benefit).
* If GPT-5.5 says **RISK** (or anything fails): fall through to the existing `_confirm_in_terminal` y/N prompt, with the risk reason printed inline so the operator sees what tripped the gate.
* If `safety.vision_gate.enabled: false`: the gate is fully bypassed and behaviour is identical to today.

Net effect (with default `run_mode: active`):

* ~95% of motion calls clear the gate and execute with no operator intervention (the desired UX).
* ~5% — when GPT-5.5 sees a person in the path, fragile glassware, a stairwell, etc. — fall back to a terminal y/N with an explicit reason. This is **new safety surface** the `active` mode never had before.

## 2. Decisions locked with operator

| ID | Question | Operator answer |
|---|---|---|
| Channel | When the gate trips, what asks the human? | **Terminal y/N** (existing `_confirm_in_terminal`). Voice ask was rejected as too complex. |
| Approach | Mode-coupled or orthogonal flag? | **Approach C** — orthogonal `safety.vision_gate.enabled` flag. |
| P1 | Backward walk (`walk` with `vx < 0`) — head cam blind to behind. | **Always RISK** — bypass GPT-5.5, force y/N. |
| P2 | `static_pose` arm motions and `say` speech. | `static_pose` **goes through** the vision gate (let GPT decide). `say` **always SAFE**, never enters the gate. |
| P3 | Cache recent verdicts (e.g. 5 s reuse for identical args)? | **No caching.** Every gated call re-evaluates. |
| P4 | False-positive vs false-negative trade-off. | **Never let a real risk through.** When in doubt → RISK. |

## 3. Architecture & components

### 3.1 New file: `g1_brain/safety/vision_risk_gate.py`

```python
@dataclass(frozen=True)
class RiskVerdict:
    safe: bool
    reason: str                  # ≤120 chars, displayed in y/N prompt
    source: Literal[
        "bypass",                # short-circuited (no LLM call)
        "vision_llm",            # GPT-5.5 returned a parseable verdict
        "frame_fail",            # no/stale/blank frame
        "parse_fail",            # GPT-5.5 returned malformed text
        "timeout",               # GPT-5.5 timed out
        "api_error",             # network / OpenAI error
    ]

class VisionRiskGate:
    def __init__(self, *, vision_client, camera_hub, cfg: dict) -> None: ...
    async def evaluate(self, tool: str, sanitized: dict) -> RiskVerdict: ...
```

Internal flow of `evaluate()`:

1. **Bypass short-circuit (no API call).**
   * `say`, `stop`, `release_arms`, `describe_scene`, `query_scene_state`, `recall_history` → `RiskVerdict(safe=True, source="bypass")`. (The non-motion ones never reach the gate anyway because they skip Rule 12; included here for defensive correctness.)
   * `walk` with `vx < 0` (backward) → `RiskVerdict(safe=False, source="bypass", reason="backward walk — head cam blind to behind")`.
2. **Frame fetch + health check.**
   * Pull latest JPEG via `camera_hub` (mirrors `SkillServer._latest_jpeg_b64_preferring_head` — refactor that helper to a hub-level method so both call sites share it).
   * Frame age must be `< vision_gate.max_frame_age_s` (default 2.0) — else `RISK / frame_fail`.
   * Mean luminance must be in `[min_brightness, max_brightness]` (defaults 30, 235 on a 0-255 scale) — else `RISK / frame_fail`.
3. **GPT-5.5 call.**
   * `await vision_client.describe(image_jpeg_b64=..., prompt=RISK_REVIEW_PROMPT, detail=cfg.detail)`.
   * Wrapped in `asyncio.wait_for(..., timeout=vision_gate.timeout_s)` (default 5.0). Timeout → `RISK / timeout`.
   * Other exceptions (rate limit, network) → `RISK / api_error`.
4. **Parse output (see §5).** Returns `vision_llm` verdict, or `parse_fail` if malformed.

### 3.2 Modified file: `g1_brain/safety/supervisor.py`

* Constructor gains optional `vision_gate: Optional[VisionRiskGate] = None`.
* `validate()` is restructured around the existing 11-rule order. After Rule 9/10 (scene checks) but before the legacy "Rule 3 continued" confirm prompt, insert **Rule 12 — vision gate**:

  ```python
  risk_reason: Optional[str] = None
  if self.vision_gate is not None:
      verdict = await self.vision_gate.evaluate(tool, sanitized)
      log.info(
          "[vision_gate] tool=%s verdict=%s source=%s reason=%s",
          tool, "SAFE" if verdict.safe else "RISK",
          verdict.source, verdict.reason,
      )
      if verdict.safe:
          return True, "", sanitized           # short-circuit
      risk_reason = verdict.reason              # fall through to confirm
  ```

* The legacy `if self.run_mode == "confirm"` becomes
  `if self.run_mode == "confirm" or risk_reason is not None`.
* `_confirm_in_terminal` gets a new optional kwarg `risk_reason: Optional[str] = None`. When set, the prompt prepends a `[RISK] {reason}` line so the operator sees why the gate intervened.

### 3.3 Modified file: `g1_brain/apps/agent_main.py`

* Construct `VisionRiskGate` **after** `vision_client` and **before** `SafetySupervisor`. Skip if disabled.
* Log a single startup line:
  * Enabled: `vision_gate enabled (timeout=5.0s, max_frame_age=2.0s, detail=auto)`.
  * Disabled: `vision_gate DISABLED — RISK fallthrough off; active mode is fully autonomous`.

### 3.4 Config additions: `configs/g1_brain.yaml`

```yaml
safety:
  vision_gate:
    enabled: true
    timeout_s: 5.0          # GPT-5.5 hard timeout; on timeout → RISK
    max_frame_age_s: 2.0    # head-cam JPEG older than this → RISK (frame_fail)
    min_brightness: 30      # mean luminance < this → RISK (too dark)
    max_brightness: 235     # mean luminance > this → RISK (white-out)
    detail: "auto"          # OpenAI image detail: low / high / auto / original
```

### 3.5 Things deliberately NOT changed

* The 11 existing safety rules — all unchanged. The vision gate is **rule 12**, only invoked when rules 1–10 already accepted the call. This avoids paying GPT-5.5 latency on calls that would have been rejected anyway.
* `_confirm_in_terminal`'s cbreak / single-keypress / 15 s timeout / arrow-key drain logic — battle-tested, kept verbatim. Only the prompt string changes.
* `observe` mode — Rule 3 still rejects all motion before the gate is even reached.
* `--no-perception` flag — the YOLO+MediaPipe pipeline can be off; the vision gate is independent (it reads JPEG → GPT-5.5, no perception modules involved). With perception off the gate still works.
* `vision-only` mode — has no motion tools, no Rule 12 call sites.

### 4.2 SAFE path (~95% of calls)

```
LLM ──tool_call──▶ realtime_agent ──validate──▶ SafetySupervisor
                                                       │
                                  (Rule 1..10 pass, enter Rule 12)
                                                       ▼
                                            VisionRiskGate.evaluate()
                                                       │
                                  ┌────────────────────┼─────────────────┐
                                  │ bypass list?       │  no              │
                                  │ ──────────────────▶│                  │
                                  │                    ▼                  │
                                  │ camera_hub.latest_head_jpeg_b64()     │
                                  │ frame age + brightness OK             │
                                  │                    ▼                  │
                                  │ vision_client.describe(image,         │
                                  │   risk_review_prompt(tool, args))     │
                                  │  GPT-5.5 (~1-3 s)  │                  │
                                  │ "SAFE: clear path forward, ..."       │
                                  │                    ▼                  │
                                  │ parse → RiskVerdict(safe=True, ...)   │
                                  └────────────────────┬─────────────────┘
                                                       ▼
                                       supervisor: return True, sanitized
                                                       ▼
                                 SkillServer._skill_walk(...)  ← run directly
                                                       ▼
                                            tool_response back to LLM
```

Operator UX: a single log line `[vision_gate] tool=walk verdict=SAFE …` then the robot moves. **Zero keystrokes.**

### 4.3 RISK path

```
LLM ──tool_call──▶ realtime_agent ──validate──▶ SafetySupervisor
                                                       │
                                              (Rule 1..10 pass)
                                                       ▼
                                            VisionRiskGate.evaluate()
                                                       │
                                  ┌────────────────────┴────────────────────┐
                                  │  GPT-5.5 returns:                       │
                                  │    "RISK: person sitting 0.7 m ahead"   │
                                  │  parse → RiskVerdict(safe=False,        │
                                  │           reason="person sitting 0.7 m  │
                                  │                   ahead")               │
                                  └────────────────────┬────────────────────┘
                                                       ▼
                          supervisor: fall through to confirm prompt with reason
                                                       ▼
                            _confirm_in_terminal(tool, sanitized, risk_reason)
                                                       │
            prints to stderr (cbreak mode):            │
            ┌──────────────────────────────────────────────────────────────┐
            │ [g1_brain confirm] tool=walk(vx=0.20, duration_s=5.0)        │
            │ [RISK] person sitting 0.7 m ahead                            │
            │ press y to accept, any other key to decline:                 │
            └──────────────────────────────────────────────────────────────┘
                                                       │
                                       operator presses y / n
                                                       ▼
                              y → return True, sanitized → execute
                              n / any other key / 15 s timeout → return False
                                                       ▼
                                LLM receives ok=False, reason="operator declined"
```

Operator UX: rare `[RISK]`-tagged prompt with a one-line reason; press y to proceed.

### 4.4 Bypass paths (zero latency)

| Tool / args | Verdict | Source |
|---|---|---|
| `say` | `SAFE` | bypass |
| `stop`, `release_arms` | `SAFE` | bypass |
| `describe_scene`, `query_scene_state`, `recall_history` | (gate not entered — non-motion) | n/a |
| `walk` with `vx < 0` (backward) | `RISK` (always) | bypass |

Backward walk is forced y/N rather than hard-rejected because the operator can still legitimately want to back up — it just must be a deliberate keystroke each time.

### 4.5 Latency budget per motion call

| Step | Typical | Worst-case |
|---|---|---|
| Rule 1..10 + frame fetch | < 5 ms | < 10 ms |
| GPT-5.5 vision call | 1.0–2.5 s | 5.0 s (timeout) |
| Parse + log | < 1 ms | < 1 ms |
| SAFE → dispatch skill | 0 | 0 |
| RISK → terminal y/N (operator present) | 1–3 s | 15 s (`_confirm_in_terminal` timeout, declines) |

**SAFE-path net overhead:** ~1.5 s median per motion call. The voice operator notices a half-beat pause between "前进 2 米" and the robot starting to step. If this proves too long in practice, the fast-follow lever is `safety.vision_gate.detail: low` (~30% latency reduction) — already supported by the config.

**Network failure:** GPT-5.5 5 s timeout → RISK → y/N. Never deadlocks.

### 4.6 Concurrency & barge-in

* The Realtime tool dispatch is single-tool serial; no two `evaluate()` calls overlap.
* Mid-evaluate barge-in ("hi sparky" while GPT-5.5 is still thinking): `cancel_in_flight()` cancels the response. The `evaluate()` coroutine still runs to completion or timeout; whichever verdict it returns is irrelevant because `_dispatch_tool` already detects `rid in self._cancelled_response_ids` and drops the function_call_output. No new code needed for this case.

## 5. Risk-review prompt & output contract

### 5.1 Action sentence

`VisionRiskGate._describe_action(tool, sanitized) -> str` renders the tool+args into a plain-English sentence. GPT-5.5 reasons better with a sentence than with raw kwargs.

| Tool | Rendering example |
|---|---|
| `walk` (vx>0) | `walk forward at 0.20 m/s for 10.0 s (≈ 2.0 m total)` |
| `walk` (vy≠0) | `walk diagonally (vx=0.10, vy=0.05) for 5.0 s` |
| `turn` | `turn ${yaw_deg}° in place at ~14°/s (≈ ${duration} s)` |
| `gesture` | `perform arm gesture "${name}"; arm sweep radius ≈ 0.6 m` |
| `static_pose` | `change body pose to "${name}"; arms move to a fixed position` |
| `look_at` | `aim head/torso toward "${target}" — minimal locomotion` |
| `approach` | `walk forward to ~${target_distance_m} m from "${target_name}"` |
| `mock_imitate` | `mirror the user's "${gesture}" gesture; large arm sweep` |

### 5.2 Full prompt template (static, built once at startup)

```
You are the safety reviewer for a Unitree G1 humanoid robot operating in
autonomous mode. The robot is about to execute the action below. The image
is the robot's first-person head-camera frame, taken < 2 s ago.

Decide whether to let the robot proceed without operator approval.

### Action
{action_sentence}

### RISK if any of the following is visible in the frame
A. Humans
   A1. Any person within ~1.5 m in the direction of motion (standing/sitting/squatting).
   A2. A child (estimated height < 1.2 m) anywhere in frame.
   A3. An elderly person or anyone with cane/walker/wheelchair anywhere in frame.
   A4. A person with their back turned to the robot.
   A5. A person doing fine-motor tasks (writing, typing, holding a cup, using a knife)
       within the action's reach (1.5 m for walk, 0.6 m for arm motions).
   A6. A person lying or seated on the floor.
   A7. For arm motions (gesture/static_pose/mock_imitate): any person within 0.6 m.

B. Animals
   B1. Any pet/animal anywhere in frame — reactions are unpredictable.

C. Fragile / valuable items along the path (1.5 m forward) or arm sweep (0.6 m)
   C1. Glassware (cups, bottles, vases, fish tanks).
   C2. Electronics (laptop, phone, tablet, monitor, headphones).
   C3. Camera gear (cameras, tripods).
   C4. Musical instruments.
   C5. Art / decor (frames, sculptures) within arm sweep.
   C6. Filled liquid containers on tables that the arm sweep would pass over.

D. Dangerous items (RISK at any distance — proximity itself is wrong)
   D1. Knives, scissors, broken glass, sharp tool tips.
   D2. Open flame, candles, stoves, heaters, irons.
   D3. Liquid spills, water/oil puddles (slip risk).
   D4. Exposed power outlets, loose cables on the floor.
   D5. Chemical containers (cleaners, paint, lab bottles).
   D6. Food spills / grease patches.

E. Surfaces / terrain
   E1. Stairs going down OR up.
   E2. Floor height-step > 5 cm (cliff edge, platform edge, balcony threshold).
   E3. Visible dark hole (drain, manhole).
   E4. Polished/reflective floor (slip risk).
   E5. Rumpled rug, raised cable, lip on the floor.
   E6. Floor not visible (camera obstructed, pointed at ceiling/wall).
   E7. Wet/oily-looking patch.

F. Spatial / geometry
   F1. Corridor or wall-gap < 1.2 m wide AND action is turn(>60°) or wide gesture.
   F2. Low ceiling / overhead obstacle within ~1.6 m of robot's head height.
   F3. Doorway directly ahead (frame may scrape even with clear path).
   F4. Stairwell drop / open-railing edge.

G. Robot self state visible in frame
   G1. Robot's own arm already touching/near an object.
   G2. Horizon tilted > 15° (already unstable).
   G3. Severe motion blur in current frame (slipping or shaking).

### SAFE only if ALL of these hold
S1. No item in A–G applies.
S2. The 1.5 m corridor in front of the robot (for walks) or the 0.6 m arm
    sweep zone (for arm motions) is clearly empty floor / empty space.
S3. The image is well-lit and you can see the floor clearly.
S4. Action parameters are reasonable for the visible space (not asked to walk
    further than you can see, not asked to turn into a wall, etc.).

### Output schema (STRICT — any deviation will be treated as RISK)
Return EXACTLY one line in this format and NOTHING ELSE:

  SAFE: <≤15-word reason>
or
  RISK: <≤15-word reason>

Examples:
  SAFE: clear empty floor for 3 m, no people, no fragile items
  RISK: person sitting 0.7 m ahead facing left, walk would intrude
  RISK: glass coffee cup on path within 1 m
  RISK: descending stairs 1 m ahead

When in doubt → RISK. Never elaborate, never ask, never explain. One line.
```

### 5.3 Output parsing contract

`VisionRiskGate._parse(text: str) -> RiskVerdict`:

1. `s = text.strip()`.
2. Take the first line only: `first = s.splitlines()[0].strip()`.
3. Match against `^(SAFE|RISK)\s*:\s*(.+?)\s*$`.
   * `SAFE` → `RiskVerdict(safe=True, reason=group(2)[:120], source="vision_llm")`.
   * `RISK` → `RiskVerdict(safe=False, reason=group(2)[:120], source="vision_llm")`.
   * No match → `RiskVerdict(safe=False, reason=("vision returned malformed text: " + s[:60]), source="parse_fail")`.

The 120-char cap keeps the y/N prompt to a single terminal line.

### 5.4 Token / cost discipline

* Prompt is fully static and built **once** at startup (not per-call).
* `detail: auto` (OpenAI-chosen) is the default; `low` is the lever if the operator wants to halve cost at the expense of fragile-object detection sensitivity.
* No system message — the entire instruction goes into the user-role text block, mirroring the existing `va_demo.VisionClient` interface (we do not touch that class).
* No multi-frame analysis; each call sends one JPEG.

### 5.5 Language / style

* Prompt and `reason` are English. Strict-format short outputs work best in English with current models, and `reason` is a one-line terminal hint, not user-facing copy.
* No i18n today. Future: add a translation pass on `reason` if Chinese terminal output is desired.

### 5.6 Boundary examples (for regression tests)

| Scenario | Expected verdict |
|---|---|
| Empty corridor, `walk` forward 5 s | `SAFE / vision_llm` |
| Glass cup on path | `RISK / vision_llm` |
| Person standing 1 m ahead, back turned | `RISK / vision_llm` (A1 + A4) |
| All-black frame (lights off) | `RISK / frame_fail` (no GPT call) |
| GPT returns `"I think it's fine"` | `RISK / parse_fail` |
| GPT returns `"SAFE: ok"` | `SAFE / vision_llm` |
| GPT returns `"SAFE\n RISK: also..."` | `SAFE / vision_llm` (first line only) |
| GPT does not respond in 5 s | `RISK / timeout` |
| Backward walk (`vx < 0`) | `RISK / bypass` (no GPT call) |
| `say(text="hello")` | `SAFE / bypass` (gate not entered, but defensive bypass anyway) |

## 6. Failure handling, observability, tests, rollout

### 6.1 Failure-mode summary

| Failure | Outcome | `RiskVerdict.source` |
|---|---|---|
| `camera_hub` returns `None` for head JPEG | RISK → y/N | `frame_fail` |
| Frame age > `max_frame_age_s` | RISK → y/N | `frame_fail` |
| Frame mean luminance outside `[min_brightness, max_brightness]` | RISK → y/N | `frame_fail` |
| GPT-5.5 timeout | RISK → y/N | `timeout` |
| GPT-5.5 raises (rate limit, network, auth) | RISK → y/N | `api_error` |
| GPT-5.5 returns malformed text | RISK → y/N | `parse_fail` |
| `safety.vision_gate.enabled: false` | gate skipped entirely | n/a |
| `vision_gate=None` passed to supervisor | gate skipped entirely | n/a |

In every failure mode the operator's worst case is a single y/N keystroke — **never** a silent auto-execute.

### 6.2 Logging

Per evaluate(), one `log.info` line:

```
[vision_gate] tool=walk verdict=SAFE source=vision_llm latency_s=1.42 reason=clear empty floor for 3 m
```

Failure modes use `log.warning`:

```
[vision_gate] tool=walk verdict=RISK source=timeout latency_s=5.00 reason=GPT-5.5 timed out after 5.0s
```

Startup line in `agent_main`:

```
vision_gate enabled (timeout=5.0s, max_frame_age=2.0s, detail=auto)
```

or

```
vision_gate DISABLED — RISK fallthrough off; active mode is fully autonomous
```

### 6.3 Tests

**`tests/test_vision_risk_gate.py`** (new) — unit tests with mocked `vision_client` and `camera_hub`:

* Bypass list: `say`, `stop`, `release_arms` → SAFE / bypass; no `vision_client.describe` calls.
* Backward walk (`walk(vx=-0.2)`) → RISK / bypass; no `vision_client.describe` call.
* No frame (camera returns `None`) → RISK / frame_fail.
* Stale frame (synthetic `frame_age_s = 5.0`) → RISK / frame_fail.
* Too-dark frame (mean luminance 10) → RISK / frame_fail.
* Too-bright frame (mean luminance 250) → RISK / frame_fail.
* `vision_client.describe` returns `"SAFE: clear"` → SAFE / vision_llm with reason `"clear"`.
* `vision_client.describe` returns `"RISK: person 0.5m"` → RISK / vision_llm.
* `vision_client.describe` returns `"I am not sure"` → RISK / parse_fail.
* `vision_client.describe` raises `asyncio.TimeoutError` (or wrapper does) → RISK / timeout.
* `vision_client.describe` raises arbitrary exception → RISK / api_error.
* Config `enabled: false` is the operator's lever in agent_main; the gate class itself is constructed only when enabled, so this is covered by an agent_main integration test.

**`tests/test_supervisor_vision_gate.py`** (new) — integration tests with a fake `VisionRiskGate` and existing `SafetySupervisor`:

* `run_mode="active"`, gate returns SAFE → `validate()` returns `True`, `_confirm_fn` never called.
* `run_mode="active"`, gate returns RISK → `validate()` calls `_confirm_fn` with `risk_reason` set; on `y` returns True, on `n` returns False with reason `"operator declined in confirm mode"`.
* `run_mode="confirm"`, gate returns SAFE → `validate()` returns True, `_confirm_fn` never called (this is the **biggest UX win** of the design).
* `run_mode="confirm"`, gate returns RISK → `validate()` calls `_confirm_fn` with `risk_reason`.
* `vision_gate=None` → existing behaviour preserved (regression guard).

**Existing `tests/test_supervisor.py`** — sweep one pass: every constructor that currently doesn't pass `vision_gate` keeps the implicit `None`, so no test changes needed except those that explicitly assert on the confirm-prompt format (we'll update them for the optional `[RISK]` line).

### 6.4 Observability / metrics

Phase 1 (this design): structured `[vision_gate]` log lines are sufficient for manual A/B and grep-based debugging.

Phase 2 (future, not in scope): emit Prometheus-style counters/histograms — `vision_gate_verdicts_total{verdict, source, tool}`, `vision_gate_latency_seconds`. Out of scope here.

### 6.5 Rollout

1. **Land with `enabled: true`** as the new default in `configs/g1_brain.yaml`. This affects the `active` mode operator (adds y/N on RISK) and the `confirm` mode operator (drops y/N on SAFE) simultaneously.
2. First-day usage recommendation: keep `--mode active` for normal voice operation; the gate is the new safety net. Use `--mode confirm` if you specifically want every-call confirmation regardless of vision verdict (debug / paranoid mode). `--mode observe` unchanged.
3. **Off switch:** `safety.vision_gate.enabled: false` reverts to the pre-design behaviour bit-for-bit. Use this for CI runs without `OPENAI_API_KEY`, when offline, or when latency budget is tight.
4. Monitor `[vision_gate]` log lines for two failure signals: high `parse_fail` rate (prompt drift) or high `timeout` rate (network). Either triggers a tune in `vision_gate.timeout_s` or a prompt iteration.

### 6.6 Out of scope / future work

* **Voice-channel risk approval.** Operator picked terminal y/N. Future enhancement could route RISK reasons through `say` and resolve via voice yes/no, but the Realtime websocket coordination is non-trivial and was deferred.
* **Caching / memoization** of recent verdicts (5 s TTL was floated and rejected — operator wants no blind windows).
* **Multi-frame temporal analysis.** Single-frame for now; the operator's mental model and prompt complexity stay simple.
* **Real-robot outdoor scenarios.** The risk taxonomy is indoor-biased (fragile glassware, stairs). When the real-robot path lights up, expect to add an outdoor rubric branch.
* **i18n of `reason`.** English only today.

## 8. Risks of this design itself

* **GPT-5.5 latency variance.** A 1.5 s median is acceptable for voice UX, but the long tail (5 s timeout) on poor connectivity will be felt. Mitigation: surface latency in the log line; expose `detail: low` and `timeout_s` for tuning.
* **Prompt brittleness.** GPT-5.5 may occasionally elaborate, summarise, or refuse the strict format. The `parse_fail` → RISK fallback catches this safely (operator presses y once), but a sustained drift would degrade UX. Mitigation: explicit "STRICT … any deviation will be treated as RISK" line in the prompt, plus regression examples in §5.6.
* **Token cost.** ~95% of motion calls now incur one vision call. At `detail: auto` and a 640×480 JPEG this is the same per-call cost as the existing `describe_scene` tool. Mitigation: `detail: low` lever, plus the operator's existing budget for vision calls already accommodates frequent `describe_scene`.
* **`active`-mode users surprised by new y/N.** Operators relying on hands-off `active` mode will, for the first time, see a terminal y/N in some scenarios. Mitigation: the startup log line is explicit ("vision_gate enabled — RISK will prompt y/N"), and the off switch is one config line away.
